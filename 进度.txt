E1 收口了。这张卡的结论是**否定的**，而且是两个方向都查过的否定。

## 两个方向都拿不到位深

**播放路径（Surface）**：`color-format` 报的是厂商私有值 **`0x7FA30C06`**（高通私有区），不是设计里假设的 `0x7F000789`。8bit 的 AVC 片源和 10bit 的 HEVC 片源**给出完全相同的这个值** —— 它连位深都不表达。

**探针路径（ByteBuffer）**：新写的 `kivo_color_probe` 对同一片源做三次 configure：

| 请求 | configure | start | start 后格式 |
|---|---|---|---|
| 不设 `color-format` | ok | ok | **21 (NV12)** |
| `P010` | ok | ok | **21 (NV12)** |
| `Surface`（**不给窗口**） | ok | ok | **21 (NV12)** |

第三行是关键：Surface 输出不可能没有窗口，但它照样 configure 成功、start 成功。**这颗 OMX 组件在 configure 阶段根本不校验 `color-format`** —— 所以“请求 P010 后配置成功”什么都证明不了，我原本设计里那个“反证”也失效了。

于是证据里写的是 `verdict = "indeterminate"` + 非空 reason（新字段 `color`，schema 升 `/7`），永远不会出现“看起来成功”的空字段。这就是卡片要的“报得出 reason”。

## 设计被实测推翻三处

1. 以为 Surface 会报 `0x7F000789`，实际是厂商私有 `0x7FA30C06`。
2. 以为“P010 configure 成功 = 支持”，且“Surface 无窗口会失败”可作反证 —— 两者都不成立。
3. 以为 configure 后就能读协商结果 —— 实际必须 **`start()` 之后**读，之前读到的是默认值 21。

三处都在 `35-p12e1-design.md` 里加了更正块，原文没删。

## 顺带量到一件对 E2/E3 很关键的事

8bit 与 10bit 片源的 `color-standard/transfer/range` 都是 **1/3/2**（BT709/SDR/limited），一模一样。用 ffprobe 核对片源：

```
hevc_1080p10.mp4: Main 10, yuv420p10le,
                  color_space=unknown, color_transfer=unknown, color_primaries=unknown
```

**那是解码器的默认值，不是片源信息。** 我们现在这个“10bit 片源”其实是 10bit SDR、没有任何色彩标记 —— E2 想验 HDR，必须先准备带 BT2020 + PQ 的真 HDR10 片源，否则测到的全是默认值。这条已经写进 `TASKS.md` 的指针段和 `AGENTS.md`。
