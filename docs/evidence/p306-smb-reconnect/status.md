## 一、起因

305 的第二次断网端到端里出现：

```
PROXY read fail @528303793 attempt=360: SMB 连接已断开，重连失败：无法连接服务器
[ffmpeg] http: Will reconnect at 528303793 in 0 second(s), error=Connection timed out.
```

断网 70 s、恢复后 20 s 内**重试 360 次仍未接上**。P253 的 62 s 能 2.2 s 接上 ⇒ 需要判定
"是策略缺陷"还是"环境问题"。

## 二、代码审查结论：策略层没有缺陷

| 检查点 | 结论 |
| --- | --- |
| 退避序列 | `SmbRetryGate` 400→800→1600→3200→4000 封顶；**离线时不翻倍**（"指数退避保护服务器，不惩罚用户"） |
| 恢复即重试 | `canAttempt()` 从离线转在线时**把退避清零** ⇒ 网络回来立刻可试，不白等 4 s |
| 每次重连是否重建会话 | `SmbPreadChannel.readAt` 失败后 `SmbReader(...).open()`，`open()` 内**每次 `nativeCreate()` 新建 ctx** ⇒ 没有全局状态残留 |
| 死句柄 | 重连前 `reader.close()` 并置 `dead=true`，避免拿旧句柄读出误导性错误 |
| 成功后旧数据 | `onReconnected()` 通知窗口清空 |

**JVM 单测 6/6 通过**（`SmbRetryGateTest`，`tests="6" failures="0" errors="0"`），
其中 `link recovery allows an immediate attempt` 正是本次怀疑的那条路径。

⇒ **没有证据表明重连策略有缺陷。**

## 三、端到端没能复现：环境被挡住

按原计划复现（起播 SMB → 断网 70 s → 恢复 → 观察 60 s），结果：

- 起播阶段就失败，net-diag 只有 3 行 `[hdr]`，**没有任何 `[play]`/`[cache]`**；
- UI 停在「**播放失败 · 无法连接服务器，请检查地址与网络**」（截图 `p306-smb-reconnect-probe.png`）；
- 设备网络本身正常：`wlan0` 有 `192.168.5.152/24`、`wifi_on=1`。

⇒ **小米路由 `192.168.5.1` 的 SMB 共享当前不可达**（不是手机断网）。
这与 305 里 `attempt=360` 的现象**可能同源**——即失败发生在"服务端不可达"，而不是"重连代码坏了"。

**因此在当前环境里无法区分**：
(a) 路由 SMB 服务掉了（环境），(b) 我们的重连真有缺陷。**不下结论。**

## 四、补上的真实缺陷：失败日志丢了 `detail`

`SmbPreadChannel` 原来只记 `failed.message`：

```kotlin
val reason = "SMB 连接已断开，重连失败：${failed.message?.take(80) ?: "未知原因"}"
```

而 `SmbFailure` 里带着 **`stage` + `detail`（`nt=0x… raw=…`）**——这正是区分
"认证错 / 共享不存在 / 网络不可达"的唯一信息。丢掉它以后，三种完全不同的故障
在日志里长得一模一样，只能靠猜（本次就是被这一点卡住）。

**改法**（只进日志，不给用户看噪音）：

```kotlin
(failed as? SmbFailure)?.let { f ->
    NetDiag.log("[smb] 重连失败 stage=${f.stage.label} detail=${f.detail}")
}
```

用户文案保持原样（`gate.lastFailure` / UI 提示不变），**不改变任何行为**，只是下次排障能一眼分清。
