# P248 · 音画同步：音频主时钟 + 视频跟随

日期：2026-11-10
设备：MatePad MRR-W29（SD865 / kona，Android 12）
片源：`[恐怖废墟].The.Ruins.2008...VC-1.TrueHD.5.1-CMCT.mkv`（20.2 GB）

## 一、症状

用户两次反馈「音画还是没有同步」。P247 之后视频侧已经满帧不卡
（逐窗口帧间隔 p50 41.6 ms），但同步问题独立存在。

## 二、先量，再改

之前的所有"同步检查"都比错了对象：拿视频位置去比音频的 **`positionUs()`**，
而那是"最后一帧解码并写进环"的位置，**领先实际出声最多 700 ms**
（环 500 ms + 预灌 200 ms）。用它在 800 ms 阈值上凑，凑出来的只是"没触发"，
不代表对齐。

新增 `playedUs()` = `已写入位置 − 环内尚未被取走的时长`，才对应听众此刻听到的那一帧。
用它量出真实偏移：

```
soft rate ... arate=1.00 avdiff=-1400ms     ← 声音比画面晚 1.4 秒
```

- `arate = 1.00`：音频自己在按 1.0x 走，不是快放/慢放；
- `ratio = 1.00`：视频也是 1.0x；
- 偏移**恒定**不增长 → 不是累积漂移，是**起点错位**。

用 ffprobe 核对源文件：视频轨与音轨 `start_time` 都是 `0.000000`，
排除容器层面的轨间偏移。

## 三、根因

视频和音频是两条**完全独立的会话**（各自 demux、各自解码、各自时钟），
都从 `pts=0` 起跑，但**启动时刻不同**：

- 音频要走自己的 `avformat_open_input` + `avformat_find_stream_info`；
- FFmpeg 默认 `probesize` 是 5 MB —— 在这部 20 GB REMUX 上，光是"认出这是 TrueHD 5.1"
  就要从 SMB 读走 5 MB，实测 **1.4 秒**。

于是音频比视频晚 1.4 s 才开始出声。两条 1.0x 的时间轴一旦错开一个固定量，
就会**永远**错开 —— 各自守时的结果就是口型一直对不上。

## 四、改法

### 4.1 音频暴露"正在出声的位置"

`soft_audio_session.{hpp,cxx}`：

```cpp
played_us_ = written_pts - ring.available_frames() * 1e6 / 48000;
```

`available_frames()` 是"已写但 AAudio 还没搬走"的帧数，这部分还没响，必须扣掉。

### 4.2 视频以音频为主时钟

`ffmpeg_local_playback_session.{hpp,cxx}` 新增 `setAudioClockUs()`，节拍改为：

| 条件 | 动作 |
| --- | --- |
| `media − clock < −150 ms` | 丢帧追赶（**必须归还帧缓冲**，否则每丢一帧漏 8.3 MB） |
| `media − clock > +50 ms` | 分段睡眠（每 100 ms 查一次 seek/暂停，避免睡死） |
| 其余 | 立即上屏 |

音频时钟每 200 ms 才采样一次，因此按墙钟**外推**（上限 250 ms），
否则每帧看到同一个值会出现 200 ms 台阶（观感是一顿一顿）。

`clock` 的失效判定：**800 ms 无更新即返回 -1**，视频退回自身 pts 节拍。
这条必须存在 —— 片尾音频先结束或音频被暂停时 `playedUs` 会定格，
继续以它为准会让视频每帧都判"超前"而越睡越久，画面就此冻在最后一帧。

### 4.3 收窄音频探针预算

```cpp
format->probesize = 1024 * 1024;          // 原 5 MB
format->max_analyze_duration = 3 * AV_TIME_BASE;  // 原 5 s
```

TrueHD 约 4 Mbps，1 MiB ≈ 2 秒音频，足够认出编码与声道布局。

### 4.4 兜底闸门从 800 ms 提到 5 s

原来的 800 ms 闸门是"各自守时"时代的凑数值。现在视频会主动追音频，
再按 800 ms 停流只会打断对齐过程、冻结音频时钟、让视频又追上来，变成来回振荡。
只保留"视频彻底解不动时不要差出分钟级"这一条保险。

## 五、实测

### 5.1 音画偏移（30 个采样）

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| `avdiff` | 恒定 **−1400 ms** | **min −793 / p50 −7 / max +134 ms** |
| `\|avdiff\| ≤ 40 ms` | 0% | **60%** |
| `\|avdiff\| ≤ 80 ms` | 0% | **87%** |

唯一的 −793 ms 出现在起播过渡态（`arate=0.00`，音频尚未出声），之后全部在 ±134 ms 内。

帧级比较（渲染那一刻 `media − clock`）：p50 **−20 ms**，范围 −114 ~ +60 µs 级抖动，
即画面略早于声音 20 ms 到达渲染点，上屏后正好落进同步窗口。

### 5.2 帧率未受影响

逐窗口帧间隔（23 个独立 60 帧窗口）：min 39.9 / p50 **41.7** / max **44.1 ms**，
**>45 ms 的窗口 0 个**。音频主导没有把视频拖成慢放。

### 5.3 丢帧代价

起播全程 `dropped=1`（仅 1 帧）。因为方向是"视频等音频"（画面超前 → 睡），
真正需要丢帧的场合极少。

## 六、遗留

**起播有约 1.4 s 的画面停顿**：视频先出帧，音频就绪要 1.4 s，视频在这一段睡眠等它。
这是"用开头 1.4 秒换全程对齐"的取舍。若要消掉，需要让音频就绪后
`seekTo(视频当前位置)` 追上来——但会引入一次音频重缓冲（约 0.5 s 静音），
当前未做，待确认观感后决定。
