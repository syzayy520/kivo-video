# 硬解到底该不该开预读（已结论：不开，机制已定位）

日期：2026-11-10 夜
设备：K40 `b6e950ee`（Android 13 / kona）
片源：
- 4K 单视频轨：`The.Furious.2026...H.265-CHDWEB.mkv`（20.9 GB，3832×1592 HEVC HDR10+）
- **多轨**：`视频/电影/Shelter 2026 USA BluRay 1080p TrueHD5.1 x265 10bit-CHD/...mkv`
  （12.19 GB，1920×804 hevc 10bit，2×TrueHD + PGS —— 用户指定的"最难播放"）

## 一、为什么要重测

243 关掉了硬解路径的预读（`PlayerComposeActivity` 里 `setPrefetchEnabled(false)`），
理由是"实测帧率 24.00 → 20.27、末尾出现 567 ms 卡顿"。

那条数据是在**块窗口会双倍读取**的版本上测的（24 MiB 逻辑读拉 50 MiB，
见 [window-double-fill](../window-double-fill/status.md)）。双倍读取意味着预读那条连接
在跟主读抢同一份带宽，而抢的额度里有一半是浪费。现在浪费没了，结论必须重测 ——
不能拿旧数字继续关着一个可能有益的开关。

## 二、方法

新增 `androidTest/smb/SmbPaceBenchInstrumentation.kt`：

- 同一次运行内 **关→开→关→开** 交替，每窗 15–20 s，切换只翻一个开关（不解码器、不重建会话）；
- 每窗结束让上一段余量排空 1.5 s，避免边界混入；
- 从原生 summary 取累计 `frames` / `dropped`，取差值得每窗独立数字；
- 报 `speed`（媒体秒 / 实际秒）与 `pace_lateness_p99`。

为什么必须同一次运行内交替：这台 NAS 的吞吐有分钟级波动（裸读 8.2–8.9 MB/s 都出现过），
分两次跑无法区分"预读的差别"和"机器当时的状态"。

## 三、第一次结果：4K 单视频轨，看不出差别

两次独立运行，前三个窗口全部健康：

| 运行 | 窗口 | 预读 | fps | dropped | speed |
| --- | --- | --- | --- | --- | --- |
| #1 | 1 | 关 | 25.80 | 0 | 1.00x |
| #1 | 2 | **开** | 25.75 | 0 | 1.00x |
| #1 | 3 | 关 | 25.80 | 0 | 1.00x |
| #2 | 1 | 关 | 26.40 | 0 | 1.00x |
| #2 | 2 | **开** | 26.33 | 0 | 1.00x |
| #2 | 3 | 关 | 26.46 | 0 | 1.00x |

开与关的差别在噪声内（0.2%）。当时我据此写下"243 的退化不再复现"——
**这个结论是错的，因为片源选错了**：4K 那条只有一条视频轨，访问接近纯顺序，
预读读的东西大半真被用上了，浪费被稀释。**换多轨片源（§五）后差别立刻显形。**

## 四、当时的判定（已被 §五 取代）

理由不是"预读有害"，而是**没有证据表明它现在有益**：吞吐略低 4%（6.9 vs 7.2），
帧率与丢帧无差别，唯一可能的好处（减少解码线程阻塞）现有观测器看不见。

这个判定方法本身没问题 —— 错的是样本。**一个"没差别"的结果，要先问"这个样本能暴露差别吗"。**

## 五、决定性证据：`Shelter`（2×TrueHD + PGS）

4K 那条只有单条视频轨、访问接近纯顺序，差别被稀释了。换用户指的"最难播放"片源：

```
视频/电影/Shelter 2026 USA BluRay 1080p TrueHD5.1 x265 10bit-CHD/...mkv
12.19 GB / 6435 s / 1920×804 / hevc 10bit / 2×TrueHD + PGS
```

同一次运行，六窗交替（12 s 一窗）：

| 窗 | 预读 | fps | dropped | 主读实际拿到 `net` |
| --- | --- | --- | --- | --- |
| #1 | 关 | 27.17 | **0** | 1.32 MB/s |
| #2 | **开** | 6.83 | **240** | **7.14 MB/s** |
| #3 | 关 | 26.91 | **0** | 3.43 MB/s |
| #4 | **开** | 24.67 | **28** | 3.94 MB/s |
| #5 | 关 | 26.58 | 1 | 5.67 MB/s |
| #6 | **开** | 21.92 | **65** | 3.73 MB/s |

**三个"开"的窗口全部丢帧，三个"关"的窗口基本不丢（0/0/1）。**

机制在 `net` 一列里：第 2 窗开预读时主读只拿到该拿的 1/6 数据，**但整机在跑 7.14 MB/s ——
已经顶到这台 NAS 的单连接上限（8–9 MB/s）**。预读线程在按顺序往前读，而 MediaExtractor
在视频 / TrueHD×2 / PGS 四条轨之间来回跳，读进去的大半立刻作废，却和主读抢同一条链路。

这解释了 243 观察到但没有解释的现象（"24.00 → 20.27、末尾 567 ms 卡顿"）：
不是预读的实现有 bug，是**预读的前提（消费者顺序访问）在这条路径上不成立**。

同一轮 4K（单视频轨）复跑也同向，只是幅度小：

```
#1 关 26.47 fps dropped=0   net=2.18
#2 开 26.33 fps dropped=0   net=0.29  ← 预读的连接不计入 net，此列在"开"窗偏低
#3 关 26.27 fps dropped=0   net=2.40
#4 开 23.80 fps dropped=39  net=2.68
#5 关 26.46 fps dropped=0   net=3.60
#6 开 25.80 fps dropped=9   net=3.57
```

## 六、结论

1. **硬解路径继续关预读。** 243 的决定是对的，本轮给出了可复算的机制：
   多轨交织的访问形态下，预读的读取全是浪费，并且与主读抢同一条 8–9 MB/s 的链路。
2. **预读只在"消费者真顺序"时成立** —— 软解走 FFmpeg 单读指针，247 实测命中率 100%，
   那条路径保持开启是正确的。开关不该按"软解/硬解"这个代理指标，而该按"访问是否顺序"，
   但在拿到软解路径上的浪费证据之前，**不改成运行时自适应**（无证据的功能不做）。
3. 用户说的"最难播放"的 `Shelter`，在预读关闭（也就是 App 的实际路径）下
   **26.6–27.2 fps、0 丢帧**，是能正常播的。

## 七、被设备状态打断的那一段（已恢复）

中途 4K HEVC 解码器一度完全不出帧：

```
START codec=OMX.qcom.video.decoder.hevc dur=6791201 ms
WINDOW ... frames=0 dropped=0 net=0.00 MB/s
SUMMARY ... samples=1 frames=0 error=dequeueOutputBuffer returned -10000
```

同一个文件在既有 `SmbPlaybackSeekInstrumentation` 里也停在 `POSITION 0 ms → 0 ms`，
而 H.264 720p 的 `local-seek.mkv` 仍然 35.9 fps / 0 丢帧 —— **播放链路没坏，是 4K HEVC 那条路**。
同期 SMB 读取完全正常（RAW 11.8 MB/s、WINDOW 11.3 MB/s）。

判断是设备侧解码器实例进了坏状态（`ps` 里有僵死的 `Z [com.kivo.cinema]`）。
重启后手机一度连到另一个 Wi-Fi（`ZTE-G36ZdT-5G`，10.0.0.247/24），访问不到 192.168.5.1，
`adb shell cmd wifi connect-network` 被拒（shell 无该权限）；切回 192.168.5.x 后一切正常，
上面的数据都是恢复之后测的。**没有"重启就好了"这种含糊结论 —— 是网络不通，不是修复。**
