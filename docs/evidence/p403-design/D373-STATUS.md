# 373 · 冷启动到首屏可交互：全链路综合计时（回应"REX 进去就加载好了"）

日期：2026-11-18

> 结论：D366–D370 各面分别优化后，首次做冷启动**综合**计时。
> 系统级 `am start -W TotalTime` **672 / 687 / 719ms**；启动动画固定 0.8s；
> 首屏数据（NAS 海报 + Emby 续播首批）在动画结束前后（0.2–1.2s）即就绪；
> 尾部 2.6–4.2s 的加载全是 `[emby-cache] HIT 1-2ms` 的**延迟重复刷新，不阻塞首屏**。
> **没有发现新的 >REX 瓶颈**，性能审计这条线到此闭合。

---

## 一、为什么做这个（承用户原始诉求）

- 用户诉求原话："rex 进去就已经加载好了，咱们的要加载好一会儿，分析 rex 怎么实现的"。
- D366（详情秒开）/D367（列表缓存）/D368（登录 hero）/D369（资源库封面墙）各自优化了单面，
  但从未在**一次冷启动里综合计时**，无法回答"现在整体还差多少"。本轮补上这个终局测量。

## 二、方法

- 3 轮：`am force-stop` → 清 net-diag → `am start -W -n .MainActivity`（系统级冷启动计时）→ 等 6s →
  解析日志时间轴（相对 `[brand] 启动动画开始`）。
- 只用 intent 起页 + force-stop，不 reboot/不 swipe（守铁律 8）。
- REX 对照：`docs/reference/rex-teardown/04-product-blueprint.md` L66 只有"冷启动首帧预算 300ms"
  的**设计预算**，非实测；IPA FairPlay 加密拿不到真实启动耗时 ⇒ 标 `not_measured + reason`，
  只给我方绝对值，不声称"达到/超过 REX"。

## 三、数据（3 轮）

| 指标 | R1 | R2 | R3 | 说明 |
|---|---|---|---|---|
| `am start -W TotalTime` | 719ms | 672ms | 687ms | 系统级：进程启动→首帧窗口 |
| WaitTime | 723 | 675 | 690 | |
| 启动动画结束(首帧可交互) | +803ms | +806ms | +802ms | `[brand]` 固定 WARM 0.8s |
| NAS 海报首批就绪 | +221~259ms | +219~235ms | +213~228ms | 8 张磁盘命中，动画期间即完成 |
| Emby 续播首批完成 | +1236ms | +476ms | +483ms | R1 偏慢系偶发；R2/R3 缓存 HIT |
| Emby 续播尾部刷新 | +1518/1873/3153ms | +914/4264ms | +2674/3016ms | 全部 `[emby-cache] HIT 1-2ms`，延迟触发、不阻塞 |

- `TotalTime` 672–719ms 与 D365 §首屏（663/666/672/693/729ms）及 274 §8.2（772/665/685）一致：
  **进程启动不是瓶颈，且历次改造无回归**。
- 首屏骨架（hero 标题/海报/续播第一批）在 0.2–1.2s 内就绪；用户感知的"加载好一会儿"主要来自
  0.8s 固定启动动画 + 数据刷新节奏，二者都不再是网络/缓存瓶颈。

## 四、裁决

- **不改代码**：没有新的可优化瓶颈。0.8s 启动动画是品牌设计（WARM 版，FULL 版 2.3s 仅首装/隔天），
  属产品决策，非性能缺陷；尾部重复刷新虽晚但全缓存命中、无网络代价，动它收益为零且有回归风险。
- **诚实边界**：REX 真实启动耗时 `not_measured`（FairPlay 加密，只有 300ms 设计预算），
  不能宣布"已追平 REX 启动"，只能说我方绝对值已稳定在亚秒级、无网络瓶颈。
- 性能审计线（D366–D373）到此闭合；后续若无新诉求，不再重复测。

## 五、诚实标注

- 3 轮样本小，但 `TotalTime` 高度一致（672–719ms）、启动动画固定 800ms，结论稳健。
- R1 续播首批 1236ms vs R2/R3 476ms 的差异是启动瞬间缓存状态/源站抖动，非代码回归（首批请求本身日志 `耗时=1-2ms`）。
- 未截首屏图（计时以系统 `am start -W` 与日志时间戳为准；截图见 D372 的 nas-162-round*.png 同一首屏）。
