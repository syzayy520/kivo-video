## 一、结论

| 项 | 结果 |
|---|---|
| 用户诉求 | 「rex 进去就已经加载好了，咱们的要加载好一会儿」+ 要求拆包分析 Rex 实现 |

| 我方真凶 | 不是网络慢，是 **Emby 侧零缓存**：详情/季/集每次进详情全重打源站（剧集拉集是最大一块） |
| 改造结果 | **二次进入 2383 ms → 74 ms**（剧集）、**1332 ms → 67 ms**（电影），日志全链路 `[emby-cache] HIT` |
| 冷路径 | 也变快：**1676 ms**（第 2 次采样）vs 改造前 2383 ms；首进仍需网络（Rex 亦然），差别是只付一次 |

（同一接口实测 290 ms–1.8 s），不是本地代码可控；四次里有三次优于改造前基线。

### 2.1 失效链路已验证（播放 → 停止 → 再进）

```
[emby] Stopped 上报 ok pos=21522ms
[emby-cache] INVALIDATE item=255945 removed=4
```

随后再进同一剧集，日志为全部 `STORE`（回源重建），证明**不会读到播放前的旧续播位**。
失效范围 `removed=4` = 详情 + 图片尺寸 + 季表 + 集表（该剧只有 1 季）。

冷进入（剧集，缓存已清）：2716 ms，其中 Emby 详情 1016 ms（源站抖动区间 290–1800 ms）、图片尺寸上限 611 ms、季集 965 ms。

## 四、本轮踩到的真 bug（已修）

缓存目录被删（系统清 cacheDir / 手工清理）后，`put()` 里 `createTempFile` 抛异常被 `runCatching` 吞掉
⇒ **静默写失败、缓存永远 MISS**，表现为"第二次进还是慢"。修法：写入前 `parentFile.mkdirs()`。
这个坑在低存储设备上会真实发生，不是测试假象。

## 四·A 拉集一次请求（补做）

`/Shows/{id}/Episodes` 不带 `SeasonId` 即返回整剧集（含 `ParentIndexNumber`）⇒ N 季从 N 次往返压到 1 次。
覆盖判定 `EmbyEpisodeGrouping.group()`：任一季为空即返回 null，退回逐季请求（防服务器分页截断后**静默少集**）。

| 项 | 结果 |
|---|---|
| 真机日志 | `[emby] all-episodes series=255945 n=47 seasons=[1]`，无 `覆盖不全` 回退 |
| 页面一致性 | `47集` / 播出日历 `47-47` 与服务器一致 |
| 冷路径 | **2383 ms → 1663 ms（−30%）** |
| 热路径 | 82 ms（全 `[emby-cache] HIT`，未退化） |
| 单测 | 新增 5 例（多季顺序/某季空/全空/季表空/多余季号），全量 111 例 0 失败 |

## 四·B 冷进详情的首帧（补做，复用既有空封面态，无新增 UI 组件）

**问题**：`DetailPreview.from()` 原来要求「必须有幕布图」才给快照。于是**没有 Primary 图的条目**
（如「继续观看」里的单集）点进来就是纯转圈等 1.2–2.3 s，日志表现为 `preview=false`。

**改法**：只要求**有标题**就给快照；没有幕布走页面本来就有的空封面态
（`DetailBackdrop` 在 `heroArtworkUrl` 为空时用 field 色 + 一行「暂无封面」）。
**没有新增任何视觉组件、没有改配色/字号/布局**。

**验证**：同一条目（`emby=255840`）日志由 `preview=false` 变为 `preview=true`；
点击后立即出现片名 / 日期 / 播放按钮 / 简介，最终态与改动前一致（截图 `detail-nohero-*` 两张对比），
无闪烁、无空白、无转圈。

## 五、已知边界

1. 首进仍需网络；冷路径受 Emby 源站抖动支配（实测 290 ms–1.8 s/请求）。
2. 首页「继续观看」进详情时 `preview=false`（无列表快照）⇒ 冷路径仍转圈；骨架属 UI 改动，未做。
3. 未做"用户可配缓存时长"（Rex 有，属设置项/UI 变更）。
4. 进度类数据最多陈旧 6 h（依赖写事件失效；第三方客户端写入我们收不到）。
