# 358 · 两臂 20 分钟长跑：**都没有复现 274 的吞吐衰减**

> 357 的结论只做到"健康源站 + 300s 下两臂都可用，复用请求数少一半"，
> 但 274 记录的衰减（226→150→100→50→48→47→42→67 KB/s）需要**更长时间**才可能暴露。
> 本批用 bangumi 源站、`originKeepAlive=1`（复用臂）与 `=0`（每块新建臂）**各跑 20 分钟**，专门验这一条。
>
> **2026-11-18 补齐 A 臂 20 分钟**（此前只有 300s、属推断级）。两臂同为同源同起点
> （《读书会》Videos/232935，1.02GB，seek 396s）、硬解 + gpu-next、20 分钟逐分钟采样
> + 内核健康度 soak。结论：**两臂都不衰减、稳态都零丢帧**；`originKeepAlive` 默认值不改。

---

## 一、结论先说

**20 分钟内没有出现吞吐衰减。** 判据三项全部不成立：

| 判据 | 前 1/3（1–7 min） | 后 1/3（14–20 min） | 结果 |
|---|---:|---:|---|
| chunk 速率（块/分） | 中位 **8.0** | 中位 **8.0** | 100%，无下降 |
| 前向缓存 `dur` | 中位 **14.1 s** | 中位 **18.6 s** | **132%**，反而更高 |
| `underrun=true` 次数 | 0 | 0 | 无 |

异常累计 **0**（`origin open fail` / `eof unexpected` / `stall` 全部为零）。

### 更强的证据：内核侧零累积丢帧

20 分钟 soak（248 个采样点，5 s/点）：

| 指标 | 5.1 s | 1258.4 s | 变化 |
|---|---:|---:|---|
| `mistimed_frame_count` | 4 | **610** | +606（0.48 次/秒，与 346 的"固有比例"结论一致） |
| **`vo_drop_count`** | **2** | **2** | **恒定，零累积丢帧** |
| `decoder_drop_count` | 0 | 0 | 0 |
| `avsync` | −0.0168 | −0.0129 | 稳定（全程 <20 ms） |
| `vf_fps` | 29.97 | 29.97 | 稳定 |

⇒ 复用连接跑了 20 分钟，**一帧都没丢**。

## 二、我中途误判了一次（记录在案）

第 12–15 分钟 `dur` 从 14.1 单调降到 **10.4 s**、前向窗口从 7.4M 降到 **3.2M**，
我当时判断"这就是 274 的衰减，只是还没到 underrun"。

**第 16 分钟它跳回 18.7 s 并一直维持到结束。**

⇒ 那不是衰减，是 **`demuxer-cache-time` 的周期性波动**（缓存上限/readahead 交互导致，
每隔十几分钟一个周期）。

**教训**：单调下降持续 4 分钟仍然不足以判定衰减 —— 这类指标必须**跑到周期完整走一遍**
（本批 20 分钟刚好覆盖一个周期）。中途下结论会得出与事实相反的判断。
这也是为什么判据不能看"某一刻"，只能看**首尾分段中位数**。

## 三、A 臂 20 分钟实测对照（2026-11-18 补齐）

A 臂（`originKeepAlive=0`，每块新建）用**与 B 臂完全相同的片源、起点、时长与采样口径**
重跑 20 分钟（脚本 `tools/p358_armA.sh`）。两臂定量对照：

| 项 | A 臂（每块新建） | B 臂（复用） |
|---|---|---|
| 采样跨度 | 246 点 / 1236 s | 248 点 / 1258 s |
| chunk 速率 前1/3→后1/3 | 6.5→7.0 /分（**108%**） | 8.0→8.0 /分（**100%**） |
| 前向缓存 `dur` 前1/3→后1/3 | 14.9→11.7 s（**79%**） | 14.1→18.6 s（**132%**） |
| `underrun`（>1min） | 0 | 0 |
| 异常 | 2（起播 `thread interrupted`） | 0 |
| `vo_drop` 起播→终值 | 0→**4**（t=15.8s 后恒定） | 2→2（全程恒定） |
| `decoder_drop` | 0 | 0 |
| `mistimed` 增速 | 0.44/s | 0.48/s |
| `avsync` 稳态 | ±0.01 s | <0.02 s |
| 趋势判定 | **未观察到吞吐衰减** | **未观察到吞吐衰减** |

### 三点如实说明

1. **A 臂 dur 后段回落到 79%**（14.9→11.7s），未过 60% 判据线，且无 underrun、
   无稳态丢帧 ⇒ 是缓存深度的轻微回落，**不是供给不足**。B 臂同段反而升到 132%，
   印证 D358 第二节的"周期性波动"——两臂相位不同，但都在健康区间。
2. **A 臂的 2 个异常**是 seek 到 396s 时旧预取线程被主动取消
   （`[play]`/`[thumb] origin open fail @…: thread interrupted`，t=10:53:22 与 10:54:13），
   起播后恒定不再增长；B 臂 UI 起播无 seek 故为 0。属起播行为差异，与吞吐无关，
   且三项判据不依赖异常计数。
3. **A 臂 vo_drop=4 vs B 臂=2**：A 臂 4 个全在 t=15.8s 一次产生、之后 1220s 恒定；
   B 臂 2 个全程恒定。同为起播瞬时 VO 抖动、稳态零累积，`decoder_drop` 两臂皆 0。
   这与 346 的结论一致（起播可能非 0，稳态不增长）。

⇒ **两臂 20 分钟都不复现 274 衰减、稳态都不丢帧**，"两臂长跑等价"从推断升级为实测。
每块新建的建连开销在 4 MiB 块 / 7–10s 间隔下被摊薄，收益不足以改变默认值（见第四节）。

## 四、这对 `originKeepAlive` 默认值意味着什么

**不改默认（仍为 0，每块新建）。**

| 理由 | 说明 |
|---|---|
| 274 的衰减证据未被推翻 | 本批只是**在 bangumi 上没复现**，不能证明它不存在于别的源站/更长时段 |
| 改默认影响所有用户 | 而当前默认已在真机长期使用中验证稳定 |
| 收益量级小 | 两臂稳态缓存深度相当（17–19 s），说明省下的建连开销没有转化为可感知的收益 |
| lovehd 那台的教训 | 同一份代码在坏服上超时 13–32 次，说明"源站质量"是比"连接策略"更大的变量 |

**什么情况下应该重新评估**：出现一台**稳定高速**的主力源站（如自建 NAS Emby），
且实测"每块新建"的建连开销 >200 ms 时 —— 那时复用的收益才会显现。
