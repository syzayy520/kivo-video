# 加载性能审计交付说明（D366–D368）

> 起点：用户对照 Rex ——「rex 进去就已经加载好了，咱们的要加载好一会儿」，并要求拆包分析 Rex 实现。
> 做法：**每一层先量出真耗时，再改，改完再量**。三轮分别落在 详情页 → 列表 → 登录/hero。

---

## 一、结论

| 场景 | 改造前 | 改造后 | 倍数 |
|---|---|---|---|
| 剧集详情 · 二次进入 | 2383 ms | **74 ms** | 32× |
| 电影详情 · 二次进入 | 1332 ms | **67 ms** | 20× |
| 剧集详情 · 首次进入 | 2383 ms | 1663 ms | −30% |
| 电影详情 · 首次进入 | 1332 ms | 836 ms | −37% |
| 进入 Emby 浏览页（connect 段） | 1225 ms | **4–5 ms** | 250× |
| 聚合搜索 · 二次进入（3 源） | 696 / 877 / 1045 ms | **4 / 4 / 4 ms** | ~200× |
| hero 最近入库 / 继续观看 | 3496 / 1390 ms | **1 / 2 ms** | — |

**一句话**：首次进入仍需网络（Rex 亦然），差别是**只付一次**；之后全部走本地。

## 二、Rex 是怎么做的（拆包实证）

Rex 是 iOS FairPlay 加密 IPA，拿不到源码，但项目内 `docs/reference/rex-teardown/rex-package/strings/`
78 份文案 JSON 把策略暴露清楚了：

| Rex 键 | 中文原文 | 含义 |
|---|---|---|
| `appSettings.copy.detail.cache.duration` | 详情缓存时长 | 详情页有可配时长的持久缓存 |
| `settings.cache.item.general` | 请求数据缓存 | 通用请求缓存（可开关） |
| `settings.cache.detailPreload.mode` | 进入详情后预加载 | 进详情即预取视频数据 |
| `settings.cache.item.modules` / `.danmakus` / `.subtitles` | 组件/弹幕/字幕缓存 | 分域缓存，互不牵连 |
| `settings.aggregated.sources.metadata.footer` | 源越靠前越优先补全元数据 | 多源补全，不吊死单链路 |

⇒ **Rex 快 = 持久化缓存 + 模块级独立异步 + 多源补全**。
缓存载体（CoreData/SQLite）、默认 TTL、并发数属 ◐ 推断，不冒充确定。

## 三、我们查到的真凶（都与"网络慢"无关）

| # | 真凶 | 证据 |
|---|---|---|
| 1 | **Emby 侧零缓存**：详情/季/集每次进页面全重打 | `detail-perf`：电影 1332 ms 里 Emby 详情 908 ms；剧集 2383 ms 里拉集 1592 ms |
| 2 | **串行累加**：Emby 详情 → TMDB 搜索 → TMDB 详情 → 图片尺寸 → 季集 | 同上，关键路径是"一跳等一跳" |
| 3 | **列表零缓存**：Emby 浏览页每个分类行一次请求 | `[emby-items]` 单次 412–1369 ms |
| 4 | **每次进页面重新登录** | `[emby-connect] login 1221 ms` |
| 5 | **无图条目进详情纯转圈**：预览快照要求必须有幕布图 | 日志 `preview=false`，等 1.2–2.3 s |

> 注意：TMDB 那两跳**本来就不慢**（336 已加 JSON 磁盘缓存，3 ms 级）。差的是 Emby 这一侧。

## 四、改动（全部无新增依赖、无 UI 视觉变更）

### 4.1 新增文件

| 文件 | 职责 |
|---|---|
| `emby/EmbyResponseCache.kt` | Emby 慢变元数据响应磁盘缓存：key=SHA256(url)、TTL 分级、只写 2xx、原子写、`.key` 伴生索引供按 id 失效 |
| `emby/EmbyEpisodeGrouping.kt` | 一次全量拉集 → 按季分组的**纯函数**，含"覆盖不全返回 null"判定 |
| `emby/EmbyAuthCache.kt` | 已登录会话内存缓存（由旧 `EmbyResumeSession` 升级，旧文件已删） |

### 4.2 缓存口径（关键设计）

| 端点 | TTL | 为什么是这个值 |
|---|---|---|
| 详情 `Users/{uid}/Items/{id}` | 6 h | 慢变；含 UserData ⇒ 写操作主动失效 |
| `Items/{id}/Images`（尺寸表） | 30 d | 只与图片 tag 有关 |
| `Shows/{sid}/Seasons`、`Episodes` | 6 h | 慢变；停止播放后按**剧集 id** 失效 |
| 列表 `Users/{uid}/Items…` | 10 min | 新片入库会变 |
| hero `recent` | 10 min | 同上 |
| hero `resume`（继续观看） | **60 s** | 带播放进度，刚看完不能显示旧位置 |
| `Items/Counts` | **不缓存** | 它同时用于判断服务器是否在线，缓存会让挂掉的服继续显示"在线" |
| 会话 `login` | 15 min | 只在内存，不落盘 |

### 4.3 并行化（D366）

`EmbyResource.loadDetails` 从串行改为**四路并行**：Emby 详情 ∥ TMDB ∥ 图片尺寸 ∥ 季表；
服务器已刮削 `ProviderIds.Tmdb` 时**免掉一次 TMDB 搜索**；
图片尺寸表只影响"库图 vs TMDB 图谁更清晰"，给 **800 ms 上限**，超时按空表走（库图兜底）。

### 4.4 拉集 N 次 → 1 次（D366 补）

`/Shows/{id}/Episodes` 不带 `SeasonId` 返回整剧集（`ParentIndexNumber` = 季号）。
**覆盖判定必须存在**：任一季为空就退回逐季请求 —— 服务器分页截断时少的集在页面上看不出来，
但选集面板会缺集，这种"静默少数据"只能靠逻辑挡。

### 4.5 冷进详情首帧（D366 补）

`DetailPreview.from()` 原来要求必须有幕布图才给快照 ⇒ 无图条目纯转圈。
改为**只要求有标题**，无幕布走 `DetailBackdrop` **既有的**空封面态。没有新增任何视觉组件。

## 六、本轮踩到的坑（都写在代码注释里了）

| 坑 | 表现 | 教训 |
|---|---|---|
| 缓存目录被删后 `put()` 静默失败 | 第二次进还是慢 | 写入前 `mkdirs()`；低存储设备会真实发生 |
| 缓存从未初始化 | Emby 热进仍每行 0.4–1.4 s，日志里**一条 `[emby-cache]` 都没有** | 那个"没有"就是证据；初始化要覆盖所有入口 |
| `EmbySessionModel` 涨到 305 行 | `ui_gate` 回归（**新建超限文件也算**） | 300 行是硬线，抽 `connect()` 后回 299 |
| 脚本写 Kotlin 正则 `\b` 变退格符 | 季集剥离静默失效 | 关键正则必须配单测（本轮已有先例） |

## 八、明确不做的事（及原因）

| 没做 | 原因 |
|---|---|
| 列表预取（Rex 的 Preload 思路） | 进一次列表要打十几个请求（剧集还要跟季集），对源站压力大；本项目有过"多一层代理 + 8 倍超买"的历史坑。收益 1.2 s → 0.3 s 不值得 |
| 用户可配缓存时长 | Rex 有，但属设置项/UI 变更；本轮铁律不碰 UI |
| 骨架屏 | 首帧缺口已用既有空封面态补上；新增骨架属视觉变更 |
| 缓存 `Items/Counts` | 它同时是"服务器是否在线"的依据，宁多一次请求不给错状态 |
