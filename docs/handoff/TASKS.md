**P13-O 已收口（2026-10-30）：`slope_halves_agree` 降为历史字段。**

那个布尔只比"同号"，真机 13 份证据里 8 份报 true、其中 3 份两半程量级差 5 倍以上，
最极端的一份两半程都为正、全序列斜率却为负。现在换成：

- 两半程各自 **HAC 标准误 + 95% 带**（`estimate_hac_slope_error_range`）；
- `gap`（差多少）+ `pooled`（这个差的误差）+ `z`（几个 σ）+ `cumulative_gap_ns`；
- `resolution_ppm` vs `budget_equivalent_ppm` —— "这套尺子够不够细"的保证条件；
- 三态 `consistent` / `inconsistent` / `unknown`，**`inconsistent` 时 `drift_verdict` 降 `unknown`**。

真机四轮（`docs/evidence/p13o/`）：all `consistent`，但**其中两轮旧布尔报 `false`**
（两半程反号），而新判据说差在噪声内（1.58σ / 1.60σ）—— 反号只是 V 形漂移的两条腿，
不是"两段不同的漂移"。这是"同号是最弱的相似性"的实证。

⚠️ **`inconsistent` 没在真机上出现**，该分支由端到端单测 O12（造 0.2→4 ppm 突变）
与校验器 O7a 覆盖，不是设备证据。另有已知口径问题：`trend` 窗口可跨 seek 段
（`segments=2` 时仍按一条线比较），本卡没修，见 `85-p13o-status.md` §六 第 4 条。

**P13-P 已收口（2026-10-30）：`lateness` 拆成「手慢了」与「表快了」，88 ms 的归因被自己推翻。**

恒等式 `Δlateness = present_step − due_step` 现在对每份证据可复算（13/13 通过）。
真机 12 轮 4K60：`|due_step| ≤ 36 µs` —— **due 侧一次都没发生**；
唯一一次 45.636 ms 干净落在 `present_side`（`present_step = +45.372 ms`），
尾巴 `[29.73, 13.65, −1.11, 0.07]` 是"一次延迟 + 三帧排空"。
`SIGSTOP` 60 ms 的正向对照判 `present_side`（79.856 ms / `due_step = +2 µs`），
证明仪器能分辨方向。

设计稿 §1.2 的推断被推翻并保留原文：漏洞在**首帧没有前一帧** ——
`p13d-4k60-r1` 的 88.231 ms 与"首帧 264 ms 冷启动 + 一帧一步排空"四条全吻合，
而"片中单帧 88 ms"被 `present_jitter.max = 19.586 ms` 排除。
P13-F 的「片中抢占」措辞**撤回**，改为「首帧排空（未证实）」。

附带修两处 P13-O 留下的红灯（成因在那一卡，不在本卡）：
`p13n` 的 `sizeof(DriftTrend) ≤ 448`（实测 528）、`p13l` 的两条预算断言
（完美线性序列被浮点噪声判成 `inconsistent` → `unknown`，已加 `kMinCumulativeGapNs = 1 µs`
材料性门槛）。详情见 `87-p13p-status.md` §五。

**P13-Q 已收口（2026-10-30）：P13-P 的"due 侧一次没发生"被整段账推翻。**

P13-P 出版的是**一步**（`due_step`），P13-Q 出版的是**整段**（两侧累积）：
`lateness[k] − lateness[0] = Σpresent_step − Σdue_step`，schema `sync/15`。

真机六轮（3 空载 + 3 满载 4 个 `yes`）：空载 4.0 / 12.1 ms，满载 40.5 / 80.5 / 97.9 ms。
最清楚的 r4（80.488 ms，零丢帧，账残差 0）：单帧口径 `present_step = +80.5 ms` 判 `present_side`，
整段口径 `cumP = +10.23` / `cumD = −70.23` 判 **`due_side`** ——
**80 ms 里 70 ms 是"表"整体前移，分几步挪的，每步都没到一帧，所以 `due_step_frames` 记 0。**
两个口径都对，只是回答的问题不同（`89-p13q-status.md` §2.2）。

已知缺陷：**丢帧时账不平**。`present_step` 跨丢帧按帧数补，`due_step` 只记最后一帧，
两个分母不同；实测各丢 2 帧的两轮残差 +140.5 ms。现在如实出版残差、丢帧轮不给累积归类。
首帧 `lateness` 不是 0 而是 18–29 µs（锚点在"到达"、读数在"交出"），Q3 的判据因此是 ≤ 1 ms。

**P13-R 已收口（2026-10-30）：`cumD` 的成因是音频时钟比墙钟快。**

`due = mono + (pts − anchor_pts − elapsed)` 的三个自变量做成四个跨度出版，`sync/16`。
真机四轮（2 空载 + 2 满载）：

| 轮 | 负载 | max | 丢帧 | `clock_ahead` | `playback_rate` |
|---|---|---|---|---|---|
| r1 / r2 | 空 | 3.87 / 17.19 ms | 0 | +0.02 / +0.08 ms | 1.000015 / 1.000023 |
| r4 | 满载 | 84.99 ms | 0 | **+118.79 ms** | **1.015105** |
| r3 | 满载 | 62.52 ms | 37 | **+426.70 ms** | **1.056475** |

`clock_ahead = elapsed_span − arrive_mono_span`，四轮跨度恒等式残差 ≤ 1 µs。
**`playback_rate` 是第三方对照**（只用首末帧的 pts 与交出时刻，不经过 `elapsed`）：
它同步给出 1.0151 / 1.0565 ⇒ **视频真的播快了 1.5% / 5.6%**，不是帧到得早的错觉。
这是一条**单调累积的 A/V 同步缺陷**（8 秒 119 ms，10 分钟 9 秒），不只是尖峰；
r3 那一轮还丢了 37 帧而 `completed = true`、`error` 为空。

本轮踩到的坑：`DueStep` 位置式初始化漏了钟读数三格，`normal_branch_frames` 照样满 480
（它只证明"函数被调了"）。已换成 `clock_supplied_frames` 并做成硬判据 R1a；
`DueStep` / `EpisodeSample` 的字段顺序从此**只能往后加**。

**P13-S 收口（2026-10-30）：门装上了，但真机 A/B 不成立。**

`ClockPositionTracker` 新增累积漂移门：**连续 60 帧位置增量 > 墙钟增量 + 累积超 45 ms**
⇒ `position -= 累积量`，计数 `drift_rebases`，`sync/17`。单测 S1/S2 全过
（1.5% 快钟必被拦、同步钟一次不触发），`ctest` 15/15。

**但三轮真机 `drift_rebases` 全是 0 —— 门一次没响**，所以 r2/r3 的
`clock_ahead ≈ +0.02 ms` 不是这次改动的功劳（那两轮本来就没异常）。
更麻烦的是 r1：`clock_ahead +247.69 ms` + `arrive_excess −263.98 ms` + 丢 18 帧，
门却没响 ⇒ 那 247 ms **不是"钟比墙快"**，而是**到达窗口被压缩**（管线跑到前面）。

**这动摇了 P13-R 的因果**：`playback_rate = 1.0151` 只证明"视频确实播快了"，
不能证明"钟的估计超前"。P13-R 里"音频时钟比墙钟快 1.5–5.4%"应降级为
"两者同时出现、方向未定"（`93-p13s-status.md` §三）。

同时发现：`pace.clock_health.jump_rebases` **一直是 0**，因为节拍器从没把 tracker 的
计数搬进 `PaceSummary` —— 这个字段是死的。

**P13-T 收口（2026-10-30）：门能证明了；尖峰与时钟在受控负载下分开了。**

修掉一处真缺陷：`PaceStats::summary()` 漏了 `out.drift_rebases` —— 于是 P13-S 的
"三轮全 0"分不清"门没响"和"响了没出版"。新增 S3 单测（1.5% 假快钟驱动完整
`FramePacer`，断言 `summary().drift_rebases ≥ 1`）钉住三段接线。

受控两轮（4 个忙循环，**开跑前实测空闲率 44.7%**，`ps` 确认 4 个 `yes` 在）：

| 轮 | max | 丢帧 | `drift_rebases` | `clock_ahead` | `playback_rate` |
|---|---|---|---|---|---|
| r1 | **80.14 ms** | 0 | 0 | **+0.03 ms** | 1.000016 |
| r2 | **41.82 ms** | 0 | 0 | **+0.02 ms** | 1.000014 |

**尖峰出现了，时钟一点没动** ⇒ `lateness` 峰值是"交出晚"，不是时间轴被推快；
P13-R 那两轮（+118.79 ms / 1.0151）是**另一件事且不是每次满载都发生**（本卡两轮没撞上）。
P13-S §五.7 那句"`jump_rebases` 是死字段"**是错的**，已在原文加更正块 ——
`FramePacer::summary()` 一直搬着它，真正没接的是本次修的 `drift_rebases`。

**P13-U 收口（2026-10-30）：位移复现了（1/3 轮），但门没响 —— 原因是判据形状。**

8 路忙循环，开跑前/跑完后各测 `/proc/stat`：**空闲率 0.0% / 0.4%**，`ps` 确认 8 个 `yes`。
三轮：r1/r2 正常（`clock_ahead` +0.01/+0.02 ms、rate 1.0000），
**r3 `clock_ahead +91.72 ms`、`ahead_wall +76.23 ms`、`playback_rate 1.011632`、零丢帧**。

`ahead_wall = elapsed_span − present_wall_span` 用**交出端**墙钟做分母，不依赖到达时刻 ——
r3 在独立基准下也领先 76 ms，**排除了"到达窗口被压缩"这个替代解释**（P13-S §3.1 的疑问）。

但 `drift_rebases = 0`：r3 最差帧（index 201）的 `due_step` 只有 **−3.8 µs**、恒等式残差 0，
说明 91.72 ms 是**分多帧摊开**的。而门的条件是"连续 60 帧 `drift > 0` 且累积 > 45 ms"——
中间夹一次零漂/负漂，`lead_streak_` 就归零，永远到不了 60。
**这是判据形状的问题，不是阈值大小**：把 45 ms 调小也没用。

**P13-V 收口（2026-10-30）：判据换成"按单帧贡献累积"，单测全过，真机仍没拦住。**

改法：累积 > 45 ms 即复位；单帧 `drift > 30 ms` 当台阶、清空累积不计入。
S1/S3/**S4（P13-U 的断续形状）**全过，C5 五条没被改坏，`ctest` 15/15。

真机 8 路负载三轮：**r2 复现到 `clock_ahead +165.58 ms`、`ahead_wall +149.33 ms`、
`playback_rate 1.021176`（8 秒快 2.1%）、丢 7 帧**，而 `drift_rebases` 仍是 **0**。

原因已定位：r2 是**一个大台阶**（单帧上百毫秒），正好被新规则当"台阶"排除；
而 `jump_limit_ns` 只管 > 1 s。**30 ms–1 s 这一档两条门都不管**，这就是现在唯一的洞 ——
也是真机反复出现的形状（P13-R/U/V 各 1/3 轮都在这一档）。

**P13-W 收口（2026-10-30）：中台阶接进门里，单测齐了，真机待验。**

改法：启动期（首帧后 1 s）之外，单帧 `drift > 30 ms` 直接按墙钟吃掉；
启动期内不拦（C5-4/C5-5 的 50 ms 台阶就在那一段，语义因此保住）；
两个入口（累积超限 / 中台阶）共用一处收尾写标志与计数。

单测：S1（1.5% 快钟）、S3（计数走到 summary）、S4（断续超前）、**S5（启动期外 60 ms 台阶）**
全过，C5 二十六条一条没坏，`ctest` 15/15。

⚠️ **`docs/evidence/p13w/` 的三轮作废**：那是在"中台阶没写计数"的构建上跑的，
`rebases = 0` 是计数漏写、不是门没响。真机要在修好的构建上重跑 8 路 3 轮，
判据是"撞上事件那轮 `drift_rebases > 0` 且 `rate → 1.000`"。

**P13-X 收口（2026-10-30）：门第一次在真机上响了，但一次就过冲。**

8 路负载四轮：**r1 `drift_rebases = 1`（首次触发）**，可复位把 `clock_ahead`
从正拨成 **−33.21 ms**、`playback_rate 0.995868`（慢 0.4%）—— **修正自己引入了同量级的误差**。
同批 r2 又出现 **+115.32 ms / rate 1.014671** 而门没响；r3 干净；r4 +23.66 ms 未触发。

两条确定的事：① 门是活的（不再是"从没响过"）；② **减整段累积量是错的**，
应只减超出部分（`cum − limit`）或限幅 —— 这是确定性缺陷，不需要更多样本。

**P13-Y 收口（2026-10-30）：复位幅度改成"只减超出部分"，真机未撞上事件。**

`position -= (cum − limit)`，`cum` 留在门限而不是清零；台阶入口仍减整段（台阶是伪值）。
单测全过。真机 8 路四轮：`clock_ahead` 最大 +4.97 ms，**门没触发是对的**，
但也因此**没能验证新幅度**（历史复现率约 1/3，四轮全空不意外）。

**P13-Z 收口（2026-10-30）：八轮四次位移，门一次没响 —— `cum_drift` 与 `clock_ahead` 不是同一笔账。**

8 路八轮：r1 +46.49 / r4 **+73.30** / r5 +19.26 / r7 +34.33 ms，`playback_rate` 最高 1.0093，
而 `drift_rebases` **全 0**。r4 已超 45 ms 门限却没触发 —— 按定义 `clock_ahead = Σdrift`，
两者对不上。

假设：`position_ns_` 不只在正常分支推进 —— `stale` 外推、`jump_rebase`、倒退钳制
都会**直接加墙钟增量**，而 `cum_drift_ns_` 只在正常分支累加。位移从这些分支漏进来，
一分钱都不记进漂移账。可判：看同批证据的 `extrapolated_frames` / `jump_rebases` 是否非 0。

**P13-AB 收口（2026-10-30）：门第一次被确定性触发 —— 有界、不过冲、与注入量无关。**

探针新增 `kivo.clock_offset_ms` / `kivo.clock_offset_at_ms`，注入点是
`AudioClockSource`（不是往 tracker 里塞开关）：`ClockOffsetSource` 包住真实时钟，
走够 `arm_after_ns` 之后**每一帧**位置都带这个偏移。证据顶层固定出版
`clock_injection` 三格（`sync/18`），判据 I1–I3 钉住"注入过 / 没注入 / 给了参数却没触发"。

真机五轮（4K60，零丢帧）：

| 轮 | 注入 | `drift_rebases` | `clock_ahead` | `playback_rate` | 预估值 |
|---|---|---|---|---|---|
| 0ms | — | 0 | +0.02 ms | 1.000014 | 1.000003 |
| 80ms@2s ×2 | 80 ms | 5 / 6 | +44.80 / +44.74 | 1.005658 / 1.005648 | 1.00564 |
| 80ms@5s | 80 ms | 10 | +44.95 | 1.005675 | 1.00566 |
| 200ms@2s | 200 ms | 2 | +44.71 | 1.005646 | 1.00563 |

**80 ms 与 200 ms 收敛到同一个残差 44.7–45.0 ms**（= `drift_limit_ns`）——
"有界"与"没门"的分界就在这里：没门时两者应分别 1.0101 / 1.0256。
`clock_ahead +44.8` 与 `cumD −45.00` 是同一件事从两端量的，五轮严丝合缝。
P13-X 的过冲（−33.21 ms）再没出现。`verify_p12_all.py` **515 份 / 四层 / 9 子校验器**。

代价与遗留：门是**事后同帧削平**，所以事件仍以一次 ~29–31 ms 的迟到现形
（注入帧 `due_step = −45.0 ms`、`present_step ≈ −15 ms`）；
残差停在门限上 ⇒ 稳态反复微调（5/6/10 次，总修正量仍是 35.2 ms）。

**P13-AC 收口（2026-10-30）：迟滞带赢了，限速被自己否掉。**

门限以前同时当"触发阈值"和"收敛目标"：`cum > 45` 触发、修到 45 停，于是稳态贴在
45.00，下一帧再挤 50 µs 又触发（P13-AB 里 5/6/10 次，总修正却只有 35.2 ms）。
现在改成**两阈值**：越过 45 进、修到 `45 − 5 = 40` 才退；修正**一次还完**（不设上限）。

**限速（本卡最初的方案）被真机否掉**，三版同一注入（80 ms @2 s）对照：

| | AB 削平到 45 | 限速 2 ms/帧 | **最终版 一次还完到 40** |
|---|---|---|---|
| 事件帧 `due_step` | −45.0 ms | −78.0 ms | **−40.0 ms** |
| 事件帧迟到 | 29.6 ms | 61.8 ms | **24.0 ms** |
| `drift_rebases` | 5 | 21 | **1** |
| 200 ms 台阶丢帧 | 0 | 5 | **0** |
| `playback_rate` | 1.00566 | 1.00505 | **1.00505** |

道理是结构性的：台阶是**输入**，当帧 `due` 已被推早，限速只决定"这一帧还多少" ——
还少点尖峰就更大。真机最终版四轮：`clock_ahead` 40.00 / 40.01 / 39.99（80/80/200 ms 注入），
`total = 注入 − 40 ms`（40.03 / 40.03 / 160.05），零丢帧，事件帧迟到 23.6–24.0 ms。
`verify_p12_all.py` **540 份 / 四层 / 9 子校验器**。

### P13-K · 自相关校正（**DONE 2026-10-30**）

- **继承的说法**：P13-J 把 r3（35 s / 700 点）的 `detectable = true` 归因为
  "IID 假设低估了 SE（残差自相关）"，并在诚实清单里写着"要更严格得上 HAC/Newey-West"。
- **前提没被证实**：真机三轮的残差一阶自相关是 `+0.019 / +0.009 / −0.014` ——
  **几乎是白的**。抽稀把 50 ms 内的连续性打断了，相邻样本来自不同的调度窗口。
  "强自相关"是个听起来合理的推断，实测不成立。
- **那 20% 从哪来**：非 seek 两轮的膨胀比稳定在 `1.199 / 1.194`，ρ1 ≈ 0 却仍有差 ——
  来源是**异方差**（HAC 的 `γ0 = Σ x²e²` 给两端高权重，而真机两端的 `lateness` 更差）。
  seek 轮是 `0.922`（< 1），说明 HAC 是双向修正而不是一律放大。
- **P13-J 的 `true` 没有复现**：同一片源同一 700 点，SE 从 `0.2152` 变成 `1.762968`（**8.2×**），
  CI `[−3.148, +3.762]`、`detectable = false`。那一轮只是恰好很安静。
  **单轮 SE 不是设备常数** —— 这是本卡最实用的一条结论。
- **做法**：新单元 `core/pace/pace_hac`（`bartlett_lags` 用 Newey–West 经验式
  `floor(4·(n/100)^(2/9))`；`estimate_hac_slope_error` 逐 lag 现算残差、不占 16 KB 栈；
  `n/(n−2)` 自由度修正让 L=0 时与 IID 同秤）；`DriftTrend` 增 9 字段；
  schema 升 `sync/9`；`slope_ppm_std_error` **换模型**（名字不变），旧值原地改名 `_iid`；
  新增半程诊断 `slope_first_half_ppm` / `slope_second_half_ppm` / `slope_halves_agree`。
- **半程诊断第一次派上用场**：r3 前半 `−3.339`、后半 `+1.051` —— 那条 `+0.307 ppm`
  不是持续漂移而是中途换向。有这个字段的话，P13-J 那个 `true` 当场就能被质疑。
- **校验器结构性改动**：六张按版本递增的 schema 表改成从 `SCHEMA_ORDER` 派生
  （此前每升一版要记得六处一起加，为此栽过三次）。新增版本登记一次即可。

### P13-L · 累积漂移 + 额度判读（**DONE 2026-10-30**）

- **继承的欠账**：`slope_detectable` 只回答"与 0 分得开吗"，而 P13-K 那个 `true`
  对应的实际累积量是 35 s × 0.48 ppm ≈ **17 µs** —— 统计上非零，人耳绝无可能察觉，
  而报告里没有任何字段阻止读者把它读成"有漂移要修"。
- **做法**（选"给累积量"而不是"改名 `nonzero_at_95pct`"）：
  新单元 `core/pace/pace_drift_budget`（`accumulate_drift` 把 ppm 积回 ns，
  并对 45 ms 额度判三态）；`DriftTrend` 增 4 字段；schema 升 `sync/10`；
  四格**紧跟** `slope_detectable` 输出（挪到末尾等于让读者自己去乘那个 ppm）。
- **额度 45 ms 的出处**：ITU-R BT.1359-1 的音频**超前**可检测阈值。不用 125 ms（同标准的
  滞后方向）是因为两个方向取较严的一侧更保守；不用常引的 "40 ms 体验上限" 是因为
  **没有可引的文档** —— 写进证据就成了一句无法核对的断言。
- **反转一条直觉**：判定用**置信带远端**积出的上界，不用点估计。CI 含 0（`detectable = false`）
  时远端积起来仍可能越过额度 —— 那种证据读成"没事"，是拿噪声当保证。
- **三轮实测**（零丢帧零 xrun）：上界 63.9 / 68.3 / 80.0 µs，额度 45 ms
  —— 用掉 **0.142% / 0.152% / 0.178%**，三轮全 `within_budget`。

  —— P13-J 与 P13-L 的分歧第一次同时出现在真机证据里。
- **顺手撞出的缺陷（下一张卡）**：`DriftSeries::note()` 只在媒体时刻**倒退**时切段；
  **向前** seek 时它看到的只是"前进"，于是两段被拼在一起回归。
  物证：`segments = 1`、`segment_accepted = 2400 > capacity 2048`、`span = 112.367 s`
  跨了一个 10 秒空洞，而 `verdict` 照样报 `within_budget`。

- **副作用（好消息）**：P13-J 的精确中位数第一次在真机上给出连续读数
  —— 八窗中位数 74~77 µs（此前一直全是 125 000）。
  同时暴露 P13-J 遗留项仍在：整场 `quantiles.p50` 三轮也是 125 000，差 **69%**。
- **变异自测踩了自己的坑**：第一版用 `copy2` 还原，它**连 mtime 一起复制**，
  增量构建判定"无需重编"，从第 3 条起每条测的都是同一条陈旧二进制 ——

- 单测 `kivo_p13l_budget_tests` 11 例 / **207 断言**（含 50 组随机上界守卫）；

### P13-M · 段边界的权威是锚点重建（**DONE 2026-10-30**）

- **继承的缺陷**：P13-L 的向前 seek 轮报 `segments = 1`、`span = 112.367 s`、
  `observed_hz = 18.466` —— 两段被拼在一个回归里。根因不是阈值不够，
  是**判定用错了信号**：`note()` 拿 `media_ns < last_media_ns_` 推断"换了时间轴"，
  而 pts 前进推不出"没换"（向前 seek 正是"前进且换了"）。
- **做法**（不加阈值，换信号）：`DriftSeries::break_segment()` 由
  **`FramePacer::reset()`** 调用 —— 那里 `tracker_.reset()` 正是 `lateness` 零点
  被重新定义的一刻。`segments` 的定义收窄成"一次锚点生命周期算一段"。
  `note()` 里的 pts 倒退保留作兜底。
- **为什么不加"跳超过 N 秒就切段"**：卡顿与向前 seek 在 pts 上**不可区分**，
  而两者的正确处理相反 —— 卡顿之前采到的点是真数据，切了就是拿真数据赔告警。
  所以段内空洞**不切段**，改为出版 `segment_largest_gap_cells` / `segment_contiguous`。
- **同一个场景重跑，缺陷自己消失**：`segments` 1→**2**、`truncated` true→**false**、
  `span` 112.367→**89.967 s**、`media_span` 129.967→**119.933 s**、
  `observed_hz` 18.466→**20.0111**、`unobserved_cells` 200→**0**。
  最后那一格说明：那 200 格本来就不是"没采到"，是"跨了一次锚点"。
- **四轮真机**：向前 seek / 向后 seek / 平跑 / **冻结 2 s**。
  前两轮 `segments = 2` 且 `truncated = false`；平跑 `segments = 1`；
  冻结轮把进程 `kill -STOP` 2 秒，第一次在真机上得到
  `segment_largest_gap_cells = 45`（2.25 s）、`contiguous = false`、
  `observed_hz = 19.6589`、xrun 1 / 丢帧 68 —— **段内空洞不会被误判成 seek**。
- **阈值 20 格 = 1 s 的论证**：20 Hz 抽样下 20 格 = 至少 24 个连续帧无样本
  （任何 ≥ 24 fps 的片源）。帧级抖动到不了这个量级：30 fps 掉三帧才凑够一格。
- **变异自测**：单元层 12 处 —— **11 条应红全部杀死、1 条等价重构仍绿**；
  校验器层 7 处 —— 6 条应红全杀、原件复制仍绿。
  其中 C6（空洞改成累加）逼出了原测试的漏洞：`max` 与"累加"在只有一个洞时
  给同一个数，13 条用例全放它过去 —— 补了 m14（5 格 + 3 格 → max 5 / 累加 8）。
- 单测 `kivo_p13m_segment_tests` 14 例 / **75 断言**；总收口 **376 份 / 四层 / 53 豁免**。
- 验收：`80-p13m-design.md`、`81-p13m-status.md`（§六 十条诚实清单）

### P13-N · 分位数必须自己说出精度（**DONE 2026-10-30**）

- **继承的缺陷**：P13-J 把窗口那一份中位数换成精确值，**却只改了一半** ——
  整场的 `quantiles.<口径>.p50` 还是直方图桶中心。四轮真机里它恒为 125 000，
  而八个窗口中位数全在 72 761~82 814，差 **66%~71%**，而 JSON 里没有任何字段
  能阻止读者把它读成"两份测量打架"。
- **根因不是精度，是表达**：125 000 是桶 512（`[0, 250 000)`）的几何中心，
  真值确实在那一桶里 —— 两个数都对，缺的是"这个数是量出来的还是算出来的"。
  改一半比不改更危险：不改时两个都是 125 000，读者会去查桶宽；
  改一半时一个 125 000 一个 73 646，读者只会认定数据有问题。
- **做法**：每个分位块的 `p50` 后接四格 —— `p50_range_low_ns` /
  `p50_range_high_ns`（= 桶界 ∩ `[min, max]`）/ `p50_bucket_samples` /
  `bucket_width_ns`。整批点另给 `median_of_window_medians_ns`
  （8 窗中位数排序后第 `(n−1)/2` 个，与 `percentile_ns(0.50)` 同秩口径）。
- **结构性修复**：`percentile_ns` 原来在函数体内联"跳过下溢 → 逐桶累加 → 命中"
  的循环；`percentile_bucket` / `percentile_range` 若各写一遍，必然在秩边界上
  分家。抽成私有 `locate(q)`，三者共用 —— P13-M 的 `segments` 正是这么坏的。
- **范围算在 core 不算在报告层**：`av_sync_report.cxx` **只在 Android 侧编译**，
  写在那里的钳制逻辑没有桌面单测；而"下界取大、上界取小"恰好容易写反，
  写反会得到一个**不含 p50 的空区间**，那在 JSON 里长得像"范围很窄、很准"。
- **三轮真机零丢帧零 xrun**：`p50` 仍是 125 000，但它旁边写着
  `range = [13 490, 250 000)`、桶内 **2553 / 2600 = 98.19%**；
  精确参照 73 999 落在范围内。r2 的 `segments = 2` / `observed_hz = 20.0111`
  与 P13-M 同一场景逐位一致 —— 这轮没碰到切片逻辑。
- **变异自测**：单元层 10 处 —— **9 条应红全杀 + 1 条等价重构仍绿**；
  校验器层 8 处 —— 7 条应红全杀 + 原件复制仍绿。
  C8（删掉 `sort`）第一次**存活**：n07 的输入是递增的，排序与否给同一个数 ——
  改成递减输入（7,6,…,0）才分开。与 P13-M 的 C6 是同一个教训：
  **凡"排序/取极值"的量，输入必须造得让两种算法给不同结果。**
- 单测 `kivo_p13n_quantile_tests` 11 例 / **76 断言**；总收口 **382 份 / 四层 / 53 豁免**。
- 验收：`82-p13n-design.md`、`83-p13n-status.md`（§六 十条诚实清单）

### P13-J · 漂移的误差棒（**DONE 2026-10-30**）

- **继承的欠账**：「漂移量准卡在 0.25 ms 桶宽 ⇒ 分辨率约 7 ppm」。去还它，发现这句话
  **过于乐观**：三轮真机的八窗中位数**全部等于 125 000**，`slope_from_windows_ppm`
  恒 0 —— 那把尺子的可分辨力不是 7 ppm，是**零个刻度**。
- **缺陷 A（尺子没刻度）**：窗口中位数走 `SignedHistogram` 桶中心，98% 的样本挤在
  桶 512（0~250 µs），八个窗全被量化成同一个数。真实 lateness 铺了 220 µs，一口吃掉。
- **缺陷 B（尺子没刻度盘）**：逐点 `slope_ppm` 是精确的，但只报一个点估计。
  `r2 = 5.5e-05` 时它照样印六位小数，读者（包括写它的我）读成"精确测到 −0.022 ppm"。
- **做法**：新单元 `core/pace/pace_window_stats`（`split_windows` + `median_of_slice`，
  原始值 `nth_element`，scratch 512，超了退回桶中心并**显式标记**）；
  `Regression` 增 `slope_se_per_ns = sqrt(SSres/(n−2)/Sxx)`；`DriftTrend` 增 6 个字段
  （`std_error` / `ci_low` / `ci_high` / `detectable` / `window_median_exact` /
  `fallback_windows`）；schema 升 `sync/8`。`std_error` **紧跟** `slope_ppm`。
- **三轮实测**（零丢帧零 xrun）：r1 130 s → 漂移 **[−0.387, +0.175] ppm**、
  r2 seek → [−0.276, +0.550]、r3 35 s → [+0.058, +0.901]。
  八窗中位数三轮 distinct 都是 **8**（旧实现是 1）。
- **意外收获**：真实中位数约 **73 µs**，旧实现的桶中心 **125 µs** —— 那个常数本身
  偏高 **71%**。前五张卡的 `p50` 读数都带着这个偏移（整场分位数至今仍是桶中心，见 §六.3）。
- **SE 公式被真机验了一次**：r3 的 SE 是 r1 的 1.50 倍，对应 `σ` 小 4.6 倍、`Sxx` 小 51 倍，
  预期 `√51 / 4.6 = 1.55`。
- **变异 12 处全红**：C++ 3（C1 第一次只红标记，加"每窗一个尖峰"后才红在数据上；
  C3 第一次把进程搞崩，给 `rank` 加下界钳制后才"红而不崩"）、Python 8、端到端 1。
- 验收：`74-p13j-design.md`、`75-p13j-status.md`（§五 八条诚实清单）

### P13-I · 窗口的身份（**DONE 2026-10-30**）

- **继承的欠账**：「`quantiles` 是整场累计 2600 个样本，`trend` 只描述最近 102.4 s 的 2048 个点」。
  去处理它，顺手撞到旁边一个**真说假话**的字段 —— 那个更严重，也不在欠账里。
- **缺陷 A**：`truncated()` 是 `total_ > kCapacity`，而 `total_` 是整场累计、`clear()` 不清。
  seek 之后"整场 3100 > 2048"被判成覆盖发生过，而环形里躺着的是第二段**整整 2000 个点**。
  自相矛盾：覆盖过的环形序列必然满 2048。**从没被看见不是因为罕见，是因为从没在 seek
  之后取过 sync 报告**（33 份带 `trend` 的证据里 32 份 `segments == 1`）。
- **缺陷 B**：分位数整场累计、趋势只有窗口，两份都说了实话但并排摆着让人当同一批读。
  r1 实测：整场 max 6.518 ms / 窗口 max 2.040 ms（差 3.2×），而 p50/p95/p99 **恰好相同**。
  "恰好相同"是最坏的情况 —— 它让两份数据看起来同源。
- **做法**：`DriftSeries` 加 `segment_total_`（唯一写入点 `clear()` 归零 + 接受时 `++`），
  `truncated ⇔ segment_total_ > kCapacity`；新单元 `core/pace/pace_drift_window`（窗口分布，
  `trend` 自带它回归过的那批点）；`segment_samples` 一删为二
  （`segment_accepted` + `window_sample_count`）；schema 升 `sync/7`；
  `window_quantiles` **不写 `worst`**（累计那份已有，同名不同口径就是 P13-E 消灭的东西）。
- **三轮实测**（零丢帧零 xrun）：r1 覆盖（窗口 2048/整场 2600）、
  r2 seek（段内 2000/整场 3100、`truncated` **false**、`media_span` 154.933 s 两段相加）、
  r3 短片（两份分布**逐桶完全相同** —— 一条路径逐帧累加，一条停机时重放序列）。
- **变异 12 处全红**：C++ 3、Python 8（M1 就是旧实现的产出，I3+I5 当场判假）、端到端 1。
  另有 **2 条判据自己假红**（H2 的 `+1` 只加一次、I5 拿整场容量比段内），
  两条都是"把整场当成一段"—— 见 `73-p13i-status.md` §六.1。
- 验收：`72-p13i-design.md`、`73-p13i-status.md`（§六 八条诚实清单）

### P13-H · `observed_hz` 的分母（**DONE 2026-10-30**）

- **继承的欠账**：「`span` 是序列窗口首末差，`accepted` 是累计，超过 102.4 s 后两者不同源」。
  去验这句话，它比欠账写的严重得多：不是"偏高几个百分点"，是**没有上界**。
- **缺陷**：`observed_hz = accepted(累计) * 1e9 / trend.span_ns(窗口，封顶 102.35 s)`。
  130 s 片源实测：同一份数据，新尺子 **20.005 Hz**，旧尺子 **25.399 Hz**。
  10 分钟的片子按旧公式会报 100 Hz 以上，旁边写着 `target_hz: 20`。
- **为什么活了四张卡**：① 27 份证据全是 8 s / 35 s 片源，`truncated` 恒 false，
  两根尺子恰好等长；② **校验器复算的是同一个除法** —— 它验"算式写没写错"，
  不验"分子分母是不是同一个作用域"。照抄算式只能证明算术没打错，不能证明量纲对。
- **判据**：不是"更准的除法"，是抽稀门接受规则蕴含的**恒等式**
  `accepted + unobserved = floor(media_span/interval) + 1`。
  27 份旧证据余量全部 **0**；旧尺子在 130 s 上差 **552**。
- **做法**：`DriftSeries::media_span_ns()` 按段累加（seek 时关段折进 `closed_span_ns_`）；
  `media_span_ns` 在 JSON 里**紧跟 `accepted`**（相邻是防腐，不是排版偏好）。
  跨度用"最后**被接受**"的帧而不是"最后观察到的"帧 —— 后者会让两根尺子差不到一帧，
  **差一点点比差很多更难发现**。`schema` 升 `sync/6`。
- **三轮实测**（130 s / 360p30 / 3900 帧 / 零丢帧零 xrun）：`accepted` 2600、
  `media_span` 129.967 s、`truncated` 全 true，恒等式 3/3 顶格成立。
- **变异 11 处全红**：C++ 4、Python 6（M1 就是旧口径本身）、端到端 1。
  其中 C++ 那处"关段用观察到的末帧"**第一次没红** —— 补了显式用例才红（见 §六.1）。
- 验收：`70-p13h-design.md`、`71-p13h-status.md`（§六 八条诚实清单）

### P13-G · 抽稀的最小可用门槛（**DONE 2026-10-30**）

- **继承的欠账**：「`per_frame` 降级分支缺真机证据，要造它得让呈现路径不传 pts」。
  去看代码，这个欠账的**前提是错的**——那条路径**不可达**：
  `drift_measurable ⇒ lateness.count() > 0 ⇒ note_presented 至少调过一次
  ⇒ drift_.note 首帧无条件接受 ⇒ sampled_samples >= 1 ⇒ decimated`。
  P13-E 为它写的 reason（`"no media pts was supplied to note_presented()"`）
  描述了一件不可能发生的事。
- **真缺陷**：`DecodedFrame::presentation_time_us` 默认 `0`，缺 pts 与"首帧 pts 真是 0"
  无法区分。整条流缺 pts ⇒ 抽稀只有 **1 个样本**、`span = 0`，
  而它的 `p50/p95/p99/max` **四个数完全相同** —— 长得像正常数据。
  E1/E2/E3/F1/F2/F2′ 会**全部通过**。这是"局部合法、整体无意义"那一族。
- **做法**：`sampling_mode` 加 `kMinDecimatedSamples = 2`、`decimated_block_is_usable()`、
  `decimated_unusable_reason()`（**"为什么"只有一个出处**，可用时返回空串）。
  `schema` 升 `sync/5`。`sampling.accepted` 仍写真实值——"采到几个"和"能不能用"是两件事。

### P13-F · `worst` 点（**DONE 2026-10-30**）

- **问题**：`max` 只说最差**多大**，说不出**在哪儿**。P13-E 遗留的 4K60 r1

### P13-D · `av_drift` 采样归一化（**DONE 2026-10-30**）

- **抽稀成立**：8 s → 160 点、35 s → 700 点，30/60/4K 三档在 8 s 上都是 160 点，
  采样率 20.08 vs 20.13 Hz（差 0.21%）。按媒体时间抽稀，与帧率无关。
- **结论反转**：同源同片长（60fps 素材降帧出 30fps 版）对照下，

- **漂移第一次有斜率**：35 s 长片 `trend.usable = true`，|slope| ≤ 1.2 ppm、`r2 ≤ 0.0042`。

- **新单元**：`core/pace/pace_drift_series`（抽稀门 + 定长环，2048 点零分配）、

### P13-E · 口径前缀（**DONE 2026-10-30**）

- **问题**：P13-D 把口径写进了 `sampling.mode`，但 `av_drift.p99` 这个**键名**不带口径。
  复制一个数去填表格的人，永远想不起去看三行之外；而且抽稀不成立时同一个键会变成逐帧值，

- **修法不是"记得看 mode"，是让裸数取不到**：分位数一律挂 `quantiles.<口径>`，

## 二、P12-C · AAudio 音频主时钟 + 呈现节拍

### 为什么先做音频，而不是先做节拍

G7 要求 `|video_pts - audio_clock| p99 < 40ms`。**同步的分母是音频时钟。**
没有音频时钟，"按 24fps 应该什么时候显示"只能拿 `steady_clock` 硬凑，
那不是 A/V 同步，是"我猜的时间轴"，做完也无法验收。

所以顺序被锁死：**先有第二个时钟，再谈同步。** 不许跳过 C1–C3 直接写节拍器的 `due_at` 计算。

### 阶段闸门（C 组整体验收，缺一不可）

1. 有声片源连续播放 60s：`AAudioStream_getXRunCount` 增量 = 0（无 underrun）；
2. 音频时钟单调不倒退，`getTimestamp` 失败时有显式降级路径并带 reason；
3. 视频每帧 `present_at - due_at` 的 p99 < 1 帧时长（G6）；
4. `|video_pts - audio_clock|` p99 < 40ms（G7）；
5. 全流程产出 `docs/evidence/p12c/<source>.json`，含 p50/p95/p99/max 与 xrun 计数。

  ```
  decode/mediacodec_output_pcm_format.{hpp,cxx}← 输出格式 → PcmFormat（纯函数）
  decode/mediacodec_audio_decoder.{hpp,cxx}    ← 送包 / 收 PCM / EOS
  probe/audio/audio_decode_feeder.{hpp,cxx}    ← 解码线程（解封装→解码→转 float→写环）
  probe/audio/audio_file_probe_report.{hpp,cxx}← 报告 → JSON（纯函数）
  probe/audio/audio_file_probe_main.cxx        ← 入口 B：文件 → 出声 → 证据
  tests/video/audio_plane/p12c_pcm_tests/      ← P1-P9
  ```
  **原卡写的 `audio_pcm_format.hpp`（放在 decode/ 下）已作废**：
  PCM 描述与转换零平台依赖，放 `core/audio/` 才能被 iOS 的 AudioUnit 复用。
- **关键判断（写死，别重新发明）**：
  - **音频路径允许 CPU 拷贝**。G5"零拷贝"只约束**视频呈现路径**。音频 PCM 必须进 AAudio 缓冲，拷贝是物理必需。
  - **转换格式只能取 `decoder.output_format()`**，不许用容器声明的格式。
    容器给的是"期望值"，用它算转换等于把平台偷改格式这件事盖掉：声道数一旦不符，
    交错步长就错，听感是噪声而不是"格式不对"。
  - **不做重采样**。AAudio 协商出的采样率/声道与片源不一致就显式失败（退出码 7）。
- **留给 C4 的硬约束**：
  1. 解码线程**不需要** `sleep_until` 绝对时间轴——环本身就是节拍（环满即停、环空即续）。
     C2 那条约束针对的是无缓冲直连，别照搬；
  2. 起流前必须预灌（本卡用 3 个 burst），否则开头几十毫秒会被如实记成欠载；
  3. 收尾顺序：**先停供给 → 等环排空 → 再停流**。反过来会把环里剩余数据记成大量欠载。
- **验收**：解码出的样本总数 = 轨道时长 × 采样率（±1 个 burst 容差）；连续播放无爆音（人耳 + xrun=0 双向确认）。
- **依赖**：C2（缓冲）、C1（输出）。

### P12-C4 · 音频主时钟

- **状态**：`DONE`（2026-10-29，七次真机 + 13 例单测）
- **证据**：`docs/evidence/p12c/p12c4-clock-{48k-stereo,44k1-mono}-run*.json`（7 份）
- **分析**：`docs/design/backend-core/16-p12c4-status.md`（设计见 `15-p12c4-design.md`）
- **落位**：`core/audio/clock/`（守卫/外推/系统时钟/类型，纯逻辑）+
  `backends/aaudio/clock/`（读时间戳、编排、计数）。
  `clock_monotonicity_guard` 从卡片写的 `backends/aaudio/clock/` 移到 `core/audio/clock/`，
  理由同 C2 把环形缓冲移到 core：iOS 也要外推+守卫，放后端等于宣布只属 Android。
- **结论**：
  - **零点问题不存在**：位置由"已呈现帧位置"驱动，`framePosition` 在首帧出声前恒为 0，
    启动开销自动被排除，无需任何常数补偿；
  - 七次运行 `timestamp_fail=0`、`fallback=0`、`stale=0`、`xrun=0`、`clamped=0`；
  - 启动开销实测**双峰**：25 ms（4 次）与 127–147 ms（3 次），不是连续抖动 ——
    这比"平均多少毫秒"更有意义，它证明任何固定补偿都会在一半的启动里错 100 ms+；
  - **官方"单调递增"承诺实测不成立**：48k 每次 2–3 次回退，44.1k 每次 8 次。
    守卫是必需品，不是防御性代码；
  - 管线延迟**按采样率分档且完全恒定**：48k = 2736 帧（57 ms）、44.1k = 6747 帧（153 ms）。
    57 ms 已超 G7 的 40 ms 阈值，C5 算 `due_at` 必须扣掉它。
- **C3 遗留静音归因（已结案）**：七次全部 `silence_head_frames=0`，
  静音全在尾部（128/198/320 帧，2.7–6.7 ms）。即**预灌足够、尾部是正常排空**，
  稳态播放期间零静音。
- **给 C5 的硬约束**：
  1. 用 `AudioClockSource::now()`，不要另造时间源；`stale=true` 时不许当作"时钟停了"；
  2. `due_at` 必须扣掉设备管线延迟（57/153 ms），否则会系统性提前排帧；
  3. 时钟查询不许加锁（视频线程每帧都要问）。

### P12-C6B · 呈现回压的边界（C7 前置调查）

- **状态**：`DONE`（2026-10-29 结题，**结论是不做优化**）
- **为什么加这张卡**：C6 §六 建议在 C7 开工前先回答「1080p 的呈现回压是否可解」。不做这张，
  C7 很可能又是一次"改完没数字"。
- **结论一（落点修正）**：那 2.01 ms **不在 `releaseOutputBuffer` 上**。1080p8 present vs norender：
  `release` 差 **−0.01 ms**（反而更快），`submit` 差 +0.03 ms，**`receive` 差 +1.99 ms（占 99%）**。
  回压表现为 `dequeueOutputBuffer` 空等满 2000 µs 后返回 `TRY_AGAIN`。
- **结论二（触发条件）**：只在「解码速率 > 显示消费速率」时出现。真实节拍下
  `TRY_AGAIN` 从 2.03 次/帧降到 **0.02–0.31 次/帧**，`receive` 占 wall 从 85.5% 降到 **0.5–3%**。
  24/30/60 fps（1080p）与 30 fps（4K）**全部 0 丢帧**。
- **结论三（不该解）**：30 fps 播放预算是 33 ms/帧，1080p 带呈现只要 5.54 ms，余量 6 倍。
  `present=false` 的 283 fps 是标尺不是目标 —— 拿它当验收等于要求解码器比显示器快 4.7 倍。
- **给 C7 的三条修正**：① 验收不能写 fps；② **C5 的 `p99=0.125ms` 测的是"交出时刻"不是"上屏时刻"**
  （采样点在 `releaseOutputBuffer` 之前，中间隔 1–3 个 vsync），C7 必须先建立上屏时刻测量；
  ③ C7 的价值在高负载下的调度免疫，取证必须构造负载，空载测不出差异。
- **分析**：`21-p12c6b-present-backpressure.md`
- **证据**：`p12c6b-pace-4k30-{merged,split}.json`（新增 2 份）+ 复用 C6 的 30 份
- **欠账**：没真去试加 buffer 数量（结论是"不该解"不是"解不了"）；无 4K60 片源；
  "上屏时刻"目前测不到（这是 C7 的第一个任务）。
- **依赖**：C6。

### P12-C7 · 精确呈现时刻

- **状态**：`DONE`（2026-10-29 结题，**有效，已设为默认**）
- **目标**：用 `AMediaCodec_releaseOutputBufferAtTime(codec, idx, ptsNanos)` 把排程交给 SurfaceFlinger。
- **做了什么**：`FramePacer` 加"只判定不睡"开关；解码器加 `release_frame_at`；

- **诚实边界**：这是"提交时刻不受调度摆布"，**不是"画面更流畅"** —— 两种结构都没丢帧。
  `schedule_lead` 是代理指标，上屏时刻仍测不到（C6B §二 已试过两条路，都堵）。
- **默认值**：已改为 `kSurfaceAtTime`，四处同步（`present_schedule.hpp`、`decode_session.hpp`、

- **验收**：`23-p12c7-status.md`（含空载/负载两张对照表与 §六 诚实清单）

- **唯一在涨的分项**：Native Heap +2.19 MB，头 10 分钟涨完就平（分配器 arena 扩张），
  PSS 总量被页回收抵平。只报总数像"什么都没发生"，只报 native 像"有泄漏"，合起来才是事实。
- **口径**：判据是 5 MB **绝对值**不是比例（比例会让"进程越大允许漏越多"）；
  它只能挡住每分钟 >0.17 MB 的持续增长，更慢的挡不住 —— 写进诚实清单。
- **两个测量坑（都不是代码 bug，是窗口 bug）**：
  ① 停机瞬间 PSS 从 105 掉到 60 MB，不裁窗口会算出"内存下降 43MB"；
  ② **这台 K40 的时钟比真实 UTC 快 8 小时**，设备证据时间戳不能与主机时间直接相减。
  两个坑都改成"从数据里识别"而不是写死秒数，且把偏移量打出来。
- **中途快照不是静止态**：`released == received` 只在会话停下后成立；
  中途只要求 `0 ≤ 在途 ≤ 16`，结束证据才要严格闭合。
- **新增**：播放器 `kivo.soak` / `kivo.soak.ms` extra（每 N 秒写一份完整 `decode/6`）；
  `tools/sample_p12d3_mem.py`（主机侧 PSS 采样）、`tools/verify_p12d3_soak.py`（分析）。
- **验收**：`29-p12d3-design.md`、`30-p12d3-status.md`（§三 三个坑、§五 七条诚实清单）
- **证据**：`p12d3-soak-r1-mem.csv` + 30 份 `-t####.json` + 结束证据 + sync
- **未做**：高码率片源；3 路并发长稳；带音轨长稳；几小时级；内存归因到分配点；温控/功耗

### P12-D5 · 上屏时刻（**DONE 2026-10-29**）

- **最重要的产出是推翻一条旧结论**：C7 说"上屏时刻拿不到"，实际是
  `dumpsys SurfaceFlinger --latency` 的**层名少了 `#id`** —— 匹配不到不报错，
  只返回刷新率一行，和"这层没有帧统计"长得一样。
- **三列语义**（两个实验验的，不是猜）：`desired`=缓冲时间戳（`surface_at_time` 下就是我们传的
  `due_at`）、`actual`=合成器锁存时刻（`CLOCK_MONOTONIC`）、`ready` 厂商相关不作判据。
- **结果**：稳态（去掉起播 0.5 s）7 轮 `surface_at_time`，Δ p99 ≤ 16.45 ms、
  max ≤ 16.47 ms（上界 = 刷新周期 16.67 ms）、**0 次错过 vsync**；
  16 忙循环把整机空闲压到 **1.1%** 仍不变，应用侧 720/720 帧、0 丢帧。
- **正向对照**：`SIGSTOP` 应用 150 ms ×3 → max 54.47 / 92.62 / 82.14 ms、1–2 次 miss。
  两组不重叠 ⇒ **量灵敏**，否则"负载下不变"只是"探针没反应"。
- **`cpu_paced` 算不了 Δ**：不带时间戳提交，第一列是媒体 pts，与单调时钟不同源。
  工具显式拒绝并写理由 —— 这不是缺陷，那个模式本来就没有"请求上屏时刻"。
- **口径**：窗口只有 128 行 ≈ 4.3 s@30fps；Δ 是"锁存"不是"液晶翻转"，差一个扫描周期；
  负载是纯 CPU 饥饿，无 GPU/IO/温控；每轮**实测空闲率**写进证据（标签不等于事实）。
- **最贵的坑**：以为停掉的后台任务其实还在跑（`TaskStop` 只杀本地 adb 客户端，
  远端 44 个忙循环还在），导致"空载"轮其实是满载 —— 全部证据推倒重测，
  之后每轮记录实测空闲率并在标签不符时告警。见 `34-p12d5-status.md` §六。
- **工具**：`tools/probe_present_timing.py`（探针，含 `--stall-ms` 正向对照）、
  `tools/verify_p12d5_present.py`（独立复算，秩索引分位数，不共享代码）
- **验收**：`33-p12d5-design.md`、`34-p12d5-status.md`（§七 九条诚实清单）
- **证据**：`docs/evidence/p12d5/p12d5-{idle-r1..r3,load5-r1..r2,load16-r1..r2,stall150-r1..r3,cpupaced-r1}.json`（11 份，全部通过复算）
- **未做**：GL 路径（`EGL_TIMESTAMP_*` 分项）、多幅度停顿曲线、4K/HEVC、多设备

### P12-E1 · `COLOR_FormatYUVP010` 协商结果（**DONE 2026-10-29**）

- **结论是否定的，且两个方向都查了**：

### P12-E4 · tone mapping（**DONE 2026-10-30，按字面达成、映射本体未实现**）

- **三条路径全部实测**（不是"想想觉得不行"）：
  1. **让屏幕变 SDR**：`cmd display set-user-disabled-hdr-types 1 2 3 4` 在 K40/MIUI 上
     设完立刻被清回 `[]`，播放 HDR 时 `dynamic_range` 仍是 HDR ⇒ **本机造不出 SDR 场景**；
  2. **让解码器转 SDR**：`color-transfer-request = 3` ⇒ `start()` 后 `output_transfer` 仍是 6、
     `honoured=false` ⇒ 组件忽略这条请求（与 E1 的 `color-format` 是两回事，单独问过）；
  3. **自研 GL shader**：不做 —— 换架构，P12-B/C/D 的 fps/丢帧/上屏时刻全部要重取证。
- **对比截图**：同一份 PQ 像素，只改 VUI 标记（`-c copy -bsf:v hevc_metadata=...`），
  A `BT2020_ITU_PQ`/HDR 与 B `V0_BT709`/SDR；中位亮度 **71 → 61（−14%）**、mean 105.99 → 91.15。
  证明"标记错了不会花屏，只会整幅发闷"。
- **算法规格（给全，但不在本架构实现）**：线性域 + BT.2390 EETF + BT2020→BT709 + BT1886 输出，
  落点在 GPU 片元着色器，代价是零拷贝直出失效。
- **不假装支持**：证据 `color.hdr.tonemap.implemented=false` + 非空 reason（HDR 源写两条理由，
  SDR 源写"无需映射"），schema 升 **`decode/10`**。
- **新增**：`probe` 第三用例（`hdr-probe/2`）、`make_configure_format_with_transfer_request()`、

### P12-F3B · 加密轨识别（**DONE 2026-10-30，F3 由 3/4 → 4/4**）

- **根因**：不是"平台不报"，是我们读错位置。平台把加密信息放在**轨道格式**的
  `crypto-mode` / `crypto-key` 上，而 `AMEDIAEXTRACTOR_SAMPLE_FLAG_ENCRYPTED` 在 K40 上恒不设。
- **三步实测**：注 `pssh` 无效 → fMP4 无效 → `track_format_dump` 看到 `crypto-mode:1`。
- **改判**：`crypto-mode`（int32，API 21）作主判据；`crypto-key` 只作旁证（读它要 API 28）。
- **拒绝点在 `open()`、`configure()` 之前**：原来配好解码器解出 25/90 帧垃圾像素还
  `completed=true` —— 比拒绝更糟。
- **三态**：`encrypted` 拒 / `clear` 放行 / **`unknown` 放行但留 reason**（明文片源同样缺这个键）。
- **实测**：加密 → `stage=open`、`return_code=12`、reason 点名 `crypto-mode=1 (aes-ctr)`；
  明文对照 → `verdict=unknown`、300/301/300 帧、0 丢帧、`completed=true`。
- **落位**：`source/encryption_key_names.hpp`、`source/encryption_facts.{hpp,cxx}`、
  `source/mediaformat_encryption.{hpp,cxx}`、`MediaExtractorSource`（open 时抄一次）、
  `DecodeSession::open()`（新错误码 `kEncryptedUnsupported=11`）、renderer `source.encryption`
  （schema `decode/12`）、JNI 返回码 12
- **工具**：`tools/inject_pssh.py`（造带 `pssh` 的样本）、探针 `hdr-probe/3`（`track_format_dump`）
- **单测**：`kivo_p12f3b_encryption_tests` 8 例 / 33 断言；`ctest -R kivo_p12` **10/10**
- **校验**：`verify_p12f3_errors.py` **4 PASS / 退出码 0**；变异（rc 5）能打红

### P12-F3 · 错误路径全覆盖（**BLOCKED 2026-10-30，3/4**）

- **三条达成**：`bad-file`（截断容器）、`no-video-track`、`no-audio-track`（降级路径）。
  三者都有非空 reason，且 reason 指向**正确的故障类型**。
- **改了一处代码**：`0 tracks` 与"有轨但没有视频轨"原本用同一句话（`no video track among 0 tracks`），

- **加密一条不可验证**：CENC 片源（`encv/sinf/senc/tenc` 齐全，`pssh=0`）在 K40 上

## 六、明确不做（防止下个助手跑偏）

| 不做的事 | 原因 |
| --- | --- |
| 软解回退（尤其 10bit） | 软解 HEVC 只声明 8bit，回退等于偷偷降质，违反 G9 |
| 用模拟器代替真机取证 | 模拟器无硬件 MediaCodec，产生的数字无意义 |
| 在 `core/` 引入 Android/AAudio 头 | 破坏"核心一行不重写"的架构前提 |
| 为兼容 API 26 而抬高 minSdk | 现有 4 处 API 28/29 符号已用 dlsym / 字面量 / 不使用 解决 |
| 按 codec 名字选解码器 | `c2.qti.hevc.decoder` 只在 XML 声明、运行时不存在 |
| 用 `getOutputImage()` / ByteBuffer 出帧 | 一旦走 CPU 读回，性能立刻塌到软解水平 |
| Vulkan 上屏 | P12 阶段不引入，先把 GLES/直出路径的数字化做完 |
