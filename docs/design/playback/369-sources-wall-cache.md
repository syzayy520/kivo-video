# 369 · 资源库封面墙：去掉重复图片缓存 + 计数缓存（承接 D367/D368）

> 前两轮把 Emby 详情页、列表、登录修完后，这一轮扫**用户第一眼看到的页面**：资源库。
> 做法照旧：先分段计时，再改，再量。

## 一、实测（真机 K40 `b6e950ee`，3 个 Emby 源）

### 1.1 数据层分段（`[src-sum]` 埋点）

| 阶段 | 冷（缓存清空） | 热（重启后） |
|---|---|---|
| `auth`（登录） | **复用 0 ms**（D368 已生效） | 复用 0 ms |
| `counts`（电影/剧集计数） | **661 / 1565 / 1395 ms** | **1 / 1 / 3 ms** |
| `posters`（最近 6 部列表） | 527 / 420 / 1126 ms | 1 / 1 / 1 ms |

### 1.2 海报图片（`[img]` 埋点）

| 场景 | 网络请求数 | 磁盘命中 | 时间跨度 |
|---|---|---|---|
| 冷启动（图片盘清空） | **13 张全走网络** | 0 | 9852 ms |
| 重启后再进 | **0** | **13** | 7090 ms（受数据层支配） |

## 二、两个发现与改法

### 2.1 海报图片：三处各造一个"只有内存"的缓存

`SourcePosterStrip`（资源库）、`EmbyResumePoster`（首页继续观看）各自维护私有 `LruCache`，
**没有磁盘层** ⇒ 每次冷启动都把海报重新下一遍（实测 13 张）。

而 `TmdbImageCache` 本来就有 **内存 + 磁盘 + 传输失败重试**，并且支持 `X-Emby-Token`
（317 起就为 Emby 缩略图加了可选 header）。改法：

| 原实现 | 现在 |
|---|---|
| `sourcePosterCache`（私有 LruCache，无盘） | 删除，走 `TmdbImageCache.load(url, token)` |
| `embyResumeCache`（私有 LruCache，无盘） | 删除，同上 |
| `EmbyAuthCache.fetchBytes`（只为上面那个服务） | 删除（无人调用后即为死代码） |

顺带在 `TmdbImageCache` 里加了一行**只对带 token 的图**生效的命中日志（`[img] disk-hit / net`），
用来量化冷热 —— 不淹没日志，也不会给 TMDB 图片刷行。

### 2.2 计数：把"不缓存"改判为 5 分钟缓存

D367 我写过"`Items/Counts` 不缓存，因为它兼作服务器在线判断"。这一轮量出来它是资源库首屏
**最大的一项**（661–1565 ms/源），于是重新核对语义：

> `SourceSummaries` **本来就有 300 秒内存节流** —— `if (elapsed - old.at < 300_000) return`。
> 也就是说"5 分钟内不重新探测"是既有且已被接受的行为，只是**每次重启就丢了**。

所以落盘缓存用同一 TTL（5 分钟）**不改变陈旧度语义**，只补上"重启后不用重探"这一层。
这是对前一轮判断的修正，理由写在代码注释与 `EmbyResponseCache.TTL_COUNTS` 上。

## 三、结果

| 计数（热） | 661–1565 ms | **1–3 ms** |
| 计数（冷） | 661–1565 ms | 661–1565 ms（首次仍需网络） |

## 四、验证

- `ui_gate` PASS；单测 111 例 0 失败；`assembleDebug` SUCCESS。
- 真机截图：三个源卡片计数（714/1667、2482/1930）、`emby.bangumi.ca` 6 张真实海报、
  在线点、⋯ 管理入口全部正常；无空白卡、无转圈、无错误文案。
- `nl2.lovehd.de` 海报条为空：该服务器本身有故障（历史已记录），列表里没有带图条目，非本轮引入。

## 五、边界（如实）

1. 首次安装/清缓存后仍要下一次（13 张），无法避免；之后跨重启都能命中。
2. 计数最多陈旧 5 分钟（与既有内存节流同口径）。
3. 图片磁盘缓存目录 `cache/tmdb-images-v2` 由系统在低存储时回收；被回收后退化为重新下载，
   不会出错（`TmdbImageCache` 只在成功响应后落盘）。
