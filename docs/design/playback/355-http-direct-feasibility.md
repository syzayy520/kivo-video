# 355 · L2 可行性裁决：HTTP/Emby 交还 mpv 原生 —— **不做**

> 背景：354 落地"本地文件直连 mpv"后，下一个候选是 L2 —— 让 mpv 直接读
> Emby/WebDAV 的原始 URL，绕过 `HttpOriginSource → LocalRangeServer`。
> 用户要求按最强实现推进，所以这条路必须先证伪或证实，而不是默认不做。
>
> **结论：不做。理由是三条硬约束，其中第一条是致命的。**

---

## 一、致命约束：mpv 的 ffmpeg **没有 TLS 后端**

这不是推测，是已经付过代价的真机实测。`mpv/LocalRangeResponder.kt` 里留着记录：

```
透明转发：代理自己做 TLS（内核的 ffmpeg **没有 TLS 后端**，真机实测 `Protocol not found`），
把源站响应原样写给内核。

【为什么不是 302】第一版就是 302，真机立刻打脸：重定向目标是 https，
而内核从没见过非回环地址 —— 我们的架构里 TLS 一直由 Java 代理层负责。
```

三条独立证据：

| 证据 | 内容 |
|---|---|
| 行为 | 第一版直通用 302，真机 mpv 报 `Protocol not found`（它连不上 https） |
| 二进制 | `libmpv.so` 里 `openssl` / `gnutls` / `libssl` 出现次数 **均为 0** |
| 运行时 | 内核日志 `Could not set AVOption tls_verify='0'` —— 没有 TLS 就不认识这个选项 |

⇒ **这句注释是整个代理层存在的第一因**：代理不是"为了统一抽象"才有的，
它是**TLS 的归属位置**。去掉代理就等于要求 ffmpeg 自己握手。

⇒ 要让 mpv 直连 https，必须**重编 ffmpeg 并启用 TLS 后端**（openssl 或 gnutls），
连带 NDK 工具链、`libmpv.so`、两处产物拷贝全部重做。而这换来的只是"少一层"，
收益见 §三。

## 二、第二约束：代理承担了 mpv **没有能力**做的事

即使解决了 TLS，直接交还 URL 仍会丢掉四项能力，其中两项是硬缺陷：

| 能力 | 在哪实现 | 丢掉会怎样 |
|---|---|---|
| **HLS master 裁单档** | `hls/HlsMaster` + 代理转发 | 真实 HLS 每个码率档是独立 `program`，**mpv 没有 `--program`** ⇒ 只能播第一个（Apple 流实测 960×540，不是最高档） |
| **token 不进 URL** | `HttpOriginClient` 只放 `X-Emby-Token` 头 | 要么 token 进 URL（泄漏到日志/历史），要么依赖 mpv 的 `--http-header-fields`（可设，但每个请求都要带，且 HLS 分片由 mpv 自己发） |
| **片尾 cues 预取** | `OriginWindowCache` 片尾窗口 | MKV 的 cues 在片尾，起播必跳一次，真机 **950 ms** 关键路径；直连后这一跳要现付 |
| **环形预读** | `HttpOriginReader` | 273 历史实测：按需取数 ⇒ 缓存被抽干 ⇒ 卡顿 11 次 → 加预读后降到 5 次 |

前两项是**功能缺失**，不是性能差异。"能播但只有 960×540"不是可以接受的退化。

## 三、第三约束：收益上限极小（已有实测数据）

354 已经把"少一层"的收益量出来了 —— 同一份代码、同一个文件、交替 13 次：

| 分段 | 直连 | 走代理 | 差 |
|---|---:|---:|---|
| `kernel_created` | 41 ms | 38 ms | +3 |
| `loadfile→首帧` | 378–414 ms | 416–423 ms | **−20~43 ms** |
| `startup_total` 中位 | 453–471 ms | 461–464 ms | **噪声内** |

而网络源的现实延迟量级：源站新建连接握手 **800–1600 ms**（273 实测），
复用 **≈300 ms**。**把 20–43 ms 丢进这个池子里，连噪声都算不上。**

⇒ L2 的性能收益预期 **< 5%**，而代价是重编工具链 + 丢掉四项能力。

## 四、结论与边界

**不做 L2。** 代理层保留，且它的定位要写清：

> **代理不是"统一抽象"的产物，是 TLS 的归属位置 + mpv 能力缺口的补齐层。**
> 它的存在理由随 mpv 的能力变化，不随审美变化。

### 什么条件下应该重新评估

| 条件 | 说明 |
|---|---|
| ffmpeg 编入 TLS 后端 | 且实测 `https` 直连可用（这是前提，不是充分条件） |
| 出现"纯明文 http + 无鉴权 + 非 HLS"的主力源 | 这时 §二 的四项能力都不需要，直连才是纯收益 |
| 实测证明代理引入 >100 ms 的稳定开销 | 目前测得 20–43 ms，远未达到 |

### 本批没有做的事（如实标注）

- **没有做 A/B 实测**（mpv 直连明文 http vs 代理）。理由：即使测出直连快 30 ms，
  在 §一/§二 的约束下结论也不会改变；而改代码加实验开关本身要动
  `PlayerUrlStart` 与 `PassthroughSource`，风险大于信息价值。
- 没有验证"给 ffmpeg 加 TLS 后 mpv 直连 https"的实际表现（需要重编，属另一个工程量级）。
