## 一、先把账算清：这 12 秒在等谁

三轮真机（K40 `b6e950ee`，485 的 1080p 版本，4.1 Mbps）合并时间线：

| 段 | s1 | base1080 | soak1080 | 在等什么 |
| --- | --- | --- | --- | --- |
| am start → mpv 内核创建 | 0.63 s | 0.50 s | 0.44 s | Activity + Compose + mpv_initialize |
| 源站 probe 表头（TLS 冷启动） | **1.83 s** | **2.06 s** | **1.62 s** | 首条 TLS 握手 + 响应头 |
| 内核 `Opening done` | 7.06 s | 4.90 s | 5.85 s | 见 §1.1 |
| `Opening done` → 首帧 | **5.43 s** | 3.6 s | 4.1 s | 见 §1.2 |
| **合计首帧** | **12.49 s** | **8.5 s** | **9.97 s** | |

### 1.1 `Opening done` 之前：内核要跳三次，每次一跳都要一条新连接

```
2.10s  tcp 连接#1  ── 读片头（Range: bytes=0-）
3.04s  stream level seek 43741 → 4315898815   ← 去片尾读 cues
3.04s  tcp 连接#2
5.71s  stream level seek → 39237              ← 回到第一个簇
5.71s  tcp 连接#3
6.39s  All headers are parsed
```

- 连接#1 由主预读泵供给（片头 4 MiB，表头 313–388 ms，**这段是好的**）。
- **连接#2（片尾 cues）是最大的一块**：表头 1.08 s（s1）/ 2.9 s（soak1080），
  正文 286 KB。同一时刻 `[play-tail]` 预取正在下**同一段字节**
  （`hdrMs=4831`，`[tail] prefetch ... ms=6493`）。
- ⇒ **同一段 286 KB 被下了两遍，分在两条连接上，而且都在起播关键路径上。**

### 1.2 `Opening done` 之后：续播 seek 要"向前读"

`queuing seek to 133.924000` → `stream level seek to 63303505` → 首帧。
内核落到**目标时刻之前的一个簇**，然后必须顺序读到 133.924 s 才出画面。
真机实测要读 ≈5 MB，在 0.5–1 MB/s 下就是 **3.6–5.4 秒**。

⇒ 这一段是**续播位的固有成本**，唯一能消掉它的办法是
**在用户点播放之前就把那段下好**（`prefetchResume` 已经存在）。

## 二、先决问题：我量的不是用户走的那条路 —— **已量，结论：探针路径不代表用户**

本轮三次采集都用 `am start --es kivo.playurl` 直接进播放页，
**跳过了详情页的 `OriginPrewarm`**（片头 4 MiB + 片尾 + 恢复点 4 MiB 全都没有）。
而用户是从详情页点的播放 —— 那条路上这些窗口已经落地。

### 2.1 G0 实测（真机 K40，2026-11-15 03:53，证据 `docs/evidence/p274-startup/realpath-old/`）

从详情页点「播放」到首帧：**2.17 s**（tap 1794686055955 → `MPV 首帧就绪` 1794686058130）。

```
1.56s  [prep] 接管详情页预热的源（连接与片尾窗口已就绪）
1.71s  [prep] 内核创建完成 ms=43 / 闸门放行 ms=43
1.73s  [tail] cache hit offset=854195684 bytes=64368     ← 片尾本地命中，零源站往返
1.83s  mkv: All headers are parsed! / Opening done
1.93s  MediaCodec started successfully
2.17s  MPV 首帧就绪
```

⇒ **真实路径 2.17 s，已达标（≤ 3 s）**；探针路径的 8.5–12.5 s 是"没有预热"的自找麻烦。
⇒ 按本文 §七的规矩：**S1（读者查窗口缓存）、S2（片尾预取优先级）、S3（闸门不等 probe）一律不做** ——
   它们优化的是探针路径，用户根本不走那条。
⇒ 只剩 **S4**（落点保温池 5 秒定时器抢连接）值得做，且它属于"长稳/拖动"卡，不是起播卡。

### 2.2 附带查清：返回详情页时的"白屏/横屏条"（2026-11-15 03:58 录屏 + 连拍取证）

| 时刻 | 截图尺寸 | 现象 |
| --- | --- | --- |
| 按返回后 ≈1 s | **2400x1080（横屏）** | 详情页**整体旋转 90°**，右侧还挂着播放器的最后一帧 |
| 按返回后 ≈2 s | 1080x2400（竖屏） | 正常 |

⇒ 根因：播放器 Activity 是 `screenOrientation="landscape"`，退出时显示还没转回竖屏，
   而详情页 Activity **没声明 `configChanges`**、窗口仍是竖屏尺寸 ⇒ 被系统 letterbox 成一条窄带。
⇒ **用户 04:02 反馈"现在没白屏了"**（期间设备被临时锁定为竖屏：`accelerometer_rotation=0`，
   测完已恢复为 `1`）⇒ 该现象**当前未复现**，暂按"待复现"记账，不在本卡动清单里。


## 三、候选修复（按 收益/风险 排序，每条都可单独开关）

| # | 做法 | 消掉哪一段 | 预期收益 | 风险 |
| --- | --- | --- | --- | --- |
| **S1** | **让读者先查窗口缓存**：`HttpOriginReader` 读到命中区间的段时，从 `windowCache` 取而不是自己再开连接 | §1.1 的连接#2（片尾）与连接#3（首簇） | 1.1–3.4 s | 中：动读路径，必须保持"读不到就回源"的语义 |
| **S2** | **片尾预取不挡关键路径**：`[play-tail]` 与主泵共用连接池，且**优先**发；或把片尾窗口从 286 KB 提到 1 MiB | §1.1 的连接#2 | 0.5–2 s | 低 |
| **S3** | **探针别挡闸门**：`[prep] 闸门放行 ms=1081–1381` —— 闸门在等 probe 的 TLS 握手，而 probe 只用于 401/403 判决 | 起播首 1.0–1.4 s | 1.0–1.4 s | 低（判决失败仍要能中止） |
| **S4** | **保温池定时器**：`OriginPrefetchKit` 用 5 s 定时器启动落点保温池（4 条连接），与"首帧之后才起保温池"的 v15 设计意图冲突 | 首帧前抢连接 | 0.2–1 s | 低（改成首帧回调触发即可） |

> S3 与 S4 是"少抢"，S1 与 S2 是"少下一遍"。**先做 S3/S4（改动小、可回退），
> 再评估 S1（收益最大但要动读路径）。**

## 七、诚实边界

- 本卡**不碰**解码、渲染、UI 布局；只改起播期的"连接与数据来源"。
- 若 G0 显示真实路径本来就 ≤ 3 s，则本卡只做 S4（消除抢连接），其余**不做** ——
  不许为了改而改。
- `Opening done` 之后那 3.6–5.4 s 的"向前读"在**没有续播位**时不存在
  （从 0 起播无 seek）；若 G0 显示主要成本在这里，优先做恢复点预取而不是读路径改造。

## 八、记账：冷启动 / 首屏慢（**本轮不处理**，用户 2026-11-15 04:03 指示"先记账，晚点来弄"）

### 8.1 用户原话

> "现在没白屏了，刚打开软件那会儿会，加载慢，你换个没打开过的就很慢。"

⇒ 两个现象：**① App 刚打开时首屏加载慢**；**② 打开一个**从没打开过**的片源时很慢**。

### 8.2 已测到的事实（真机 K40）

| 指标 | 数值 | 口径 |
| --- | --- | --- |
| `am start -W` 冷启动 TotalTime | **772 / 665 / 685 ms**（3 次，COLD） | Activity 进程起来到首帧 ⇒ **这一步不慢** |
| 首次打开某片源的详情 | **未测** | 详情页要现拉 TMDB + Emby 两跳 |
| App 有无自定义 `Application` | **无**（清单里 `<application>` 没有 `android:name`） | ⇒ 不存在 `Application.onCreate` 里的重活 |

⇒ 慢**不在进程启动**，在**首屏/详情的数据取得**（首页 feed 三路：TMDB / Emby / 本地媒体；
详情页两跳：TMDB + Emby，且详情要现拉海报与季集表）。

### 8.3 下次开卡要回答的问题（先量，不先改）

1. 首页首屏的**三路数据是串行还是并行**？第一帧前有几次网络往返？
2. 「没打开过的片源」比打开过的慢，差在哪一跳？（缓存未命中 ⇒ TMDB 详情 + Emby 详情 + 海报 + 季集表）
3. 有没有**占位/骨架**？还是白屏等到数据齐？
4. 冷启动后是否已经建立了源站连接（`OriginPrewarm`）？没有的话第一批请求全部要付 TLS 握手。

### 8.4 约束

- 动这一块属于 **UI 首屏与数据编排**，与播放链路正交 ⇒ 单独立卡，别混进播放的验收里。
- 本卡（274 起播）已经证伪了自己的大部分内容（见 §二 G0）⇒ **本文件按"起播已基本达标"结案**，
  只保留 S4（保温池定时器）作为待办，塞进 §二十八 的长稳卡里一起做。
