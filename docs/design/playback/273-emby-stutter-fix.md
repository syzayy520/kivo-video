# 273 · Emby 播放卡顿：根因定位与修复设计（v7 取数层收口 · v11 起播提速收口 · v13 预览浪费收口）

> 卡号：273。症状：**播放 Emby 时非常卡**，别的播放器（SenPlayer 等）同一片源流畅。
> 设备：Redmi K40 `b6e950ee` / `dd137cf7`；服务器：`emby.bangumi.ca`（Emby 4.8.0.62，Cloudflare 边缘）。
> 片源：《清潭国际高中 S01E01 贪婪》HEVC 3840×1920 @23.976 + AAC 44.1 kHz，854,260,052 B / 32:42。
> 证据：[`docs/evidence/p273-emby-stutter/`](../evidence/p273-emby-stutter/README.md)（v4 现场 + v5 收口 + v6/v7 取数层重构 + v8–v11 起播提速 + v12/v13 预览浪费）
>
> **v7 收的是"播放中卡"，v11 收的是"起播慢"，v13 收的是"预览浪费"。** 两者是同一条链上的两段：
> v7 让**持续播放**不再缓冲（0 次 `Enter buffering`）；
> v11 让**冷启动到首帧**从 5.1 s 压到 3.2 s，且**全程不新建连接**（表头 max 362 ms）。
> v1–v11 的结论被真机实测逐条推翻过五次，
> 本文保留推翻链，因为**每一条被推翻的结论都是当初做错设计的直接原因**。
>
> **v6/v7 一句话**：卡顿是**取数层**的问题（连接生命周期 + 预读节奏），
> 不是内核问题，也不是源站带宽问题。
> v6 把"一条长连接读到底"改成"**有界分块 + keep-alive 复用**"，
> v7 又补了三处真机暴露的破口（416 空跑、预览继承主内核预读、内存三份缓存叠加）。
>
> **v8–v11 一句话**：起播慢是**连接冷**（新建连接要 1.0–1.3 s 握手）
> 加**定位晚**（续播位在起播之后才 seek）两件事叠加。
> v8 让连接提前热起来（keep-alive 池 + 常驻 keeper），
> v9 把续播位塞进 `loadfile` 的 `start=` 让内核一打开就落在目标位置，
> v10 证明**串行** keeper 会偷连接（倒退），
> v11 改成**并行** keeper 才真正拿到"全程零新建连接"。
>
> **v13 一句话**：拖动进度条时浮窗里那一帧，让**预览内核**下载了 **38.1 MiB**。
> v12 用 7 组 mpv 参数证明**内核侧治不了**（最好还剩 16.1 MiB），
> v13 改成在**供给侧**截断单次响应（4 MiB 上限 + 预览不许在 EOF 重连），
> 收到 **10.1 MiB**，且播放主链路逐字节未动。详见 §十一。

## 一、结论先行

**卡顿是取数层的问题，不是内核问题，也不是源站带宽问题。**

4K 片源的持续消耗只有 **435 KB/s**（854,260,052 B / 1962.889 s），
而源站**新连接**实测能跑 **2.4–7.6 MB/s**（v5 收口后 18 个连接周期中位数 3.7 MB/s）。
带宽一直够 —— 坏的是**连接的生命周期**：

> 一条被闲置过的源站 TCP 连接会**塌陷**到 60–250 KB/s，
> 靠指数退避要 **~60 秒**才恢复；而**新建连接立刻满速**。

连接一塌陷，就低于 435 KB/s 的需求 ⇒ 缓存吃干 ⇒ `Enter buffering` ⇒ 卡死。
v4 的 `net-diag.log` 里那条"累计平均速率一路掉到 16 KB/s"的曲线，
就是**一条从未被回收的连接在老化**的现场。

**修法不是"多开连接"（实测并行对总带宽无增益），而是"让连接保持年轻"**：

| 规则 | 做法 | 为什么 |
| --- | --- | --- |
| **闲置即回收** | 连接空闲 ≥ 3 s ⇒ 直接关掉，下次要读时重开 | 老化的触发条件是"闲置"；新连接满速 |
| **慢读即换连接** | 实测速率 < 300 KB/s 且该连接**曾经**跑过 > 1 MB/s ⇒ 换新连接 | 老化的第二种表现是"读着读着变慢" |
| **重开门槛 4 MiB** | 只有环形缓冲剩 ≥ 4 MiB 才允许重开 | 新连接的表头延迟 1.26–1.79 s，空档太大会被摊成停顿 |

> **v6 推翻了上面三条的适用范围**：v5 的"长连接读到底 + 主动回收"虽然治好了老化，
> 却让**每次回收都要新建连接**（真机 754–968 ms，且只有 ≈2 MB/s）。
> v6 换成"**有界分块**"：块读完 ⇒ 响应结束 ⇒ 连接**回 keep-alive 池** ⇒
> 下一块复用同一根 TCP（真机复用 ≈300 ms / 10 MB/s）。
> 于是"连接保持年轻"不再靠回收，而是靠**不让响应有尽头**。
> 详见 §九。

### 1.1 起播慢（v8–v11 收的第二段）

v7 收完"播放中不卡"之后，用户视角还剩一件事：**点开要等 5 秒才出画面**。
这一段**不是带宽问题**，是两个延迟叠加：

| 延迟源 | 实测 | 修法 | 版本 |
| --- | --- | --- | --- |
| **连接冷**：新建连接要 TLS 握手 | 新建 **983–1301 ms** / 复用 **266–362 ms** | keep-alive 池预热 + 常驻 keeper | v8 / v11 |
| **定位晚**：续播位在起播**之后**才 seek | 多付一整轮"读 cues + 找关键帧" | `loadfile` 带 `start=`，内核一打开就落在目标位置 | v9 |

v11 实测：**起播到首帧 3.201 s，全程 35 次请求零新建连接**（表头 max 362 ms）。
详见 §十。

### 1.2 预览浪费（v13 收的第三段）

拖动进度条时，浮窗里那一帧由**独立的第二个 mpv 实例**取。
它为了取一帧下载了 **38.1 MiB** —— 因为 FFmpeg 收到的是**开口区间**
（`Range: bytes=N-`），出帧之后**内核还会继续往前读**（实测 9 s / ≈24 MiB）。

mpv 侧 7 组参数（v12）证明**内核侧治不了** ⇒ 只能在**供给侧**截断单次响应：

| 修法 | 作用 |
| --- | --- |
| 代理侧单次响应上限 4 MiB（**偏移 0 豁免**） | 截断；偏移 0 豁免是因为 FFmpeg 在那里靠 `Content-Length` 推**整个文件大小**，截了会让所有后续 seek 失效 |
| 预览 URL `reconnect_at_eof=0` | 否则 FFmpeg 到截断点会重连继续拉 ⇒ 截断白做 |
| 预览环 4→2 MiB、块 2→1 MiB | 每连接浪费 ≈ 环 + 块；3 条连接 ⇒ 18 → 9 MiB |

v13 实测：**10.1 MiB**（多点扫描 13.1 MiB / 20 点），帧照出，**播放主链路逐字节未动**。
详见 §十一。

## 二、结论推翻链（必须记住，否则会重犯）

| 版本 | 当时的结论 | 被什么推翻 |
| --- | --- | --- |
| v1 | 单连接长流速率会衰减到 16 KB/s | **半对**：那曲线是**累计均值**，不是瞬时速率；衰减是真的（老化），但幅度被误读 |
| v2 | 分片并行能把聚合带宽拉起来 | **假**：实测 4 连接并行 2.0–3.2 MB/s，与单连接 2.8 MB/s 同量级 |
| v2 | 每 1 MiB 一片、等整片到手 | **真**：每片一条新连接 = 每片付一次 0.4–2.4 s 表头延迟；读侧等整片 ⇒ 一片 1 MiB 用了 35.4 s |
| v3 | 改"一条长连接顺序读" | **半对**：顺序读方向对，但**连接一直不回收** ⇒ 撞上老化 ⇒ 仍然卡 |
| v4 | "带宽不够，需要多连接" | **假**：源站给单连接满速就有 2.4–7.6 MB/s |
| v5 | **连接老化；回收 + 慢读换连接 + 4 MiB 重开门槛** | —— 0 次缓冲，但**每次回收都要新建连接**（754–968 ms） |
| **v6** | **有界分块（4 MiB）+ keep-alive 复用；连接不回收，让响应有尽头** | —— 表头 p50 **362 ms**（复用），请求数 19 次 / 128 MiB |
| **v7** | **416 空跑就地判掉 + 预览独立预读 + 三份缓存收敛** | —— 播放中 0 缓冲，但**冷启动到首帧仍 5.1 s**（起播段未收） |
| **v8** | **起播慢是连接冷 ⇒ 预热 keep-alive 池** | —— 半对：表头 max 1076→695 ms，但起播只到 3.232 s（**预热被抢走了**，见 v10） |
| **v9** | **续播位在起播后才 seek ⇒ 改 `loadfile` 带 `start=`** | —— 成立：起播 3.127 s，起播后不再多付一轮定位 |
| **v10** | **单个 keeper 线程串行保温** | —— **假**：keeper 抢走了 `totalSize()` 刚还池的连接 ⇒ 首块 978 ms、跳读 1211 ms，**比不保温还慢** |
| **v11** | **N 个 keeper 线程并行保温** | —— 成立：起播 3.201 s，**35 次请求零新建连接**（表头 max 362 ms） |
| **v12** | **预览浪费能靠 mpv 参数治**（`cache` / `cache-secs` / `demuxer-max-bytes` / `demuxer-readahead-secs`） | —— **假**：7 组全试，最好还剩 16.1 MiB，最差涨到 42.1 MiB。内核侧控的是**缓存多大**，不是**这次读要不要停** |
| **v13** | **在供给侧截断单次响应（4 MiB 上限）+ 预览不许在 EOF 重连 + 预览环收小** | —— 成立：预览下载 **38.1 → 10.1 MiB**，帧照出，EOF 后仍能 seek；播放主链路逐字节未动 |

**教训三（v10 才有）**：**保温线程会偷连接**。
keep-alive 池是**先到先得**的：keeper 刚把自己的连接还回池，下一个取数请求就可能
**捡到那条已被 Cloudflare 判死的连接**，于是比新建还慢。
"保温"只有在**池里有富余连接**时才是纯收益 ⇒ 必须并行占住 N 条，
让取数侧永远能捡到一条**刚用过、确定还热**的。

**教训四（v8 才有）**：**"预热"不等于"保温"**。
一次性预热（打一次请求把连接塞进池）在池被取空后就失效了；
源站**不主动关空闲连接**（Node 探针：闲置 30 s 后仍可复用），
所以正确的做法是**常驻 keeper 每 8 s 续一次**，让池里永远有热连接。

**教训一**：测速率必须用**瞬时值**（窗口字节 ÷ 窗口耗时），
用累计均值当速率会直接带偏整张设计稿。

**教训二（v6 才学到的）**：**"连接老化"与"连接回收"是两件事**。
v5 把老化当成了"必须回收"，于是把连接生命周期做成了慢性病；
真根因是"**响应没有尽头**"—— 只要响应一直开着，连接就一直年轻。
把块做成有界的，连接自然回池，回收逻辑整条删掉。

## 三、根因（v5，附可复算证据）

### R1（真根因）：源站连接老化 —— 闲置后塌陷到 60–250 KB/s

- 需求侧：435 KB/s（恒定）。
- 新连接侧：v5 收口后 18 个连接周期，实测 **2459–7609 KB/s**，中位 3663 KB/s。
- 老化侧：连接闲置后速率塌陷，需要 ~60 s 指数退避恢复。

v4 的现场（`docs/evidence/p273-emby-stutter/net-diag.log`，本目录上一版）：

```
[play] net 8MiB  rate=2837 KB/s     ← 起播
[play] net 84MiB rate=16 KB/s       ← 同一根连接，115 秒后
```

⇒ 必然在 2–3 分钟内把缓存吃干。

### R2（并发放大）：预览内核重复下载同一个文件

`MpvThumbnailReader` 自起**第二个 mpv 实例**，通过自己的 `LocalRangeServer`
把同一个 815 MB 文件**从头又下载一遍**（v4 实测 `[thumb] net 32 MiB`），
而它要的只是一帧缩略图。⇒ 带宽被自己砍一半，内存也多一套 4K 解码器。

**v5 未修**（本卡不碰预览语义），但它是下一卡 273-B 的第一项。

### R3（次要）：MKV cues 在文件尾 ⇒ 起播要跳到 854 MB 再跳回 0

实测起播要开 3 条源站连接（0 / cues 尾 854,195,684 / 6072），
每条付一次表头延迟。v5 后起播 **1.605 s**（`Opening done`），
比 v4 的 13.9–14.3 s 好太多 —— 因为预读把 cues 尾部取数**并行**掉了。

## 四、v5 实现（家族树）

> ⚠️ **v6 删掉了 `OriginConnectionHealth.kt`**（速率窗口 / 空闲计时）。
> 它的存在前提是"连接会被回收"，而 v6 改成"响应有尽头 ⇒ 连接回池"之后，
> 不再需要判断"这条连接是不是老了"。留着它就是留着一段永不执行的判断。

```
net/
├── ByteSource.kt              （不变）随机读契约
├── HttpOriginClient.kt        源站 HTTP 连接的唯一出入口
│      · token 只进 X-Emby-Token 头，永不进 URL / 日志 / mpv 属性
│      · 手写重定向跟随（跨主机跳转后补回 token 头）
│      · openStream(offset) → 顺序读流（206 + Content-Range 校验）
├── HttpOriginSource.kt        ByteSource 视图：每个 mpv 连接一个独立读者
│      · openReader(offset) → HttpOriginReader（RangeReaderSource）
│      · legacy readAt 路径单独一个读者（不与 mpv 连接共享）
├── HttpOriginReader.kt        读侧：readAt → 环形缓冲 copyOut
├── OriginPrefetchBuffer.kt    环形缓冲（16 MiB）：copyIn / copyOut / resetTo / awaitRoom
├── OriginConnectionHealth.kt  连接健康度：速率窗口 + 空闲计时
│      · 速率只按**阻塞读耗时**计（环形缓冲满的等待不算慢）
│      · 窗口按**字节**触发（512 KiB），不是按时间
├── OriginConnectionLease.kt   一条连接的全生命周期：开 / 读 / 失败恢复 / 闲置回收 / 慢读换连接
└── OriginPrefetchPump.kt      生产循环：什么时候读 / 写哪 / 该不该跳读
```

**为什么拆成这五个文件**：按**变化原因**拆，不是按 widget 拆。

| 文件 | 变化原因 | 单独可测 |
| --- | --- | --- |
| `OriginConnectionHealth` | 阈值/窗口口径变了 | 纯计算，可单测 |
| `OriginConnectionLease` | 连接策略变了 | 需要 client + buffer |
| `OriginPrefetchPump` | 生产节奏变了 | 需要 buffer + lease |
| `OriginPrefetchBuffer` | 缓冲布局变了 | 纯内存 |
| `HttpOriginReader` | 读侧契约变了 | 需要 buffer |

### 关键设计点（都是踩过坑才定下来的）

1. **速率只按阻塞读耗时算**。
   若按两次读之间的墙钟时间算，**环形缓冲写满导致的等待会被误判成"连接慢"**，
   于是每一次缓冲写满都触发重连 ⇒ 重连风暴。
2. **速率窗口按字节触发（512 KiB），不按时间**。
   一次 4 MiB 补满在 11 MB/s 下只要 0.4 s，时间窗口永远等不满 ⇒ 永远测不出速率。
3. **重开门槛 4 MiB**：新连接的表头延迟 1.26–1.79 s，
   如果在"缓冲快满"时才重开，这 1.4 s 会被摊进播放 ⇒ 停顿。
   门槛 4 MiB ≈ 9 秒播放量，够覆盖握手 + 握手后的第一波数据。
4. **每个 mpv 连接一个独立读者**（`openReader`），
   不与预览/旧路径共享 —— 共享会让一个读者的跳读把另一个读者的数据流搅乱。
5. **`requestJump` 先 `closeCurrent()`** 再等 `readPosition` 追上：
   正在阻塞读的连接必须先打断，否则跳读会等它自然读完。

## 六、遗留（诚实清单，未达成项不藏）

### L1 · 内存 924 MB → 503,061 KB（**按 MiB 口径达成，按 MB 口径差 3.1 MB**）

v5 真机分解（`dumpsys meminfo`）：

| 状态 | TOTAL PSS | Native Heap | Dalvik Heap |
| --- | --- | --- | --- |
| v5 播放中 | 924,482 KB | 572,116 KB | 47,148 KB |
| v5 退出播放后 | 152,267 KB | 21,636 KB | 10,996 KB |
| **v11 播放中** | **503,061 KB** | 301,148 KB | 30,908 KB |

v11 分解（`v11/meminfo-playback.txt`）：

| 项 | KB |
| --- | --- |
| Native Heap | 301,148 |
| Graphics | 100,900 |
| EGL mtrack | 93,056 |
| Dalvik Heap | 30,908 |
| **TOTAL PSS** | **503,061**（TOTAL RSS 623,588） |

⇒ 相对 v5 降 **45.6 %**，主导项是 Native Heap（572 → 301 MB），
来源是 v6/v7 的**缓存收敛**（三份缓存叠成一份）与 v11 的**连接复用**
（不再为每次回收新建 TLS 缓冲与缓冲池）。

> **口径诚实说明**：`503,061 KB` = **491.3 MiB** = **503.1 MB**。
> 判据写的是 "< 500 MB"，按 MiB 成立、按 MB **差 0.6 %**。
> 这不是"达成"，是**逼近**。真正的余量要靠渲染侧（下面 L1 续）收。

**L1 续 · 渲染侧的回拷已经去掉，剩下的显存侧是 273-B 的活**：

> ⚠️ **本条在 v13 复核时改写过一次**：v11 稿写的是"当前 `mediacodec-copy` 走回拷路径"——
> **那是 v5 时期的事实，v13 的代码已经换成零拷贝 `mediacodec`**（`mpv_options.cpp` 的
> `hwdec_out = "mediacodec"`）。真机日志（`v13/mpv-kernel.log`）：
>
> ```
> [0.003] Set property: hwdec="mediacodec" -> 1
> [2.228] hevc_mediacodec: Using surface 0xb4000072de7cd660
> [2.278] hevc_mediacodec: MediaCodec started successfully: codec = OMX.qcom.video.decoder.hevc
> [3.332] Using hardware decoding (mediacodec).        ← 零拷贝，不是 mediacodec-copy
> ```
>
> 换零拷贝的那次实测（同片源同口径）：native 337 MB → **278 MB**，PSS 737 MB → **544 MB**。
> 也就是说"4K 帧回拷（11.06 MB/帧）"这个 273-B 的**第一项已经做完**，不是待办。

v13 剩下的内存构成（`v13/meminfo-playback.txt`）：

| 项 | KB | 说明 |
| --- | --- | --- |
| EGL mtrack | 93,056 | 我们自己的 EGL/GLES3 上下文 + libplacebo 纹理（**显存侧**） |
| Graphics | 100,900 | 图形缓冲（**显存侧**） |
| Native Heap | 305,096 | mpv demux 缓存（64 MiB 前向 + 16 MiB 回看）+ 源站缓冲 + 解码器 |
| Dalvik Heap | 31,072 | |
| **TOTAL PSS** | **507,744** | = 484.5 MiB / 507.7 MB |

⇒ 剩下的杠杆有两个方向，都归 **273-B**：
**① 显存侧**（EGL + Graphics ≈ 194 MB）：限帧队列 / 纹理池上限 / 帧缓冲复用；
**② native 侧**：mpv 的 demux 缓存前向 64 MiB 是不是给大了（本片源需求只有 435 KB/s，
64 MiB ≈ **154 秒**的片源），以及**预览内核作为第二个 4K mpv 实例**的生命周期。

### L2 · 预览内核仍在重复下载整片（**v13 已收口，见 §十一**）

v11 实测：`[thumb]` **20 次请求 / 38.1 MiB**，只为取一帧。
（v7 是 36.1 MiB，v5 是 64 MiB —— v7 的"预览独立预读"让它降了，
但**它仍在从头下载**，没有只读目标区间。）

带宽上是 38.1 MiB 的浪费，内存上是**第二个 mpv 实例**（4K 解码器 + 纹理）。
v13 收掉了**带宽**这一半（38.1 → 10.1 MiB，机制见 §十一）；
**内存**那一半（第二个 4K mpv 实例的生命周期）仍是 273-B 的活。

### L3 · 起播仍要读 cues（在文件尾）

起播现在只开 1 条源站连接、1.605 s（v5）→ **1.401 s**（v11）拿到 `Opening done`，
但"跳到文件尾读 MKV cues"这件事本身还在
（`net-diag` 里仍有 `from=854195684` 的请求）。
v11 靠 keep-alive 复用把它的代价压到 **334 ms**（一次复用连接），
**没有消除**。真消除要预取 cues 尾部并缓存 —— 单独卡（273-F）。

### L4 · 单连接带宽仍是上限

本片源 435 KB/s 需求下没问题；v11 实测 35 次请求全部复用同源满速。
若源站给单个连接的上限更低，仍需要多连接分片。**当前源站给满速，所以不做。**

### L5 · Android 上 TLS 会话复用无效（**放弃项，已验证**）

PC 端 JDK 实测 TLS session resumption 有效（1182 ms → ≈700 ms）。
**Android 端实测无效**（新建连接恒为 1000–1200 ms）。
于是"缩短握手"这条路在 Android 上走不通 ⇒ v11 只能靠**复用连接**，
不能靠**让握手更快**。**明确放弃，不再追。**

## 七、边界与不做的事

- **不改 SMB 路径的读层**：SMB 走自己的块窗口/预读/断网恢复，老化机制不成立。
- **不做多连接并行取数**：实测并行对总带宽无增益，只放大连接数与握手成本。
- **不动 `PlaybackPrefs` 的设置项语义**：缓冲上限仍由用户设置（64–256 MiB）。
- **不追 MKV cues 预取**：单独卡（273-F）。
- **不在本卡改渲染侧**：零拷贝（`mediacodec`）在 v13 之前就换好了（见 L1 续）；
  剩下的**显存侧**（EGL 93 MB + Graphics 101 MB）与**预览内核生命周期**归 273-B。
- **不追 TLS 会话复用**：PC 有效、Android 无效（L5），放弃。
- **不改 `start=` 的语义边界**：`start=` 只用于**冷启动落在续播位**，
  不用于"起播后再 seek"——后者走 mpv 的 `seek` 命令，路径不同，不要混。
- **keeper 不做自适应降级**：keeper 每 8 s 一次 1 字节请求，成本恒定且极小
  （8 s × 2 线程 ≈ 0.3 KB/s），不值得为"省电"引入状态机。

## 九、v6 · 取数层重构（有界分块 + keep-alive 复用）

### 9.1 v5 留下的病

v5 治好了"连接老化"，但引入了另一条慢性病：**回收即新建**。

v5 的连接是 `Range: bytes=OFF-`（无上界）—— 响应**永远不会结束**，
于是这条连接永远回不了 keep-alive 池；v5 一到"空闲 3 s"就把它关掉，
下一次要读时**重新握手**：真机 754–968 ms，且只有 ≈2 MB/s。
207 秒的会话里有 166 秒 mpv 在缓冲 —— 全花在"等新连接"上。

### 9.2 v6 的三条规则

| 规则 | 做法 | 真机收益 |
| --- | --- | --- |
| **有界分块** | 每次请求 `Range: bytes=OFF-END`（默认 4 MiB），块读完**响应自然结束** | 连接回池 ⇒ 下一块复用同一根 TCP |
| **环满不掐连接** | 环满时把块的尾巴读进 `carry`，让这一块**读完** | 半途掐断的响应会把连接晾在池外，下次续读它可能已退化成 60–250 KB/s |
| **跳读作废 carry** | 换位置时 carry 清零 | 旧位置的尾巴绝不写进新位置的环 |

**复用的实测对比**（同一源站、同一片源）：

| 场景 | 表头延迟 | 速率 |
| --- | --- | --- |
| 新建连接（v5 回收后） | 754–968 ms | ≈2 MB/s |
| **keep-alive 复用（v6）** | **317–1219 ms，中位 362** | **10 MB/s** |

### 9.3 v6 家族树（`net/`）

```
net/
├── ByteSource.kt              随机读契约（不变）
├── HttpOriginClient.kt        源站 HTTP 的唯一出入口（有界分块 + keep-alive 池）
│      · token 只进 X-Emby-Token 头，永不进 URL / 日志
│      · openChunk(start) → 一次有界范围请求，解析 Content-Range 的 /total
├── HttpOriginSource.kt        ByteSource 视图：**每个 mpv 连接一个独立读者**
├── HttpOriginReader.kt        读侧：readAt → 环 copyOut；跳读 → pump.requestJump
├── OriginPrefetchBuffer.kt    环形缓冲（默认 8 MiB）：copyIn / copyOut / resetTo / awaitRoom
├── OriginConnectionLease.kt   一条连接的生命周期：开哪块 / 读到哪 / 失败重开 / 越界就地判掉
└── OriginPrefetchPump.kt      生产循环：什么时候读 / 写哪 / 该不该跳读
```

**为什么按"变化原因"拆**（不是按 widget 拆）：

| 文件 | 变化原因 | 单独可测 |
| --- | --- | --- |
| `HttpOriginClient` | 源站协议 / 分块大小变了 | 需要 HTTP 源站 |
| `HttpOriginReader` | 读侧契约变了 | 需要 buffer |
| `OriginPrefetchBuffer` | 缓冲布局变了 | 纯内存 |
| `OriginConnectionLease` | 连接策略变了 | 需要 client + buffer |
| `OriginPrefetchPump` | 生产节奏变了 | 需要 buffer + lease |

**v6 删掉的文件**：`OriginConnectionHealth.kt`（速率窗口 + 空闲计时）。
它的前提是"连接会被回收"；v6 改成"响应有尽头"之后，
不再需要判断"这条连接是不是老了"，留着它就是留着一段永不执行的判断。

### 9.4 为什么"每个 mpv 连接一个独立读者"

mpv 内核走 FFmpeg 的 `http` 协议，**每次 seek 都新开一条连接**，新旧连接会短暂重叠。
单游标的源会被两个读者互相顶掉 ⇒ 每条连接必须有一套自己的连接与缓冲。
代价是**内存按连接数倍增**（真机同时活 3 条：head / cues / 播放），
这是 v7 必须收敛内存的原因之一。

## 十、v8–v11 · 起播提速收口

### 10.1 问题：v7 之后"播放中不卡了"，但"点开要等 5 秒"

v7 收完持续播放之后，用户视角还剩一个明显的等待：
冷启动点开到第一帧出来要 **5 秒量级**。这不是带宽问题
（4K 片源持续消耗只有 435 KB/s，源站给单连接满速 2.4–7.6 MB/s），
是两个**延迟**叠在一起：

| 延迟源 | 真机实测 | 性质 |
| --- | --- | --- |
| **连接冷**：新建连接要 TCP + TLS 握手 | 新建 **983–1301 ms** / 复用 **266–362 ms** | 源站侧（Cloudflare 边缘），本地无法优化握手本身 |
| **定位晚**：续播位在起播**之后**才 seek | 起播后还要多付一整轮"读 cues + 找关键帧" | **本地可优化** |

### 10.2 v8 · keep-alive 池预热（**只对了一半**）

**做法**：在 `HttpOriginSource` 初始化时先打一次 1 字节请求，把连接塞进 JDK 的
keep-alive 池，让随后的取数请求直接复用。

**实测**：表头 max 从 **1076 ms → 695 ms**；起播从 5.1 s → **3.232 s**。

**但它只对了一半**：一次性预热在池被取空后就失效了。
更糟的是它**引入了 v10 的那个坑**：预热占着池里的连接，
取数侧不一定捡得到。

### 10.3 v9 · `loadfile` 带 `start=`（**成立**）

**问题**：续播位是**起播之后**才 seek 的 —— mpv 先在 0 打开文件、
打开容器、读完 cues，才跳到目标位置。用户看到的是"黑屏 → 转圈 → 画面"。

**做法**：把续播位塞进 mpv 的**每文件选项** `start=`，让内核**一打开就落在目标位置**。

```
// loadfile 的第 5 个参数是 per-file options
loadfile <url> replace 0 start=531.155
```

**改动面**（4 个文件，每个都是"一处语义"）：

| 文件 | 改动 |
| --- | --- |
| `mpv_commands.cpp` | `load_file_impl` 增加 `start_seconds`；> 0 时用带 options 的 `loadfile` |
| `mpv_session.hpp` | `Session::load_file(url, start_seconds, error)` |
| `jni_mpv_bridge.cpp` | `nativeLoadFile` 增一个 `jdouble` |
| `MpvNative.kt` / `MpvPlaybackSession.kt` | `loadFile(url, startSeconds)` / `start(..., startSeconds)` |

**实测**：起播 **3.127 s**，且 mpv 日志里 `queuing seek to 582.124000` 出现在
**1.925 s**（v8 是 1.716 s 之后还有一轮定位），起播后不再多付定位那一步。

### 10.4 v10 · 串行 keeper（**倒退，被自己证伪**）

**做法**：把一次性预热改成**常驻 keeper**（每 8 s 打一次 1 字节请求，续住连接）。

**串行版（v10）实测反而更差**：

| 指标 | v9（无 keeper） | v10（串行 keeper） |
| --- | --- | --- |
| 首块表头 | — | **978 ms** |
| 跳读表头 | — | **1211 ms** |
| 起播完成 | 3.152 s | **4.628 s** |
| 表头 max | 467 ms | **1165 ms** |

**根因（这是 v10 最有价值的地方）**：
keeper 刚把自己的连接还回池，取数侧紧接着就把**那条连接捡走了** ——
而 Cloudflare 侧的连接可能已经被判死，于是**比新建还慢**。
keep-alive 池是**先到先得**的，保温者与取数者**在抢同一条连接**。

### 10.5 v11 · 并行 keeper（**成立**）

**做法**：keeper 改成 **N = 2 个并行守护线程**，各自每 8 s 续一次自己的连接。
池里始终有**富余**的热连接，取数侧随便捡哪条都是**刚用过、确定还热**的那条。

**实测（v11，240 s 会话 + 拖动会话）**：

| 指标 | v11 实测 |
| --- | --- |
| `Opening done` | **1.401 s** |
| `queuing seek to 531.155000` | 1.571 s |
| `seek done` | 1.859 s |
| **首帧（`first video frame after restart shown`）** | **3.201 s** |
| `playback restart complete @ 531.156000` | 3.217 s |
| 240 s 会话请求数 | 35 次 |
| 表头 min / p50 / p99 / max | **266 / 287 / 362 / 362 ms** |
| 新建连接次数 | **0**（表头 max 362 ms ⇒ 没有一次是握手级的 1000+ ms） |
| `Enter buffering` / `End buffering` | **0 / 0** |
| 渲染 | 5641 帧 / 235.4 s = **23.96 fps**，间隔 > 200 ms **0 次**，max 194 ms，p99 43 ms，失败帧 0 |
| 音频欠载 | **1 次**（起播瞬态，t = 3.218 s） |
| 拖到未缓存位置 | seek 15.346 → 首帧 **16.785 s**（**1.44 s**），跳读表头 **≤ 334 ms（复用）** |
| 内存 TOTAL PSS | **503,061 KB** |
| 预览 `[thumb]` | 20 次请求 / **38.1 MiB**（未修，见 L2） |

### 10.6 版本对照链（全部可从证据日志复算）

| 版本 | 改动 | 起播场景 | 起播完成 | 表头 max | 结论 |
| --- | --- | --- | --- | --- | --- |
| v7 | — | 从 0 起播 | 2.548 s | 1076 ms | 播放中不卡，起播慢 |
| v8 | 一次性预热 | 续播 500 s | 3.257 s | 695 ms | 预热有效但会被抢 |
| v9 | `+ start=` | 续播 582 s | 3.152 s | 467 ms | 定位晚，已修 |
| v10 | 串行 keeper | 续播 318 s | **4.628 s** | **1165 ms** | **倒退** |
| v11 | 并行 keeper | 续播 531 s | **3.217 s** | **362 ms** | **成立** |

> **对照链的可比性说明**：v7 是**从 0 起播**，v8–v11 都是**续播到片中段**，
> 两者**不可直接比**（续播要多付定位成本）。
> v7 拖到 1566 s 用 **5.176 s**，与 v11 拖到未缓存位置用 **1.44 s** 才是同一场景的对照。
> 跨版本的**硬指标**是表头延迟：1076 → 362 ms，这个与场景无关。

### 10.7 v11 的家族树增量

```
net/
├── HttpOriginClient.kt      （v8）· warmConnection()：1 字节范围请求，读满 ⇒ 连接回池
├── HttpOriginSource.kt      （v8）· 持有 warmupPool，随 close() 一起关
└── OriginWarmupPool.kt      （v8 一次性 → v11 常驻并行）
        · N 个守护线程，各自每 8 s 续一次自己的连接
        · 只在失败时记日志（成功的续期没有价值，进日志只会淹没真故障）
```

**为什么 keeper 单独一个文件**：它是**"连接保温"**这件事的策略，
与"取数"（`HttpOriginClient`）、"读侧"（`HttpOriginReader`）、
"缓冲布局"（`OriginPrefetchBuffer`）**变化原因完全不同** ——
改保温节奏不该动取数实现，反过来也一样。

## 十一、v13 · 预览浪费收口（供给侧截断 + 预览环收小）

### 11.1 这一段要解决什么

用户在播放页横向拖动进度条时，浮窗里要出**目标位置的那一帧**。
这个预览走的是**独立的第二个 mpv 实例**（`MpvThumbnailReader`），
它自己也去源站取数 —— 实测**为了取一帧下载了 38.1 MiB**（v11 的 `[thumb]` 20 次请求）。

两个数字必须分开说：

| 浪费的一半 | 量 | 收在谁那里 |
| --- | --- | --- |
| **带宽** | 38.1 MiB / 次 | **本卡（v13）** |
| **内存** | 第二个 4K mpv 实例（解码器 + 纹理） | 273-B（预览内核生命周期） |

### 11.2 v12 · 先证伪"mpv 参数能治"

在动供给侧之前，先穷举了 mpv 侧能拧的旋钮 —— 全部用**运行时下发**（`--es kivo.thumbOpt`），
一次装机跑完 7 组，每组都有回执与下载量读数（`v12/*-net.log`）：

| 组 | 参数 | 预览下载 |
| --- | --- | --- |
| v0 | 默认 | 34.1 MiB |
| v1 | `demuxer-readahead-secs=0` | 42.1 MiB |
| v2 | `cache=no` | 30.1 MiB |
| v3 | `cache=no` + `demuxer-readahead-secs=0` | 30.1 MiB |
| v4 | `cache-secs=0.2` + `demuxer-max-bytes=64KiB` | 30.1 MiB |
| v5 | `demuxer-max-bytes=1MiB` + `demuxer-max-back-bytes=0` | 36.1 MiB |
| v6 | `cache=no` + `demuxer-max-bytes=64KiB` + `demuxer-readahead-secs=0` | **16.1 MiB** |

**结论：mpv 侧治不了。** 最好的一组（v6）也还要 16.1 MiB，而且 v1 反而**涨到 42.1 MiB**。

### 11.3 根因：开口区间 + 内核往前读

FFmpeg 的 HTTP 协议层对 mpv 发的请求是**开口区间**（`Range: bytes=N-`），
它**不会**"读够一个关键帧就停"—— 它会一路往前读到内核说够。
mpv 侧的 `cache` / `cache-secs` / `demuxer-max-bytes` / `demuxer-max-back-bytes` /
`demuxer-readahead-secs` 控的是**缓存有多大**，**不是**"这次读要不要停"。

真机日志把这件事说得很直白（v12）：

```
seek 落到 475 s（字节 266,455,742）→ 0.83 s 出帧
……然后内核继续往前读了 9 s，约 24 MiB
```

⇒ **要截断，只能在供给侧截**（我们自己的 range 代理），
或者**换一个不往前读的协议**（代价太大）。

### 11.4 v13 的修法（三条）

**① 单次响应上限（供给侧截断）** —— 新文件 `mpv/LocalRangeResponder.kt`：

```kotlin
private fun capEnd(start: Long, end: Long): Long {
    if (maxRangeBytes <= 0 || start <= 0) return end   // 片头(偏移0)不截
    val span = end - start + 1
    if (span <= maxRangeBytes) return end
    return start + maxRangeBytes - 1
}
```

> **为什么偏移 0 不截**：FFmpeg 在片头那一跳是从 `Content-Length`（200 响应）
> 推导**整个文件大小**的。截了它 ⇒ 文件大小变成 4 MiB ⇒ **之后所有 seek 都定位不到**。
> 这是本卡唯一一个"看起来可以省、其实不能省"的地方，必须豁免。

**② 预览不许在 EOF 处重连** —— `LocalRangeServer.urlFor(id, reconnect = false)`：

预览的 URL 带 `reconnect_at_eof=0`（播放主链路仍是 `1`）。
否则 FFmpeg 到了截断点会**重连并继续往后拉** —— 截断就白做了。

**③ 预览的环与块收小** —— `PlayerUrlStart.kt`：

```
THUMB_CAPACITY_BYTES : 4 MiB → 2 MiB
THUMB_CHUNK_BYTES    : 2 MiB → 1 MiB
```

按连接隔离的预读模型下，**每条连接的浪费 ≈ 环 + 一块**（内核不按需取数，泵会预读）。
一次预览会话有 3 条连接 ⇒ 18 MiB → **9 MiB**。

### 11.6 v13 的家族树增量

```
mpv/
├── LocalRangeServer.kt      409 → 216 行 · 只剩"连接骨架"（accept / HEAD / GET / close）

| `respondHead(out, size)` | HEAD ⇒ 200 + `Content-Length`（FFmpeg 在片头靠它推文件大小） |
| `respondGet(out, source, rangeHeader)` | GET ⇒ 解析 Range → 截断 → 206 + `Content-Range` → 分块写 |

## 十二、v14 · MKV cues 预取（片尾缓存）

### 12.1 起播慢的最后一跳在哪

v13 之后起播还差 **3.478 s**（首帧）。把真机日志按毫秒排开（`v13/net-diag.log`，
以 mpv 打开 URL 为 t=0）：

| t | 发生了什么 | 谁在等 |
| --- | --- | --- |
| 0 | 内核请求 `bytes=0-`，代理去源站取第一块（表头 **358 ms**） | |
| 358 | 片头表头到 ⇒ 内核拿到 EBML 容器头 | |
| **422** | **内核请求 `bytes=854195684-`（片尾 cues）** | 这一次请求**从头到尾 475 ms** |
| 836 | cues 的源站表头到（414 ms） | |
| 898 | cues 交付内核 | |
| 1232 | 内核回退到 `bytes=6072-`（读完 cues 后重开） | |
| 1563 | 它的表头到（331 ms） | |
| 2260 | `Opening done` | |
| 2400 | `queuing seek to 143.727` | |
| 2734 | `seek done`（目标字节 79,040,646 的块表头 329 ms ⇒ 2686 到） | |
| **3478** | **首帧** | |

⇒ **cues 那一跳（422 → 898）整段压在关键路径上**：内核拿到 cues 才能算出
"跳到 143.727 s 对应哪个字节簇"，才发得出后面那几跳。

### 12.2 为什么不能靠"少付一次表头"

表头 414 ms 不是握手（握手是 983–1301 ms），是**源站对范围请求的响应延迟**，
v11 复用连接时也是 334 ms。**池里有几条热连接都改不动它** ——
只能**提前把这段字节拿到本地**。

而"提前"是可行的：片源总长在 `main.size()` 那一步就已经知道了
（1 字节范围请求，≈350 ms），比 mpv 打开 URL **早**。
片尾 cues 就在**文件末尾**（本片源：cues 段 = 最后 64,368 字节），
所以总长一知道，片尾的字节位置也就知道了。

### 12.3 两条被实测否掉的"更省事的做法"

| 想法 | 实测结果 | 结论 |
| --- | --- | --- |
| 用**后缀范围** `Range: bytes=-1048576` 直接要"最后 1 MiB"（不用先知道总长） | 源站把它当成 `bytes=0-1048576` 返回了**片头**：`Content-Range: bytes 0-1048576/854260052` | **不支持**。尾窗口起点只能靠总长算 ⇒ 预取必然晚于 `size()` 一步 |
| 用 **416 探测**拿总长（`Range: bytes=<很大>-` ⇒ `Content-Range: bytes */总长`） | 成立，但**省不掉时间** | 仍是一次往返，和 `bytes=0-0` 同价。不用 |

⇒ 预取的**起点**由 `size()` 决定，而 `size()` 完成的那一刻 mpv 也差不多打开了 URL。
这就是下面 §12.5 那条"读侧等在飞的预取"的由来。

### 12.4 修法：片尾缓存（预取 + 命中即本地供）

```
net/
├── OriginTailCache.kt    （新）· 片尾窗口的存与取：后台预取 / 覆盖判定 / 读出
├── TailCachedReader.kt   （新）· 读侧装饰器：缓存优先，缺则委托（代理器按需建委托）
├── OriginHeadParser.kt   （新）· 响应头语义解析（从 HttpOriginClient 拆出，见铁律）
├── HttpOriginClient.kt   （改）· openChunk 拆出 openRange(start, end)：片尾要精确长度
└── HttpOriginSource.kt   （改）· 持有缓存；prefetchTail() 触发预取；openReader 包一层
```

**为什么拆成两个文件**：
`OriginTailCache` 是**策略**（取哪一段、什么时候取、命中没有）；
`TailCachedReader` 是**读侧机制**（命中先给缓存、没命中再开连接）。
前者会因为"cues 在哪、窗口多大"变，后者只会因为"读怎么走"变。

**为什么多出 `OriginHeadParser`**：`HttpOriginClient` 加了 `openRange` 之后
变成 302 行，**破了 300 行铁律**。响应头解析（`Content-Range` / `Content-Length`
→ 总长 / 起点 / 终点）是**另一种变化原因**（源站换实现 / 换头），
与"连接怎么开、失败怎么翻译"无关 ⇒ 拆出去，顺带把 client 压回 289 行。

**关键取舍（都写在这里，免得以后被当成 bug 修掉）**：

| 取舍 | 决定 | 为什么 |
| --- | --- | --- |
| 窗口多大 | **1 MiB** | 本片源 cues 只有 64 KB，1 MiB 留足余量；代价是每会话多下 1 MiB（≈200 MiB 的 0.5 %） |
| 窗口不够大怎么办 | **不命中 ⇒ 照旧走网络** | 缓存是**加速**，不是**依赖**。cues 段特别大的片源只是拿不到这个加速，不会出错 |
| 要不要解析 EBML 找 cues 起点 | **不解析** | 解析要在字节流里扫 `0x1C53BB6B`，**认错了就会把错字节喂给内核**。宁可少命中，不冒这个险 |
| 偏移 0 要不要缓存 | **不缓存** | 片头是内核判定"文件多长"的地方（`Content-Length`），跟片尾缓存无关 |
| 预览源要不要预取 | **不要** | 预览第一次用到时才 `size()`，那时预取已经晚了；而且会白给预览加 1 MiB（v13 才把预览从 38.1 降到 10.1 MiB） |
| 预取失败怎么办 | **回源站** | 缓存是加速器，不是依赖。失败只少一次加速，功能不缺（**不许静默降级**：失败会写进 `net-diag.log`） |

### 12.5 读侧怎么走（为什么不会把连接位置弄乱）

代理是**顺序**读的：先读 64 KiB，再读 256 KiB、256 KiB……
缓存可能只覆盖前面一段。所以装饰器必须能**只供一部分**：

```
readAt(offset):
    缓存窗口覆盖 offset ⇒ 从缓存拷（可能少于 len，这是合法的部分读）
    否则 ⇒ 委托读者从 offset 读
```

委托读者**按需建**（`openDelegate(offset)`）：缓存供了一半之后如果要网络，
就从**当前 offset** 重新开读者 —— 不会把"已经在缓存里的那段"再要一遍。

**命中判定**：请求 offset 落在缓存窗口 `[总长-1MiB, 总长]` 内即命中，
拷到窗口末尾为止（不足则只拷剩余的部分，剩余部分回源站）。
本片源 cues 请求是 `bytes=854195684-`（开口到 EOF），
缓存窗口是 `[853212028, 854260052]` ⇒ **整段命中 ⇒ 一字节网络都不用**。

### 12.6 读侧要**等在飞的预取**（本卡最容易做错的一处）

内核跳到片尾的时机（t=+422 ms）**早于**预取落地（t≈+550 ms）——
差 ~130 ms。为什么：预取的起点由 `size()` 决定，而 `size()` 完成时 mpv 也差不多打开了 URL。

如果读侧此时**直接回源站**，就是**又开一条连接**下同一段字节，
还多付一次 414 ms 表头 —— 缓存等于白做。

所以读侧在"请求落在**正在预取**的窗口里"时**等它落地**（上限 5 s）：

| 状态 | 读侧行为 |
| --- | --- |
| 窗口已就绪 | 直接从内存拷（**零连接**） |
| 预取在飞，且请求落在它的窗口里 | **等**它落地（≤5 s）⇒ 仍然零连接 |
| 预取在飞，但请求不在它的窗口里 | 不等，照常走网络 |
| 预取失败 | 照常走网络（功能不缺） |

等待上限的意义：宁可多开一条连接，也不让内核干等超过 5 s。

## 十三、v15 · 起播关键路径（自己把自己的假设证伪，然后重算）

### 13.1 先证伪 §十二 的那条假设

§12.4 写"窗口取 1 MiB，留足余量"。**这个假设被 v14 的 A/B 直接打掉**
（`v14/ab/`，6 轮，同一台设备、连续跑、同一份断点状态，
`--ei kivo.tailWindowKiB` 运行时切换）：

| 窗口 | `Opening done`（内核相对时间） | `Opening done → 首帧` | 片尾那一跳 |
| --- | --- | --- | --- |
| 关（0 KiB） | 1.439 / **1.490** s | 0.262 / 1.509 s | 代理实拉 64 KB，81–191 ms |
| 256 KiB | 1.314 / 1.460 s | 1.795 / 1.292 s | **内存命中，零连接** |
| 1 MiB | **1.888** / 1.688 s | 1.434 / 1.560 s | 内存命中，零连接 |

⇒ **窗口越大，起播越慢**（1 MiB 比关掉还慢 0.2–0.4 s）。机理：

- cues 段在**文件末尾**，而预取是**从头往尾**流式下载的
  ⇒ 窗口里**最后**到的才是 cues；
- 所以"cues 可供"的时间 = **整窗下完的时间**，不是"cues 那段下完的时间"；
- 窗口 1 MiB ⇒ cues 要等 1 MiB 全部下完（真机 1.1–1.5 s）⇒ 比直连还慢。

⇒ §12.4 那句"1 MiB 留足余量"是**反的**：余量越大越亏。
窗口的取值只能是"**刚好盖住 cues**"，而 cues 只有 64,368 字节（本片源）。
这条结论同时说明：**片尾预取不是"越大越保险"，而是"越小越快、且必须 ≥ cues"**。

### 13.2 起播的真实结构：四跳串行

把内核侧（mpv 相对时钟）与取数侧（绝对时间）并排（`v14/ab/r1-off-*`）：

| # | 什么时候 | 干了什么 | 代价 |
| --- | --- | --- | --- |
| ① | **内核 t=0 之前** | `main.size()` 探一次总长（1 字节范围请求） | **≈300 ms（纯开销）** |
| ② | t=0.011 | 内核 GET `bytes=0-` ⇒ 代理开第一块 | 表头 309 ms |
| ③ | t=0.332 | 内核读 SeekHead 拿到 cues 偏移 ⇒ GET `bytes=854195684-` | 表头 275 ms + 传输 190 ms |
| ④ | t=0.808 | 内核读完 cues 后**回读** `bytes=6072-`（FFmpeg 读完 cues 把游标退回段首） | 表头 324 ms |
| — | t=1.439 | `Opening done` | |
| — | t=1.701 | 首帧 | |

四个 RTT 串行 ⇒ **墙钟 ≈ 300 + 1.44 = 1.74 s 到首帧**。
每跳 275–324 ms 都是**源站对范围请求的响应延迟**（不是握手，握手是 983–1301 ms），
池里热连接也改不动。

### 13.3 三条改法（本卡）

**改法 A · 总长跟着"自己这一跳"回来（省 ① 的 300 ms）**

① 那次探测**没有给任何人带来新信息**：代理写响应头要总长，
而**它随后要开的那一块的响应头里就带着总长**（`Content-Range` 的 `/total`）。
所以：代理先开读者（源站请求立刻发出），再问读者要总长 ——
**总长与首字节同一跳到达，比单独探一次省一整个 RTT**。

- 读者侧：`HttpOriginReader.size()` 已经在等 `buffer.knownTotal`
  （`OriginConnectionLease.open()` 从块响应头里 `setTotal`）⇒ 机制已具备，只是没被用在这条路上。
- 代理侧：`respondGet` 改成"先开读者 → 再问总长 → 再写响应头"。
- **失败语义不变**：探针（鉴权/范围支持）仍然跑，只是**不再挡在起播前面** ——
  它与内核起播**并行**，失败照样带 reason 退出（G9：不许静默降级）。

**改法 B · 片尾窗口按"刚好盖住 cues"定量（省 ③ 的一半）**

- 窗口默认从 **1 MiB 收到 64 KiB**（本片源 cues = 64,368 B ⇒ 刚好盖住）。
- 预取**必须在 t=0 就发出去**才有意义：它和 ② 同时发，
  表头 300 ms + 传输 ~110 ms ⇒ cues 在 **≈410 ms** 就绪；
  而直连要到 **≈795 ms**（③ 的请求 332 ms 才发出）。
- **前提是 t=0 就知道总长** ⇒ 总长必须**由外面给**：
  Emby 的 `MediaSources[0].Size` 在详情请求里**已经解析好了**
  （`EmbyClient.details` → `EmbyMediaInfo.sizeBytes`）⇒ 塞进 intent 即可，零额外请求。
- 这个"总长"是**提示**不是**权威**：代理写响应头用的总长仍然取自**它自己那一跳的响应头**
  ⇒ 提示错了也只会让预取白下（缓存窗口按响应里的真实起点算 ⇒ 不会喂错字节）。

**改法 C · ④ 那一跳（回读 6072）留到下一卡**

④ 读的是 ② 已经拿到手的那 12 KB（`0..11904`）——**内核在把同一段字节再要一遍**。
根治办法是取数层留一份"片头缓存"（生产侧落盘那 12 KB，回读时直接供），
能省一整个 RTT（≈280 ms）。**本卡不做**：它要动生产侧（`OriginPrefetchPump`）
与读侧的接缝，风险比 A/B 大，且与 A/B 争同一批连接 —— 先把 A、B 测干净。

### 13.4 家族树增量

```

├── HttpOriginSource.kt   （改）· 总长有三种来源：外给提示 / 块响应头学到的 / 探针探到的
├── HttpOriginClient.kt   （改）· 块响应头里的总长顺手报给源（供源记住，省掉后面的 416 判定等待）
├── TailCachedReader.kt   （改）· size() 改为"先问委托读者"（委托读者能从自己那跳学到总长）
├── OriginTailCache.kt    （改）· 窗口默认 64 KiB；预取可用"外给的总长"提前发出去

（内核换 Range 语义 vs 供数策略变）⇒ 拆出去，顺带把 responder 压回 280 行以内。

**为什么 `HttpOriginClient` 只加一行回调**：它已经是"源站连接的唯一出入口"，
"这一跳看到了总长"本来就是它的事 ⇒ 顺手报给源，不新增文件。

### 13.5 关键取舍（写在这里，免得以后被当成 bug 修掉）

| 取舍 | 决定 | 为什么 |
| --- | --- | --- |
| 总长用"外给的提示"还是"探针探到的" | **两者都要，但用途分开** | 提示给**预取**用（要 t=0 就能发）；权威值给**代理写响应头**用（必须来自实际响应） |
| 探针还留不留 | **留，但不再挡路** | 它是唯一的**鉴权判决**来源（401/403/404 要有用户能看懂的话，G9）。并行跑，失败照样退出 |
| 片尾窗口多大 | **64 KiB** | cues 只有 64,368 B；窗口越大 cues 越晚到（13.1 实测）。**cues 特别大的片源就是拿不到这个加速，不会出错** |
| 提示的总长错了怎么办 | **只影响预取白下** | 缓存按响应里的真实起点/长度存 ⇒ 不会喂错字节；代理写响应头用的是权威值 |
| 要不要解析 EBML 找 cues 起点 | **不解析** | 认错一位就把错字节喂给内核，比慢更糟（沿用 §12.4 的决定） |
| ④ 那一跳（回读 6072） | **本卡不做** | 见 13.3 改法 C：动生产侧，风险大，先测 A、B |

## 十四、v16 · 详情页预热（把源站握手挪出起播关键路径）

### 14.1 问题：起播那一刻，所有连接都在忙

真机实测（emby.bangumi.ca，Redmi K40）：

| 连接 | 表头延迟 | 4 MiB 耗时 |
| --- | --- | --- |
| **新建**（TLS 握手） | **983–1601 ms** | 2.0–2.3 s（≈2 MB/s） |
| **复用**（keep-alive 池里） | **270–360 ms** | 0.42 s（≈10 MB/s） |

差 3–5 倍。而内核起播**一次要三跳**（片头 → cues → 回跳片头），
起播那一刻这三条连接**同时**要建 ⇒ 实测"4 条并发握手时每条 1.2–1.6 s"（互相抢）。

⇒ 关键不是"少开连接"，而是**让起播那一刻已经有连接可借**。

### 14.2 改法：详情页就预热（进程级）

详情页在**用户点播放之前**就已经有：URL、token、片源总长
（Emby 详情里就有，零额外请求）⇒ 连接与片尾窗口可以先建好。

`net/OriginPrewarm.kt`（新，进程级登记处）做两件事：

1. **探测**（1 字节范围请求）：顺带把**总长记进源**、把**连接放回 keep-alive 池**
   （读完响应体 ⇒ 连接回池 ⇒ 玩家页第一跳直接复用，约 300 ms）。
2. **片尾预取**：把 MKV 的 cues 那一段抓进内存（内核起播必跳到片尾读 cues）。

**为什么是进程级**：① JDK 的 `HttpURLConnection.KeepAliveCache` 是**静态**的
（进程全局）⇒ 详情页建好的连接天然能被玩家页复用；
② 片尾缓存挂在**源对象**上 ⇒ 源被玩家页接手，缓存跟着走。

**窗口放大到 256 KiB**：cues 长度**随片源变** —— 真机两个片源分别是
64,368 B 与 **130,494 B**，64 KiB 盖不住第二个。
**为什么放大不会像 §13.1 那样变慢**：v14 被打回的原因是"**起播瞬间才发**"
（尾段冷、窗口大就晚到）；这里的预热是**详情页**发起的 ——
用户还在看简介，窗口早就落地 ⇒ 放大只是多下几百 KB，**不占起播关键路径**。

### 14.3 家族树增量

```
net/
├── OriginPrewarm.kt      （新）· 进程级预热登记处：详情页 offer / 玩家页 take / 销毁 discard
├── HttpOriginSource.kt   （改）· 预取片尾（用外给的总长 t=0 就发）；保温池延后到首帧之后
ui/detail/
└── EmbyResource.kt       （改）· 详情页 offer 预热；页面销毁时 discard（没人接手就关掉）
ui/compose/
└── PlayerUrlPrepare.kt   （改）· 玩家页 take 详情页预热好的源（别再握手一次）
```

**为什么保温池要延后到首帧之后**：保温连接与起播关键路径上的请求
**抢同一次 TLS 握手**（真机：片头表头从 277 ms 涨到 957–2112 ms，起播 1.13 s → 2.9 s）。
起播只有一次机会，保温随时可以补 ⇒ **保温让路**。

### 14.4 诚实首帧：这个口径是本卡立的

"起播多快"之前一直用**应用锚点**（net-diag 里的 `MPV 首帧就绪`），
而它用的是"播放时钟起跳" —— **比画面真正出现早 1.5–2.8 s**。

本卡改成**诚实首帧** = 渲染层真正 swap 过一帧（`.diag` 里首个 `RND +Nms post #0`）。
口径写在复算工具里（`tools/p273_prewarm_ab.mjs`），两种口径并排打印，不藏。

### 14.5 实测（A/B：同一台设备、同一片源 233908、连续跑）

`v16/ab4/`（新构建后重跑；C = 直接起播无预热，P = 详情页预热）：

| | 闸门等待 | **诚实首帧**（渲染层 post #0） | 尾命中字节 | 尾回源次数 |
| --- | --- | --- | --- | --- |
| C 无预热 | 1401 / 1069 / 1082 ms | 2410 / 5078 / **4551** ms | 0 / 62284 / 62568 | 0 / 1 / 1 |
| P 详情页预热 | 100 / **92** / 89 ms | 1802 / **2170** / 3104 ms | **130494 ×3** | **0 / 0 / 0** |

⇒ **诚实首帧中位 4551 → 2170 ms（−2381 ms，−52.3%）**；
闸门等待中位 1082 → 92 ms；预热路径的尾窗口**三次全命中、零回源**。

## 十五、v17 · 片头窗口预取（把"起播第一跳"也搬出关键路径）

### 15.1 v16 之后还剩什么

v16 把**源站握手**挪出了关键路径，但真机复算发现关键路径上仍有三跳要回源：

| 跳 | 内容 | v16 的状态 |
| --- | --- | --- |
| ① | 片头 / 容器头（`bytes=0-`） | **仍回源**（新连接，800–1600 ms 表头） |
| ② | cues（文件尾） | 已命中（尾窗口 130,494 B，1 ms） |
| ③ | 恢复点所在簇（任意字节偏移） | **仍回源**（冷中段，实测 0.34 MB/s） |

⇒ v16 只干掉了 ②。①③ 两条都在**片头侧**（字节 0 附近与恢复点附近），
而**详情页预热**恰好可以顺带把 ① 拿下。

### 15.2 改法：把"尾缓存"泛化成"多窗口缓存"，加一片头窗口

原来的 `OriginTailCache` 只会记一个尾窗口。v17 把它改成
`OriginWindowCache`：**任意 [start, endExclusive) 区间**都能登记、都能命中，
每个窗口自带独立的取数客户端与状态机。

片头窗口 = **4 MiB**（`OriginPrewarm.PREWARM_HEAD_WINDOW_BYTES`）。

**为什么是 4 MiB**：真机片源的**恢复点**普遍落在文件前段
（实测 2,127,000 B / 8,490,718 B），4 MiB 能盖住前者的整个
"片头 → 恢复点"区间；再大则详情页下载量线性上涨，收益递减。

**为什么敢放大**：与 v14 被打回的理由不同 —— v14 是"**起播瞬间才发**"
（尾段冷、窗口大就晚到）；本窗口是**详情页**发的，用户还在看简介，
窗口早就落地 ⇒ 放大不占起播关键路径。

### 15.3 家族树增量（v17）

```
net/
├── OriginWindowCache.kt   （新）· 多窗口区间缓存：登记 / 落地 / 命中 / 关闭
├── CachedReader.kt        （新）· 缓存优先、落空即固定走委托的读取器
├── HttpOriginSource.kt    （改）· 一个窗口缓存 + 片头/片尾两个预取客户端
├── OriginPrewarm.kt       （改）· 预热顺序改为 片头 → 片尾 → 探测
└── OriginTailCache.kt     （删）· 功能并入 OriginWindowCache
    TailCachedReader.kt    （删）· 功能并入 CachedReader
```

**`CachedReader` 的关键约束**：**第一次落空就固定走委托**。
若不这么做，一个窗口在流播中途落地，读取器会"跳回去"读缓存，
导致字节位置与内核期望错位。

**为什么片头窗口 `waitMs = 0`**：片头窗口在详情页就已 READY，
玩家页取用时不应再等；尾窗口同理。

### 15.4 实测（A/B：同机、同片源、连续跑）

`v17/ab1/`（C = 无预热直接起播，P = 详情页预热）：

| 轮 | 路径 | 闸门等待 | **诚实首帧** | 片头命中数 | 尾命中字节 | 尾回源 | **关键路径源站往返** |
| --- | --- | --- | --- | --- | --- | --- | --- |
| c1 | 无预热 | 1047 ms | 2161 ms | 0 | 0 | 0 | 1 |
| c2 | 无预热 | 1125 ms | 4389 ms | 0 | 0 | 1 | 2 |
| c3 | 无预热 | 1030 ms | 3614 ms | 0 | 0 | 1 | 2 |
| **p1** | **详情页预热** | 107 ms | **690 ms** | **26** | **130,494** | 0 | **0** |
| p2 | — | 轮次无效（导航到别的片源，无播放） | | | | | |
| p3 | 详情页预热 | 100 ms | 3926 ms | 17 | 130,494 | 0 | 1 |

⇒ **诚实首帧中位 3614 → 2308 ms（−1306 ms，−36.1%）**；闸门等待中位 1030 → 103 ms。

**p1 是本卡的理想态**：整个 4 MiB 片头 **21 ms 内全部本地供出**
（`[head] cache hit` × 26）、cues **1 ms** 命中，
源站第一次分块直接从 `from=4194304` 开始 ——
**没有 `from=0`、没有 cues 回源、没有恢复点那一跳**。
诚实首帧 **690 ms**（v16 的 P 中位是 2170 ms）。

### 15.5 诚实的局限：片头窗口只覆盖"窗口内"的恢复点

p3 比 p1 慢，原因是**恢复点变了**：

| 轮 | 恢复点字节 | 落在 4 MiB 窗口内？ | 诚实首帧 |
| --- | --- | --- | --- |
| p1 | 2,127,000 | ✅ | 690 ms |
| p3 | 8,490,718 | ❌ | 3926 ms |

窗口盖不到时，第 ③ 跳（恢复点簇）仍要回源，
而**中段是冷的**（实测 0.34 MB/s）⇒ 这一跳独占了 ~3.1 s。

⇒ **下一卡（v18）的靶心就是第 ③ 跳**：
用**已经缓存在尾窗口里的 cues** 把"已知的恢复时间"换算成
"精确的簇字节偏移"，再定向预取那一簇。
（猜错的后果只是"没命中"，绝不会把错的字节喂给内核 —— 与此前被否的
"精确 cues 大小/字节匹配"方案不是一回事。）

## 十六、v18 · 恢复点定向预取（把"续播那一跳"也搬出关键路径）

### 16.1 靶心：第 ③ 跳（恢复点所在的那个簇）

v17 §15.5 已经把话说死了：**片头窗口盖不住恢复点**时，那一跳独占 ~3.2 s。

真机数据（片源 = Emby `Videos/233908/stream?static=true`，1,935,985,234 B）：

| 量 | 值 | 出处 |
| --- | --- | --- |
| 续播位 | 21.063 s | `watch.json` 播报 |
| 内核 seek 落点 | **8,490,718 B** | mpv 日志 `stream level seek from 1935985234 to 8490718` |
| 片头窗口覆盖 | 0 .. 4,194,304 B | v17 的 4 MiB |
| ⇒ 覆盖？ | **否**（差 4.3 MB） | — |
| 中段下载速率 | 0.34–0.5 MB/s（冷） | 真机实测 |

⇒ v18 要做的就是：**在详情页阶段把那 4.3 MB 提前抓下来**。

### 16.2 改法：cues → 偏移 → 定向抓（不是"猜字节"）

MKV 容器里有一张 **cues 表**（"刻度时间 → 簇位置"）。v16 起**片尾窗口就已经下好了**，
所以读懂它**不多下任何一个字节**。

新增家族树增量：

```
net/
├── MkvEbml.kt             （新）· EBML 元素读法（SeekHead / Info / Cues）
├── MkvCueIndex.kt         （新）· cues 表 → 时间 → 簇字节偏移
├── OriginResumePrefetch.kt（新）· 恢复点定向预取（只在详情页做）
├── OriginWindowCache.kt   （改）· awaitWindow 可"跟随在飞窗口"；requestedRange 暴露窗口区间
└── OriginPrewarm.kt       （改）· 预热链末尾加 prefetchResume
```

**为什么敢把偏移算准**：cues 的 `SeekPosition` 是**相对 Segment 数据起点**的，
再乘 `TimecodeScale` 换成时间刻度 —— 两者都能从**已缓存的**片头/片尾窗口里读出来
（`MkvCueIndex.clusterOffsetAt(timeMs)` 返回的是**文件绝对偏移**）。

**猜错的后果**：只有"没命中"（那一跳照常回源站）⇒ **绝不会把错字节喂给内核**。

**为什么窗口要"边下边给"**（`OriginWindow.publish`）：读侧 `awaitWindow` 等的是
"本来就该到的字节"，不是白等 —— 预取连接**已经建好**（省一次 TLS 握手），
而内核那一跳直接命中内存。

### 16.3 第一版在真机上死锁（自己踩的坑，记在这儿）

`OriginWindowCache.awaitWindow` 的 `when` 分支里**算出了 Snapshot 却没 `return`**：

```kotlin
w.state == OriginWindow.State.READY -> {
    val data = w.snapshot(w.filled) ?: return null
    Snapshot(w.actualStart, data)      // ← 没有 return
}
```

⇒ `while (true)` 空转**并且一直占着 monitor** ⇒ 两个预取线程（`KivoWindowPrefe`）
全部卡在 futex 上，日志里一条 `[head]/[tail]/[resume] prefetch window` 都不会出现。

**定位手段（值得记住）**：`/proc/<pid>/task/<tid>/{comm,syscall,stat}` ——
预热线程状态 `R`（累计 ~200 s CPU）、两个窗口线程 `futex` 等**同一把**锁。
只看线程名和栈顶（都在 `awaitWindow`）会误判成"源站慢"。

### 16.4 独立验证：cues 算出来的偏移 == 内核自己 seek 的偏移

| 来源 | 值 |
| --- | --- |
| 我们的 cues 解析（`MkvCueIndex`） | 4244 条，21,063 ms → **8,490,718** |
| mpv 自己的 seek（内核日志） | `stream level seek from 1935985234 to` **8490718** |

两边**独立算出同一个字节** ⇒ cues 解析没错位。

## 十七、v19 · 起播期音频欠载的判决（内核自报 ≠ 设备断音）

### 17.1 现象

内核日志在**起播瞬间**报欠载，随后自己重启音频：

```
[   0.635][v][cplayer] playback restart complete @ 21.063000, audio=playing, video=playing
[   0.638][w][cplayer] Audio device underrun detected.
[   0.640][v][cplayer] restarting audio after underrun
```

拖动 seek 之后还会再来一次（t=35.376 / 36.122 / 36.142）。

### 17.2 为什么不能只信内核

`Audio device underrun detected.` 是 **mpv 自己报的**（`[cplayer]` 级别），
它说的是"**我的音频环被读空了**"，**不等于设备上真的断音**。
设备侧另有两个**独立**计数器：

| 计数器 | 出处 | 含义 |
| --- | --- | --- |
| 混音器原始欠载计数 | `dumpsys media.audio_flinger` 的 `Normal mixer raw underrun counters: partial=… empty=…` | 混音器**真的**喂不上数据的次数（全局） |
| 音轨 `Underruns` / `Flushed` | 同一份 dump 的音轨表（`Client` 列 = 进程 PID ⇒ 可按我们的 PID 过滤） | 本进程这条轨的欠载/被 flush 次数 |

### 17.3 实测判决（`v19/audio/`）

| 阶段 | 本应用音轨行 | 音轨 `Underruns` | 混音器原始计数（全局） |
| --- | --- | --- | --- |
| 起播前 | 尚无本应用的轨 | — | `partial=0 empty=198` |
| 起播 30 s 后 | `672 yes 15909 … A 0 0 509.70 t` | **0** | `partial=0 empty=198` |
| 拖动 seek 后 | `672 yes 15909 … A 0 23056 430.10 t` | **0** | `partial=0 empty=198` |

⇒ **两个独立的设备侧计数器在起播、稳态 30 s、拖动 seek 之后全程没有增加**
（全局混音器 `empty` 恒为 198；本应用音轨 `Underruns` 恒为 0）。

### 17.4 结论（两句，别混成一句）

1. **设备上没有真的断音** ⇒ 用户听到的音频是连续的。**这条已判决。**
2. **但内核侧的欠载提示确实存在**，且它会**自己重启音频**
   （`restarting audio after underrun`）。它每次都发生在 **seek 落点之后 3 ms 内** ——
   同期源站往返 0、缓冲事件 0 ⇒ **不是取数层喂不上数据**，
   是 mpv 在 flush 音频设备后重建输出环的固有抖动。

### 17.5 试过并否掉的一条路

试过 `audio-stream-silence=on`（让内核在欠载时补静音而不是重启）：
mpv 接受了该选项并自己警告
`The --audio-stream-silence option is set. This will break certain player behavior.`，
但**欠载一次也没消**（起播 1 次 + seek 2 次，与不开时完全相同）——
因为 mpv 0.39 的 `audiotrack` AO 不支持静音填充控制；
换来的只有 A/V 同步被改动 ⇒ **收益为零、代价明确 ⇒ 不开**。

⇒ 结论：**这条提示是 mpv 的固有噪声，不改代码**（除不掉，也不影响听感）。
归入 §十九 缺口清单的 **G-音频**，定性为"**已判决：不影响听感**"，不是待办。

## 十八、v20：字幕字体集最小化（起播期 −126 MB 原生内存）

### 18.1 现象

起播期逐秒原生内存曲线（v23 逐秒采样，Redmi K40，1080p H.264 流）：

| 相对首帧 | 原生堆 (KB) |
| --- | --- |
| −4.38 s | 1,684 |
| −3.18 s | 13,188 |
| −1.90 s | 13,396 |
| **−0.67 s** | **205,536** |
| +0.60 s | 206,748 |
| +5.71 s | 240,148 |

⇒ 一次 **+192 MB** 的跳变，落在**首帧前约 1.9 s 内**；此后 6 s 内再爬 +35 MB，然后**完全平**（24 s 内 240,148 → 240,896）。
退出播放页 ⇒ 这块内存**全部归还**（不是泄漏）。

### 18.2 归因：四个候选逐一排除

| 候选假设 | 排除依据（真机） |
| --- | --- |
| demux 缓存太大 | `cache-secs=15`、`demuxer-max-bytes=16MiB` 两组 A/B，原生堆**不变**（245–247 MB）；实测缓存 `total` 只有 **25.2 MB** |
| 音频输出缓冲 | 运行期把 `ao` 换成 `null`（AO 缓冲实测仅 172800 字节），原生堆**纹丝不动**（241.8 MB） |
| 视频输出/渲染器 | 运行期换 `vo` 会连带触发**软解**（另 +98 MB），无法单独观察 |
| 硬解初始化本身 | 三次独立运行，跳变窗口都落在 `[Opening done → 首帧]` 之间；且**从 0 开始播**（无续播远跳）跳变依旧 ⇒ 与 seek 无关 |

### 18.3 根因：libass 把整个系统字体目录装进了进程

内核日志里有 **242 条** `Loading font file '/system/fonts/…'` —— libass 正在**逐个加载系统字体目录里的每一个文件**。

真机核对（`ls -l /system/fonts` 与日志里的文件名求交）：

| 项 | 值 |
| --- | --- |
| 被装入的字体文件数 | **239** |
| 这些文件的磁盘合计 | **125.6 MB** |
| 其中最大的几个 | NotoSerifCJK-Regular.ttc 25.1 MB / NotoSansCJK-Regular.ttc 18.6 MB / MiSansTCVF.ttf 9.4 MB / NotoColorEmojiLegacy.ttf 8.8 MB |

**机制**：我们编的 libass 没有 `CONFIG_FONTCONFIG`（没有字体提供器），
于是 mpv 的 `sub-fonts-dir=/system/fonts` 走 libass 的 `ass_set_fonts_dir()` ——
它对该目录里的**每个条目**调一次 `ass_add_font()`；
FreeType 的 `FT_New_Face` 会把整个文件读进内存 ⇒ **125.6 MB 全部常驻**。

**为什么以前没发现**：这套 `sub-fonts-dir=/system/fonts` 是为了修"中文字幕全是豆腐块"
而加的（见 `mpv_options.cpp` 里的说明）—— 方向对，**代价没算**：
为了显示一种字体，把系统里 239 个字体（含两个 CJK 全家桶、两个 Emoji 字体）全搬了进来。

**预览内核不受影响**：`MpvThumbOptions` 里 `sid=no` ⇒ libass 从不初始化 ⇒ 预览内核加载 **0** 个字体。

### 18.4 修法：最小字体目录（符号链接，不复制）

libass 认的是**目录**，所以把"要用哪个字体"变成"这个目录里只有哪个字体"。

| 环节 | 做法 |
| --- | --- |
| 选字体 | 候选表按优先级取**第一个存在**的 CJK 字体（NotoSansCJK-Regular.ttc → NotoSerifCJK-Regular.ttc → DroidSansFallback … → MiSansVF.ttf），并带上它对应的**族名**（.ttc 取 0 号 face 的族名） |
| 建目录 | 应用私有目录 `files/subfonts/`，把选中的字体**符号链接**进去（不复制 18.6 MB） |
| 交给内核 | `sub-fonts-dir` 指向该目录、`osd-font`/`sub-font` 用该字体的族名 |
| 附加字体 | 再链一个 `NotoColorEmoji.ttf`（2.96 MB）：Noto Sans CJK 已含拉丁、标点、假名，**唯一缺口是表情符号**；这是**故意**留的缺口，不是漏选 |
| 兜底 | 一个候选都找不到 ⇒ 回退到旧的 `/system/fonts` 行为，并把原因写进 `net-diag.log`（**不许静默降级**：字幕会掉字形，必须留痕） |

**为什么是符号链接**：18.6 MB 的 TTC 复制一份进应用目录，是纯粹的一次性浪费；
`ass_add_font()` 走 `FT_New_Face(path)` ⇒ 跟随符号链接 ⇒ 零拷贝、零重复。

**兜底也是要留痕的**：回退意味着"多占约 125 MB 原生内存"，所以
`[subfonts] 系统里没有可用的 CJK 字体文件，退回整目录 /system/fonts` 这行
必须出现在 `net-diag.log` 里 —— 否则就是一个静默的性能退化。

### 18.4.1 实测收益（Redmi K40，同一构建体系、同一个 Emby 流）

复算命令：

| **G-拖动** | 远跳落点后**停 0.597 s**（`Enter buffering` → `End buffering`） | v24 第 3 次拖动：`seek` 149.763 s → 首帧 152.288 s → 缓冲停 152.448–152.953 s | **用户可见卡顿** | ⏳ **v26 收**（§二十：落点定向预取） |
| **G-HDR** | **EGL 是 RGBA8888 / ES2 8bit 窗口，dataspace=UNKNOWN，hdr metadata types=0**；mpv 一个 HDR 选项都没设 | `dumpsys display`：K40 **支持 HDR10**（`mSupportedHdrTypes=[1,2,3,4]`、`mMaxLuminance=420`、面板 `mNits=[2,500,900]`）⇒ **屏幕能 HDR，我们没走 HDR** | **硬伤** | ⏳ **下一段（§二十一）** |
| **G-字幕·字体匹配** | 中文豆腐块 | `fontselect: (Noto Sans CJK JP, 400, 0) -> NotoSansCJKjp-Regular` | — | ✅ **已收**（v13 之后一直正常，v20 保持） |

### 19.3 本轮新增/关闭的缺口

**关闭**：G-内存·字体（v20）、G-音频（判决为不影响听感）、G-起播·冷路径（有预热时）。

**新增（此前清单里没有）**：

1. **G-内存·demux / G-内存·超买** —— v20 把 126 MB 字体拿掉之后，
   逐秒原生堆曲线**没有停**：第 5 s 之后仍以 2–4 MB/s 稳步爬升，24 s 时到 111.7 MB。
   内核日志自己说清了原因：
   `[cache] fw=31.8M total=43.2M dur=58.5s underrun=false rate=1.0M/s`
   ⇒ **mpv 的 demux 缓存被"时间"（`cache-secs=60`）撑到 58.5 s**，
   而这条流的实际码率只有约 392 KB/s ⇒ 43.2 MB 缓存 ≈ 154 s 的片源。
   同一时间窗里取数层下载 **52.1 MiB**、实际消费约 9 MiB ⇒ **超买 5.8×**。
   ⇒ 这两件事是**同一个旋钮**：`cache-secs`（以及它背后的 `demuxer-max-bytes=64MiB`）。
   **收法**：把 `cache-secs` 从 60 降到与"抗抖动"真正匹配的值（候选 15/20/30 s），
   A/B 看**缓冲事件是否仍为 0** 与**缓存占用/下载量**各降多少。

2. **G-HDR** —— 屏幕**能** HDR，我们**没走** HDR：
   - 我们的 EGL 配置是 `RGBA8888 + ES2`（`mpv_egl_surface.cpp`），
     `dumpsys SurfaceFlinger` 里我们的图层 `dataspace=UNKNOWN (0)`、`hdr metadata types=0`；
   - mpv 侧 `target-trc` / `target-prim` / `target-peak` / `tone-mapping` / `target-colorspace`
     **一个都没设**（`mpv_options.cpp` 里没有）；
   - 设备侧能力是**够的**：`mSupportedHdrTypes=[1,2,3,4]`（Dolby Vision / HDR10 / HDR10+ / HLG），
     `supportedColorModes=[0,7,9]`（含 wide gamut 与 HDR），面板 `mNits=[2,500,900]`，
     `isHbmEnabled=true`；
   - GL 侧也**够**：`GLES 3.2` + `GL_EXT_color_buffer_half_float` + `GL_EXT_texture_type_2_10_10_10_REV`
     + `GL_OES_texture_half_float`（真机 `mpv-kernel.log` 实测）。
   ⇒ 缺的只是"**把这条链路打开**"：EGL 走 10-bit + `BT2020_PQ` dataspace，
     mpv 侧把显示目标（TRC/prim/peak）告诉 libplacebo。
   **这是下一段（§二十一）的主线。**

## 二十、v25/v26 · 播放段最后两个缺口（缓存超买 + 远跳停顿）

> 段序说明：**播放段先收口，HDR 段在其后**（§二十一）。
> 本段收的是 §十九 里剩下的两项真缺口：`G-内存·demux` / `G-内存·超买`
> 与 `G-拖动`（远跳后 0.6 s 停顿）。

### 20.1 v25 · demux 缓存：不是泄漏，是**顶到了字节上限**

v24 长稳（120 s 逐秒 meminfo，`v24-soak/`）给出的曲线是**台阶**不是斜坡：

| 时刻 | 原生堆 | mpv `demuxer-cache-state.total-bytes` |
| --- | --- | --- |
| s=5 | 56.1 MB | — |
| s=10…s=65 | ~87.5 MB（平台） | 19.4M → 32.9M |
| s=70…s=115 | ~104.4 MB（平台） | 47.5M |
| s=120 | 121.6 MB | **80.0M**（= 64 MiB 前向 + 16 MiB 回看，**顶格**） |

⇒ **原生堆的每一次台阶都对应 demux 包队列的一次扩容**，最后一次直接顶到
`demuxer-max-bytes` + `demuxer-max-back-bytes` 的字节上限。
**不是泄漏**（不会随时间无限长），但这 80 MB 是**常驻**的，而且它是超买的来源：
mpv 为了把缓存填满，会在起播后**多读**远超播放所需的数据。

**片源的实际码率**：缓存时长 ÷ 字节数 ⇒ 19.4 MB / 58.3 s ≈ **0.33 MB/s**。
⇒ 80 MB 缓存 ≈ **240 s 的片源**，而 `cache-secs=60` 本该只要 60 s ≈ 20 MB。
**是字节上限先顶格，不是时间上限** ⇒ 两个旋钮都要动。

#### 20.1.1 收法

| 旋钮 | 现状 | 收后 | 依据 |
| --- | --- | --- | --- |
| `cache-secs` | 60 | **20** | 20 s ≈ 6.6 MB 实际媒体，够盖住源站抖动 |
| `demuxer-max-bytes` | 64 MiB | **32 MiB** | 高码率片源的时间闸不够用（20 s × 10 MB/s = 200 MB） |
| `demuxer-max-back-bytes` | 16 MiB | **8 MiB** | 回看 8 MiB ≈ 24 s 媒体，够"往回拖一点" |

⇒ 三者**同时**收：时间闸管"媒体够不够"，字节闸管"内存别爆"，回看闸管"内存别爆"。

### 20.2 v26 · 远跳落点后 0.6 s 停顿：那一段字节**不在本地**

v24 第 3 次拖动（跳到 4932 s）实测：

```
[ 149.762] Run command: seek, target="4932.163000"
[ 149.763] stream level seek from 53281274 to 1613145699   ← 落点的字节偏移
[ 151.044] [mkv] seek done                                ← 1.28 s：那一簇从源站取回来了
[ 152.288] first video frame after restart shown           ← 2.53 s：首帧
[ 152.448] Enter buffering (buffer went from 100% -> 0%)   ← 首帧之后**又**空了
[ 152.953] End buffering (waited 0.597546 secs)           ← 停 0.6 s
```

**归因**：seek 把 demux 缓存**冲掉了**（缓存里只剩头部那一段：
`[mkv] cached range 0: 17.559000 <-> 182.599000`），
内核在 1.61 GB 处重新起流；**那之后的下一个簇**还得再回源站取一次 ⇒ 0.6 s。
⇒ **不是解码慢，不是网络抖**（那 0.6 s 里没有新的 TCP 握手），
是"**落点后面那一段字节我们手里没有**"。

#### 20.2.1 收法：把落点那一段**提前**抓下来

内核的落点偏移 `1613145699` 就是"时间 4932.163 s 对应的簇"——
而 MKV 的 **cues 表**里就有这个映射（v18 已经用它消掉了续播那一跳）。
⇒ 把同一套机制复用到**拖动落点**上：

1. 播放在跑时**后台**把 cues 索引备好（片头布局 + 片尾 cues）；
2. 用户松手（seek 落定）时，用落点时间换算出簇偏移，
   **在把 seek 发给内核之前**就把那一段（4 MiB）抓进窗口缓存；
3. 内核 seek 落地后要数据时，代理**从窗口缓存供**（本地命中，不回源站）⇒ 0 停顿。

【为什么不放在"拖动过程中"】拖动过程中时间在变，每 120 ms 一次 ⇒
每变一次就抓 4 MiB = 白下几十兆。只有**松手那一刻**的落点才是真的。

【失败语义】cues 解析不出来 / 索引没备好 ⇒ **不预取** ⇒
那一跳照常回源站（功能不缺，只是没加速）—— 与 v18 同一条规矩。
