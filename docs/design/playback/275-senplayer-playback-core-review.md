## 二、需要更正/补齐的条目

### 2.1 [K2]「4K 6.7 MB/s vs 单连接 2.16 MB/s，1.53 fps」——已过时，且归因错了

275 稿 §2.1 引用它来说明"网络供数慢导致停顿"。本轮真机复测后的真实链条是：

| 环节 | 当时的结论 | 本轮实测（真机 K40） |
| --- | --- | --- |
| 4K 卡成 PPT 的原因 | 源站吞吐不够 | **拿错了版本**：同一 item（485）有 `2160p`（**54.5 Mbps**）与 `1080p`（**4.1 Mbps**）两份，旧代码取了 `MediaSources[0]` = 4K |
| 选源后 | — | 1080p 版本 **23.79 / 23.91 fps，0 次 Enter buffering**（`docs/evidence/p274-startup/`） |
| 剩余卡顿 | 归给"带宽不够" | **归给「长连接吞吐衰减」**：同一条 keep-alive 连接连续取 8 个 4 MiB 块，正文速率 **226 → 150 → 100 → 50 → 48 → 47 → 42 → 67 KB/s**；每块新建连接则 **203 / 630 / 372 / 678 KB/s**（PC 同源同时段对照） |

⇒ 275 稿 §五 5.2 那句"并发预读只在同源真机数据证明源站允许叠加带宽后启用"，
**要补上更靠前的一条**：**先查「同一条连接是否随时间衰减」**。
本轮证据表明：在本片源上，**换连接（`Connection: close`）的收益（5–10 倍）远大于并发（≤1.4 倍）**。
⇒ 并发预读（`274-parallel-prefetch.md`）继续搁置，不是错，只是**排不上第一**。

### 2.2 §八 第 1 条「确认探针不会改变路径」——本轮实测差 **5 倍**，必须写进判据表

| 路径 | 首帧（真机 K40，485 的 1080p 版本） |
| --- | --- |
| 探针路径（`am start --es kivo.playurl`，跳过详情页预热） | **8.5 / 9.97 / 12.49 s**（三轮） |
| **真实用户路径**（详情页点「播放」，`OriginPrewarm` 已生效） | **2.17 s**（`docs/evidence/p274-startup/realpath-old/`） |

⇒ 真实路径里：片尾 **本地命中**（`[tail] cache hit`，零源站往返）、
内核 `Opening done` 1.83 s、`MediaCodec started` 1.93 s、首帧 2.17 s。
⇒ **建议 275 稿把"真实入口基线"写进 §六 6.2 表格的第一行**，
并注明"探针路径的数字不得作为用户感知起播的验收依据"。

### 2.3 §六 6.1 的指标表：补一列「当前是否可采、在哪采」

275 稿列了 11 个指标，但没说现在能不能采、从哪采。Kivo 现状：

| 指标 | 现状 | 采集点 |
| --- | --- | --- |
| `startup_total_ms` | ✅ 可采 | `net-diag.log` 的 `MPV 首帧就绪`（锚点）+ tap 时刻 |
| `open_ms` | ✅ 可采 | mpv 内核日志 `Opening done`（相对时钟） |
| `first_decode_ms` | ✅ 可采 | `MediaCodec started successfully` |
| `first_present_ms` | ✅ 可采 | `first video frame after restart shown` |
| `read_latency_ms` | ✅ 可采 | `[play] origin chunk ... hdrMs=` |
| `buffer_runway_ms` | ✅ 可采 | `[cache] fw= total= dur= rate= underrun=` |
| `render_gap_ms` | ✅ 可采 | `tools/p273_gaps.mjs`（读 `mpv-kernel.log.diag`） |
| `buffering` | ✅ 可采 | mpv 内核日志 `Enter buffering` 计数 |
| `frames_dropped` | ⚠️ 部分 | mpv `vo-drop-frame-count` 未接；当前只能看渲染帧数差 |
| `seek_total_ms` | ⚠️ 部分 | 有落点钩子（`kivo.landSeekSecs`），但没有"请求→落点"自动计时 |
| `network_recovery_ms` | ❌ 未采 | 断网恢复只能靠 `mpv-kernel.log` 的时间戳人工推 |
| `thermal_context` | ❌ 未采 | 未接 |

⇒ 建议：**先把这 12 个指标的"现状列"补进 275 稿**，
再谈补采。理由：下一步最缺的不是新指标，而是"把已有的 8 个指标形成常规回归"。

### 2.4 §3.2 的家族树：建议标注"边界，不是本轮交付"

275 稿列了 6 个建议新增文件（`PlaybackCoordinator` / `PlaybackSessionActor` /
`PlaybackProgressStore` / `PlaybackDiagnostics` / `MpvRenderHost` / `SourceAdapter`）。
稿子自己写了"不要求为每个节点机械新增文件"，但**树图会被当成待办清单**。
⇒ 建议在树图上方加一行：**"这是边界说明；本轮不新增其中任何一个文件。
   275 稿第 8 条实施顺序的第 2 步（会话 actor / generation 收敛）需要单独立卡，
   不与播放性能卡混做"**。

### 2.5 275 稿漏掉的三件事（建议补进 §十一/§十二）

1. **HDR 没有位置**。274 已判：`当前 render API（legacy RA / vo_gpu）路径不具备 HDR 输出能力`
   （实测 `Disabling HDR peak computation (compute shaders=0, SSBO=1)`），
   完整 HDR 需要 `vo_gpu_next`（架构级）。275 稿的架构图与指标表都没有 HDR 的位置，
   ⇒ 建议明写"本稿不覆盖 HDR；HDR 归属 274 稿且当前被架构闸门挡住"。
2. **显示旋转这一层**（用户 2026-11-14 报过"返回时白屏一会儿"）。
   本轮取证：按返回后 ≈1 s 截图是 **2400x1080 横屏、详情页整体旋转 90°**，
   ≈2 s 才回到竖屏正常。根因：播放器 Activity `screenOrientation="landscape"`，
   详情页 Activity **未声明 `configChanges`**、窗口仍是竖屏尺寸 ⇒ 被系统 letterbox 成窄带。
   ⇒ 275 稿 §四 4.3 讲的是 **Surface 生命周期**，缺 **显示/窗口方向** 这一层。
3. **源站吞吐随时段变化**。用户 2026-11-15 反馈："深夜好像不会卡，下午的时候就会卡"。
   ⇒ **任何"卡/不卡"的验收都必须在同一时段做 A/B**，
   夜间臂只能当对照，不能据此判 PASS/FAIL。
   这条对"复刻 SenPlayer 流畅度"尤其关键：
   **如果 senplayer 是在夜间比出来的，那这个对照无效**；
   要下结论，必须**同一时段、同一片源、同一设备**比 senplayer 与 Kivo。
