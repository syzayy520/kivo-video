# 274 · 主链路并发预读（单连接 2.16 MB/s 硬墙的解法）

状态：**设计稿（待实施）**
上游：[273-emby-stutter-fix.md](273-emby-stutter-fix.md) §二十六（容量边界实测）
证据：`docs/evidence/p274-user-stutter/4k-485/`（4K 实测 1.53 fps）

---

## 一、要解决的具体问题

| 事实 | 数值 | 来源 |
| --- | --- | --- |
| 4K 片源码率 | **6.7 MB/s**（53 Mbps） | `ffprobe` 直读 Emby 485 |
| **主链路单连接上限** | **2.16 MB/s** | `4k-485/` 块间隔中位 1852 ms ÷ 4 MiB |
| 实测结果 | 1.53 fps · 起播 34.3 s · 渲染间隔 max 17.7 s | 同上 |
| CPU 占用 | 6.4%（硬解 mediacodec） | `top` 采样 |

⇒ **不是解码、不是 CPU、不是磁盘**：**取数吞吐差 3.1 倍**。

**已有的反例**：落点窗口用 4 片并发，实测 **3079 KB/s**（`v35-land/`）。
⇒ **同样的机制搬到主链路，才可能过 6.7 MB/s。**

## 二、三条路的取舍

| 方案 | 做法 | 优点 | 缺点 | 判决 |
| --- | --- | --- | --- | --- |
| A 滚动窗口 | pump 改用 `OriginWindowCache.prefetch(parts=4)` 预取 16 MiB 窗口，ring 从窗口喂 | 直接复用已验证的并发实现 | 窗口 16 MiB + ring 8 MiB **双份内存**；窗口边界要处理回绕；改动面大 | ❌ 内存与复杂度不划算 |
| **B 块内分片并行** | 一个 4 MiB 块分 4 片，**各片一条连接并行读**，pump 按顺序消费 | **不动 ring、不动 pump 结构**；失败只重开单片；内存只多 3 MiB | 需要新写一个"分片并行读取器" | ✅ **选它** |
| C 取消 ring | 直接用窗口当缓冲 | 内存最省 | 大重构，违反"禁止大重构" | ❌ |

## 三、方案 B 的架构

### 3.1 一句话

**把"一个块一条连接串行读"换成"一个块 N 条连接并行读、按顺序交付"** ——
网络侧并行（要吞吐），交付侧串行（保 ring 语义不变）。

### 3.2 家族树增量（单文件单职责）

```
android/app/src/main/java/com/kivo/cinema/net/
├─ OriginPrefetchPump.kt        改：读块改为向 ParallelChunkReader 取（保留原 lease 分支）
├─ OriginConnectionLease.kt     不动（保留为回退路径）
└─ OriginParallelChunk.kt       【新增】只做一件事：一个块的 N 片并行读取 + 按序交付
```

**为什么独立成文件**：它管的是"**一个块内部怎么并行**"，
而 `OriginConnectionLease` 管的是"**块与块之间怎么衔接**（开块/读完归还/失败重开）"。
两种变化原因 ⇒ 拆开。

### 3.3 数据流

```
                    ┌─ slice0: [start,        start+1MiB)  ─┐
块 start..start+4MiB ├─ slice1: [start+1MiB,   start+2MiB)  ─┤  N 条连接并行读
                    ├─ slice2: ...                            │  各自填自己的 sliceBuf
                    └─ slice3: ...                          ─┘
                              ↓ 各片就绪标志
                    pump 按 slice0→1→2→3 顺序 copyIn 到 ring
                              ↓
                    内核经 HTTP 代理从 ring 读（语义完全不变）
```

### 3.4 关键参数

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `PARTS`（每块分片数） | **4**（可开关覆盖） | 落点窗口 4 片实测 3079 KB/s；8 并发在源站不加总带宽（§25.1） |
| 分片大小 | `chunkBytes / PARTS` = **1 MiB** | 4 MiB ÷ 4 |
| 单片重试 | 连续失败 3 次 ⇒ 该片标记失败，整块失败 | 与 lease 的 `MAX_CONSECUTIVE_FAILURES=5` 同量级 |
| 等待粒度 | `awaitSlice` 超时 300 ms 轮询 | 与 `READ_WAIT_MS` 一致 |

### 3.5 失败语义（必须与现有 lease 对齐）

| 情况 | 处理 |
| --- | --- |
| 单片读失败 | 只重开**该片**（从该片已读位置续），不影响其它片 |
| 单片 EOF 且到文件尾 | 标记该片完成，整块按实际长度交付 |
| 单片连续失败超限 | 整块失败 ⇒ pump 用**当前写入位置**重开一块（**保留缓冲**，与 lease 一致） |
| 越界起点（`target >= total`） | 就地判掉，`markEndOfFile()`，不去打源站（沿用 lease 的现有逻辑） |
| 跳读 | 关掉整块所有片 ⇒ pump 从新位置重开 |

### 3.6 开关与回退（必须可一键回退）

```kotlin
// PlayerUrlStart 里读 intent，默认走并发
val parts = intent.getIntExtra("kivo.playParts", DEFAULT_PARTS)   // 1 = 旧行为
```

⇒ `kivo.playParts=1` **等价于旧版单连接**，用于 A/B 与线上回退。
⇒ 改动**不删** `OriginConnectionLease`，两条路径并存。

## 五、验收判据（真机 K40 `b6e950ee`，日志采前先清空）

| # | 判据 | 目标 |
| --- | --- | --- |
| 1 | **1080p(233908) 不回归** | ≥ 23.5 fps · 缓冲 0 · 与 `parts=1` 无显著差异 |
| 2 | **4K(485) 吞吐** | ≥ **6.0 MB/s**（当前 0.35–2.16） |
| 3 | **4K 帧率** | ≥ **23.0 fps**（当前 1.53） |
| 4 | **4K 起播** | < **10 s**（当前 34.3 s） |
| 5 | 4K `Enter buffering` | ≤ 1 次 / 60 s |
| 6 | 渲染间隔 max | ≤ 500 ms |
| 7 | `parts=1` 回归 | 与改动前同片源同量级（容差 ±15%） |
| 8 | 内存 | native 堆增量 ≤ 16 MiB（4 片 × 1 MiB × 若干块） |

**判据 2 若达不到 6.0**：说明源站对该客户端总带宽有上限（§25.1 的 4.55 MB/s），
则 4K **不可能**直传流畅 ⇒ 转方案（`PlaybackInfo` 转码），并在规格里写明结论。

## 六、诚实边界

- 本设计**只解决吞吐**，不解决 4K 起播 34 秒（那是另一条：`Opening done` 前 32 秒空白）。
- 并发能否叠加到 6 MB/s，**取决于源站是否按连接限速**。
  §25.1 测到 4/8 并发都是 4.5 MB/s，但那是 **curl 在 `run-as` 沙箱里**的结果，
  该环境已证明不可信（绕过 DNS 连百度都失败，§25 更正）。
  ⇒ **必须用 App 实测量定**，这也是 §五 判据 2 存在的意义。
- 若源站总带宽确实 < 6.7 MB/s，本方案**不会**让 4K 流畅 —— 那时唯一出路是转码。
