# 119 · P13-AF 设计：门看不看分辨率与帧率

- 日期：2026-10-31
- 前置：`114-p13ae-status.md`（四档 ppm 全中，但**全部跑在 360p30 上**）
- 目标：把"门只看时钟、与分辨率/帧率无关"从**推理**变成**证据**

---

## 一、要证的那句话

P13-AE 的判据是 `expected = max(0, ⌊(ppm × T − limit) / band⌋ + 1)`，
式子里只有 **ppm / 时长 / limit / band** 四个量 —— **没有分辨率，也没有帧率**。

所以本卡是一次**证伪尝试**：如果 `rebases` 随分辨率或帧率移动，那个式子就是错的，
门的实现里就藏着一条"负载会影响判定"的路径；如果不移动，这句话才有资格写进文档。

**"推理成立"和"证据成立"是两件事。** 前者只要求我读得懂公式，后者要求我跑过。

---

## 二、为什么不能沿用 8 秒片源

2000 ppm 在 8 秒里只累积 16 ms，门限 45 ms —— **算术上不可能触发**（P13-AE §一）。
所以三个臂都用 **60 秒**片源：`2000 ppm × 58 s = 116 ms`，预期触发约 **15 次**。

片源当场生成（`testsrc2` + 440 Hz 正弦，H.264 + AAC 48k），三臂只有一处不同：

| 臂 | 分辨率 | 帧率 | 用途 |
| --- | --- | --- | --- |
| A | 1920×1080 | 30 | **基线** |
| B | 1920×1080 | **60** | 只看帧率：A vs B |
| C | **3840×2160** | 30 | 只看分辨率：A vs C |

**为什么不做 2×2 四臂**：4K60 的 60 秒编码要十几分钟，而 A/B/C 三点已经能把
"帧率"和"分辨率"两个自变量各自分离（A 是公共基线）。**多一个臂换不来多一条结论。**

## 三、判据

| 编号 | 判据 | 门槛 |
| --- | --- | --- |
| R1 | 三臂的 `drift_rebases` 与预测之差 | 全部 ≤ 2 + `ppm×1s/band`（同 P13-AE 的容差） |
| R2 | 三臂之间的极差 | ≤ 4 次（约 10%），否则说明有第二个自变量 |
| R3 | 三臂 `clock_ahead` | 全部落在 `[limit − band, limit + 2 帧]` |
| R4 | 三臂的稳态修正幅度 | 除首次外平均 ≤ band + 1 ms |
| R5 | 每臂两轮 | 同一臂两轮之差 ≤ 3 次（可复现） |

R2 要写成绝对次数而不是百分比：15 次的 10% 是 1.5，但计数是整数，
用"极差 ≤ 4"才不会因为四舍五入把一次正常抖动判红。

### 顺带产出（不判红，但必须记）

同一批 6 轮会带出 `metrics.cpu`：**4K30 与 1080p30 的 CPU 占比差多少**。
P14-A 已经有过 4K60 vs 1080p60 的对照（18.57% → 19.53%），
本卡用 60 秒长片再验一次 —— 如果长片上 4K 的 CPU 反而更高，那 P14-A 的结论
只对 8 秒成立，得写清楚。

## 五、诚实清单（开工前）

1. **60 秒不是 2 小时。** 长片上"每秒一次 5 ms 修正"的累积效应仍然没测。
2. **`testsrc2` 是合成内容。** 真实影片的码率波动更大，解码耗时不均匀；
   本卡测的是"平均负载变了门会不会动"，不是"极端尖峰下会不会动"。
3. **4K 只测 30fps。** 4K60 的 60 秒片源编码成本太高，没做。
   所以"4K60 上结论同样成立"这句话本卡**证不了**，只能说 4K 这个自变量被单独验过。
4. **三臂的片源内容不完全相同**（同滤镜、不同分辨率/帧率，编码器行为不同）。
   如果要严格控内容，得用同一份母版下变换 —— 本卡用的是同一组 lavfi 参数，
   算"同一类内容"，不算"逐帧同源"。
5. **仍然只有 K40、只有 Debug 构建。**
