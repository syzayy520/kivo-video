# P13-C · 4K + 音频（验收：两个证据字段的 bug + 帧率才是变量）

- 版本：V1.0
- 日期：2026-10-30
- 上游：`60-p13b-status.md` §七（4K + 音频未测）
- 设计从简：目标单一（4K60 + 音频是否仍同步），代码改动只有两行赋值 + 一条跨字段检查
- **结论：4K 完全不影响音画同步；真正改变 `av_drift` 尾部的是帧率（30→60fps）。**
- 顺带修掉两个「证据字段恒错」的 bug —— 它们比 4K 的数据重要。

## 二、结论：分辨率不是变量，帧率才是

**4K60 与 1080p60 的 `av_drift` 几乎相同**（p99 都在 0.6–1.9 ms）。
所以「4K 会让音画同步变差」这个担心不成立 —— 4K 的解码负载没有传导到音频时钟。

**变的是帧率**：p99 从 30fps 的 0.125–0.375 ms 涨到 60fps 的 0.6–1.9 ms，约 4 倍。

合理的解释（是解释，不是结论）：`av_drift` 是在**每次 present 时采样**的。
60fps 的采样密度是 30fps 的两倍，采样越密越容易捉到抖动尾巴。
p50 始终是 0.125 ms（= 6 个 48kHz 采样，量化步长），说明**中位数没变，只是尾部被看得更清楚**。

**绝对值仍然安全**：即使最大的单次尖峰 20.6 ms，也只在 480 次采样里出现一次，
且人耳的音画不同步阈值约 20 ms —— 那是持续偏移的阈值，不是单帧尖峰。

> 这一条要说清楚：**我们不是在"4K 下仍达标"，而是在"4K 根本不构成负担"。**
> 后者是更强的话。

## 三、两个「证据字段恒错」的 bug（本卡的真正产出）

### bug 1：`audio.opened` 从未被赋值

`AvSyncStats` 有 `opened` / `started` 字段，渲染器一直在输出它们，
但 `AudioPlayback` **从来没往 `stats_` 里写过**。

后果：**15 份 sync 证据全部写着 `audio.opened: false`**，
而同一份证据里 `clock_source: audio_timestamp`、`av_drift.samples: 180`。
音频明明在跑，字段说没打开。

**为什么一直没被发现**：`false` 是一个看起来完全合理的值 ——
它不像 `null` 或 `-1` 那样刺眼，也不违反任何单字段判据。
这正是「恒错的字段」比「缺失的字段」更危险的地方。

### bug 2：`audio.started` 被 `stop()` 清掉

修好 `opened` 后，`started` 仍然全 false —— 因为证据是在 `stop()` **之后**采集的，
而 `stop()` 里把 `started_` 置回了 false。

**证据记的是"这一轮发生过什么"，不是"此刻的内部状态"。** 所以 `stats_.started`
在 stop 时不再复位，只有内部状态 `started_` 复位。

### 修法与防呆

| 层 | 改动 |
| --- | --- |
| `audio_playback.cxx` | `open()` 成功 → `stats_.opened = true`；`start()` 成功 → `stats_.started = true`；`stop()` **不清** `stats_.started` |
| `verify_p12_all.py` | 新增**跨字段一致性**检查：`clock_source == audio_timestamp` 或 `av_drift.samples > 0` 时，`audio.opened` 与 `audio.started` 必须都为 true |

**为什么必须是跨字段检查**：单看 `audio.opened=false` 完全合法（真的没开音频的情况存在）。
只有把它和 `clock_source=audio_timestamp` 放在一起，矛盾才显现。
**这一类 bug 在设计判据时就要想"哪个字段能当证人"。**

## 五、诚实清单（五条）

1. **`surface_at_time` 下 `av_drift` 不可测**（C8 的既有结论，不是本卡引入）。
   真实路径的同步只能靠「零丢帧 + 零 xrun + 音频时钟为主」间接证明。
   **想测 drift 必须退回 `cpu_paced`，那时就不走零拷贝直出了。**
2. **只有 8 秒片源**。长片（>1 min）的 drift 趋势未测 —— 累积误差是另一类问题。
3. **只用了合成正弦音（440 Hz）**。真实音乐/对白对时钟抖动更敏感？未验证。
4. **`max` 出现过 20.6 ms 的单次尖峰**（4k60-cpu-r2）。480 次采样里一次，
   判断为偶发调度抖动，但没有抓到原因（未采 logcat 调度信息）。
5. **`cpu_paced` 与 `surface_at_time` 是两条路径**。它们的 `av_drift` 不能互相引用 ——
   前者有 CPU 睡眠参与，后者交给合成器定时。

## 六、下一步

1. **长片 drift 趋势**（>1 min）：累积偏移比单帧尖峰更值得担心。
2. **低端机**：4K60 + 音频在低端 SoC 上是否仍零 xrun —— 这是最可能出问题的地方。
3. **`av_drift` 的采样语义**：现在每次 present 采一次，60fps 下密度翻倍，
   导致 p99 不可比。**建议按"每 N 帧采一次"固定采样率**，否则跨帧率的 p99 永远不可比。
   这条要单独立卡。
