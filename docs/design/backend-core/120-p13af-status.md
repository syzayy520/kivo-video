# 120 · P13-AF 验收：门不看分辨率，也不看帧率 —— 六轮全中同一个数

- 日期：2026-10-31
- 前置：`119-p13af-design.md`
- 结论：**三臂 × 两轮，全部 15 次触发，与预测的 15 次一字不差；三臂极差 = 0。**
  "门只看时钟"从推理变成证据。
- 顺带得到一组比 P14-A 更干净的双变量分解：**帧率 +37% CPU，4K 只 +5%。**

## 二、这条结论的形状

预测式 `expected = max(0, ⌊(ppm × T − limit) / band⌋ + 1)` 里**没有分辨率，也没有帧率**。
六轮把它验成了：**像素从 2.07 MP 到 8.29 MP（4×）、帧数从 1770 到 3570（2×），
触发次数一个都没动。**

这不是"差不多"，是**同一个整数**。所以：

> 门的判定只依赖 `(ppm, 时长, limit, band)` 四个量。
> 分辨率与帧率只改"解码要花多少 CPU"，不改"门什么时候动作"。

**为什么这条证据值钱**：AE 的四档 ppm 全跑在 360p30 上，当时只能说"推起来应该无关"。
现在有三个臂的实测，而"应该"两个字可以删了。

## 三、顺带：比 P14-A 更干净的 CPU 分解

| 臂 | 进程 CPU | 相对基线 |
| --- | --- | --- |
| A 1080p30 | **12.4%** | — |
| B 1080p60 | **17.0%** | **+37%** |
| C 4K30 | **13.0%** | **+5%** |

两个自变量被分离了：

- **帧率 +37%**：60fps 要做两倍的送包/收帧/上屏往返 —— 与 P12-B 的"每帧固定开销"
  结论完全一致（限制来自每帧的固定成本，不是像素吞吐）。
- **分辨率 +5%**：4 倍像素只换来 0.6 个百分点，硬解 + 零拷贝直出的直接结果。

同一批数据里还有一个附带确认：**稳态分配 303 次 / 60 s = 5.05 次/秒**，
三臂一模一样 —— 与 P14-B 的"5 次/秒在主线程、与帧率无关"第三次对上。

## 五、诚实清单（五条）

1. **4K 只测了 30fps。** 4K60 的 60 s 片源编码要十几分钟，没做。
   所以"4K60 上同样成立"本卡证不了 —— 只能说分辨率与帧率各自被单独验过。
2. **60 秒不是 2 小时。** 长片上每秒一次 5 ms 修正的累积效应仍未测。
3. **`testsrc2` 是合成内容**，码率平稳。真实影片的码率/解码耗时波动更大；
   本卡测的是"平均负载变了门会不会动"，不是"尖峰下会不会动"。
4. **三臂内容同类不同源**（同 lavfi 参数、不同分辨率/帧率）。不是逐帧同源下变换。
5. **只有 K40、只有 Debug 构建。** 换低端 SoC 后 CPU 占比会变，
   但"触发次数不变"这条应当仍然成立 —— 因为它是纯时钟逻辑，不是负载逻辑。
   **这条是推理，没有第二台机器验过。**
