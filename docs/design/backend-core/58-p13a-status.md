## 一、实测结果（K40 / SM8250 / Android 13，2400×1080 屏）

| 片源 | 分辨率 | 位深 | 码率 | 帧数（收/上屏/丢） | fps | 实时比 | 首帧 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `p13a_1080p60_hevc50m` | 1920×1080 | 8 | **46.7 Mbps** | 301 / 300 / **0** | 60.2 | 1.00 | **47.0 ms** |
| `p13a_4k60_hevc8` | 3840×2160 | 8 | 23.0 Mbps | 301 / 300 / **0** | 60.0 | 1.00 | 66.3 ms |
| `p13a_4k60_hevc10` | 3840×2160 | **10** | 25.4 Mbps | 301 / 300 / **0** | 59.2 | 0.99 | **132.5 ms** |
| `p13a_4k60_avc8` | 3840×2160 | 8 | 16.8 Mbps | 301 / 300 / **0** | 59.4 | 0.99 | 115.9 ms |

四组全部 `frames_dropped_late = 0`、`catch_up_frames = 0`、`completed = true`。
10bit 组的 `color.source_is_10bit = true` —— 位深确实进了解码器，不是把 10bit 当 8bit 播。

## 二、三个结论（每一条都和此前的假设不同）

### 1. 4K60 AVC 的"5% 余量"是保守的

能力表说 `avc_4k60 → best_fps = 63`（`63 / 60 = 1.05`），我在 P13-A 设计里把它列为
"最可能暴露真实上限的高压组"。

实测：**59.4 fps、0.99× 实时、零丢帧**。

也就是说 `achievableFrameRatesFor` 给的是一个**保守下界**，不是精确值。
这条要记进方法论：**厂商声明的"可达帧率"偏低，别拿它当上限判死。**

### 2. 10bit 4K60 没有代价

设计里我写过一句警示：

> API 是 per-codec，不是 per-profile —— 10bit 和 8bit 报同一个 149fps，
> 这恰恰说明这个数字**没考虑位深**。所以 10bit 4K60 必须单独实测。

实测：**59.2 fps、零丢帧**。这台设备上，10bit 与 8bit 的代价小到测不出来。

**但结论只到"这台设备"为止。** `getSupportedFrameRatesFor` 不区分 profile 这件事仍然成立，
换一颗 SoC 完全可能 8bit 跑 60、10bit 掉到 30。所以这套测法要保留。

### 3. 首帧时延随分辨率明显上升（**这是冷启动，不是 seek**）

| 分辨率 | 冷启动首帧 |
| --- | --- |
| 1080p60 | **47.0 ms** |
| 4K60 HEVC 8bit | 66.3 ms |
| 4K60 AVC | 115.9 ms |
| 4K60 HEVC 10bit | **132.5 ms** |

> **更正（P13-B）**：我在这里写过"150 ms 的预算在 4K 上会不够"，那是错的，错了两层：
> 1. 这些数字是**冷启动**（`open()` 后第一次 `start()`，要建组件、配 Surface），
>    而 G8 的 150 ms 判的是**seek 后首帧**（codec 已热，只 flush）。实测 4K 的 seek 是 **27.7–41.7 ms**；
> 2. 就算按 150 ms 判冷启动，**132.5 ms 也没超** —— 真实的说法是余量从 3.2× 缩到 1.13×。
>
> 结论修订：G8 需要**按场景拆成两条**（冷启动 200 ms / seek 150 ms），
> 而不是"4K 需要更宽的 seek 预算"。详见 `59-p13b-design.md`。

## 四、一个活了 6 张卡的 bug（比 4K 结论更重要）

**现象**：播 4K 时读 `source.width` 抛 `KeyError`。

**根因**：`decode_stats_renderer` 里有两个 `"source"` 键。

- 原有：`"source": {mime, width, height, duration_us}`（P12-B 起就有）
- 我在 **P12-F3B** 加加密事实时，另起了 `"source": {encryption: {...}}`

JSON 允许重复键，解析器取**后者** —— 于是 `source.mime/width/height/duration_us`
被整个吞掉，而文件看上去完全正常。

**为什么 6 张卡没发现**：

1. E2–F3 那几张卡读的是 `color.source_mime`，不是 `source.mime` —— 恰好绕开了；
2. 总收口层 2 没有检查 `source.mime`；
3. 直到 P13-A 要按分辨率分类，才第一次读 `source.width`。

**修法**：

1. renderer 里 encryption 嵌进原有 `source` 段（现在只有一个 `source` 键）；
2. **总收口层 1 加了重复键检查**（`object_pairs_hook`，Python 默认不报）；
3. 自检加了一个**文本层**变异 —— 注意：dict 里同名赋值只是覆盖，
   **重复键只能在 JSON 文本层构造**，用 dict 做变异会得到一个假通过的自检（我第一次就这么错了，
   自检从 9 变成 8 才发现）。

**教训（进家族树）**：证据里新增段落前，先 `grep` 这个键有没有被用过。
一个 `grep -c '"source"'` 就能发现的事，让一个字段静默丢了 6 张卡。

## 五、诚实清单（六条）

1. **只有一台设备**（K40 / SM8250）。所有 4K 结论的适用范围就是这一颗 SoC。
2. **屏幕是 2400×1080**，4K 片源必然被 Surface 缩放。测的是**解码 + 缩放上屏**，
   不是 4K 原生输出。
3. **每组只跑了 1 轮**（5 秒片源）。P12 里那些"3 轮以上"的稳定性结论，
   这里还没做 —— 要补 3 轮才能说"稳定"。
4. **片源是合成图案（`testsrc2`）**，不是真实视频。真实内容的码率分布更不均匀，
   峰值可能更高。46.7 Mbps 是 CBR 近似，不是 VBR 尖峰。
5. **没有测音频 + 4K 同时**。4K 视频 + 音频时钟的组合是新场景。
6. **能力探测（`p13a-framerate`）是声明值**，本卡的真播数据才是实测值。两者要分开引用。

## 六、下一步（按优先级）

1. **4K 下的 seek 预算**（§二 第 3 条）：这是唯一一个被本卡"证伪"的既有结论 ——
   150 ms 在 4K 上不够。要么分级，要么拆出口径。
2. **4K + 音频**：`av_drift` 在 4K 上是否仍然 0.125–0.375 ms 量级？
3. **4K 稳定性轮次**：每规格补到 3 轮，才能说"稳定"。
4. **真实内容片源**：合成图案的码率分布太理想。
