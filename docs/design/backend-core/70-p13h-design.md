# P13-H 设计：两个口径的一次除法 —— 102.4 秒之后 `observed_hz` 会自己涨

> 前序：`69-p13g-status.md` §七.2 记着一条欠账：「`span` 是序列窗口首末差，
> `accepted` 是累计，超过 2048 点 / 20 Hz 之后两者不同源」。本卡去验这句话，
> 发现它不是"精度问题"，是**一条会自己长数的错误证据**。

---

## 一、缺陷

`av_sync_report.cxx` 里这一句：

```cpp
const double observed_hz =
    (pace.drift.span_ns > 0)
        ? static_cast<double>(pace.sampled_samples) * 1e9 /
              static_cast<double>(pace.drift.span_ns)
        : 0.0;
```

- 分子 `sampled_samples` = `DriftSeries::total_`，**全场累计**，只增不减，
  环形覆盖之后仍然继续涨。
- 分母 `drift.span_ns` = `at(n-1).media_ns - at(0).media_ns`，
  `n = size() ≤ kCapacity = 2048`，**窗口**跨度，封顶 2047 × 50 ms = 102.35 s。

8 秒片源上两者同源，所以数字对。超过 102.4 秒之后，分子继续涨、分母钉死：

| 播放时长 | accepted（≈20 Hz） | span | `observed_hz` 报出 |
|---|---|---|---|
| 8 s | 160 | 7.95 s | 20.126 |
| 35 s | 700 | 34.97 s | 20.019 |
| 130 s | ≈2600 | 102.35 s | **≈25.4** |
| 600 s | ≈12000 | 102.35 s | **≈117** |

这是一个**没有任何上界**的数。而它旁边的 `target_hz` 写着 20 —— 一份
"实际节奏 117 Hz / 目标 20 Hz"的证据不会让人怀疑数据，只会让人怀疑抽稀门写错了。

### 为什么一直没人抓到

两层原因叠在一起，缺一层都不会漏这么久。

**① 取证的长度不够。** 全部 27 份真机证据都是 8 s 或 35 s 的片源，
`truncated` 恒为 false，两根尺子恰好等长。缺陷只存在于**没人跑过的时长**里。

**② 校验器复算的是同一个公式。**

```python
expected_hz = accepted * 1e9 / span      # span 取的是 trend.span_ns
```

它验的是"报告写没写对算式"，不是"分子分母是不是同一个作用域"。
算式一字不差地照抄过来，于是两边一起错、一起通过。
**复算公式只能证明算术没打错，不能证明量纲对。** 这是本卡最值得记的一条。

---

## 二、能抓住它的不变量

`observed_hz` 不该用"复算同一个除法"来验，该用**机制本身**来验。

抽稀门的接受规则（`pace_drift_series.cxx:7-65`）是确定的：

1. 首帧无条件接受 → `+1`；
2. 其后每次接受都要求 `media_ns ≥ next_due_ns_`，而接受后
   `next_due_ns_` 被推到**严格大于**该帧媒体时刻的下一个格点；
3. 没有帧跨过的格点不补样本，只累加 `unobserved_`。

于是整场会话（`segments == 1`）恒有：

```
accepted + unobserved_cells == floor(media_span / interval) + 1
```

**这个等式是精确的，不是"大约"。** 用 27 份现有真机证据核对，
余量全部为 **0**：

| 片源 | accepted | span | floor(span/50ms)+1 | 余量 |
|---|---|---|---|---|
| 8 s（20 份） | 160 | 7.950 s | 160 | 0 |
| 8 s 30fps（3 份） | 160 | 7.967 s | 160 | 0 |
| 35 s（3 份） | 700 | 34.967 s | 700 | 0 |

左边是"接受数 + 空格数"，右边是"媒体时间跨过多少个格点"。
左边涨了右边没涨，只有一种解释：**两边的媒体时间不是同一段**。

这正是本缺陷的形状。130 秒那一轮：左边 2600，右边 `floor(102.35/0.05)+1 = 2048`
—— 差 552，一眼可见。

所以要补的不是"更准的除法"，是**一条把分子和分母绑在同一段时间上的判据**。

## 三、改法

### 3.1 让 `DriftSeries` 自己给出累计跨度

现在没有任何一处知道"整场媒体时间跨了多久" —— 序列只留最近 102.4 s，
`total_` 又只是个数。补一个累计量，按**段**累加：

```cpp
[[nodiscard]] std::int64_t media_span_ns() const noexcept;
```

- 段内：`最后被接受的帧 - segment_first_media_ns_`（实时可变）；
- 段结束时（seek / `clear()`）：把该段跨度折进 `closed_span_ns_`，段内重新起算。

**"最后被接受的帧"，不是"最后观察到的帧"。** 两者差的是尾部被抽稀门拒掉的那几帧。
用后者会让累计跨度比窗口跨度大不到一帧 —— 两根尺子差一点点，比差很多更难发现。
这一条是被单测 `t04` 打出来的：第一版实现用的就是 `last_media_ns_`（观察值），当场红。

为什么按段累加而不是 `末帧 - 首帧`：seek 之后媒体时刻倒退，
`末 - 首` 会得到一个负数或一个把两段误差算进去的假跨度。
按段累加是"每段各算各的，再加起来"—— 这才是 `total_ / span` 的正确分母，
因为 `total_` 也是每段各算各的再加起来。

### 3.2 分子分母放进同一格

JSON 的 `sampling` 里，`media_span_ns` 紧跟在 `accepted` 后面：

```json
"accepted": 2600,
"media_span_ns": 129950000000,
"observed_hz": 20.008,
```

**相邻不是排版偏好，是防腐。** 读者要算这个除法，两个操作数就在眼皮底下，
不可能一个取累计、一个取窗口。`trend.span_ns` 保持窗口口径不变 ——
它回答的是另一个问题（"这段回归用的是多长的时间"），两者名字不同、位置不同。

### 3.3 结构门也换成累计跨度

`decimated_block_is_usable(accepted, span)` 现在收的是窗口跨度。
它问的是"媒体时间在这批样本上有没有推进"—— 这是**整场**问题，
换成 `media_span_ns`。8 秒片源上两者相等，所以已有行为一字不变。

### 3.4 schema 升 `/6`

`media_span_ns` 是新增字段，且 `/3`–`/5` 的 `observed_hz` 语义不同
（那三版的分母是窗口跨度，只是那些证据没有触发覆盖，所以碰巧对）。
不重写旧证据 —— 重写等于伪造。旧版按旧判据读，H 判据只对 `/6` 成立。

## 四、判据 H1–H4

| 编号 | 判据 | 它抓什么 |
|---|---|---|
| **H0** | `sampling.media_span_ns` 必须在 | 缺了它，读者又要去别处找分母 |
| **H1** | `accepted + unobserved == floor(media_span/interval) + 1`（`segments == 1`，精确相等）；多段时降为 `<= floor(...) + segments` | 分子分母不同源。**本卡的全部意义** |
| **H2** | `observed_hz ≤ 1e9/interval + 1e9/media_span` | 节奏超过格点目标速度。H1 的速率表述 |
| **H3** | `truncated == false ⇒ media_span == trend.span_ns`；`truncated == true ⇒ media_span > trend.span_ns > 0` | 两根尺子该等长时不等长（累计没实现 / 实现成窗口） |
| **H4** | `accepted == 0 ⇒ media_span == 0 ∧ observed_hz == 0` | 零样本却量到跨度 |

H1 在单段时是**恒等式**，多段时只能给上界：每段各有一个 "+1"（首帧无条件接受），
而 `floor(a) + floor(b) ≤ floor(a+b)`，求和后保证不了相等。
证据里没有分段明细，硬要等式会产出假红 —— 假红比漏报更快地训练人忽略告警。
（设计初稿写的是"多段报不适用"，实现改成了上界：宁可给一条弱判据，
也不留一个"跳过"的洞 —— 跳过和通过在校验器输出里长得一样。）

H1 与本缺陷的关系要说清：**它不是为这个缺陷量身写的**。
它是抽稀门的接受规则本身蕴含的等式，任何一处把"接受数"和"媒体时间"
算到不同段上，它都会红。本缺陷恰好是第一个撞上来的。

## 五、取证

缺陷只在 > 102.4 s 时出现，而设备上最长的片源是 35 s。需要造一份：

`p13h_360p30_130s_av.mp4` —— 640×360 / 30 fps / H.264 8 bit + AAC。
选 360p 不是偷懒：解码要足够便宜，这样这一轮量到的是**抽稀门的节奏**，
不是"4K 播不动"。130 s × 20 Hz = 2600 点 > 2048，必定触发覆盖。

取证要同时看到两件事：

1. `truncated == true`（覆盖真的发生了，否则等于什么都没验到）；
2. `accepted + unobserved == floor(media_span/interval) + 1` 成立 ——
   而**同一个文件**若把分母换回 `trend.span_ns`，等式差 552。

第 2 条是本卡的证明方式：不是"改完没红"，是"同一份数据，旧尺子红、新尺子绿"。

## 六、诚实边界（先写明）

1. **改的是口径，不是抽稀门。** 接受规则一个字没动，`accepted` 仍是真值。
   变的只是那个除法拿谁做分母。
2. **`observed_hz` 从来不是精度问题。** 8 秒片源上旧值和新值逐位相同，
   所以本卡不会让任何一张旧表变好看或变难看。
3. **多段（seek）只有单元测试覆盖。** 真机上没有造 seek 取证，
   `media_span_ns` 在 `segments > 1` 时是"各段跨度之和"，这个行为靠单测钉住。
4. **仍然只有一把 7 ppm 的尺子。** 漂移量准的上限没动。
5. **H1 是恒等式，不是容差判据。** 一旦哪天抽稀门的规则变了（比如补采空格），
   它会红 —— 那时该改的是等式，不是把判据放宽。
