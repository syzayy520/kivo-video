# 80 · P13-M 设计：段边界的权威是锚点重建，不是 pts 的走向

> 卡片：P13-M
> 前置：P13-L（`78-p13l-design.md`）在真机上撞出一份 `segments = 1` 的缺陷证据
> 结论：`segments` 的判据从"pts 倒退"改成"锚点重建"（事件驱动，无阈值）；
> 段内真空洞不切段，改为出版 `segment_largest_gap_cells` / `segment_contiguous`
> schema：`kivo.p12c.sync/10` → `/11`

---

## 一、问题

### 1.1 那份证据说了什么

P13-L 第一次跑"向前 seek"轮（30 s 处跳到 40 s）时，报告写出：

| 字段 | 值 | 实际 |
|---|---|---|
| `segments` | `1` | 两段 |
| `span_ns` | 112 366 666 000（112.367 s） | 两段各 30 s / 82 s |
| `segment_accepted` | `2400` | 120 s × 20 Hz ✓ |
| `truncated` | `true` | 段内 2400 > 2048 ✓（这条是对的） |
| `observed_hz` | `18.466` | 应为 20.0 |
| `media_span_ns` | 129 966 666 000 | 实际走过的只有 120 s |
| `unobserved_cells` | `200` | 那 200 格就是被跳过的 10 秒 |

`segments = 1` 是**假的**。而它一旦是假的，后面三个数跟着错：
`span_ns` 把两段之间的十秒空白算进去了，于是 `media_span` 多算 10 s、
`observed_hz` 的商被压低到 18.47 —— 报告上一个"采样不足"的告警，实际
一个格点都没漏采。

### 1.2 根因不是阈值，是信号

上一版的判据只有一条：

```cpp
} else if (media_ns < last_media_ns_) {   // 媒体时刻倒退 = 换了时间轴
```

这条判据本身**没错**：pts 倒退必然意味着时间轴变了，那是充分条件。
错的是它的使用方式 —— 代码拿它当**充要**条件用：没倒退 ⇒ 同一段。

而 pts 的走向只在一个方向上携带信息：

| pts 相对上一帧 | 能推出什么 | 推不出什么 |
|---|---|---|
| 倒退 | 换了时间轴（必真） | —— |
| 前进 | **什么也推不出** | "没换时间轴" |

向前 seek 就是"前进且换了时间轴"。用存在性（倒退）去证明不存在性
（没换时间轴），必然漏一次。

### 1.3 为什么"加个阈值"是错的解法

第一反应是：向前跳超过 N 秒就切段。这个解法有两个问题，第二个是致命的。

1. **阈值没有根据**。为什么是 5 s 不是 3 s 不是 10 s？任何取值都会被问。
2. **它把"卡顿"和"向前 seek"混为一谈，而这两件事的正确处理相反。**

   - 真卡顿：播放器冻了 10 秒，然后从原处继续。时间轴**没换**，锚点**没换**。
     卡顿之前采到的那些点是**真数据**，回归它们是有意义的。切段会把它们
     全部作废（`clear()` 清环形），那是拿真数据赔一个告警。
   - 向前 seek：时间轴换了，`lateness = present_at − due_at` 的零点换了。
     卡顿之前的点与之后的点**不属于同一个零点**，拼在一起拟合出来的是
     "两个零点之间的跳变"，不是速率差。

   两者在 pts 上长得**一模一样**（都是"媒体时间前进了一大截"）。
   于是任何基于 pts 的判据都不可能同时做对这两件事。

### 1.4 那件事其实有人知道

`DecodeSession::seek_to()` → `begin_run()` → `pacer_->reset()`。
`reset()` 里第一行就是 `tracker_.reset()` —— **锚点被销毁**。

也就是说，"换了一条时间轴"这个事实在系统里是**有权威记录的**，
只是漂移序列没被告知。P13-L 那份证据的注释里写着
"`clear()` 顺手关掉旧段"，而那个 `clear()` 从来没在 seek 时被调用过 ——
它只在 `note()` 自己"看出"倒退时才触发。

所以本卡不需要发明判据，只需要**把已有的那个事实接上**。

## 二、做法

### 2.1 `segments` 的定义收窄成"锚点生命周期"

```
一段 = 一次 FramePacer::reset() 到下一次
```

理由是一条定义链：

1. `lateness = present_at − due_at`；
2. `due_at` 由锚点定义（`due = mono + (pts − anchor_pts − elapsed)`）；
3. 锚点重建 ⇒ 同一个 `lateness` 数值代表的**不再是同一个东西**；
4. 跨过这一刻的回归，拟合的是"两个零点之间的截距跳变 + 速率差"，
   而读者要的只有速率差。

第 4 条正是 `slope_halves_agree` 那个诊断想抓的东西 —— 但它只看符号，
分不出"持续漂移"与"中途换向"。切段比诊断更彻底：不让两种东西进同一锅。

这条定义**没有阈值**，因为它是事件驱动的。

### 2.2 三个新接口，一条接线

```cpp
// pace_drift_series.hpp
void break_segment() noexcept;                       // 关段 + 清环形 + segments_++
std::int32_t largest_gap_cells() const noexcept;     // 段内最宽空洞（格点）
bool contiguous() const noexcept;                     // ≤ kMaxContiguousGapCells

// pace_stats.hpp
void note_anchor_reset() noexcept;                   // 转发到 drift_.break_segment()

// frame_pacer.cxx —— 整张卡就是这一行
void FramePacer::reset() noexcept {
    tracker_.reset();
    stats_.note_anchor_reset();      // ← P13-M
    ...
}
```

为什么接在 `FramePacer::reset()` 而不是 `DecodeSession::seek_to()`：
`begin_run()` 是本类唯一的起跑入口，`start()` / `seek_to()` /
`resume_after_seek()` 三条路都走它。三个调用点各写一次，迟早漏一处，
而漏的那一处不会有任何判据报红。

### 2.3 `break_segment()` 在空会话上是空操作

每个会话的 `start()` 都会走一次 `reset()`。若那里无条件 `segments_++`，
**每一份证据都会从 `segments = 2` 起步** —— 一个恒真的告警，
读者只会学会忽略它（这正是 F2/H1/H2 那几条判据反复栽过的形状）。

所以判据是"有东西可关"，不是"调用过函数"：

```cpp
if (!has_last_) return;
clear();      // 内部先 close_segment() 再清环形
++segments_;
```

### 2.4 段内真空洞：不切段，但要出版

切段解决不了卡顿（切了会丢真数据），所以段内空洞只能**忍着**。
但"忍着"不等于"不说"：`span_ns` 是"末 − 首"，空洞落在里面，
于是 `slope_ppm × span` 的累积量与 `observed_hz` 都会偏。

两个字段把它说出来：

| 字段 | 含义 |
|---|---|
| `segment_largest_gap_cells` | 段内相邻两个被接受样本之间最宽的空洞，单位格点（50 ms） |
| `segment_contiguous` | 该值 ≤ 20 |

**为什么是 `max` 而不是累加**：回归的可信度取决于最宽的那个洞。十个
100 ms 的小洞不会让一条直线失去意义，一个 10 s 的大洞会。累计值
（`unobserved_cells`）答不出这个。

**为什么阈值是 20 格 = 1 s**：20 Hz 抽样下 20 格意味着至少 24 个连续帧
一个样本都没进来（任何 ≥ 24 fps 的片源都会跨过 24 个格点）。帧级抖动
到不了这个量级 —— 30 fps 掉一帧是 33 ms，掉三帧（100 ms）才凑够**一格**。
能连续丢掉二十多个帧的只有卡顿或时间轴跳变。

**这个字段不触发任何判定**。它只回答"这条直线横跨了多宽的一个洞"，
让读者知道 `span_ns` 里含着一个洞。要不要因此打折看，是读者的事。

### 2.5 保持不变的两件事

1. **pts 倒退仍然切段**（兜底）。倒退是充分条件，它永远成立；而且
   单测与将来的调用方可能根本没有 pacer。`note()` 里那条分支改成调
   `break_segment()`，行为不变。
2. **`clear()` 不计数**。它是"整段重来"（换片源），不是"时间轴变了"。
   这一点没动 —— 但它在生产路径上没有调用方，只有单测用。

### 2.6 与 P13-D 抽稀门的关系

`note()` 的三条接受理由一条没动。特别是 ①（首帧必采）：切段之后
`has_last_ == false`，下一帧无条件进序列 —— 所以 seek 之后头几帧一定
有样本，而那几帧恰好是"新锚点稳不稳"最该看的地方。

## 三、判据 M0–M4

校验器**无法**从 JSON 判断"这个 `segments` 是不是漏切了"（它没有 pts 序列）。
能做的是把这件事的**痕迹**变成可核对的结构。

| 判据 | 内容 | 它抓什么 |
|---|---|---|
| M0 | 三字段齐全 | 报告层没跟上 schema |
| M1 | `contiguous ⟺ gap ≤ 20` | 布尔与格数各算各的（阈值在 Python 侧独立写死） |
| M2 | `gap ≤ floor(span/interval)` | **单位守卫**：格点误写成纳秒会立刻越界 |
| M3 | `gap ≤ unobserved_cells` | **记账守卫**：切段时清了最大值却漏了累计 |
| M4 | 单段时 `gap > 0 ⟺ unobserved > 0` | **接线守卫**：只有一段时两者必须同零或同正 |

M4 在多段时降成"不适用"：前面几段的空格也算进累计，那时 `gap == 0`
而 `unobserved > 0` 是**正常**的（最后一段一个洞都没有）。

## 四、变异自测计划

| # | 变异 | 预期 |
|---|---|---|
| C1 | 删掉 `FramePacer::reset()` 里的 `note_anchor_reset()` | m12 红 |
| C2 | `break_segment()` 去掉 `if (!has_last_) return;` | m01 / m08 红 |
| C3 | `break_segment()` 里去掉 `clear()` | m02 / m03 红 |
| C4 | `break_segment()` 里去掉 `++segments_` | m03 / m12 红 |
| C5 | `clear()` 里不清 `largest_gap_cells_` | m06 / m11 红 |
| C6 | `largest_gap_cells_` 改成累加而非取 max | **m14** 红（max 5 / 累加 8） |
| C7 | `contiguous()` 改成 `<` 而不是 `<=` | m05 红 |
| C8 | `note()` 的倒退分支改回 `clear(); ++segments_;`（不走 `break_segment`） | 应**仍绿**（等价重构） |
| C9 | `summary()` 里 `contiguous` 恒定 true | m11 红 |
| C10 | `summarize_drift` 里 `segment_largest_gap_cells` 不接线（恒 0） | m13 红 |
| C11 | `media_span_ns()` 只算最后一段（丢掉 `closed_span_ns_`） | m02 / m07 红 |
| C12 | 倒退兜底不再切段（`clear()` 但不 `++segments_`） | m09 红 |

C11 原计划写"改回末 − 首"，但那个表达式在本类里**不存在** ——
`closed_span_ns_` 已经按段累加了，旧的"跨段相减"写法没有留下可改的锚点。
改成"只算最后一段"，是同一类错误的另一种形态（也是更容易犯的一种）。

C8 是"应仍绿"的一条：它验证的是等价重构，不是行为。把它写进来是为了
证明其余十条的红**不是**因为测试对实现细节过敏。

## 五、不做的事

1. **不给"向前跳"加阈值切段。** 理由见 §1.3：卡顿与向前 seek 在 pts 上
   不可区分，而两者的正确处理相反。
2. **不改 `media_span_ns()` / `observed_hz` 的洞口径。** 段内真空洞时
   这两个数仍把洞算进去 —— 已经用 `contiguous` 标出来了。真要在公式里
   减掉，得先解决"低帧率片源每个格点都空一半"的问题（`unobserved_cells`
   目前把"帧率低"和"播放卡住"混在一起），那是另一张卡。
3. **不给 `segment_contiguous == false` 就判 `usable = false`。** 一个
   2 秒的卡顿不该让一条 90 秒的回归失去资格。出版，不判定。
4. **不改 `PaceSummary` 的其余字段**，不动任何直方图。

## 六、诚实清单（设计期）

1. `segments` 的语义变了，而且**同名不同义**。旧证据（`/10` 及以前）的
   `segments` 是"pts 倒退次数 + 1"，新证据是"锚点重建次数 + 1"。
   两者在真 seek 上一致，在"停再起"上不一致。这一条必须写进状态卡，
   并且**不能**回头重写旧证据。
2. `segment_contiguous` 在写这份设计稿时**没有任何真机观测**：43 份历史证据里
   `unobserved_cells` 非零的只有 1 份（2 格 = 100 ms），远低于 20 格阈值。
   计划用 `kill -STOP` 冻 2 秒制造一次 —— **后来做到了**，见
   `81-p13m-status.md` §三之一：空洞 45 格、`contiguous = false`、xrun 1。
   但那是人为冻结，自然播放里仍然一份都没有。
3. `kMaxContiguousGapCells = 20` 是**论证出来的**（≥24 帧无样本），
   不是测出来的。没有一份证据落在边界附近，所以这个数没有被数据检验过。
4. 段内空洞让 `media_span` / `observed_hz` 偏的事实**依然存在**，
   本卡只是让它可见。`contiguous == false` 时那两个数不能当"走过的时长"读。
5. `break_segment()` 在 `stop()` 之后再 `start()` 时也会触发，于是
   `segments` 会把"暂停再继续"算成一次切段。这是**刻意的**（锚点确实重建了），
   但会让"`segments - 1` = seek 次数"这个等式在暂停过的会话上不成立。
6. 向前 seek 的落点若**恰好**与上一帧的 pts 相接（跳 0 秒），`segments`
   会 +1 而数据上什么也没断。这种情形下多算一段是保守的（宁可少拟合
   一段，也不要跨零点），但它确实是一个"多余"的段。
