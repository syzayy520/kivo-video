# P16-P1B18 · 「速率伺服」在当前架构下可行吗？

- 日期：2026-11-06
- 定位：`183` §七 Q1 问"该不该改成 PLL/伺服式时钟恢复"。本卡不猜设计意图，
  只查**架构上有没有落点**。门闸：构思 → 查证 → 结论 → 边界。
- 上位：`183` §四 方案 B、`197`（门追不上）、`198`（调 band 修不完）。
- 工作目录 `C:\kivo video`；`F:\kivo` **只读**；**零代码改动**。

---

## 一、问题

`197`/`198` 已经证明：位置复位（bang-bang）在持续频差下追不上，调 `band` 只能缓解。
自然的下一步是"改速率而不是改位置"。但**视频侧的速率到底在哪调**？本卡查这个。

---

## 二、查证：视频侧有没有独立的速率入口

`frame_pacer.cxx:89-92`（正常分支）：

```cpp
const std::int64_t media_delta_ns =
    pts_ns - tracker_.anchor_pts_ns() - reading.elapsed_ns;
due_at_ns = reading.mono_ns + media_delta_ns;
```

`elapsed_ns` 来自 `ClockPositionTracker::Reading`，而它是
`position_ns_ - anchor_position_ns_`（`clock_position_tracker.cxx:252`）——
**就是音频钟的已播时间**。

所以 `due_at` 完全由音频钟决定：**视频没有独立的播放速率**。
要让视频"慢一点"去抵消音频钟快 0.2%，只能让 `elapsed` 增长变慢 ——
而 `elapsed` 就是音频钟本身。

### 改音频时钟的两条路

| 路径 | 手段 | 现状 |
| --- | --- | --- |
| A 位置钳制 | 周期性把 `position_ns_` 减一截（现有漂移门） | 已实现，`197` 证明追不上 |
| B 改音频输出速率 | 重采样（把 48 kHz 数据按 47.9 kHz 消费）或运行时改采样率 | **两条都不可用**，见下 |

**为什么 B 不可用**：

1. `AAudio` 的采样率只能在 builder 阶段设定（`AAudioStreamBuilder_setSampleRate`），
   **没有运行时改速率的接口**；
2. 项目明确不做重采样 —— `audio_playback.cxx:101-115` 对"协商采样率 ≠ 片源采样率"
   直接拒绝，注释写着"resampling is intentionally not implemented"。

---

## 三、结论

**在当前架构下，"速率伺服"没有落点。**

不是"门的设计不好"，而是：视频的 `due_at` 已经严格跟着音频钟，
而音频钟只能"改位置"（钳制）或"改输出速率"（重采样）。
后者被架构明确排除，所以**相位钳制是唯一可行的手段**。

`197` 的"门追不上"因此不是调参问题，是**架构没有速率维度**的必然结果。

### 如果将来要做速率伺服，前置条件是

| 方案 | 代价 | 风险 |
| --- | --- | --- |
| 引入 `libswresample` 做 48k → 47.9k 微重采样 | 新增依赖 + 每帧转换成本 | 音质、延迟、xrun 都要重测 |
| 用 `AAudio` 的 `setBufferSize` / 重启流近似变速 | 不能真正改速率 | 会有间隙，等于 seek |
| 接受频差，只做相位钳制（现状） | 35 s 累积 ≤ 70 ms（2000 ppm） | 大频差下画面周期性跳 5–40 ms |

所以 Q1 的真正问题不是"要不要 PLL"，而是"**要不要为音频重采样付代价**"。
那是一个架构决策，不是控制律调整。

## 四、更正（P1B19）：B 方案的代价比初版判断低

初版写"B 方案两条都不可用"，**这句过重，本卡更正**。查依赖后的实际事实：

| 事实 | 证据 |
| --- | --- |
| **Android APK 里没有 FFmpeg** | `android/app/src/main/cpp/CMakeLists.txt` 对 `ffmpeg/swresample/avcodec` **零引用** |
| 桌面构建才有 FFmpeg | `backend/CMakeLists.txt:1` `option(KIVO_ENABLE_FFMPEG ... OFF)`；`:119` 链接 `swresample swscale`，仅在 `FFMPEG_ROOT` 设置且开关 ON 时 |
| 有 FFmpeg 音频解码后端，但没进 APK | `backend/src/video/audio_plane/decode/ffmpeg/**` 不在 Android 清单里 |

所以：

- "引入 FFmpeg 做重采样"确实是重活（交叉编译 + APK 体积 + 授权），**不可取**；
- 但 **0.2% 的微调根本不需要 FFmpeg**：线性插值或"每 500 个样本均匀丢 1 个"即可，
  约 **100 行**，0.2% 量级的音质影响可忽略；
- 因此 B 方案的真实代价不是"引入 FFmpeg"，而是**"写一个微调重采样器 + 重测 G7/xrun/音质"**。

结论修正为：**速率伺服在架构上可行，代价中等**（~100 行 + 一轮完整回归），
不是"没有落点"。是否需要付这个代价，仍是产品判断，但至少不是"必须背 FFmpeg"。

## 四之二、再更正（P1B22 实验证伪）

`200` 的内核接进 `AudioPlayback` 后做了对照实验（注入 2000 ppm + trim 0/2000）：
**`phase_error` 两组都是 65.8 ms，trim 完全无效。**

原因：`phase_error` 读的是 **AAudio 设备 timestamp**，微调输出样本数只改"送出去的内容"，
**不改设备播放位置**。设备仍按自己的晶振走。

所以：

- 上面"B 方案可行、~100 行"的更正**是错的**；
- **初版判断（"没有落点"）才是对的** —— 但理由要换成"时钟来自设备 timestamp，
  重采样改不了它"，而不是"AAudio 没有接口"；
- 要真正改音频时钟，只能改采样率并**重建流**（会有间隙，P12-F2A 明确不重建）。

`200` 的内核作为"变速播放"的底层仍然可用，但**不能解决 A1**。
