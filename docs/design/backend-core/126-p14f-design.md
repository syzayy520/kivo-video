# 126 · P14-F 设计：时钟异常的**出现率**（P14-D 只证明"发生过一次"）

- 日期：2026-10-31
- 前置：`124-p14d-status.md` §三（30 分钟 1 次跳变）、`125-p14e-status.md`（仪器已就绪）
- 目标：用**多轮短会话**换分母，把"发生过"变成"多久一次、什么形状"

---

## 一、为什么不是"连跑 4 轮 30 分钟"

那要 2 小时设备时间，而且**一轮只贡献一个分子**。
更有信息量的做法是反过来：**缩短单轮、拉长轮数**。

先看已有数据的量级：P13-AE 的 8 轮（每轮 2–3 分钟）里有 2 轮出现
`monotonic_rejects = 1`；P14-D 的 30 分钟里有 3 次 reject + 1 次 jump。
两处合起来的量级是 **≈ 1 次 / 8 分钟**，不是"30 分钟一次"。

所以：**6 轮 × 300 秒 = 30 分钟设备时间**，预期能拿到 3–4 个事件，
加上 AE/D 已有的，够算一个数量级而不是一句"偶发"。

## 三、每轮判什么

| 编号 | 判据 | 说明 |
| --- | --- | --- |
| H1 | 每轮的 `monotonic_rejects` / `jumps_clamped` / `trace.event_count` 都报出来 | 三个数应当自洽：`event_count` = 至少 `rejects + clamped` 的次数（事件上限 3） |
| H2 | 每个事件必须能判"谁跳的"：`candidate` 自己跳（设备）还是 `accepted` 被压（守卫） | 用窗口里 `pivot` 那一行的三个数判 |
| H3 | 出现率写成"每次事件相隔多少分钟"，**并标明样本量** | n 小就必须说 n 小，不能写"约每 8 分钟一次"就收工 |
| H4 | 每轮不许丢帧、p99 ≤ 1 帧 | 异常本身不该影响播放；影响了就是另一个问题 |

H1 的"至少"是刻意的：`trace` 只留 3 格，超过 3 次事件时 `event_count` 会小于真实次数。
**这个已知的截断必须写出来**，否则会被读成"这轮只有 3 次"。

## 五、诚实清单（开工前）

1. **6 轮 30 分钟仍然是小样本。** 出现率只能给量级（"每 5–15 分钟一次"这种），
   给不了置信区间。要置信区间得跑到几十次事件，那是几个小时的事。
2. **`trace` 只留 3 格。** 一轮里超过 3 次事件时，第 4 次起没有窗口 ——
   计数仍然准，形状只能看前三个。
3. **短会话可能改变发生率。** 5 分钟的会话没有长时间升温、没有后台切走再回来；
   30 分钟那一轮的事件可能来自"跑久了"这件事本身。**本卡测的是"短会话里的率"**，
   与 30 分钟那一轮不是同一个分母。
4. **ppm = 0 时门几乎不动**，所以这一轮的 `drift_rebases` 应当接近 0 ——
   若不为 0，说明有真实漂移，那要单独看。
5. **仍然只有 K40。**
