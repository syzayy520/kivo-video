# 160 · P14-W 验收：门在 60 s 上响 49 次，把 288 ms 的累积压到 42 ms

- 日期：2026-10-31
- 前置：`159-p14w-design.md`（8 s 量程不足，换 60 s）
- 结论：**门是活的，而且形状与设计预期一致**。5 000 ppm × 58 s 的 288 ms 累积被夹在
  40–45 ms，复位 49 次（预期 49.5），零丢帧、零超预算。8 s 上的沉默是**量程**，
  不是门坏了 —— 这一点从推测变成了观测。

---

两组数字对得上，说明那一行改动没有碰到测量本身。

**三条算术自证**

1. 复位次数：`(288 − 42) / 5 ms = 49.2` ⇒ 实测 **49**。
2. 单次修正：`band + 一帧的累积 = 5 ms + 0.08 ms` ⇒ 实测 5.10 / 5.20 / 5.77 ms。
3. 残差：`limit − band = 40 ms`，实测 last 40.36–44.67 ms，**max 从未超过 45.000 ms**。

## 二、代价：没有

| 指标 | ①（门开，5 000 ppm） | ②（门关，5 000 ppm） | ③（不注入） |
|---|---|---|---|
| `frames_dropped` | 0 | 0 | 0 |
| `over_budget_frames` | 0 | 0 | 0 |
| 单帧迟到 max | 11.09 ms | 1.03 ms | 12.45 ms |
| 呈现帧 | 3600/3600 | 3600/3600 | 3600/3600 |

门开那一轮的迟到最大值 11.09 ms 是**注入本身**造成的（时间轴每帧被推早一点点），
`over_budget_frames` 仍是 0 —— 也就是说 49 次复位没有一次让任何一帧超过自己的预算。

## 三、修掉一个语义缺陷：`limit_reach_s` 在门开时是错的

①②同一份数据，`limit_reach_s` 一个印 **63.6 s**、一个印 **9.3 s**。
63.6 s 那一轮里门**已经动作了 49 次** —— 它不是算错，是**问错了问题**：

```
limit_reach_s = limit_ns / |media_rate − 1|
```

`media_rate` 在门开时是**修正后**的净速率（1.0007），不是注入的 5 000 ppm（1.005）。
拿它算"多久撞门"，等于问"被修好的东西还要多久坏"。

**改法**（`sync/34`）：`gate_scale()` 多收一个 `drift_rebases`，非 0 ⇒
`limit_reach_s_measured = false` + `kGateActedReason`。
`limit_ppm_equivalent` 照算（它与门动没动过无关）。
判据 `verify_p12c_sync.py` 加 **V5**：门动过就必须因**这个**理由闭嘴；
反过来门没动过却引用这条理由，说明开关传反了。

修完 ⑤⑥ 复跑：门开 ⑤ `reach_measured=false`（理由正确），门关 ⑥ `reach = 9.32 s`。

**V5 的第一版自己是错的**：它被写在 `else`（不可算）分支里，于是"门动了 49 次
却仍报可算"从 `if` 分支溜了过去 —— 正是这条判据要抓的那一种。
变异 **M9** 打不红时才发现整段被缩进吞进了上面的 `if`。修完 10/10 全对上：

| 变异 | 期望 | 结果 |
|---|---|---|
| M1–M6（V 组原有 6 条） | 红 | 全红 |
| M7 末位抖动 1e-9 | 绿 | 绿 |
| **M8 门动过 49 次却仍报可算** | 红 | 红 |
| **M9 门没动过却用"修完后"的理由** | 红 | 红 |
| **M10 `/34` 门没动过** | 绿 | 绿 |

**交接文档里"全仓 224 份判据 exit 0"是只跑了 `verify_p12c_sync`，没跑总闸**。

- 教训与 §4 那条老账同源：**判据落后于实现，不会自己报错，只会让新证据无判据可守**
  （脚本自己的报错文案早就写了这句话，只是没人把它跑起来）。

## 五、还有一处没解释干净：一次 105 ms 的修正

④a 的 `drift_max_correction_ns = 104.71 ms`，是 band（5 ms）的 21 倍；
④b/④c 与 ① 都没有（5.2 / 5.8 / 5.1 ms）。

算术指向一个唯一自洽的解释：

```
修正总量 350.16 ms − 49 次 × 5 ms = 105.16 ms   ← 恰好那一笔
```

即：**启动期盲区（首帧后 1 s，P13-W 的保护）里 `cum` 自由累积；盲区一结束，
第一次读把攒下的量一次还完**。这一笔的大小 = 那一秒里时钟超前了多少，
而它取决于启动时音频/视频谁先起跑 —— 所以它**有时有、有时没有**。

- 三条旁证：只有 ④a 有；`total − n×band` 恰好等于它；领先量轨迹 `max` 仍是 45.00 ms
  （那一笔发生在基准帧之前，被吸收进基准）。
- **未直接测到时刻**（证据里没有逐次修正的时间戳），所以写成"最自洽的解释"，不是结论。
- 影响：④a 零丢帧、`over_budget_frames = 0`、单帧迟到 max 2.59 ms ⇒ 实际无害。
  但"盲区结束时一次性还清"这件事本身值得下一张卡给它一个时间戳。

## 六、诚实清单

1. **只有一台设备**（K40），1080p60 与 4K30 两种片源；没有 4K60 60 s（编码成本）。
2. **105 ms 那一笔没有时间戳**，只有算术与"三轮里一轮有"两条旁证。
3. **`limit_reach_s` 的修法选择了"闭嘴"**，而不是"改印注入速率" —— 因为报告层
   不知道注入参数（那是探针的事），知道的话就会把探针语义写进产品报告。
4. **`over_budget_frames` 的阈值（一帧）没动**，49 次复位一次都没触发它。
5. ⑥ 的 `reach = 9.32 s` 与设计预期 9.0 s 差 3.5%，因为 `arm_after = 2 s`
   让实际注入窗口是 58 s 而不是 60 s —— 这是分母差异，不是算错。
