# P13-H 状态卡：`observed_hz` 的分母 —— 一个会自己长数的证据

> 设计：`70-p13h-design.md` · 证据：`docs/evidence/p13h/`（3 轮 × 130 s，`sync/6`）
> 前序：`69-p13g-status.md` §七.2 把这条列为欠账，原话是「`span` 是序列窗口首末差，
> `accepted` 是累计，超过 2048 点 / 20 Hz 之后两者不同源，`observed_hz` 会偏高」。
> 本卡去验这句话。它不是"偏高几个百分点"，是**没有上界**。

---

## 一、缺陷

`av_sync_report.cxx` 上一版：

```cpp
observed_hz = sampled_samples * 1e9 / pace.drift.span_ns;
//             ^^^^^^^^^^^^^^^ 累计（total_）    ^^^^^^^^^^^^^^^^^ 窗口（封顶 102.35 s）
```

分母 `trend.span_ns` 是 `at(n-1).media_ns - at(0).media_ns`，`n ≤ kCapacity = 2048`，
所以它封顶 2047 × 50 ms = 102.35 s；分子只增不减。超过 102.4 秒之后商随片长线性增长。

本轮真机实测（130 s / 360p30 / 3900 帧 / 零丢帧）：

| | 值 |
|---|---|
| `accepted` | 2600 |
| `media_span_ns`（累计） | 129.967 s |
| `trend.span_ns`（窗口） | 102.367 s |
| **新尺子** `observed_hz` | **20.005** |
| **旧尺子**（同一份数据） | **25.399** |

10 分钟的片子按这个公式会报 100 Hz 以上，旁边还写着 `target_hz: 20`。
那个数不会让人怀疑数据，只会让人怀疑抽稀门写错了 —— 而它其实一直是对的。

### 为什么活了四张卡

两层原因，缺一层都不会漏这么久：

1. **取证的长度不够。** 全部 27 份真机证据是 8 s 与 35 s 片源，`truncated` 恒 false，
   两根尺子恰好等长。缺陷只存在于**没人跑过的时长**里。
2. **校验器复算的是同一个公式。** `expected_hz = accepted * 1e9 / span`，
   `span` 取的还是 `trend.span_ns`。它验的是"报告有没有把算式写错"，
   不是"分子分母是不是同一个作用域"。**照抄算式只能证明算术没打错，不能证明量纲对。**

---

## 二、能抓住它的东西

不是"更准的除法"，是一条把分子和分母绑在同一段时间上的**恒等式**：

```
accepted + unobserved_cells == floor(media_span / interval) + 1
```

它来自抽稀门的接受规则本身（首帧无条件接受 +1；此后每跨一个格点接受一次；
没帧跨过的格点只记 `unobserved`），所以是精确等式，不是容差。

用 27 份旧证据核对，余量全部为 **0**：

| 片源 | accepted | span | floor(span/50ms)+1 | 余量 |
|---|---|---|---|---|
| 8 s / 60fps（20 份） | 160 | 7.950 s | 160 | 0 |
| 8 s / 30fps（3 份） | 160 | 7.967 s | 160 | 0 |
| 35 s / 30fps（3 份） | 700 | 34.967 s | 700 | 0 |
| **130 s（本卡 3 份）** | **2600** | **129.967 s** | **2600** | **0** |

旧尺子在同一份 130 s 数据上：`floor(102.367/0.05)+1 = 2048`，左边 2600 —— **差 552**。

## 三、改法

1. `DriftSeries` 增加 `media_span_ns()`：**按段累加**的整场媒体跨度
   （段内实时算 `末接受点 − 段首`，`clear()`/seek 时把该段折进 `closed_span_ns_`）。
   按段累加而不是 `末 − 首`：seek 之后媒体时刻倒退，`末 − 首` 会得到负数或把两段误差算进去的假跨度。
2. `PaceSummary::drift_media_span_ns` 带出去；`observed_hz` 与结构门都用它。
3. JSON 里 `media_span_ns` **紧跟 `accepted`** —— 相邻不是排版偏好，是防腐：
   想再算这个除法的人，两个操作数就在眼皮底下，不会一个取累计一个取窗口。
4. schema → `sync/6`。`/3`–`/5` 的旧证据不重写（重写等于伪造），H 判据只对 `/6` 生效。

一个刻意的选择：**跨度用"最后被接受"的帧，不用"最后观察到"的帧**。
两者差的是尾部被抽稀门拒掉的那几帧。用后者会让累计跨度比窗口跨度大不到一帧 ——
**两根尺子差一点点，比差很多更难发现**。这一条是被单测 `t04` 打出来的
（第一版实现就是用的 `last_media_ns_`，`t04` 当场红）。

## 四、判据与变异

| 编号 | 判据 | 结果 |
|---|---|---|
| H0 | 声明 `sampling.media_span_ns` | 3/3 ✓ |
| H1 | `accepted + unobserved = floor(media_span/interval)+1`（单段恒等式） | 3/3 ✓ |
| H2 | `observed_hz ≤ 1e9/interval + 1e9/media_span` | 3/3 ✓ |
| H3 | 覆盖后 ⇒ 累计 > 窗口；未覆盖 ⇒ 累计 = 窗口 | 3/3 ✓ |
| H4 | 零样本 ⇒ 零跨度、零节奏 | 不适用（三轮都有样本） |

H2 是 H1 的速率表述，单独列出来是因为它读起来最直白：
20.005 Hz 对上限 20.008 Hz —— 顶在上界上是正常的（首帧那次无条件接受），
超了只能是口径混了。

**变异（C++ 4 处、Python 6 处、端到端 1 处，全部按预期打红）**

- C++：① `media_span_ns()` 换回窗口跨度（10 条红，5 个用例）；② 关段用"最后观察到"的帧；
  ③ 关段重复累加 / 完全不关段（4 条红）；④ `PaceSummary` 接错源。
  ② 第一次**没红** —— 见 §六.1。
- Python：M1 分母=窗口跨度（4 红，就是本缺陷本身）、M2 只改 hz 不改 span、M3 缺 `media_span_ns`、
  M4 覆盖后 span=0、M5 `truncated` 翻假、M6 `unobserved_cells` 虚报。
- 端到端：把 M1 写进 `docs/evidence/p13h/p13h-mutation-bad-sync.json` 跑总收口 →
  层 4 红、结论「不可交付」。**并且先断言了它确实进了 `docs/evidence/p13*/*-sync.json` 的 glob**
  （P13-F 那条教训：文件名不匹配 `*-sync.json`，坏证据压根没被扫到，总收口照样全绿）。

单测 `kivo_p13h_media_span_tests`：11 例 / 47 断言。

## 六、诚实清单

1. **我自己的测试第一版是绿的，但它守不住东西。** 变异②（关段用"最后观察到"的帧）
   第一次跑**没红** —— 九个用例里最后一帧永远是被接受的（`feed()` 走整格），
   覆盖不到"尾部有拒帧"。补了显式用例 `t11`（一帧被拒，然后 `clear()`）才红。
   这与 P13-G 的 `t07`、P13-F 的"测试自己也会假通过"同族，**三次都是同一个病**：
   断言想守的场景没被数据覆盖。区别只是伪装：那次是文件没被扫到，这次是分布没被采到，
   再上次是概率太低。
2. **`media_span_ns` 只做了单段的真机验证。** seek（`segments > 1`）只有单测
   （`t07`/`t08`）覆盖，没有真机 seek 取证。该场景下 H1 从恒等式降成上界，
   因为"每段各有一个 +1"。
3. **102.4 s 的窗口仍然在。** 本卡只修了"拿窗口跨度去除累计样本数"这一处口径混用。
   `quantiles.media_time_decimated` 是**整场累计**（2600 个样本），
   而 `trend` 只描述**最近 102.4 s**（2048 个点）—— 这两个数在长片源上不同源，
   只是各自都说了实话（`trend.truncated = true`）。这是下一张卡的候选。
4. **`observed_hz` 是整场平均，不是窗口内的即时节奏。** 播放中途卡住 10 秒再恢复，
   整场平均看不出来（会被 `unobserved_cells` 部分体现）。没做窗口内节奏。
5. **只有 3 轮，且只有 360p。** 选 360p 是刻意的：解码要足够便宜，
   这样量到的是抽稀门的节奏，不是"360p 能不能播"。**这份证据不支持任何关于长片 4K 的结论。**
6. **`/3`–`/5` 的证据仍按旧判据读。** 它们的 `observed_hz` 分母是窗口跨度，
   只是片长都在 102.4 s 内所以碰巧对。不重写、也不假装它们被新判据覆盖过。
7. **漂移量准仍是 7 ppm 的尺子。** 三轮 `slope_from_windows_ppm` 都是 0.000、`r2 ≈ 0`，
   只能说"小于这把尺子的分辨率"，不能说"零漂移"。这条从 P13-D 欠到现在，一个字没动。
8. **`/5` 的版本历史当时漏写了。** 改 `kSchema` 却没在版本注释里加一行 ——
   本卡补上，并在这条注释里注明了这次漏写（改一处忘另一处，本族的第五次）。
