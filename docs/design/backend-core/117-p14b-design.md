# 117 · P14-B 设计：把那 5 次/秒的分配**指认**到线程

- 日期：2026-10-31
- 前置：`116-p14a-status.md` §三（稳态分配 5 次/秒，与帧数无关，不知道是谁）
- 目标：给 `operator new` 计数加**线程维度**，让"5 次/秒"变成一个带名字的线程

---

## 一、为什么必须归因，而不是继续猜

P14-A 已经证明了三件事：总量（5 次/秒）、形状（与帧数无关）、后果（不影响播放）。
缺的是**主语**。没有主语，G3 只能一直写"未达标"，而"未达标"无法指导任何改动：

| 如果那 5 次/秒来自… | 结论 |
| --- | --- |
| 呈现线程（每帧路径） | G3 真不达标，得改成零分配 |
| UI 统计轮询线程 | **播放路径是干净的**，G3 该按"播放线程"重新表述 |
| 音频线程 | 要单独定一条音频侧的预算 |
| JNI / Kotlin 侧 | 属于探针工装，不该进 G3 的账 |

四种情况对应的动作完全不同。**继续优化之前，必须先知道是哪一种。**

## 二、怎么做：定长槽表 + 线程局部槽号

```cpp
struct Slot {                    // 8 个，够了
    std::atomic<int> tid;        // 0 = 空槽
    std::atomic<int64> calls;
    std::atomic<int64> bytes;
    char name[24];               // 快照时才填，填一次就缓存
};
thread_local int my_slot = -1;   // 平凡类型，无析构、无守卫变量、不分配
```

`note_call()` 里：

1. `my_slot < 0` → CAS 抢一个空槽，写入 `gettid()`；
2. 累加该槽的 `calls/bytes`；
3. 槽满了（第 9 个线程）→ 记到 `overflow` 槽，**不丢样本**。

**为什么不用 `std::unordered_map<tid, …>`**：那本身就要分配，而且是在
`operator new` 里面分配 —— 递归。定长数组是唯一安全的选择。

**为什么 `thread_local int` 不会递归**：平凡类型的 `thread_local` 走的是
TLS 直接寻址，没有动态初始化、没有 `__cxa_guard`，不触碰堆。
这一点必须写进注释，否则下一个维护者会"顺手"把它换成 `thread_local std::optional<...>`，
然后整个 App 卡死在第一次分配上。

**重入护栏**：`thread_local bool in_hook`。计数体内若再发生分配（理论上不该有），
直接跳过，绝不递归。

### 线程名从哪来

快照时（此时计数已 `suspend()`）读一次 `/proc/self/task/<tid>/comm`，填进槽里并缓存。
**只读一次**：8 个槽最多 8 次 `open/read/close`，摊在整场播放里可以忽略。
不在 `note_call` 里读，因为那会在分配路径上做 I/O。

Android 上 `comm` 对 Java 线程是线程名（`main`、`RenderThread`、`kivo-poll`…），
对 native 线程是我们自己 `pthread_setname_np` 设的名字。够用来指认。

## 三、证据形状

`metrics.alloc` 增一个数组：

```json
"threads": [
  {"tid": 12345, "name": "kivo-recv", "calls": 0, "bytes": 0},
  {"tid": 12380, "name": "kivo-poll", "calls": 653, "bytes": 165176}
],
"thread_count": 2,
"overflow_calls": 0
```

`thread_count` 与 `overflow_calls` 必须出版：**没有它们，"只有两个线程分配过"
和"槽满了后面全丢了"长得一样**。

## 四、判据

| 编号 | 判据 | 说明 |
| --- | --- | --- |
| N1 | `thread_count ≥ 1` 且 `overflow_calls = 0` | 表够用。溢出说明线程数超 8，归因不完整 |
| N2 | 每个槽 `calls` 之和 = `calls_total` | 分桶不漏账。漏了就说明有分配没进任何槽 |
| N3 | **呈现线程的 `calls_steady` 报出确定值** | 这才是 G3 的正主。本卡不要求它是 0 |
| N4 | 归因结论写进状态卡：那 5 次/秒属于哪个线程、是否在播放路径上 | 没有这句，本卡等于没做 |

N3 特意不写"= 0"：先测出来，再谈达不达标。

## 五、诚实清单（开工前）

1. **线程名可能为空。** 内核 `comm` 最长 15 字节，未命名的线程叫 tid 本身。
   空名不等于"没有这个线程"。
2. **`gettid()` 会复用。** 线程退出后 tid 可能被新线程拿到，
   于是两个不同生命期的线程挤进同一个槽。8 秒到 130 秒的片源里概率极低，但不能说没有。
3. **槽表是 8 个。** 超过 8 个线程分配过就会进 `overflow`。
   `overflow_calls ≠ 0` 时，本卡的归因结论**只覆盖前 8 个线程**。
4. **归因不改变 G3 的判据文本。** 如果 5 次/秒来自 UI 轮询，
   该改的是"G3 的适用范围"（播放线程 vs 进程），而不是把数字改小。
   **改口径必须显式写进状态卡，不能悄悄换分母。**
5. **仍然只有 K40、只有 Debug。**
