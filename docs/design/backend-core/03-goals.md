- 日期：2026-10-28

## 零、为什么要重建而不是优化

现有 P5 视频平面的契约是 `DecodedFrame{ std::vector<uint8_t> }`。
**只要帧是字节数组，GPU 帧就必须回读到内存**，硬解收益当场归零。
所以这不是性能优化，是契约层的重建。

实测基线（Intel UHD 630，本机）：

| 事实 | 数字 | 含义 |
|---|---|---|
| 1080p HEVC10 软解 | 280 fps（9.34x 实时） | 解码不是瓶颈 |
| 项目实际播放 | 8.6 fps | **瓶颈在呈现路径** |
| 硬解 CPU 时间 | 0.469s → 0.016s | 硬解价值是释放 CPU，不是刷帧率 |

## 一、目标（G1–G10，全部可量化）

### G1 硬解吞吐与保真

> 1080p HEVC Main10 纯解码 ≥ 250 fps，且协商到 **P010**（10bit 不落 8bit）。

- 测量：自研探针（`kivo_hw_decode_probe`）解码 300 帧，输出 `decoded_frames / elapsed`。
- 反例条件：协商到 NV12 即判失败（说明 10bit 被砍成 8bit）。

### G2 硬解 CPU 效率

> 硬解 CPU 时间 ≤ 同片源软解的 **10%**。

- 测量：探针同时跑软解对照，输出 `cpu_ratio`。
- 依据：本机实测可达 3.4%（0.016/0.469），10% 是留三轮余量的保守线。

### G3 稳态零堆分配

> 解码+呈现稳态循环内，`operator new` 调用次数 = **0**。

- 测量：替换全局 `operator new` 计数，跳过前 30 帧预热后统计。
- 反例条件：任何 `std::vector` 在热路径上重新分配即判失败。

### G4 表面池不泄漏

> 连续解码 1000 帧后，池内 `in_use` 归还数为 0，`allocated` 数量收敛（不再增长）。

- 测量：池自报 `allocated / peak_allocated / leaked`，探针输出该三元组。
- 反例条件：`leaked > 0` 即失败，不允许"轻微泄漏"。

> **Android 侧处置（P15-E，2026-11-01）：不适用。**
> 输出面由 `MediaCodec` + `Surface` 管理，本仓库**没有自研表面池**，
> G4 的三个量（`allocated / peak_allocated / leaked`）在这里没有对应物。
> 标成"不适用"而不是让它一直挂着"未验" —— **空着的验收项比错误的验收项更容易被忘掉**
> （`177-p15-probe-plan.md` §五）。P11 的 Windows 参考实现仍然按本条验。

### G5 零拷贝上屏

> 呈现路径上 CPU 侧像素拷贝次数 = **0**。

- 测量：代码级断言（无 `memcpy`/`Map`/`sws_scale` 在判定路径）+ 运行时统计
  `cpu_copy_bytes` 恒为 0。
- 反例条件：任何一帧走 `sws_scale → RGBA` 即失败。

### G6 帧节奏

> 24/30/60 fps 片源，丢帧率 < **0.5%**，present 间隔抖动 p99 < **1 帧时长**。

- 测量：节拍器记录每帧 `present_at - due_at`，输出直方图与 p50/p99。

### G7 音画同步

> |video_pts - audio_clock| p99 < **40 ms**（约 1 帧 @25fps）。

- 测量：音频主时钟驱动视频，逐帧记录偏差，输出 p50/p95/p99/max。

### G8 Seek 正确且快

> seek 后首帧显示延迟 < **150 ms**，且 seek 后 30 帧内无花屏/错序。

- 测量：`avformat_seek_file` + `avcodec_flush_buffers` + 重新填充；
  用帧号水印（画面烧入 pts）验证首帧正确性。

### G9 无静默降级

> 任何能力缺失必须带非空 `reason`，且必须在 UI 可见。

- 测量：`GpuDecodeCapability::reason_if_unavailable` 非空率 = 100%（当不可用时）。
- 反例条件：`get_format` 静默返回软解格式即失败（已由策略单元测试守住）。

### G10 证据产物

> 每个阶段产出可复核的 JSON 证据，含设备名、格式、帧率、CPU、内存、时间戳。

- 路径：`artifacts/p11/<stage>/<name>.json`
- 要求：能被第三方脚本重算，不接受手填。

## 二、阶段与闸门

| 阶段 | 内容 | 闸门 | 状态 |
|---|---|---|---|
| P11-A | D3D11 设备 + D3D11VA 解码器 + get_format 策略 | 编译通过 + 策略单测绿 | ✅ 已完成 |
| **P11-A2** | **真实片源硬解探针（自研代码，非 CLI）** | G1 + G2 + G10 | ✅ 全部通过（501fps / P010 / 7.66% 周期） |
| P11-B | 表面池 + 有界帧队列 | G3 + G4 | ⬅ 下一步（帧表已池化，纹理池未做） |
| P11-C | 零拷贝上屏（NV12/P010 着色器 + flip 交换链） | G5 + 画面正确性 | 待启 |
| P11-D | 节拍器 + 音频主时钟 A/V 同步 | G6 + G7 | 待启 |
| P11-E | 10bit 全链路 + HDR 元数据 | G8 之 10bit 部分 | 待启 |
| P11-F | Seek 与容错 | G8 + G9 | 待启 |
| P11-G | 假契约族回收、证据收口 | G10 全量 | 待启 |

**注意平台顺序**：用户目标为 **Android → iOS → 桌面**。
Windows D3D11 后端的角色是参考实现与逻辑验证台，不是最终交付平台。
详见 `04-platform-strategy.md`。

**顺序调整说明**：原计划 P11-B 先于 P11-C。基于 10-28 实测（解码非瓶颈），
**P11-C 提为与 P11-B 同等优先**——先消掉 `sws_scale → RGBA → QImage` 才能让 8fps 变正常。

## 三、不许做的事（红线）

1. 不许为了让测试变绿而放宽断言。
2. 不许用 `Fake*` 类型充当实现（P5G 的教训）。
3. 不许在呈现路径引入任何形式的像素回读。
4. 不许把多个职责塞进一个文件（单文件 > 400 行即需拆分评审）。
5. 不许在没有实测数字的情况下宣称达标。
