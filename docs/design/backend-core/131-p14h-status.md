  `backends/aaudio/clock/aaudio_clock_source.cxx`（喂 `elapsed`）

## 一、改了什么（一行判据）

```cpp
// 旧：advance > 200 ms                       ← 隐含"查询间隔 ≪ 200 ms"
// 新：advance > 200 ms + elapsed             ← elapsed = 距上一次观测的墙钟增量
```

放行量同步改成 `threshold + elapsed`。只放 200 ms 会凭空扣掉"过了 383 ms 只走 200 ms"
那 183 ms 的真实进度 —— 那正是 P14-G 里每次钳制造成的错位。

| 用例 | 注入 | 钳制 | 越阈值残差 | 长间隔 | 丢帧 | p99 | 最大迟到 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `inject300`（60 s） | 300 ms 台阶 | **0** | 0 | 1 / 340 ms | 0 | 0.12 ms | — |

对照 P14-G（修之前）：同一条 30 分钟片源，四轮**每轮各 1 次假钳制**（276 / 383 / 253 ms 间隔）；
60 s 烟测在启动后 757 ms 也钳了 1 次。**现在两份都是 0。**

长跑这一轮的 `max_candidate_step = 233.78 ms` 与 `max_mono_step = 233.77 ms` 逐位相等 ——
又一个"间隔吃掉整段前进"的样本，而它这次**没有被误判**。

## 三、顺带修正一条旧结论（P14-E）

判据第一版写的是"注入 300 ms 必须触发钳制"。真机把它判红了，**红得对**：

| 项 | 值 |
| --- | --- |
| `clock_injection.offset_ns` | 300 ms |
| 守卫侧的 `max_forward_ns` | **82 µs** |
| `beyond_threshold` | **0** |

台阶根本没进守卫的视野。原因是拓扑：`ClockOffsetSource` 包在 `AaudioClockSource`
**外面**（`jni_session_handle.cxx:341`），注入加在守卫**下游**。

所以 P14-E §二 里"人为 300 ms 跳变验证了钳制"这个归因是错的 ——
那一轮窗口里的 `candidate +225.45 ms` 是**原始流**上的一次跳变，与注入无因果关系。
更正已追加到 `125-p14e-status.md` §八（原文不改，追加更正），
那次跳变与 P14-D 的 931 ms 一起挂进待查。

**这是判据建错了地方，不是实现坏了** —— 区别在于前者要改代码，后者要改判据。

## 六、诚实清单

1. **"真跳变仍被钳制"只有桌面证据，没有真机证据。** 生产路径上制造不出真跳变：
   注入在守卫下游（本卡的发现），而设备在 121 分钟里一次没跳（P14-G）。
   所以这一条只能靠 C25 / C27 两张桌面断言，**不能声称"真机上验证过"**。
2. **代价是明确的**：设备若真的在"我们没看的那段时间"里跳了，守卫不再发现。
   这是有意的取舍 —— 没有观测就没有证据，假装能判才是错的。
3. **本卡不解决"为什么会停 233–383 ms"**，只让它不再变成假钳制。
   停顿时长本身（233 / 234 / 340 ms）在不同轮次都在同一量级，值得单独查。
4. **最大迟到 9.07 ms 不能归因给这次修改**。P14-G 四轮是 6.4 / 6.4 / 87.2 / 87.6 ms，
   而 87 ms 那两轮的钳制都发生在片尾 —— 与"钳制拖慢帧"的因果不符。**样本不够，不下结论。**
