- **结论：拆出一条新判据 G8a（冷启动 ≤ 300 ms），G8b（seek ≤ 150 ms）不变且 4K 上余量 3× 以上。**

## 二、更正一：我把冷启动当成了 seek

`58-p13a-status.md` 原话：

> 150 ms 的 G8 预算在 4K 上不够。

**错在混口径。** 那两个数字（66–133 ms）是**冷启动**（`open()` 后第一次 `start()`，
要建组件、绑 Surface），而 G8 判的是**seek 后首帧**（codec 已热，只 flush）。
实测 4K 的 seek 只有 **36–49 ms**。

为什么能混：**它们共用同一个计数器** `counters.first_frame_latency_us`。
而这个计数器在 `begin_run()` 里会被重置 —— 所以一份证据里根本区分不出来。

修法（本卡代码改动全在这里）：

- `DecodeSession` 新增 `cold_start_first_frame_us_`，在**第一次 `seek_to()` 之前**抓一次，之后不再改；
- `snapshot()` 里两者分开输出：`timing.first_frame_latency_us`（最后一段）、
  `cold_start.first_frame_us`（第一次起跑）；
- 证据 schema → **`decode/13`**，新增 `cold_start` 段（含判定）。

## 三、更正二：133 ms 本来就在 150 ms 内

即使按我自己的逻辑，`132.5 < 150` —— **"不够"这个事实也不成立**。

真实情况是**余量从 3.2×（1080p 47 ms）缩到 1.13×（4K 133 ms）**。
余量薄和超标是两件事：前者要求"把阈值定得合理"，后者才要求"改实现"。

而这一步只需要一次除法和一次比较。**两份数据当时都在手上，我没做。**

---

## 四、更正三（本卡过程中）：200 ms 也是拍的

第一版 `kColdStartBudgetUs` 我定 200 ms，依据是 P13-A 的**单轮**数据（132.5 ms）。

真机跑第一轮就红了：**206 ms**。随后 18 轮纯冷启动测出 4K10 的分布是
122–146 ms（中位 136），而 206 ms 那个值来自带 seek 的那次运行。

**200 ms 会偶发失败 → 偶发红的判据等于没有判据**（分不清退步和噪声）。
改为 **300 ms**：给已观测最大值 206 ms 1.46× 余量。

> 教训：**冷启动的方差远大于中位数暗示的程度，阈值必须按已观测最大值定，
> 不能按中位数、更不能按单轮。** 这条已写进 `seek_budget.hpp` 的注释。

## 六、诚实清单（五条）

1. **21 轮里 4K10 最大 146 ms，但曾观测到 206 ms**（那次是带 seek 的运行）。
   300 ms 覆盖了它，但**样本仍不足以给出 P99** —— 只能说"19 次观测内没超"。
2. **冷启动包含 Surface 首次 attach 的开销**，这部分受系统状态（后台进程、GPU 调度）影响，
   K40 上的分布不代表低端机会一样。
3. **只测了 60fps 片源**。30fps 片源的冷启动未测（预期更快，但不假设）。
4. **`cold_start` 只在 seek 之前抓一次**。如果一次会话里 `start()` 被调用两次
   （比如中途 stop + start），第二次的冷启动值不会被记录 —— 当前没有这种路径，
   但代码没有防御。
5. **schema 现在是 `decode/13`**，`p13a` 那批还是 `/12`（没有 `cold_start` 段）。
   这是版本演进，不是错误，但读证据时要按 schema 判断字段是否存在。
