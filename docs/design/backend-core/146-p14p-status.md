## 三、预言核对：一条全对，一条对了一半

| 预言 | 设计卡写的 | 实测 | 判定 |
|---|---|---|---|
| 11 个数逐位相等 | 相等 | 相等 | ✅ |
| `p50_range` == `p99_range` | 相等，量级 [15 417, 250 000) | 相等，[15 625, 250 000) | ✅（形式对，下限错） |

第二条的下限我写错了，原因是我把"桶界 ∩ `[min, max]`"当成了桶界：桶 512 的下界是 0，
真正钳住它的是这一轮的 `min_ns`（最小迟到）。三轮实测分别是 **15 417 / 14 948 / 15 625**
—— 它是数据，不是常量，**本来就不该被预言成一个固定值**。设计卡没改。

顺带一个观察：`p50_bucket_samples = 1798 / 1800`，也就是说 1800 帧里只有 2 帧落在
250 µs 以外。这个桶里到底挤了多少东西，在 `/26` 的 `lateness_ns` 上是**看不到的** ——
它只印一个 `125000`。

## 四、顺带撞出来的事：屏幕一睡，报告就会算出一笔加不起来的账

### 4.1 现场

第一次取证时屏幕在第 2.8 秒熄灭（设备超时），当时那份 `cpu_paced` 报告是：

| 字段 | 值 |
|---|---|
| `frames_decided` | **1800** |
| `presented` | **84** |
| `dropped` | **0** |
| `present_wall_span_ns` | 2.766 s |
| `frame_count`（顶层） | 84 |
| `lateness_ns.p99` | 43 625 000（是的，43.6 ms，比一帧还长） |
| `drop_ratio` | **0.0** —— 完美 |

`presented + dropped = 84`，而 `decided = 1800`。**1716 帧没有交代**，而
`drop_ratio` 拿 `0 / (84 + 0)` 算出 0.0，读起来是"零丢帧、完美"。

屏幕一熄，SurfaceFlinger 不再回调，只有 84 帧真的上屏；而解码器照样把 1800 帧走完，
节拍器照样对 1800 帧做了决定。三个数各自都对，合起来是一个洞。

### 4.2 为什么它值得记下来

这不是本卡的错，也不是新 bug（P12-C 起就这样），但它和本卡修的是**同一族病**：
**一笔账的两个部分没有互相校验**。P14-L/N 修"0 冒充观测"，P14-O/P 修"桶中心冒充精确值"，
这一条是"分母只数了自己那一半"。

**没有任何判据看 `presented + dropped == frames_decided`。** 这是下一张卡的第一项
（见 §八），本卡不顺手加 —— 加一条判据要自己的设计卡、自己的预言、自己的变异，
混进本卡就会变成"顺手加一点"。

### 4.3 我犯的两个错，都在这里

1. **那两份坏证据被我覆盖掉了。** 干净重跑时我 `rm -f docs/evidence/p14p/*.json`，
   把 84 帧那份删了。上面的数字是从会话里逐字抄的，**仓库里没有文件可以复核**。
   留档应当放 `superseded/`（`iter_evidence()` 会跳过它），而不是删掉。
2. **我改了手机的 `screen_off_timeout`**（设成 1800000），取证完设回 **60000** ——
   但**原值我没有先读**，所以"还原"只是还原成一个常见默认值，不保证是用户原来的数。
   脚本里改成了 `svc power stayon usb`（插着 USB 就别熄屏，可逆、不动系统设置），
   取证结束后已 `svc power stayon false` 还原。

### 4.4 复现尝试没成功

用 `input keyevent KEYCODE_HOME` 在播放中切后台，等 20 s 与再等一轮，**都没有写出报告**
（进程仍在，`mCurrentFocus` 是桌面）。所以 84 帧那份的成因我只知道"屏幕熄灭"这一半，
"报告为什么还是写出来了"那一半没查清。结论按半条记。

## 五、判据与变异

### 5.1 R0–R5

| 编号 | 判据 | 实测 |
|---|---|---|
| R0 | 块在，且带七格 | ✓ 两份都带 |
| R1 | `bucket_width_ns == 250000`（Python 侧独立写死） | ✓ 两份都是 250000 |
| R2 | `p50` / `p99` 落在各自 `[low, high]` 内 | ✓ |
| R3 | `0 ≤ bucket_samples ≤ samples` | ✓ |
| R4 | `measured=false ⇒ 七格全 0` | ✓ `attime` 那份整块 0 |
| R5 | 11 个数与 `quantiles.per_frame` 逐位相等 | ✓ `cpu_paced` 相等；`attime` 判"**不可判**" |

R5 在孪生块缺席时判"不可判"而**不是**"通过"，措辞也进了变异自测（U0 专门检查这句话在不在）。
理由：`/26` 那次 `D2 = 5.00x` 的教训 —— 一个"不适用"如果长得和"通过"一样，
下一个读者就会把它当通过用。

**R 组的位置**：在 Q 组之后、`drift = doc.get("av_drift", {})` 之前。它不读 `av_drift`
的任何字段，而 `check_file()` 在 `sampling` 缺失、`mode == not_measured` 两处会提前
`return`。P14-N 的 Q 组第一次写在所有 `return` 之后，六条判据一条都没跑到 ——
同一个错不犯第二次。

### 5.2 变异：7 红 + 2 绿 + 旧版本 1 条，全部按预期

两个底座，因为 R5 会吞掉 R1–R4 的地盘（孪生块在场时，改任何一格 R5 都能抓）：

| 用例 | 底座 | 改动 | 结果 |
|---|---|---|---|
| W0 | cpu_paced | 原样 | 仍绿 |
| W1 | cpu_paced | 删掉 `bucket_width_ns` | **R0** 红，未牵连 |
| W2 | cpu_paced | `p50_bucket_samples + 1` | **R5** 红，未牵连 |
| W3 | cpu_paced | `p99` 推到自己范围外 250 µs | R5 红 + 牵连 R2（已声明） |
| U0 | attime + 人造自洽块 | 原样 | 仍绿，且 **R5 说"不可判"** |
| U1 | 同上 | 没量到却留一个非零范围格 | **R4** 红，未牵连 |

## 七、诚实清单

1. **这张卡没有改变任何一个判定。** 门禁 F3（`p99 > 一帧`）在这一轮上余量是
   `33 333 333 / 250 000 ≈ 133 倍`，加不加范围它都过。改的是**证据等级**：
   临界的那几轮从此可辨，而"临界"在 `/26` 上根本看不出来。
2. **R5 在真机上不能区分"抄 p50"与"按 q=0.99 算"。** `p50` 与 `p99` 同落在桶 512，
   两种写法结果本来相同。可杀死性只有 `build/mutate_p14p_verifier.py` 自证，那份不进仓库。
3. **`schedule_lead_ns` 仍然是裸数。** 它的第二个数是 `p90 − p10`（两个桶中心相减），
   给差值出版误差是另一道题，本卡按 §二 的边界没做。
4. **`p95` 仍然没有范围**，也没有判据消费它。
5. **84 帧那份证据被我覆盖掉了**，见 §4.3。上面的数字不可复核。
6. **手机 `screen_off_timeout` 的"还原"不可靠**，见 §4.3。
7. **"屏幕熄灭"只解释了一半**，见 §4.4：报告为什么在那种状态下还是被写出来了，没查清。
8. 本卡**没有**动 `Q0–Q5`、`N0–N13`、`D1/D2` 任何一条；也没动 `decode` 侧一个字。

## 八、下一张卡的候选（按价值排序）

1. **`presented + dropped == frames_decided` 没有判据。** §四的现场是一个现成的反例：
   1716 帧凭空消失，而 `drop_ratio` 报 0.0。这条最该先做 —— 它是**唯一一个已知的、
   有真实反例、而判据完全缺席**的洞。
2. **桶宽细化。** D2 至今不可判的唯一原因是 250 µs 比 30 fps 侧的真值还大 8 倍
   （`p99_range_low_ns` 甚至等于 `min_ns`，说明整个分布挤在第一个桶里）。
   这是让 D2 真能判的唯一路径，但会动全部历史证据的可比性，要单独一张卡。
3. **`schedule_lead_ns` 的误差**：它的 `spread` 是两个桶中心相减，误差可达两个桶宽。
4. **G6/G7 在默认档上的真正测量**：P14-K/L/N/P 都只让"没量到"和"量到多粗"变显式，
   没让测量发生。要测上屏时刻必须改呈现路径（合成器回调）。
5. **第二台机器**（`192.168.5.148:5555`）：`surface_at_time` 跨机型最可能变。
