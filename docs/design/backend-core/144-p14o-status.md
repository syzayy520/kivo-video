> 卡片：P14-O（设计见 `143-p14o-design.md`）

## 二、真机证据（`docs/evidence/p14o/`）

同设备（Redmi K40 / `b6e950ee`）、同分辨率 1080p、同片长 60 s、同参数（`cpu_paced`、
门开、3600/1800 帧、**0 丢帧**），只差帧率。

| 块 | 30 fps | 60 fps |
|---|---|---|
| `quantiles.media_time_decimated.p99` | 125 000 | 125 000 |
| `p99_range` | [15 417, 250 000) | [16 094, 150 522) |
| `p99_bucket_samples / samples` | 1196 / 1200 | **1200 / 1200** |
| `quantiles.per_frame.p99` | 125 000 | 125 000 |
| `per_frame.p99_range` | [15 417, 250 000) | [16 094, 250 000) |
| `per_frame.p99_bucket_samples / samples` | 1787 / 1800 | 3588 / 3600 |

`p99_bucket_samples = 1200/1200` 这一格说的是：**这一轮 60fps 的每一个抽稀样本都在
250 µs 以内**。所以它的范围只能靠"桶界 ∩ [min, max]"收到 [16 094, 150 522) ——
上界由最大样本（150 521）钳住，不是桶界。

## 三、预言核对：一条对，两条错

设计卡 §五 用 `p13af` 那份旧的 60fps 证据算出了三个预言。**两个错了，不改设计卡**
（把设计卡改成与结果一致，就是伪造预测）。

| 预言 | 设计卡写的 | 实测 | 判定 |
|---|---|---|---|
| 30fps `p99_range` | [15 625, 250 000) | [15 417, 250 000) | 形状对（桶界被 `min` 钳住）；具体下限随轮次的 `min` 走 |
| 60fps `p99_range` | [500 000, 750 000) | **[16 094, 150 522)** | ✗ 错 |
| D2 商区间 | [2.00x, 48.00x] | **[0.06x, 9.76x]** | ✗ 错 |

错的原因不是算错，是**前提没复现**：预言假设 60fps 会重复 `p13af` 那次的
`p99 = 625 000`（桶 514，桶里只有 3 个样本）。这一轮它把 1200 个样本全放进了第一个桶。
桶号一变，桶界之比全变 —— 而"桶界之比"正是上一张卡里那个 `2.00x` 的来源，
所以它也跟着没了。

## 四、顺带撞出来的事：`5.00x` 不是帧率的性质

D2 存在的理由写在它的注释里：「若抽稀后 60fps 的 p99 仍是 30fps 的 4 倍，
说明 P13-C 那句『采样密度』解释错了，真实原因在别处。」

三次 60fps 运行（同设备、同片源、同参数、都是 3600 帧 0 丢帧）：

| 轮次 | schema | `decimated.p99` | `decimated.max` | `pace.lateness_ns.p99` | `max` |
|---|---|---|---|---|---|
| `p13af-b60-r1` | /20 | 625 000 | 3 949 169 | 375 000 | 7 193 611 |
| `p13af-b60-r2` | /20 | 625 000 | 23 190 832 | 375 000 | 23 190 832 |
| `p14o-1080p60` | /26 | **125 000** | **150 521** | 125 000 | **1 151 759** |

第三次的延迟整体低一个量级（最大 1.15 ms vs 7.2 / 23.2 ms）。也就是说：

- `5.00x` 是**那两轮**的性质，不是 60fps 的性质；
- P13-C 的"采样密度"解释至少不是全部原因 —— 变量在运行状态里，不在帧率里；
- 而 `n = 3` 不足以说清是"前两次异常"还是"这一次异常"。**不加因果结论。**

这一条是这张卡真正的产出。`p99` 有了范围之后，D2 给出的第一个可复算的结论不是
"通过"或"失败"，而是"这条判据在量一件不稳的东西"。

## 五、判据与变异

### 5.1 N8–N13（仅 `/26`）

| 编号 | 内容 | 在真机证据上 |
|---|---|---|
| N8 | 每个分位块都有 `p99` 三格 | ✓ 3 个块各带三格 |
| N9 | `p99 ∈ [low, high]` | ✓ |
| N10 | `0 ≤ p99_bucket_samples ≤ samples` | ✓ |
| N11 | 范围不宽于一个桶 | ✓ |
| N12 | 从分布复算桶内样本数（q=0.99） | ✓ |
| N13 | 从分布复算范围（q=0.99） | ✓ |

`/25` 及更早的证据**不进这一组**（门槛 `>= /26`）：那些文件里 `p99` 是裸整数，
拿新判据去判只会产出一批假红 —— P14-M 修的就是这类假红。

### 5.2 D2 三段式

```
ratio_lo = fast_lo / slow_hi    最有利于「没漂移」的读法
ratio_hi = fast_hi / slow_lo    最不利于「没漂移」的读法

ratio_lo > 2.0   → 失败（区间整个在门槛之上）
ratio_hi ≤ 2.0   → 通过（区间整个在门槛之下）
其余             → 不可判，但把区间印出来
```

实测输出（全量 16 份配对池）：

```
0.125 ms / 0.125 ms = 1.00x（点估计）；按范围读是 [0.06x, 9.76x]
（30fps ∈ [15417, 250000)，60fps ∈ [16094, 150522)）：区间跨过门槛 2.0x ⇒ 不可判；
只比 2/16 份带 `p99` 范围的证据（30fps 去掉 12 份、60fps 去掉 2 份：`/26` 之前的
证据没有 p99 范围，混进来就是混合物的中位数）
```

**配对池按版本过滤**是这一卡新增的：不同 schema = 不同量具，把两把尺量出的数
一起取中位数，得到的是混合物的中位数。份数下降会打印出来，不安静地发生。

### 5.3 变异（`build/mutate_p14o_verifier.py`，不进仓库）

应红 6 条 / 应绿 2 条 / D2 三段各一条，**全部按预期**：

| 变异 | 期望 | 结果 |
|---|---|---|
| V0 原样复制 | 绿 | ✓ 绿 |
| V1 删掉 `p99_bucket_samples` | N8 红 | ✓ |
| V2 `p99` 改到范围之外 | N9 红 | ✓ |
| V3 桶内样本数 = 总数 + 1 | N10 红 | ✓（牵连 N12） |
| V4 范围下界外扩 300 µs | N11 红 | ✓（牵连 N13） |
| V5 抬尾巴后原样 | 绿 | ✓ 绿 |
| V6 抬尾巴后抄 p50 的桶内样本数 | N12 红 | ✓ |
| V7 抬尾巴后抄 p50 的范围 | N13 红 | ✓（牵连 N9） |
| P1 区间整个在门槛之上 | 失败 | ✓ |
| P2 区间整个在门槛之下 | 通过 | ✓ |
| P3 区间跨过门槛 | 不可判 | ✓ |

V5–V7 需要一个**抬尾巴**的底座：真机那份证据里 `p50` 与 `p99` 同在第 512 桶，
"抄 p50"在它身上是正确答案，抄了不会红。拿它测 N13 会得出"判据抓不住复制粘贴"
的错误结论 —— 而真实原因是这一份分布里两个分位数本来就同桶。
所以 V5–V7 先把 20 个样本挪到桶 514，让两者分家。

抬尾巴时**必须同时改三份分布**（`decimated` / `per_frame` / `trend.window_quantiles`）：
只改一份会被 `I4`（未覆盖且单段 ⇒ 逐桶相同）当场抓住。这个脚本第一版就是这么
被打回来的两次 —— 那不是底座坏了，是判据在正常工作。

## 七、诚实清单

1. **D2 仍然不可判。** 本卡没把它变成可判，改的只是"不可判"的证据等级：从一句
   手算的形容词，变成一个别人能算出同一个数的区间。要真判得了，得细化桶宽 ——
   250 µs 比 30fps 侧 p99 的真值（15–30 µs 量级）还大 8 倍，那一格的信息量接近于零。
2. **预言两条错了**，原因写在 §三，设计卡没改。
3. **`n = 3` 不足以下因果结论。** §四只说"5.00x 不复现"，没说"前两次异常"或
   "这一次异常"。要说清，得跑更多轮，且要记录当时的温度/后台负载 —— 现在两份证据
   里都没有这些。
4. **只做了 `p99`。** `p95` 没有范围：没有任何判据消费它，加字段是要付版本代价的。
5. **`pace.lateness_ns` 仍是裸的桶中心。** 它由 `PaceSummary` 直接出版
   （`samples/p50/p99/max/measured/reason`），不经 `render_quantiles`，所以这一卡
   没碰它。要给它加范围得同时动 `pace_stats.hpp` 与 `decode/18`，是独立一张卡。
6. **配对池只加了"按版本"这一维。** "同源 / 同轮次"没做 —— 完整重构要回答
   "人为注入轮次算不算同源"，那是决策，不是实现。
7. **N12/N13 在真机证据上无法区分 p50/p99**（两者同桶），只能靠构造证据证明；
   构造证据留在 `build/` 下，不进仓库，所以这两个判据的"可杀死性"没有仓库内自证 ——
   只有这份状态卡和一个需要手动跑的脚本。
