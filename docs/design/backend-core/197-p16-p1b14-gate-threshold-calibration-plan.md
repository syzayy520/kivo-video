## 一、构思

`183` §七 Q2 问的是"若用伺服，估计窗口取多长、阈值怎么定"。要回答它，
先得知道**现在这个门在什么频差下开始动作** —— 这个数字目前没有，只有一句
"45 ms 门限"和一堆 `rebases=5/6/10` 的观测。

方法：注入已知频差，让 35 s 播放累积出确定的总偏差，看 `drift_rebases` 何时从 0 变正。
累积 = ppm × 35 s：

| 注入 ppm | 35 s 累积 | 预期门行为 |
| --- | --- | --- |
| 0 | 0 ms | 不触发 |
| 500 | 17.5 ms | 不触发（< 45 ms） |
| 1000 | 35 ms | 不触发（< 45 ms） |
| 1500 | 52.5 ms | **应触发**（> 45 ms） |
| 2000 | 70 ms | 应触发 1–2 次 |
| 5000 | 175 ms | 应触发 3–4 次 |

临界点应落在 1000–1500 ppm 之间。**这就是门限的实测标定。**

## 五、结果（2026-11-06）

### 六组实测（decode + sync 同轮）

| 注入 ppm | `rate_ppm` | 35 s 累积（理论） | `drift_rebases` | `corrected_total` | `max_correction` |
| --- | --- | --- | --- | --- | --- |
| 0 | -8.83 | 0 ms | **0** | 0 ms | 0 ms |
| 500 | 453.39 | 17.5 ms | **0** | 0 ms | 0 ms |
| 1000 | 979.01 | 35 ms | **0** | 0 ms | 0 ms |
| 1500 | 1506.18 | 52.5 ms | **1** | 5.1 ms | 5.1 ms |
| 2000 | 2014.20 | 70 ms | **5** | 25.2 ms | 5.0 ms |
| 5000 | 4956.53 | 175 ms | **29** | 170.3 ms | 27.7 ms |

> 1500 ppm 首轮证据是 **0 字节文件**（设备侧也没写出来），补跑一次才拿到。
> 原因是那轮 `am start` 后应用没写出证据，**不是数据异常**；补跑结果与线性趋势一致。

### 判据核对

| 判据 | 结果 |
| --- | --- |
| W1（`rate_ppm` 线性、偏差 < 100 ppm） | **PASS**：-9 / 453 / 979 / 1506 / 2014 / 4957，全部与注入值差 < 50 ppm |
| W2（累积 < 45 ms 组 `rebases=0`；> 45 ms 组 ≥1） | **PASS**：0/500/1000 全 0；1500/2000/5000 分别 1/5/29 |
| W3（临界点落在 1000–1500 ppm） | **PASS**：1000 ppm（35 ms）沉默，1500 ppm（52.5 ms）触发 1 次 |

### 关键发现：迟滞带在持续频差下失效

- `2000 ppm` 轮：累积 70 ms，但 `corrected_total` 只有 **25.2 ms**，`max_correction` 恰好 **5.0 ms**
  —— 等于 `drift_band_ns`。也就是说门每次只修一个 band，修 5 次仍追不上累积。
- `5000 ppm` 轮：29 次复位、`max_correction` 27.7 ms —— 每次修正量变大，但仍然是"追着修"。
- **`corrected_total` 与累积偏差不匹配**（25.2 vs 70、170.3 vs 175）：门没有消除偏差，
  只是把它压在阈值附近来回抖。这正是 `183` 说的"bang-bang 与持续频差形状不匹配"的实测版。

### 对 Q2 的直接回答

- 门从 **1000–1500 ppm（35 s 口径）** 之间开始动作；
- 迟滞带 `5 ms` 只在"累积速度 < 2 ms/s"时有效；注入 ≥ 2000 ppm（2 ms/s）后，
  门退化成"每 ~2.5 s 修 5 ms"的反复微调；
- 所以若换速率伺服，**估计窗口至少要覆盖 2–3 秒**（否则看不到 2 ms/s 的斜率），
  阈值不能继续用"45 ms 绝对量 + 5 ms 带"这种形状。

### 路径覆盖补测（默认路径）

六组都跑在 `cpu_paced`，但**产品默认是 `surface_at_time`**。补测一轮
`--es kivo.present surface_at_time` + 2000 ppm：

| 字段 | 值 |
| --- | --- |
| `present_schedule` | `surface_at_time` |
| `rate_ppm` | **1965.72**（与注入 2000 差 34 ppm / 0.17%） |
| `phase_error_ns` | 65,575,920（理论 70 ms） |
| 帧数 / 丢帧 | 1050 / 0 |
| `completed` / `error` | true / `""` |

**结论**：出版链路不依赖 `cpu_paced`；默认路径同样能测到频差，精度与 `cpu_paced`
同量级（1966 vs 2014）。这一点对换伺服很关键 —— 默认路径才是产品行为。

### 追问：调大 `band` 够不够？（**离线推演，非实测**）

门的行为可写成两行：`target = limit − band`；`cum > limit` 时一次修到 `target`。
于是稳态残差就是 `limit − band`，触发周期 ≈ `band / (ppm × 1e-6)`：

| `band` | 稳态残差 | 2000 ppm 触发周期 | 2000 ppm 单次修正 | 5000 ppm 触发周期 |
| --- | --- | --- | --- | --- |
| 5 ms（现状） | **40 ms** | 2.5 s | 5 ms（实测 5.0） | 1.0 s（实测 29 次） |
| 10 ms | 35 ms | 5 s | 10 ms | 2.0 s |
| 15 ms | 30 ms | 7.5 s | 15 ms | 3.0 s |
| 20 ms | 25 ms | 10 s | 20 ms | 4.0 s |

**推演结论**：

- 调大 `band` 能**同时**降低残差、减少触发次数 —— 看起来是双赢；
- 但代价是**单次修正变大**（5 → 20 ms），一次跳 20 ms 的画面抖动可能比"每 2.5 s 修 5 ms"更明显；
- 更关键：**它没有改变"周期性复位位置"的本质**，只是把"小步高频"换成"大步低频"。
  只要钟还在持续快，`cum` 就会一直往上爬，门就得一直修。

所以"调参"能缓解、不能根治；**是否换成"改速率而不是改位置"**，才是 `183` §七 Q1 那个问题。
本表是**推演**（由 `PacePolicy` 的代码逻辑 + `197` 实测点推算），
要变成实测需要把 `drift_band_ns` 参数化（Kotlin → JNI → native 共 6 处），
本卡不做，留作实现卡的第一步。
