# P13-E 状态卡：口径前缀 —— 裸 `p99` 已在结构上不存在

> 设计：`64-p13e-design.md`。前序：`63-p13d-status.md`。
> 证据：`docs/evidence/p13d/` 26 份（13 轮 × decode+sync），**全部出自同一 APK**。
> 结论：判据 E1–E3 全通过；总收口 306 份 / 8 个子校验器 exit 0。

---

## 一、改了什么

`av_drift` 从"顶层一堆分位数 + 一个说明口径的字段"，改成"分位数只能从口径里取"：

```jsonc
// /2（P13-D）—— p99 躺在不带口径的键下面
"av_drift": {
  "sampling": { "mode": "media_time_decimated", ... },
  "samples": 160, "p50": ..., "p99": 625000, "max": ...,
  "per_frame": { "p99": 875000, ... },
  "trend": { ... }
}

// /3（P13-E）—— 想取一个数，必须先说口径
"av_drift": {
  "sampling": {
    "mode": "media_time_decimated",
    "cross_frame_rate_set": "quantiles.media_time_decimated",
    ...
  },
  "quantiles": {
    "media_time_decimated": { "samples": 160, "p50": ..., "p99": 625000, ... },
    "per_frame":            { "samples": 480, "p50": ..., "p99": 875000, ... }
  },
  "trend": { ... }
}
```

`json["av_drift"]["p99"]` 现在直接 KeyError。这不是命名约定，是**取不到**。

### D2：方向与 P13-D 一致，幅度不稳

| 卡 | mtd/p99 30fps | mtd/p99 60fps | 比值 |
| --- | --- | --- | --- |
| P13-D | 1.625 | 0.375 | 0.23× |
| P13-E | 1.875 | 0.875 | **0.47×** |

**方向没变**：同源同片长同分辨率下，60fps 的抽稀 p99 仍然更低（不是"高 4–5 倍"）。
幅度从 0.23× 漂到 0.47×，正好落在上一卡声明过的那条限制上——
160 个样本的 p99 就是"第 2 差的样本"，三轮跨度可以到 3.4×。
**任何以单轮值下的结论都不可用**，这里给的是中位数与区间。

### 漂移：仍然只能说"< 7 ppm"

35 s 三轮 `usable=true`，|slope| ≤ 1.83 ppm、r2 ≤ 0.0038，8 个窗口中位数全是 125000 ns
（一个桶宽），窗口斜率恒 0。分辨率上限 ≈ 7.1 ppm。与 P13-D 同结论，**没有变好也没有变坏**。

## 四、过程里修掉的五个缺陷

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | `render_quantiles` 还留着 P13-D 的 `trailing_comma` 参数，新结构下多写一个尾逗号 | `json.load` 当场 `Illegal trailing comma`——**整份证据作废**，且只在真机上才发现 |
| 2 | 总收口 `card_checks` 只分发 `sync/1` | P13-D 的 26 份 `/2` 证据**从未被层 2 校验过**：在白名单里、能解析，但"可测却没有样本"一条没查 |
| 3 | `Report(Path("D2 media_time_decimated/p99 比值"))` | `Path.name` 把 `/` 前当目录，输出只剩 `p99 比值` —— **本卡唯一的产出被自己的显示层吃掉** |
| 4 | 校验器通过时仍打印"有 accepted 却没有 quantiles.media_time_decimated —— 样本去哪了？" | 一行 ✓ 配一句失败措辞，读的人会以为坏了 |
| 5 | 我自己的汇总脚本用 `.get(key, 0)` | 关音频那轮整行印 `0.000` —— **正是本卡刚写进设计文档 §三 的"假零"**，写完后十分钟自己犯了一次 |

第 5 条是这轮最值得记的一条：一条规则写进文档不等于它会被遵守，
所以它必须同时是**代码里的默认行为**（缺就印 `—`，不印 0），否则连写规则的人都会违反。
第 2 条则说明"加 schema 忘了加分发"是这类免检漏洞的固定成因。

## 五、诚实清单（五条）

1. **`sampling.accepted` 在不可测轮仍是 160。** 计数器与"可发布数据"不是一回事：
   序列确实采到了点（相对节拍器自己的目标时刻），但没有音频时钟来定义"漂移"，
   所以 `quantiles` 是空对象。**读的时候必须把计数器与分位数分开看**——
   `accepted=160` + `quantiles={}` 不是矛盾，是"采了但不可发布"。
2. **4K60 r1 有一个尖峰没解释。** 抽稀 max 57 ms、逐帧 max 88 ms、p99 8.6 ms，
   另外两轮是 1.6 / 0.9 ms。三轮里的一轮，无法归因（可能是系统抢占）。
   单看这一轮会得出"4K 不行"，而另两轮不支持。
3. **`per_frame` 降级分支没有真机证据。** `note_presented()` 拿不到媒体时刻的那条路
   目前只有单测覆盖；要造它得让呈现路径不传 pts，本轮没做。
4. **`/1`、`/2` 的旧证据不重写。** 重写等于伪造。校验器对它们报"不适用"，
   所以历史证据与 `/3` 之间**不能直接比**——要比就看 `63-p13d-status.md` 的旧表。
5. **总收口的层 4 只跑结构判据。** D1/D2 是跨组对照，需要同一批证据成对喂进去；
   总收口按目录逐份遍历，凑不齐一对会误判。手动命令写在 `TASKS.md`。

## 六、下一步

1. **4K60 的尖峰要单独查。** 一次 88 ms 的逐帧 max 会被后来的人当成"4K 播不动"，
   而真原因可能是首轮冷启动 / 系统抢占。要么复现并给出归因，要么在证据里标注"未归因"。
   —— 现在它只是躺在表里，谁读到都会各自猜一个原因。
2. **`per_frame` 降级分支补一轮真机证据。** 判据只有在两条路上都跑过才算闭合。
3. **漂移量准的前提仍是分辨率。** 7 ppm 的尺子上讨论 1 ppm 的改动是在改猜测——
   要先解决 0.25 ms 桶宽 / 35 s 片长，这条从 P13-D 到现在没变。
