# 76 · P13-K 设计：给标准误换一把承认自相关的尺子

> 一句话：**P13-J 的误差棒用错了噪声模型。**
> 它假定相邻样本的残差互不相干，而 `lateness` 恰恰是强自相关的
> （vsync 相位、CPU 调频、抽稀本身抹平慢变分量）。正相关让有效样本数远小于 `n`，
> SE 被系统性低估、置信带过窄 —— 于是 r3 那条 `r2 = 0.007` 的线被判成"看得见"。
> 本卡把 SE 换成 Newey–West（Bartlett 核），并给出一条能分开
> "持续漂移"与"中途跳一下"的半程诊断。

## 一、问题

### 1.1 P13-J 自己造的假阳性

P13-J 收口时三轮真机并列，第三轮很刺眼：

| 轮次 | 片源 | 样本 | `slope_ppm` | `SE` | 95% CI | `detectable` | `r2` |
|---|---|---|---|---|---|---|---|
| r1 | 130 s 360p30 | 2600 | −0.105857 | 0.1435 | [−0.387, +0.175] | false | 5.5e−05 |
| r2 | 130 s + seek | 2000 | +0.137157 | 0.2106 | [−0.276, +0.550] | false | 5.1e−03 |
| r3 | 35 s 1080p30 | 700 | +0.479713 | 0.2152 | **[+0.058, +0.901]** | **true** | **2.2e−04** |

r3 的置信带不含 0，按定义"看得见"。可它旁边写着 `r2 = 0.00022` ——
那条线只解释 **0.02%** 的方差。一个解释力如此之低的斜率被判为"检出"，
只有两种解释：要么那把尺子太乐观，要么那 700 个点真的在往下走。

当时的处理是"建议别信"，但那只是把问题推给读者。**判据不能靠人肉打折。**

### 1.2 为什么 IID 假设在这里必然偏小

`slope_ppm_std_error_iid = sqrt( SSres/(n−2) / Sxx )`。它的推导默认残差
两两独立、同方差。而 `lateness` 的残差至少有四个正相关来源：

1. **vsync 相位**：同一个刷新周期里的连续帧共享同一份抖动；
2. **CPU 调频 / 温控**：几十毫秒到几秒尺度的状态会连着影响一批帧；
3. **抽稀本身**：50 ms 格点横跨 1~3 帧，慢变分量被"取样"后变成相邻样本同向；
4. **音频时钟的滤波状态**：`AudioTrack` 的播放头不是每帧都刷新。

正相关 `ρ` 下，均值（这里等价于斜率）的方差不再按 `1/n` 收缩，而是
`(1+ρ)/(1−ρ)` 倍。ρ = 0.9 时这个因子是 **19**，SE 该放大 `√19 ≈ 4.4` 倍。
P13-J 印出来的 SE 里没有这一项，所以它是个**乐观下界** —— 当时的头文件里
就写着这句，但写注释不等于修好。

### 1.3 为什么不能简单"乘一个安全系数"

一个常数系数（比如一律 ×2）在两种情形下都是错的：

- 残差其实是**负**相关（交替抖动）：IID 的 SE 反而偏**大**，乘 2 只会更保守到失真；
- ρ 随片长、片源、机器、热状态变化：r3 只有 35 s、缓存刚热，ρ 很可能明显小于 r1。

所以这张卡的目标不是"把 r3 的 `true` 改回 `false`"——那是结论先行。
目标是**让 `ρ` 从数据里被估出来**，再让 `detectable` 站在估出来的 SE 上。
如果估完 r3 仍然是 `true`，那它就是个真的（只是量级很小）。

## 二、做法

### 2.1 新单元 `core/pace/pace_hac`

只做一件事：给一条**已拟合好**的直线算 HAC 斜率标准误。

```
u_i  = x_i · e_i                       x 为去均值时刻，e 为残差
γ_l  = Σ_{i} u_i · u_{i+l}
Var  = [γ_0 + 2 Σ_{l=1..L} (1 − l/(L+1)) γ_l] / Sxx² · n/(n−2)
```

四个刻意的选择：

| 选择 | 理由 | 不这么做会怎样 |
|---|---|---|
| 只收 `series` 与 `slope_per_ns` | 截距可由前两者推出，多传一个参数就多一处能传错 | 调用方算错截距，γ_l 与 ssr 用了**两套残差**，膨胀比悄悄偏离 1 且不报错 |
| 带宽 `L = floor(4·(n/100)^(2/9))`（Newey–West 经验式） | n=100 给 4、n=2048 给 7，增长极慢，对应"越长容得越多但收益递减" | 拍一个常数，让 700 点和 2048 点共用同一个 L |
| 逐 lag 现算残差，**不占 16 KB 栈** | 只在停机出报告时调一次，`O((L+1)·n) ≈ 1.6 万`次乘加 | `core/pace` 全族的稳态约束是"不进堆"，栈上再来一块 16 KB 迟早撞上线程预算 |
| `n/(n−2)` 自由度修正 | 让 `L=0` 时 HAC 与 IID 落在**同一把秤**上 | 膨胀比永远差一个常数因子，读者会把它读成自相关 |

除了 SE，还顺带给出两个读数：

- `hac_lags`：实际用的带宽。写进证据是为了**可复算** —— 校验器独立按公式重算它；
- `hac_lag1_autocorrelation`：残差一阶自相关，一句话解释"为什么要修正"。

### 2.2 趋势接线：一个字段换了语义

`slope_ppm_std_error` 从 `/9` 起是 HAC 值，**名字没变**。旧口径原地改名
`slope_ppm_std_error_iid`。

为什么改名而不是并排放两个新字段：读者不该在 `_iid` 与 `_hac` 之间二选一 ——
该用的那个必须就叫 `slope_ppm_std_error`。旧值留着只为**对照**：
`slope_ppm_std_error_inflation = SE_hac / SE_iid` 就是"上一版窄了几倍"。

⚠️ 同名不同义是这份证据最忌讳的病，所以这个决定被写进状态卡诚实清单第一条，
并由判据 **K0** 盯住三个字段必须同时存在（缺一个就红）。

膨胀比取 **SE 之比**而非方差之比：读者眼前摆着两个 SE，比例就该是同一把秤上的
两个数直接相除，不该让他自己去开方。

### 2.3 半程诊断：`slope_first_half_ppm` / `slope_second_half_ppm`

HAC 回答"这个斜率有多准"，答不了"它是一条持续的漂移，还是中途跳了一下"。
两种情形给出同样的全序列斜率，含义却相反：

- 持续漂移 = 时钟速率差，会**一直累积**（10 分钟 600 ms）；
- 一次错位 = 不会继续变大，要修的是那一次（丢帧、调度尖峰）。

各取一半再各拟合一次，方向一比就分开了。`slope_halves_agree` 只说方向、
没有阈值、**不参与任何判定** —— 斜率本身接近 0 时符号由噪声决定，
那时 true/false 就是掷硬币。校验器只验它与两个数自洽（K6）。

### 2.4 报告层 `/9`

`trend` 块新增 8 格，全部紧跟在 `slope_ppm` / `slope_ppm_std_error` 那一段里
（不甩到块尾：这些数分开摆，读者就会单看斜率那六位小数）。
`slope_ppm_std_error` 的渲染位置不变，语义变；`_iid` 与膨胀比紧随其后。

### 2.5 校验器：把"同一张表只改一半"从结构上消掉

`verify_p13d_drift.py` 里原本有 6 张 schema 表（`SUPPORTED_SCHEMAS` /
`SCHEMA_WITH_WORST` / `_FLOOR` / `_MEDIA_SPAN` / `_WINDOW` / `_CONFIDENCE`），
每升一次版本都要记得六处一起加一项。这个项目为此栽过**三次**：

1. `check_pair` 硬编码 `/3` → `/4` 的证据从没进过配对池；
2. `SCHEMA_WITH_WORST` 改成元组却仍用 `==` → F 判据对 `/4` `/5` 全静默"不适用"；
3. `SCHEMA_WITH_MEDIA_SPAN` 是标量 → 升 `/7` 的那一刻 H0–H4 对新证据全部失效。

每次的后果一模一样：**新证据带着一整块没人验的字段通过总收口，输出里连一行
"不适用"都没有**。`/9` 起改成从一张版本序表派生：

```python
SCHEMA_ORDER = ("/3", "/4", "/5", "/6", "/7", "/8", "/9")
def _schemas_from(version): ...          # 从该版本起的所有 schema
SCHEMA_WITH_HAC = _schemas_from("/9")
```

前提是"版本严格累积"——这在本项目成立（每版保留旧版全部字段）。
新增一个版本只需登记一次，六张表同时跟上。

## 三、判据 K0–K6

| 编号 | 内容 | 抓的是哪类错 |
|---|---|---|
| **K0** | 9 个字段齐全 | 报告层没跟上 schema；"半套绿"比全红更危险 |
| **K1** | `hac_lags` 可由样本数复算（含 `≤ n−3` 钳位） | 带宽被写死成常数；校验器复算同一个公式（P13-H 那次的病） |
| **K2** | ρ1 ∈ [−1, 1] | 自相关公式写反 / 分母用了 `n` 而不是 `Σe²` |
| **K3** | 膨胀比 = SE_hac / SE_iid | 膨胀比走了另一条路径，变成第三个互不相干的数 |
| **K4** | `hac_estimated = false` ⇒ SE 等于 IID 旧值 | "没修正"与"修正过"在 JSON 上长得一模一样 |
| **K5** | 带子变宽（inflation ≥ 1）时不许造出新的检出 | 字段接反：把 HAC 与 IID 的位置互换 |
| **K6** | `slope_halves_agree` 与两个半程斜率自洽 | 布尔与两个数分家，读者拿矛盾的值做决定 |

K5 是本卡的**目的判据**：修正只会让带子变宽，所以它永远不该让"看不见"变成
"看得见"。若出现这种组合，不可能是统计现象，只能是接线错误。

## 五、不做的事

| 不做 | 原因 |
|---|---|
| 块自助法（block bootstrap） | 能给出更好的置信带，但要重排序列、占内存，且与现有"纯函数、不分配"的家族约束冲突。HAC 先看数据怎么说 |
| Andrews 数据驱动带宽 / prewhitening | 带宽选择是另一整套方法论。经验式足够回答"上一版窄了几倍" |
| Prais–Winsten / GLS 重估斜率 | 那会改 `slope_ppm` 本身。本卡只换尺子、不动读数 —— 换读数会让历史对照全部失效 |
| 改整场分位数（`quantiles.<口径>`）的口径 | 它仍是桶中心。P13-J 已把窗口那份改成精确值，整场那份是另一张卡（见状态卡诚实清单） |
| 给 `detectable` 加 `r2` 门槛 | 阈值是拍出来的。要让 `r2` 参与判定，得先有"多大算够"的依据；先看 HAC 修正后还剩几个 true |

## 六、诚实清单（设计期）

1. **同名不同义**：`slope_ppm_std_error` 在 `/9` 前后是两把尺子。任何跨卡对照
   都必须先看 schema 号。
2. **HAC 只修一阶结构**：Bartlett 核在 `L` 阶截断，长记忆（慢漂移）会被截掉一部分，
   所以 SE 仍可能偏小 —— 比 IID 好，但不等于真值。
3. **半程诊断没有阈值**：它只说方向。两个半程都极小但同号时会说"一致"，
   而那和"持续漂移"不是一回事。
4. **不做多重比较校正**：一份证据只看一个区间的检出，不涉及多次检验。
5. **仍只覆盖 360p/1080p、30fps**：不支持任何 4K / 高帧率结论。
