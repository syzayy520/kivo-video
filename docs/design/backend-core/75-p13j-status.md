> 比之前那句"7 ppm"好一个半数量级 —— 而那个 7 ppm 从来没被量到过。

## 二、三轮真机（Redmi K40 / Android 13 / arm64-v8a）

零丢帧、零 xrun。

| 轮次 | 片源 | 帧 | accepted | `slope_ppm` | `SE` | 95% CI | `detectable` | `r2` |
|---|---|---|---|---|---|---|---|---|
| r1 | 130 s 360p30 | 3900 | 2600 | −0.105857 | 0.1435 | **[−0.387, +0.175]** | false | 0.000266 |
| r2 | 130 s + 55→30 s seek | 3000 | 3099 | +0.137157 | 0.2106 | **[−0.276, +0.550]** | false | 0.000212 |
| r3 | 35 s 1080p30 | 1050 | 700 | +0.479713 | 0.2152 | **[+0.058, +0.901]** | **true** | 0.007071 |

**读法变了。** 以前写 `slope_ppm = -0.105857`，读者只能自己猜可信度；现在同一份数据写的是
"漂移在 **±0.39 ppm** 之内"，这是第一次能说出一个带依据的上界。

### 2.1 窗口终于有刻度了

| 轮次 | 八窗中位数（旧 → 新） | 不同取值 | `delta_median_ns`（旧 → 新） |
|---|---|---|---|
| r1 | 全 125 000 → 73 323 … 73 843 | 1 → **8** | 0 → **520** |
| r2 | 全 125 000 → 72 605 … 75 302 | 1 → **8** | 0 → **95** |
| r3 | 全 125 000 → 71 874 … 77 916 | 1 → **8** | 0 → **2 500** |

`slope_from_windows_ppm` 从恒 0 变成 0.001244 / −0.009691 / 0.143726。

### 2.2 一个没预料到的结果：那个 125 000 本身就是错的

真实中位数约 **73 µs**，桶中心 **125 µs** —— 偏高 **71%**。

所以旧实现不只是"把八个数压成同一个"，它压成的那个数也不对。之前从 P13-D 到 P13-I
的所有 `p50` 读数（如果被引用过）都带着这个偏移。这不是本卡修好的：整场
`quantiles.<口径>.p50` **仍然是直方图的桶中心 125 000**（见 §五.2）。

### 2.3 SE 的公式被真机验证了一次

r3 的 SE 是 r1 的 **1.50 倍**。从公式看，`SE = sqrt(σ̂²/Sxx)`，其中：

| | r1 | r3 | 比 |
|---|---|---|---|
| 样本 σ（按桶估算） | 229.3 µs | 49.8 µs | 1/4.6 |
| `Sxx` | ∝ 2600 × 102.4² | ∝ 700 × 35.0² | 1/51 |
| 预期 SE 比 | — | — | `√(51)/4.6 = 1.55` |
| 实测 SE 比 | — | — | **1.50** |

吻合。r3 的噪声比 r1 小 4.6 倍（`max` 只有 1.17 ms，r1 有 5.42 ms 的尖峰），
所以同样的斜率在 35 s 上更容易"显著"。

## 四、变异自测

### 4.1 C++ 三处

| 变异 | 内容 | 结果 |
|---|---|---|
| C1 | `median_of_slice` 一律走桶中心（退回旧实现） | **14 处红** |
| C2 | 不填 `slope_se_per_ns`（等于宣称"没有误差"） | **8 处红** |
| C3 | 秩从 `(n+1)/2` 改成 `n/2` | **1 处红** |

**C1 第一次只红了 3 行标记。** 原因见 `74-p13j-design.md` §4.1：窗内 lateness 恒定时
`percentile_ns()` 把桶中心钳回 `[min,max]`，又还原成原值。加"每窗一个 300 µs 尖峰"
之后才红在数据上。**变异红在哪，比红不红重要。**

**C3 第一次把进程搞崩了**（`cannot seek array iterator before begin`，单点窗 `rank = 0`）。
崩溃的变异没有信息量 —— 它只证明进程会死，证明不了判据能抓错。已给 `rank` 加下界钳制，
之后 C3 稳定红在 `t08` 的 n=7 那条。

### 4.2 Python 八处

| 变异 | 打的判据 |
|---|---|
| M1 SE 抹成 0 | J2 + J3 |
| M2 CI 含 0 却说看得见 | J3 |
| M3 CI 下界挪 0.1 | J2 |
| M4 `exact=true` 但 `fallback=3` | J4 |
| M5 中位数压成同一个数 | **J5**（+D5 顺带） |
| M6 SE 为负 | J1（只红一条，见下） |
| M7 删掉 `slope_ppm_std_error` | J0 |
| M8 降级窗 + 零窗口斜率 | **J6**（+D5 顺带） |

M6 第一次连带红了 J3，文案写成"SE=0（残差为零）"——而实际是 −0.14，那句话是错的。
已把 `se < 0` 拆成独立分支（报"不适用，见 J1"），现在 M6 只红 J1。

### 4.3 端到端一处

植入 `p13j-mutation-bad-sync.json`（M2）→ 先断言它**真进了** `*-sync.json` 的 glob
（P13-F 踩过"名字不匹配所以压根没扫"），再跑总收口 → **层 4 红、结论"不可交付"**。

## 五、诚实清单

1. ⚠️ **`slope_detectable = true` 不等于"有线性漂移"，它只说"斜率不为零"。**
   r3 就是一个活例子：`detectable = true` 而 `r2 = 0.007`（那条线只解释 0.7% 的方差）。
   判读必须把 `r2` 一起看。本卡没把 `r2` 纳入检出判定 —— 那需要先解决下一条。
2. ⚠️ **SE 假设残差独立同分布，而 `lateness` 是强自相关的**（vsync 抖动 + 抽稀序列
   本身平滑）。真实不确定度**大于**这里给出的值，置信带是**乐观下界**。r3 那个
   `true` 很可能就是低估的后果 —— 35 s 上 700 个自相关样本，有效样本数远小于 700。
   要更严格得上 HAC / Newey-West，那是下一张卡。
3. ⚠️ **整场 `p50` 仍是桶中心。** `quantiles.media_time_decimated.p50 = 125 000`
   而 `window_median_ns` 是 73 000 量级 —— 同一批点，两个 p50，差 71%。
   本卡只修了窗口那一半。两份数并排会让人困惑，而这正是本卡新造的困惑。
4. ⚠️ 1.96 是正态近似，n = 30 时应该用 t（t ≈ 2.04，差 4%，在噪声量级内）。
   没有按 n 切系数，因为切换点本身是个假精度。
5. ⚠️ scratch 512 的降级路径**只在单测里走到过**（合成数据把 600 点挤在一窗）；
   真机每窗 256 点，一次没踩到。降级证据按 J6 会被判红，需要人工审。
6. ⚠️ 一轮 seek、只 seek 一次。r2 的 `media_span` 与段落切分没做多段压力测试。
7. ⚠️ 只有 360p / 1080p，不支持任何 4K 结论。
8. ⚠️ 本卡**不会让任何历史"漂移为 0"的结论变真**。它只让"小于多少"这句话第一次有依据。
