## 一、为什么不直接做返回地址采样

在 `operator new` 里存 `__builtin_return_address(0)` 就能拿到**调用点**，
看着一步到位。但它要连带解决三件事：

1. **符号化**：`dladdr` 只认动态符号，`static`/内联函数拿不到名字，
   于是证据里会出现一堆 `0x7f…`；
2. **地址基数**：`.so` 的装载基址每次不同，不出版基址，地址离线也解不出来；
3. **容量**：调用点可能几十个，槽表要么放大要么只留 top-N（而 top-N 需要排序/淘汰）。

**这三件事的成本远高于"先排除法"**。而排除法只要三轮、不要一行新代码。
所以本卡先做便宜的那半：**给线程起名 + 三例对照**。
如果结论是"音频侧"，问题就定位到一个族；如果三例都是 5 次/秒，
才值得上返回地址采样。

> 这条顺序是本项目的常规做法：**先花十分钟把范围砍掉一半，再决定要不要造新工具。**

## 二、三例对照

| 例 | 参数 | 如果 5 次/秒消失，说明 |
| --- | --- | --- |
| `base` | `pace=1`，音频自动 | —— （基线） |
| `noaudio` | `pace=1`，`kivo.audio off` | 来自音频侧（时钟轮询 / 喂音线程） |
| `nopace` | `pace=0` | 来自节拍器（每帧决策或它的快照） |

片源：`p13af_1080p30_60s_av.mp4`（60 s，与 P13-AF 同一份）。
`ppm = 0`：本卡只看分配，不需要注入。

### 判据

| 编号 | 判据 | 说明 |
| --- | --- | --- |
| N5 | worker 槽的 `name` 非空，且等于 `kivo-decode` | 起名接上了（合并模式） |
| N6 | 三例的 `calls_steady` **都报出确定值** | 报 0 是结论，报 300 也是结论 |
| N7 | 结论必须写明"5 次/秒属于哪个子系统，或明确说排除法没能排除" | **排除失败也是结论**，不许含糊过去 |

N7 是这张卡最容易糊弄过去的地方：三例都是 5 次/秒时，
很容易写一句"在主线程，与播放无关"就收工。那句话在 P14-B 已经写过了，
本卡要么给出更细的归属，要么老实说"三例都排不掉"。

## 三、预期（先写下来，跑完对）

主线程 5 次/秒 ≈ 每 200 ms 一次，**与帧率无关**（P14-B 已证）。
三种可能里，我押**第二种**：

1. `noaudio` 掉到 0 → 音频侧轮询（最省事的解释）；
2. **三例都是 5 次/秒** → 与音频、节拍都无关，是主线程上某个固定周期的任务
   （UI 统计轮询 / 进度回调 / JNI 边界的字符串）；
3. `nopace` 掉到 0 → 节拍器（但它每帧一次，与"与帧率无关"矛盾，可能性最低）。

**这个预判要写进状态卡并接受检验** —— 预测错了好过没预测。

## 四、诚实清单（开工前）

1. **排除法只能给"子系统"，给不到"行号"。** 本卡不承诺定位。
2. **`kivo.audio off` 改变的不只是音频线程**：没有音轨就没有音频时钟，
   节拍器会退到 `system` 时钟，`due_at` 的计算路径也跟着变。
   所以 `noaudio` 那一例就算掉到 0，也只能说"与音频相关"，不能精确到线程。
3. **三例各只有一轮。** 分配是确定性的（不是负载相关的随机量），
   但主线程的轮询可能受 UI 状态影响 —— 单轮的结论要标明"单轮"。
4. **线程名只覆盖我们自己的线程。** Kotlin 侧的线程名由 JVM 起，
   我们只读不写；`main` 在 Android 上显示为进程名（`com.kivo.cinema`）。
