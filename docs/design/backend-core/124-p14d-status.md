# 124 · P14-D 验收：30 分钟长跑 —— 门稳住了，但撞到一次时钟跳变

- 日期：2026-10-31
- 前置：`123-p14d-design.md`
- 结论：**门的长时间行为是稳的**（`lateness` 30 分钟不累积、缓冲 54001 个零泄漏、
  分配率 4.99 次/秒不随时间涨）；**但长跑第一次撞到 60 秒轮次从未出现的时钟跳变**，
  它同时解释了三处异常。

---

## 一、一轮 30 分钟（720p30 / 1800 s / 2000 ppm / 门开 / `cpu_paced`）

| 项 | 实测 | 判据 | 判定 |
| --- | --- | --- | --- |
| 帧数 | 53999 / 54000 | — | — |
| 触发次数 | **706** | 预测 711（±2） | **SKIP**（见 §三） |
| 丢帧 | **1** | L2 = 0 | **FAIL** |
| xrun | 0 | — | ✅ |
| `lateness` p50 / p99 / max | 0.125 / **0.625** / 93.17 ms | L3 p99 ≤ 33.3 ms | ✅ |
| 稳态每次修正 | 5.52 ms | L4 ≤ 6 ms | ✅ |
| `trend` 首末窗口中位数之差 | **−0.255 ms**（斜率 0.146 ppm） | L5 ≤ 5 ms 且不单调上升 | ✅ |
| 稳态分配 | 8985 次 / 1800 s = **4.99 /s** | L6 ≈ 5 /s | ✅ |
| `kivo-decode` 分配 | **1 次 / 30 分钟** | — | ✅ |
| 缓冲 | 54001 取走 / 54001 归还 / **泄漏 0** | L7 | ✅ |

进程 CPU 12.48%、呈现线程 0.71%（720p30，比 1080p 轻）。

---

## 二、最重要的一条：**没有"周期性踏步"**

`trend` 的最后 102 秒里，8 个窗口中位数从 76.52 µs 走到 76.27 µs —— **差 −255 ns**，
斜率 0.146 ppm（≈ 每秒 0.15 µs）。

也就是说：门在这 30 分钟里做了 706 次修正，**但没有把 `lateness` 推成一个斜坡**。
L5 想验的正是这个：**如果每秒一次的 5 ms 修正被"记账不干净"，`lateness` 会随时间爬升；
它没有爬。**

同时 `lateness` 的 p50 仍是 0.125 ms（= 6 个 48 kHz 采样的量化步长），p99 0.625 ms。
**30 分钟的抖动分布与 8 秒的一致。**

---

## 三、长跑撞到的那件事：一次 931 ms 的修正

`clock_health` 三格同时非零：

| 字段 | 值 |
| --- | --- |
| `jump_rebases` | **1** |
| `monotonic_rejects` | 3 |
| `extrapolated_frames` | 3 |
| `drift_max_correction_ns` | **931.38 ms** |
| 最差帧 lateness | 93.17 ms（媒体时刻 44.1 s） |

三处异常指向同一个时刻（≈ 44 s）：

1. 一次 **931 ms** 的修正（正常每次 5 ms）；
2. 唯一那帧丢失 / 5 次 `over_budget`；
3. 触发次数比预测少 5 次 —— 因为那一次大修正**替掉了约 186 次小触发**。

**为什么判 SKIP 而不是 FAIL**：预测式只描述"注入的速率漂移"，它没有"跳变"这一项。
一次跳变会让两边都对不上，这是**公式的边界**，不是门算错了。
所以校验器打印 SKIP 并写明 `jump_rebases=1`，**不是把阈值从 2 放宽到 10**
（放宽阈值 = 为了让红灯变绿改判据，这个项目禁止这么做）。

---

## 四、这笔账有一小块对不上（诚实记账）

| 项 | 值 |
| --- | --- |
| 注入应累积 | `2000 ppm × 1798 s` = **3596 ms** |
| 实际修正总量 | **4820 ms** |
| 差额 | **+1224 ms** |
| 已知来源 | 那次跳变贡献 ≈ 931 ms |
| **未归因** | **≈ 293 ms**（30 分钟里 ≈ 163 ppm 的额外超前） |

293 ms 没有解释。可能是音频时钟自身的晶振偏差（163 ppm 对手机晶振偏大，
但温度/负载下不是不可能），也可能是另两次 `monotonic_rejects` 留下的残差。
**本卡不猜，记下来。**

---

## 五、这轮失败的那一条（L2：丢帧 = 0）

30 分钟丢 **1 帧**（1/54000 = 0.0019%）。G6 的门槛是丢帧率 < 0.5% ——
**按 G6 是过的，而且余量 250 倍**；按我在设计稿里写的"L2 = 0"是不过的。

**两条都写出来，不挑对自己有利的那条。** 需要说明的是：那 1 帧落在 §三 的同一次跳变上，
不是稳态丢帧。

## 七、诚实清单（六条）

1. **30 分钟不是 2 小时。** 这次跳变出现在 44 秒，2 小时里可能有 150 次同类的 ——
   也可能一次都没有。**单次事件的出现率，一轮 30 分钟说不出来。**
2. **只有一轮。** 再跑一轮要 30 分钟；本卡的结论都标"单轮"。
3. **那 293 ms 未归因。** 不猜。
4. **`trend` 只看最后 102 秒**（序列容量 2048 点 @20 Hz，`truncated = true`）。
   全程平不平，靠的是 `lateness` 的 p50/p99 与 8 秒基线一致这条间接证据。
5. **720p 不是 4K。** 长片用 4K 不现实（编码 + 推送 + 存储）。
6. **只有 K40。**
