# P13-F：最差那一下在哪儿 —— 给分位数补上位置

> 前序：`65-p13e-status.md` §六.1 遗留的「4K60 r1 有一个尖峰没解释」。
> 本卡不是修 bug，是补上**让那个问题可以被回答**的那一格数据。

---

## 一、问题：报告能说「最差多大」，说不出「最差在哪」

P13-E 的证据表里躺着这一行：

| 轮次 | 帧 | mtd/p50 | mtd/p99 | mtd/max | pf/p99 | pf/max |
| --- | --- | --- | --- | --- | --- | --- |
| 4K60 r1 | 480 | 0.125 | 8.625 | **57.070** | **24.875** | **88.231** |

另外两轮是 1.6 / 0.9 ms。把这一轮的直方图展开，形态是这样的（`per_frame`，桶宽 0.25 ms）：

```
[1.00, 1.25)  ×3     ← 其余 464 个样本都在 [0, 1.00) 里
[1.25, 1.50)  ×1
[1.75, 2.00)  ×1
[2.25, 2.50)  ×1
[3.00, 3.25)  ×1
[8.50, 8.75)  ×1
[10.00,10.25) ×1
[10.50,10.75) ×1
[18.25,18.50) ×1
[24.75,25.00) ×1
[40.75,41.00) ×1
[57.00,57.25) ×1
[73.25,73.50) ×1
[88.00,88.25) ×1
```

**除最低那个桶外，每一级恰好一个样本。** 这个形态已经排除了两种解释：

- **不是持续劣化。** 持续劣化会让整个分布右移，p50 会跟着动。这里 p50 = 0.125 ms，
  与另外两轮**一模一样**。坏的是尾巴，不是主体。
- **大概率不是多次独立抢占。** 独立抢占会形成几个孤立的聚集，
  而不是一条「间隔递增」的阶梯。

剩下两种解释，在**分布上完全不可区分**：

| 解释 | 机制 |
| --- | --- |
| (a) 单次长卡顿后逐级追赶 | 视频 pts 停住、音频时钟继续走，每帧欠一点 |
| (b) 片尾收尾 | 最后几帧被重复呈现或 pts 不再推进 |

而且尾部那 6 个值（18.25 / 24.75 / 40.75 / 57.0 / 73.25 / 88.0）的**差值**是
6.5 / 16.0 / 16.25 / 16.25 / 14.75 ms —— 后四个几乎正好是一帧（16.67 ms）。
这更像 (a)/(b) 的同一种机制，而不是外部抢占。

**唯一能区分 (a) 和 (b) 的是位置。** 而报告层没有位置。

这一格缺失的代价不是「少个字段」：谁读到这张表，都会各自猜一个原因。
最糟的读法是「4K 播不动」，而另外两轮不支持这个结论。

## 二、根因：位置是序列的属性，而报告只留了分布

`SignedHistogram` 按定义丢掉顺序 —— 这不是缺陷，是它该做的事。
`percentile_ns(0.99)` 回答「第 2 差的样本多大」，永远不可能回答「它在第几个」。

而序列**其实在内存里**：`DriftSeries` 存了 2048 个 `DriftPoint{media_ns, lateness_ns}`，
按时间正序可取。从 P13-D 起它就在那儿，只是从来没人问过它「最大那个在第几」。

所以这一卡不需要新采集、不需要新通路，只需要**问一次**。

## 三、结构：`quantiles.<口径>.worst`

```jsonc
"quantiles": {
  "media_time_decimated": {
    "samples": 160,
    "p50": 125000, "p95": 375000, "p99": 8625000, "max": 57070364,
    "worst": {
      "index": 152,          // 当前窗口内时间正序的第几个被接受的样本（0 基）
      "of": 160,             // 该口径样本总数
      "media_ns": 7600000000,// 那一点的媒体时刻 —— 直接对 source.duration_us
      "lateness_ns": 57070364
    },
    "histogram": { ... }
  }
}
```

### 位置写在 `histogram` 之前

`render_quantiles` 有一条不变量：**块结尾不写逗号，块内 `histogram` 永远是最后一个成员**。
P13-E 已经在逗号上栽过一次（多写一个尾逗号 → 整份证据作废，且只在真机上才发现）。
`worst` 插在 `max` 与 `histogram` 之间，这条不变量一个字都不用改。

### `index` 是全场序号，不是窗口内序号

极值在 `note()` 里**累计**维护（O(1)），不是出报告时扫序列。
这个决定同时定死了 `index` / `of` 的含意：整场第几个、整场共几个。

扫序列的写法看着更自然，但它会在环形覆盖后与直方图分家 ——
直方图是累计的，最大值若发生在已被覆盖的旧段，序列里就找不回来了，
于是 `worst < max`，判据 F1 当场红，而且红得毫无道理（两个字段都对，只是口径不同）。

**代价**：`index` 不能拿去 `at()` 取点（`at()` 收窗口内下标）。这一条写在头文件里。

> 设计初稿写的是"环形覆盖后 `index` 是窗口内序号、`of` 同步缩成窗口大小"。
> 实现时改成累计维护，所以 F2 从"`of ≤ samples`"收紧成"`of == samples`"。
> 文档与代码不一致的地方，以能跑的那一份为准，并且把改的理由留下来。

### 为什么 `index` 和 `media_ns` 都要

- `index / (of - 1)` 是位置比 —— 回答「前 5% / 后 5%」。
- `media_ns` 回答「什么时刻」，且能直接与 `source.duration_us` 对照。
- 只有 `index` 会在 seek 之后串味（新时间轴从 0 重新计数）；
  只有 `media_ns` 则算不出占比。两个都在，读的人不用自己推。

位置比**不单独存**。存了就是两份位置，迟早不一致。

### 不存整条序列

160 / 480 个点全写进 JSON，证据文件从 ~6 KB 涨到 ~40 KB，而没有人会逐点读。
报告是摘要；「最差在哪」是摘要能承载的最大信息量。
要看全序列应当是另一条诊断通道（`--dump-drift`），不属于证据 JSON。

## 四、归到哪个家

```
core/pace/
├── pace_drift_series.hpp/.cxx    # + struct DriftExtreme；+ DriftSeries::max_point()
├── pace_stats.hpp/.cxx           # + DriftExtreme 逐帧极值；note_presented() 里 O(1) 比较
```

- **`DriftExtreme` 与 `DriftPoint` 同族**，放在 `pace_drift_series.hpp`：
  两者都是「漂移点的描述」，一个是单点、一个是极值点。
- **抽稀口径的极值由 `DriftSeries` 自己算**（`max_point()`）：
  它拥有序列，只有它能回答「第几个」。
- **逐帧口径的极值由 `PaceStats` 记**：逐帧**没有序列**（只有直方图），
  而 `note_presented(lateness_ns, media_ns)` 是唯一同时握着这两个值的地方。

### 为什么不让直方图记位置

`SignedHistogram::add(value)` 不知道媒体时刻。给它加一个 `media_ns` 参数，
等于让**分布类去管时间轴** —— 那是序列的职责。分布管分布，序列管位置。

### 为什么不给 `PaceStats` 也加一条逐帧序列

逐帧 480 点、60 秒 3600 点，超出 `kCapacity` 后环形覆盖，
而逐帧分布本来就不需要序列 —— 它的 p99 由直方图给。
为记一个极值而养一条 2048 点的序列是浪费；O(1) 比较就够。

## 五、判据 F

| 判据 | 内容 |
| --- | --- |
| F1 | `worst.lateness_ns == 同口径 max`，**逐位相等** |
| F2 | `0 ≤ index < of == samples`，且 `0 ≤ media_ns ≤ duration_us × 1000` |
| F3 | `samples > 0` ⇔ 存在 `worst`；`quantiles` 为空对象时不许出现 `worst` |

F1 是这卡最重要的一条：它证明**极值与直方图没有分家**。
两个字段各自维护、算法不同（一个扫序列、一个查桶），
若哪天 `max` 改了算法而 `worst` 没跟上，F1 立刻打红。

变异自测（必须全红）：

| 变异 | 命中 |
| --- | --- |
| `worst.lateness_ns = max + 1` | F1 |
| `worst.index = of` | F2 |
| `worst.media_ns` 写成桶下标 × 桶宽 | F2（超 duration） |
| `samples = 0` 却给一份 `worst` | F3 |
| 删掉 `worst` 整格 | F1（取不到即失败） |

## 六、这卡真正的产出：归因表

改完重跑 4K60 五轮，读 `worst.index/of` 与 `worst.media_ns`：

| 观察到 | 结论 |
| --- | --- |
| 五轮 max 都 < 10 ms | 88 ms 是单次偶发，标注「未复现」，不写进结论 |
| `index/of > 0.9`（片尾） | 收尾问题，**不是**播放能力问题 |
| `index/of < 0.1`（片头） | 冷启动 / 解码器初始化 |
| 位置分散 | 系统抢占，与 4K 分辨率无关 |

**边界**：这卡只给「最差那一下在哪」，**不给为什么**。
要归因到「是 CPU 抢占还是 pts 停滞」，还需要 per-frame 时间线
（`present_at`、`pts`、`audio_position` 三列逐帧落盘），那是下一张卡。

## 七、不做什么

- **不 dump 全序列。** 见 §三。
- **不重跑 `/1`、`/2`、`/3` 的证据。** 重写等于伪造。
- **不改抽稀逻辑、不改采样间隔、不改 `kCapacity`。** 这卡只加一格观测。
- **不把 `worst` 接进总收口层 4 的跨组对照。** D1/D2 需要成对喂入，
  总收口按目录逐份遍历 —— 同样的理由，同样的边界。
- **不解释这一轮的 88 ms。** 归因表给出的是「在哪」，不是「为什么」。
