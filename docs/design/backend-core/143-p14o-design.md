# 143 · P14-O 设计：让 `p99` 说出它可能的范围

> 卡片：P14-O
> 前置：P13-N（`p50_range`，`sync/12`）只给 `p50` 出版了范围；
> P14-M（`139-p14m-design.md`）修判据覆盖面时，第一次让 D1/D2 的配对池非空，
> 于是撞上一条**判不了的判据**并因此发现了这个洞。
> 结论：`quantiles.<口径>` 的 `p99` 后接三格范围；`sync/25` → `/26`；
> D2 从"断言不可判"改成"用区间算出来不可判"。
> **本卡不承诺把 D2 变成可判** —— 真机上它仍然不可判，但那时它是一个算式，不是一句话。

---

## 一、问题：判据说"差 20 倍"，而读者没法核对这句话

### 1.1 现场

`verify_p13d_drift.py` 的 D2 判据（P13-C 立的）：抽稀口径下，60fps 的 p99 不应超过
30fps 的 2 倍。P14-M 让配对池第一次非空之后，它撞到这样一对（1080p 60 s，
同设备同码率，只差帧率）：

| 侧 | `p99` | 落在哪个桶 | 那个桶里几个样本 | 桶覆盖 |
|---|---|---|---|---|
| 30 fps（`p13af-a1080p30-r1`） | 125 000 | 512 | **1196 / 1200** | [0, 250 000) |
| 60 fps（`p13af-b1080p60-r1`） | 625 000 | 514 | **3 / 1200** | [500 000, 750 000) |

商的点估计 5.00x。判据要求 ≤ 2.0x，于是它要么判失败、要么判通过 —— 两个都是编。

P14-M 给它写了 `not_applicable`，理由里那句"商算出来是 5.00x 但区间能差 20 倍"
是**手算的形容词**。读者拿到这份 JSON 无法核对：`/25` 的结构里 `p99` 是一个
裸整数，没有任何字段说明它是桶中心、也没说那个桶有多宽。要复算"这个 5.00x 有多少
是量化误差"，得自己把 `histogram.buckets` 捞出来数一遍 —— 而判据的全部意义
就是**不要求读者自己数**。

### 1.2 为什么 P13-N 当时只做了 `p50`

P13-N 的证据是："同一份 JSON 里两个 p50 差 66%"（桶中心 125 000 vs 真中位数 74 835）。
那是 `p50` 被误读的**直接现场**，所以先修它。`p99` 当时没有现场，只有一句
"将来也会有人误读"。

P14-M 把"将来"变成了现在：D2 就是那个误读现场，而且它是**唯一**一个
拿两个不同口径的 p99 相除的判据 —— 分母越小，同样的绝对量化误差被放大得越多。
30 fps 侧的真值在 15–30 µs 量级（`p50_range_low_ns` 在 11 666–32 552 之间波动），
而桶宽 250 µs 比这个真值还大 8 倍：**那一格的信息量接近于零**。

### 1.3 这一卡的真正产出

不是"让 D2 通过"，也不是"让 D2 可判"。是：

- `p99` 旁边出现它可能的范围，读者不必再从 `histogram` 手算；
- D2 的"不可判"变成 `[2.00x, 48.00x]` 这样的**算式**，任何人可以复算；
- 顺带把"桶宽是堵点"这句话从定性变成定量：区间下界正好压着门槛 2.00x，
  说明**在最乐观的读法下这条判据也没有余量**。

## 二、边界

| 项 | 本卡做不做 | 理由 |
|---|---|---|
| `quantiles.<口径>.p99` 三格范围 | ✅ 做 | D2 的直接输入 |
| D2 三段式判定（区间不交 ⇒ 判；相交 ⇒ 不可判但印区间） | ✅ 做 | 本卡存在的理由 |
| `p95` 也出版范围 | ❌ 不做 | 没有任何判据消费它。加字段是要付版本代价的，没有消费者的字段就是负债 |
| `pace.lateness_ns.p50/p99` 的范围 | ❌ 不做 | 那是**另一条链**：`pace.lateness_ns` 由 `PaceSummary` 直接出版（`samples/p50/p99/max/measured/reason`），不经 `render_quantiles`。给它加范围要动 `pace_stats.hpp` + `decode/18`，是独立一张卡 |
| 细化桶宽 | ❌ 不做 | 桶宽是 `SignedHistogram` 的定义（±128 ms / 1024 桶），改它等于改所有历史证据的可比性。本卡只让精度**可见**，不改精度本身 |
| `check_pair` 的分组键加"同源" | ⚠️ 部分做 | 见 §四.2：配对前先按 schema 版本过滤。完整的分组键重构留给下一卡 |

## 三、设计

### 3.1 三格，位置紧贴被解释的那个数

`render_quantiles()` 里，`p99` 之后、`max` 之前：

```
"p99": 625000,
"p99_range_low_ns": 500000,
"p99_range_high_ns": 750000,
"p99_bucket_samples": 3,
"max": 3949169,
```

`bucket_width_ns` **不再印第二遍**。它已经是这个块的公共定义（现在挂在 `p50` 那四格
后面），一个块里出现两次同一定义，迟早会有一次被人只改了其中一处。

这三格的键名与 `p50` 那三格逐字对齐（只换前缀）：同一件事在两个位置用两套命名，
读者要在脑子里做翻译，而翻译就会出错。

### 3.2 值从哪来：`percentile_range(q)` 已经是泛型

`SignedHistogram::percentile_range(double q)`（P13-N 写的）接受的本来就是任意 `q`，
报告层只是**从来没拿 0.99 调过它**。所以核心层一个字符都不用改 ——
这件事本身要记在状态卡里：不是"实现了新算法"，是"发现已有的算法只有一个调用点"。

### 3.3 报告层：两条 p50/p99 序列共用一个写法

`render_quantiles` 里现在会出现两次"取范围 → 印三格"。复制两遍是这类字段
最容易分家的写法（一次复制错前缀，`p99_range_low_ns` 里装的就会是 p50 的范围，
而 JSON 里它看起来完全正常）。

所以在匿名命名空间里加一个只能干一件事的函数：

```cpp
void render_range_cells(std::ostringstream& out, const std::string& pad,
                        const char* prefix, const SignedHistogram& histogram, double q);
```

它印 `<prefix>_range_low_ns` / `_range_high_ns` / `_bucket_samples`，`p50` 与 `p99`
各调一次。**它不做钳制、不做判断** —— 范围由 `SignedHistogram::percentile_range()`
算，理由与 P13-N 相同：这个文件只在 Android 侧编译，写在这里的逻辑没有桌面单测兜底。

### 3.4 schema `25` → `26`

加字段就升版本。升版本之后 P14-M 那条"认不出的高版本判红"会立刻生效：
任何还在用旧 `SCHEMA_LATEST` 的校验器都会报红，而不是静默跳过。

顺序因此固定为**先改判据、再升版本、最后取证**。

## 四、判据

### 4.1 N8–N13：`p99` 的三格（`verify_p13d_drift.py`）

N0–N7 守的是 `p50`，一个字都不改。`p99` 另开六个编号，门槛 `schema >= /26`：

| 编号 | 判据 | 抓什么 |
|---|---|---|
| N8 | 每个分位块都有 `p99` 三格 | 漏写（只改了 `p50` 那条路） |
| N9 | `p99 ∈ [low, high]` | 范围不含它要解释的数 |
| N10 | `0 ≤ p99_bucket_samples ≤ samples` | 桶内样本数越界 |
| N11 | `high − low ≤ 桶宽` | 范围不是求交来的（求交只会更窄） |
| N12 | `p99_bucket_samples` 等于从 `histogram` 复算（q=0.99）的桶计数 | 填了 `p50` 那一桶的计数 |
| N13 | `(low, high)` 等于从 `histogram` 复算的范围（q=0.99） | **填了 `p50` 的范围** —— 这是本卡最可能犯的错 |

N13 是这一组的核心：把 `p50` 的范围原样写进 `p99` 的三格，JSON 依然自洽
（N9 甚至可能过，因为 `p50 ≤ p99` 且 `p50` 的范围上界常常是 250 000），
只有"从分布按 q=0.99 复算"能抓住它。

`replay_p50_range(hist)` 改名为 `replay_percentile_range(hist, q)`，N6 与 N13
共用同一个实现。一个函数两个调用点，不是两份代码 —— 两份代码在秩口径上
分家只是时间问题。

### 4.2 D2：三段式

```
slow = 30fps 的 p99 中位数,  区间 [slow_lo, slow_hi)
fast = 60fps 的 p99 中位数,  区间 [fast_lo, fast_hi)
ratio_lo = fast_lo / slow_hi        ← 最有利于"没漂移"的读法
ratio_hi = fast_hi / slow_lo        ← 最不利于"没漂移"的读法
```

| 情形 | 判定 | 理由 |
|---|---|---|
| `ratio_lo > 2.0` | ❌ 失败 | 区间整个在门槛之上：换个读法也过不了 |
| `ratio_hi <= 2.0` | ✅ 通过 | 区间整个在门槛之下 |
| 其余 | 不可判 | 区间跨过门槛 —— 但**印出区间**，不再写形容词 |

没有范围字段的旧证据（`/12`–`/25`）走回原来那条"分辨力地板"分支，行为不变。

**配对池先按版本过滤**：一组里只要有一份带 `p99` 范围，就只用带范围的。
不同 schema = 不同量具，把两把尺量出的数一起取中位数，得到的是混合物的中位数——
这正是 P13-C 第一版"把所有 30fps 放一桶"犯的错，只是换了个维度。
过滤后会打印"本轮只比 N/M 份"，因为**份数下降本身是一个结论**，
不能安静地发生。

## 五、验收

| 项 | 判据 |
|---|---|
| 桌面构建 | `kivo_p12c_core_pace` 与单测目标编过 |
| 单测 | `quantile_tests` 增 n12/n13 两条，全绿 |
| 门禁 | `ctest -C Debug -R "kivo_p1[234]"` 25/25 |
| 旧证据 | `/25` 及更早**不被** N8–N13 误判（门槛 `>= /26`） |
| 新证据 | 真机 1080p30 + 1080p60 各一轮，`/26`，每块带三格 |
| 总收口 | `verify_p12_all.py` 全绿，覆盖份数不降 |
| 变异 | N8–N13 各一条，D2 三段各一条，全部按预期 |

**预言并在取证后核对**（用 §1.1 的桶号可以直接算出，不靠跑一遍才知道）：

| 量 | 预言值 | 依据 |
|---|---|---|
| 30fps `p99_range` | [15625, 250000) | 桶 512 ∩ `[min=15625, max+1)` |
| 60fps `p99_range` | [500000, 750000) | 桶 514 ∩ `[min, max+1)` |
| D2 商区间 | **[2.00x, 48.00x]** | 500000/250000 与 750000/15625 |

下界 2.00x 不是巧合：两侧 p99 分别落在桶 512 与 514，下界就是两个桶界之比。
**它正好等于门槛** —— 这条判据在最乐观的读法下也没有余量。

## 六、不做

1. **不细化桶宽。** 见 §二。
2. **不给 `p95` 出版范围。** 没有判据消费它。
3. **不动 `pace.lateness_ns`。** 它由 `PaceSummary` 直接出版，不经 `render_quantiles`。
4. **不改 N0–N7 的任何一条。** `p50` 那六条是绿的，动它就是把已知的绿换成未知。
5. **不重构 `check_pair` 的分组键。** 本卡只加"按版本过滤"，完整重构（同源、同轮次）
   留给下一卡 —— 那时才需要决定"人为注入轮次算不算同源"。

## 七、自然家族树

本卡**不新增源文件**，只在既有家族里各加一格。

```
backend/include_private/video/video_plane/core/pace/
└── pace_histogram.hpp            ← 不改：percentile_range(q) 本来就是泛型

backend/src/video/video_plane/backends/avsync/report/
└── av_sync_report.cxx            ← 改：render_range_cells + p99 三格 + schema /26

backend/tests/video/pace/p13n_quantile_tests/
└── quantile_tests.cpp            ← 改：n12（p99 范围与 p50 不同且含 p99）、
                                        n13（溢出时退化成点）

tools/
├── verify_p13d_drift.py           ← 改：N8–N13 + D2 三段式 + SCHEMA_LATEST 26
├── verify_p12_all.py              ← 改：两张表登记 /26
└── run_p14o_p99_range.sh          ← 新：两个帧率各一轮

docs/
├── design/backend-core/143-p14o-design.md
├── design/backend-core/144-p14o-status.md
└── evidence/p14o/                 ← 新：真机两轮
```

**一个文件一件事**：
`av_sync_report.cxx` 的职责是"把统计量写成 JSON"，`render_range_cells` 只是
"把三格印出来"这一个动作的重复消除，不承担任何判断；
判断（区间怎么算）在 `pace_histogram.cxx`，判定（区间够不够判）在 `verify_p13d_drift.py`。
三处各一件事，没有一处同时知道两件事。
