# 139 · P14-M 设计：判据本身也要有人验

> 卡片：P14-M（P14 系列收尾）
> 前置：P14-L（`137-p14l-design.md`）诚实清单第①条 —— `sync` 报告同一缺陷一处未改
> 结论：先不接 `sync` 侧，先把**判据的覆盖面**修好。实测 204 份 `sync` 证据里有
> **138 份从来没有被 drift 判据看过**，而总收口一直报「四层通过」。
> schema：不动（`sync/24` 不变）——这张卡只改验证脚本

---

## 一、问题：三种「没验」长得像「验过了」

### 1.1 起因

P14-L 收尾时我写下下一步是「先接 `sync` 侧」。动手前先跑了一遍现状，撞到的是另一件事：

```
$ python tools/verify_p13d_drift.py docs/evidence/p14l/p14l-cpupaced-1080p30-sync.json
– p14l-cpupaced-1080p30-sync.json：不适用（schema 是 'kivo.p12c.sync/24'：
  D/E/F 判据只适用于 ('kivo.p12c.sync/3', …, 'kivo.p12c.sync/13')）
另有 1 份不适用（不是失败）。
结论：全部通过。
```

一份证据，四十多条判据，**一条都没跑**，而结论是「全部通过」。

### 1.2 三层缺口

| 层 | 缺口 | 影响份数 |
|---|---|---|
| ① 扫描范围 | 总收口只 `glob("docs/evidence/p13*/*-sync.json")` | `p14*` 目录 **28 份** + `p12c`/`p12d`/`p12f3` **15 份**，共 43 份一次都没被喂进去 |
| ② 版本表 | `SCHEMA_ORDER` 停在 `/13`，而报告已经到 `/24` | `p13*` 目录里 **95 份**判「不适用」 |
| ③ 判据假设 | 版本补上之后才暴露出来的陈旧前提 | 见 §一.4 |

实测分布（`docs/evidence/p1*/*-sync.json`，204 份）：

```
p13* 目录  161 份  ├─ schema /3–/13   54 份  ← 真的被验过
                   ├─ schema > /13    95 份  ← 版本不认识，判「不适用」
                   └─ schema /1       12 份  ← 旧格式，判「不适用」（诚实）
p14* 目录   28 份                          ← 完全没进扫描范围
p12* 目录   15 份                          ← 完全没进扫描范围（其中 15 份为 /1）
────────────────────────────────────────────────────────────────
修前真正被验过的：           54 份
修前从未被 drift 判据看过：  95 + 28 + 15 = 138 份（占 204 份的 68%）
```

关键在第三行：那 95 份是 `/14`–`/24`，**字段一个不缺，只是脚本没登记过这些版本**。
它们与 `/1` 那 27 份被判「不适用」的性质完全不同 —— 一个是判据没话说，一个是判据没看。

### 1.3 为什么这是同一个病

这个项目已经为「两张表只更新一张」栽过三次：

| 卡 | 形态 |
|---|---|
| P13-E | `card_checks` 漏分发 —— 加了卡，没加进分发表 |
| P13-F | 层 4 只扫 `p13d/` —— 新增证据目录不在白名单 |
| P13-K | 五张 schema 表各写各的 —— 改成从 `SCHEMA_ORDER` 派生 |

P13-K 的修法是对的：**版本序单点登记，判据自动跟进**。但它只解决了「五张表」，没解决「那张 ORDER 表本身谁来看」。

于是第三代出现了：**`SCHEMA_ORDER` 从 `/13` 之后没人加，而这一路的失败模式是「不适用」，不是「失败」** ——
所以它比前三次更隐蔽：前三次至少会缺字段报红，这一次连红都不会有。

> 一句话：**「不适用」被算成了「通过」。**

### 1.4 补齐覆盖之后炸出来的四条

把版本表临时扩到 `/24`（只在 `build/p14m_recon/probe_drift.py` 里试，不改原文件），
全量 209 份跑一遍：**13 份红，14 项失败**，全部集中在三条判据上。

| 判据 | 份数 | 实测 | 真因 |
|---|---|---|---|
| K3 膨胀比 | 9 | 证据 1.242853 vs 复算 1.242880 | 容差 1e-5 是按「舍入 3e-6」估的；两个 SE 都是 `%.6f`，**除法**把相对误差叠加到 ≈3.3e-5 |
| L5 `unknown ⇔ 不可用` | 3 | `verdict=unknown`、`usable=True` | P13-O 加了**第二条** `unknown` 成因（半程 `inconsistent`），判据没跟上 |
| H2 `observed_hz` 上界 | 2 | 20.016681 vs 上限 20.016681 | 拿**打印到 6 位**的值去比**精确重算**的上界，末位四舍五入即判「超了」 |

三条里最值得记的是 H2：精算后 `observed` 与 `ceiling` 的差是 **0.0**（都是 `1200/(59.95 s)`）。
判据把「正好落在边界上」判成了「越过边界」——**它自己制造了一条红**。

### 1.5 第四条：配对池一放开，D1/D2 第一次真的开始配对

`check_pair`（D1/D2）也挂在 `SUPPORTED_SCHEMAS` 上。版本表停在 `/13` 时，
**配对池整批为空** —— 这与 P13-F 那次「D1/D2 配对池整批为空，那两卡的证据从来没被跨组判据看过」
是同一个错的**复发**。

放开之后第一次配对，立刻抓到：

```
✗ D2 media_time_decimated/p99：60fps ≤ 30fps 的 2x
  —— 0.625 ms / 0.125 ms = 5.00x
```

定性结论：**不可判，不是失败**。

| 组 | p99 | 桶宽 | 含义 |
|---|---|---|---|
| 30fps（9 份中位数） | 125 000 ns | 250 000 ns | 落在**第一个桶的中心** —— 桶底 |
| 60fps（2 份） | 625 000 ns | 250 000 ns | 第 3 个桶，有真实邻样本 |

`p14h-smoke` 的原话：1200 个样本里 **1199 个在第 512 桶**，`p50_range_low_ns = 12291`、
`high_ns = 250000`。也就是说这个「p99 = 125 µs」的真实取值区间是 `[12 µs, 250 µs]`，
**上下差 20 倍**。拿它的中心当分母，商可以是 2.5x 到无穷。

这是 P13-N 那条教训（`p50_range`）的横向延伸：**P13-N 只给 `p50` 出版了范围，`p99` 没有。**
所以 D2 在现有桶宽下不能判 —— 它该说「不可判」，而不是「通过」或「失败」。

## 二、设计

### 2.1 版本表：区间取代逐版本登记

```python
SCHEMA_MIN    = 3
SCHEMA_LATEST = 24
SCHEMA_ORDER  = tuple(f"/{n}" for n in range(SCHEMA_MIN, SCHEMA_LATEST + 1))
```

「新增一个版本」这个动作从**要记得改表**变成**只改一个数**。

### 2.2 未知高版本：灰变红

这是整张卡的核心判据。

| 情况 | 现在 | 改成 |
|---|---|---|
| 版本 < `SCHEMA_MIN`（`/1`、`/2`） | 不适用 | 不适用（旧格式确实没有这些字段，合理） |
| 版本在区间内 | 判 | 判 |
| 版本 > `SCHEMA_LATEST` | **不适用 → 沉默通过** | **失败**：「脚本落后于实现」 |

理由：判据不认识这一版，唯一诚实的结论是「我验不了」，而「验不了」在汇总里必须是红的。
否则下一个版本又会在无人察觉的情况下沉默通过 ——正是这次发生的事。

### 2.3 覆盖清单：不适用必须点名

`main()` 末尾原来只印一句「另有 N 份不适用（不是失败）」。
改成**按 schema 版本分组**列出来：

```
覆盖：180 份（判据真的跑了）
不适用：28 份 —— **这不是通过**，只是这些判据对它们没话说
不适用：15 份
  /1   15 份  —— 旧格式，分位数在顶层
```

这样「28 份不适用」不可能再被读成「都很正常」。

### 2.4 四条判据的修法

| 判据 | 修法 | 为什么不是放宽阈值 |
|---|---|---|
| K3 | 容差 1e-5 → `1e-4 × max(1,|expect|)` | 1e-4 是**按打印精度推出来的地板**（实测最大偏差 3.3e-5）；真走另一条公式会差几个数量级 |
| L5 | `unknown ⇒ (!usable or halves_relation == inconsistent)`；`within/over ⇒ usable 且不改判` | 接受 P13-O 新增的语义，不是取消判据 |
| H2 | 用 `accepted`（整数）与 `media_span`（整数）**重算** `observed`，再与上界比 | 证据里那个 `observed_hz` 是 `%.6f` 打印值；拿它比精确界，等于拿尺子的刻度去比尺子本身 |
| D2 | 任一侧 `p99 ≤ bucket_width` ⇒ **不适用**，理由写进输出 | 分辨力不足时不下结论 —— 与 P13-O 的 `slope_halves_resolution_sufficient` 同一取舍 |

### 2.5 扫描范围

`verify_p12_all.py` 里 `docs/evidence/p13*/*-sync.json` → `docs/evidence/p1*/*-sync.json`。

代价：`p12c` / `p12d` / `p12f3` 的 15 份 `/1` 证据也会进来，全部判「不适用」。
**这正是要的** —— 它们本来就该在清单里被点名，而不是靠「glob 没扫到」消失。

## 三、自然家族树（动哪些文件）

```
tools/
├── verify_p13d_drift.py     ← 版本区间 / 未知版本=红 / 覆盖清单 / K3 / L5 / H2 / D2
└── verify_p12_all.py        ← 扫描范围 p13* → p1*
```

**只动两个文件，不动 C++，不动报告层，不改 schema。**
这张卡的全部产出是「判据终于跑起来了」，按项目铁律这不需要改实现——
需要改实现的是它跑出来的结论。

---

## 四、不做的事（边界）

1. **不改 `sync` 报告。** P14-L 诚实清单第①条（sync 侧 `over_budget_frames` / `lateness_ns`
   仍是裸数）留到下一张卡。理由：先让判据能验，再接字段——反过来就是
   「新字段带着一整块没人验的字段通过总收口」，P13-K 那张卡存在的理由。
2. **不给 `p99` 出版范围。** D2 这一轮判「不可判」就够了；细化桶宽或给 p99 加范围
   是独立一张卡（会波及 204 份证据的可比性）。
3. **不改 D2 的 2x 阈值。** 阈值不是这次的病；分辨力才是。
4. **不合并 `p13af` / `p14*` 的 30fps 池。** 分组键不动，只加「不可判」分支。

## 五、验收

| 项 | 判据 |
|---|---|
| 覆盖 | 204 份 `sync` 证据全部有结论（通过 / 失败 / 不适用+理由），不再有一份「没被打开」 |
| 未知版本 | 造一份 `sync/25` 的样本 ⇒ **必须红**，且理由写「脚本落后于实现」 |
| K3 | 全部证据通过；植入 `inflation = se/iid × 1.5` ⇒ 红 |
| L5 | 3 份 `inconsistent` 证据通过；把一份 `within_budget` 改成 `unknown` ⇒ 红 |
| H2 | 2 份边界证据通过；把 `accepted` 加 100 ⇒ 红 |
| D2 | 5.00x 那份判「不适用」并写明分辨力地板；把桶宽改成 50 000 ⇒ 恢复可判 |
| 总收口 | `verify_p12_all.py` 四层通过，且输出里能看到「覆盖 180 份 / 不适用 28 份」 |

## 六、这张卡真正的结论

P14-L 修的是「一个 0 不知道自己是哪来的」。
P14-M 修的是**「一个判据说不知道，然后被当成了通过」**。

前者是字段语义，后者是**证据链的最外层**：如果验证脚本可以静默地不看，
那么前面 14 张卡做的所有 `measured` / `range` / `verdict` 都只是写给人看的装饰。
