# 82 · P13-N 设计：分位数必须自己说出精度

> 卡片：P13-N
> 前置：P13-J（`74-p13j-design.md`）把窗口中位数换成精确值，却没管同名的整场 p50
> 结论：每个 `quantiles.<口径>` 的 `p50` 后面出版「可能范围 + 桶内样本数 + 桶宽」，
> 整批点另给一个精确参照 `median_of_window_medians_ns`
> schema：`kivo.p12c.sync/11` → `/12`

---

## 一、问题

### 1.1 同一份证据里的两个 p50

从 P13-M 的四轮真机证据里任取一份（`docs/evidence/p13m/p13m-plain-r1-sync.json`）：

| 字段 | 值 |
|---|---|
| `quantiles.media_time_decimated.p50` | **125 000 ns** |
| `quantiles.media_time_decimated.p95` | **125 000 ns** |
| `quantiles.per_frame.p50` | **125 000 ns** |
| `trend.window_quantiles.p50` | **125 000 ns** |
| `trend.window_median_ns[0..7]` | 73 385 / 73 646 / 74 364 / 73 688 / 73 438 / 73 855 / 73 437 / 73 646 |

四个 p50 全是 125 000，而同一份证据里八个窗口中位数全在 73 400~74 400。
差 **68%**。

四轮都一样：

| 轮次 | 桶 512 里样本 | 占比 | `quantiles.*.p50` | 窗口中位数的中位数 | 偏高 |
|---|---|---|---|---|---|
| r1 平跑 | 2568 / 2600 | 98.77% | 125 000 | 73 646 | **+69.7%** |
| r2 向前 seek | 2349 / 2400 | 97.88% | 125 000 | 73 844 | +69.3% |
| r3 向后 seek | 3147 / 3199 | 98.37% | 125 000 | 73 438 | +70.2% |
| r4 冻结 2 s | 2518 / 2555 | 98.55% | 125 000 | 73 321 | +70.5% |

### 1.2 它们不打架

`p50 = 125 000` 是**直方图桶 512 的中心**。桶 512 覆盖 `[0, 250 000)`。
真中位数 73 646 确确实实在这个区间里。

所以这两件事都对：

- 直方图只能告诉你「中位数落在 0~250 µs 这一桶」；
- 精确选值告诉你「就是 73.6 µs」。

**错的是表达**：`125 000` 被写成一个裸整数，紧挨着 `p95: 125000`、`p99: 375000`、
`max: 2632241`，读者没有任何线索能判断第一个数是不是量出来的。

### 1.3 一个更刺眼的旁证

`p50` 和 `p95` 相等（都是 125 000）。两个**不同的分位数**给出**同一个数** ——
这本身就在说"这把尺子在这个范围内只有一个刻度"。

而 `p99 = 375 000` 也是桶中心（桶 513 的中心）。整份分布真正的形状
（`min = 10 782`，`max = 2 632 241`）只体现在 `min` / `max` 两格上，
中间三个分位数全是 250 µs 网格上的点。

### 1.4 这个错是 P13-J 带进来的

P13-J 把八个窗口中位数从"每窗一个直方图取桶中心"换成"从原始值 `nth_element` 选"，
理由写得明明白白：桶中心量化误差 ±125 µs，与要分辨的 130 µs 同量级，
**用桶版本 1 ppm 这个量级永远量不出来**。

但那轮只改了窗口那一份。整场的 `quantiles.<口径>.p50` 还在用桶中心，
而它和窗口那一份**在 JSON 里看起来是同一把尺子** —— 两个都叫 p50。

改一半比不改更危险：不改时两个都是 125 000，读者会去查桶宽；
改一半时一个 125 000、一个 73 646，读者只会认定"数据有问题"。

### 1.5 为什么不能"顺手把 p50 改成精确值"

直方图是**累计**的（覆盖整场，环形覆盖之后继续加），而序列环只有 2048 点
（102.4 s）。130 s 的片源里，直方图有 2600 个样本，序列里只剩最后 2048 个。

拿序列算精确 p50，得到的是"最后 102.4 s 的中位数"，而字段名写着整场 ——
那是 P13-H 修过的同一个病（分子累计、分母窗口），只是这次藏在一次替换里。

要真做整场精确分位数，得存下全部样本或引入分位数草图（t-digest 之类）。
前者内存随时长线性增长，后者是一个新算法 + 一套新误差分析 —— 为了一格
只差 ±125 µs 的数，代价与收益完全不成比例。

**这条判据真正要回答的问题不是"更准是多少"，是"读者会不会读错"。**

## 二、做法

### 2.1 补的是表达，不是精度

`p50` 的值一个字不改（还是桶中心，还是可复算）。改的是它**旁边多了三格**：

```json
"p50": 125000,
"p50_range_low_ns": 10782,
"p50_range_high_ns": 250000,
"p50_bucket_samples": 2568,
"bucket_width_ns": 250000,
```

读法：**"p50 = 125 000，它可能的范围是 [10 782, 250 000)，那个范围里 2568 个样本
（占 98.8%），尺子的刻度是 250 000。"**

三格各回答一个问题：

| 字段 | 回答 | 为什么必须有 |
|---|---|---|
| `p50_range_low/high_ns` | 真值可能在哪 | 只给 `bucket_width_ns`，读者还得自己算桶号、自己乘、自己夹 min/max |
| `p50_bucket_samples` | 这个范围里挤了多少样本 | 98.8% 挤在一个桶里，和 3% 挤在一个桶里，`p50` 的可信度完全不同 |
| `bucket_width_ns` | 刻度是多少 | 它是**定义**不是观测；写出来，上面两个数就能独立复算 |

`p50_range` 取的是 `桶界 ∩ [min, max]`，不是裸桶界。这一轮 `min = 10 782`，
所以下界是 10 782 而不是 0 —— 真值不可能是 0（一个样本都没有）。
钳制只会让范围**变窄**，编码成判据 N4。

### 2.2 定位只能有一个来源

`percentile_ns(q)` 原来在函数体里内联了一段「跳过下溢 → 逐桶累加 → 命中」的循环。
`percentile_bucket(q)` 如果要再写一遍，两段代码就会在边界上分家：

- `rank <= below_` 还是 `rank < below_`？
- 桶内命中是 `rank <= accumulated` 还是 `<`？

任一处写反，证据里就会出现「p50 = 125 000，落在桶 511」这种自相矛盾的一对。
P13-M 的 `segments` 正是这么坏的（两处各算一遍"是不是新时间轴"）。

所以抽成私有 `locate(q)`，两个公开函数都调它：

```cpp
struct Located {
    std::int32_t bucket = PercentileBucket::kBelowRange;  // -1 / kBucketCount
    std::int64_t samples = 0;                              // 该桶（或溢出区）计数
};
[[nodiscard]] Located locate(double q) const noexcept;
```

`percentile_ns` 拿 `bucket` 去取桶中心并钳进 `[min, max]`；
`percentile_bucket` 把 `bucket` / `samples` 原样交出去。

判据 N5 / N6 从 `histogram.buckets` **独立复算**这两件事，与证据逐位比对。

### 2.3 范围算在 core，不算在报告层

`av_sync_report.cxx` **只在 Android 侧编译**（`backend/CMakeLists.txt` 里没有它）。
写在那里的逻辑没有桌面单测，只能靠真机证据 + Python 复算。

而"钳制"这件事恰好有两处容易写反：

```cpp
out.low_ns  = std::max(bucket_low_ns(i), min_);       // 下界取大
out.high_ns = std::min(bucket_high_ns(i), max_ + 1);  // 上界取小（开界）
```

取反了会得到一个**不含 `p50` 的空区间**，而空区间在 JSON 里长得像
"范围很窄、很准"。所以这一格落在 `SignedHistogram::percentile_range()`，
由单测 n03 / n04 在桌面上钉住。

`SignedHistogram::bucket_low_ns()` / `bucket_high_ns()` 同时补上 ——
三者（中心/下界/上界）是同一套映射的三种说法，必须写在一个地方。

### 2.4 整批点给一个精确参照

`trend` 里加一格：

```json
"median_of_window_medians_ns": 73646,
```

R 是 8 个 `window_median_ns` 排序后的第 `(n−1)/2` 个。

**它不是全体样本的中位数** —— 中位数不可合并，只有各窗样本数相等时才近似成立
（满容量单段时每窗 ≈ 256 点）。字段名里带 `of_window_medians` 就是为了
不让人把它当成 `p50` 的精确版。

它的作用是给那个 68% 的差一个**可引用、可复算**的对照值：
读者拿 `quantiles.*.p50 = 125000` 和 `median_of_window_medians_ns = 73646`
并排看，再看 `p50_range = [10782, 250000)`，那 68% 立刻从"数据有问题"
变成"桶太粗"。而 73646 这个数**完全可以从 `window_median_ns` 数组复算**
（判据 N7）。

只在 `window_median_exact == true` 时出版。有窗退回桶中心时，这个"中位数的中位数"
混着桶中心与真值，拿去对照只会把两个误差叠加 —— 那时整格不写，
缺席本身就是一句"这一轮没有精确参照"。

### 2.5 秩口径必须与 `percentile_ns(0.50)` 一致

`(n−1)/2` 而不是 `n/2`：

| n | `(n−1)/2` | `n/2` | `percentile_ns(0.50)` 的秩 |
|---|---|---|---|
| 8 | 3（第 4 个） | 4（第 5 个） | `ceil(0.5×8) = 4` → 第 4 个 ✓ |
| 7 | 3（第 4 个） | 3（第 4 个） | `ceil(0.5×7) = 4` → 第 4 个 ✓ |
| 1 | 0 | 0 | `ceil(0.5)` = 1 → 第 1 个 ✓ |

n = 8 时两者差一个元素。两个中位数用两套秩，就没法放在同一张表里比 ——
而这张卡存在的全部理由就是让它们能比。单测 n07 用一个严格递增的构造
（第 w 窗的值恰好是 `w` ms）把这件事钉死：正确答案 3 ms，`n/2` 会给 4 ms。

## 三、判据 N0–N7

| # | 判据 | 抓什么 |
|---|---|---|
| N0 | 每个分位块都有四格 | 报告层没跟上 schema，或某个块漏写 |
| N1 | `bucket_width_ns == 250000` | 桶宽在 Python 侧**独立写死**，不从证据读 |
| N2 | `p50 ∈ [range_low, range_high]` | 声明的范围不含它要解释的那个数 |
| N3 | `0 ≤ p50_bucket_samples ≤ samples` | 填了负数或超过总数 |
| N4 | `range_high − range_low ≤ 桶宽` | 求交只会变窄；宽于一个桶说明这一格不是求交得来的 |
| N5 | `p50_bucket_samples` = 从 `histogram` 复算的桶计数 | 恒填 0 / 恒填总数 / 填了 `below` |
| N6 | `range` = 从 `histogram` 复算的范围 | N5 钉桶号，这条钉交界 |
| N7 | `median_of_window_medians_ns` = `window_median_ns` 排序后第 `(n−1)/2` 个 | 秩口径写成 `n/2`，或不排序直接取中间 |

N5 / N6 是这一组里唯一"不信任何手填数字"的部分：桶号、桶计数、范围全部从
`histogram.buckets` 重算。`/11` 及以前根本做不到 —— 那时证据里只有 `p50`
一个数，没有桶号，复算方无从核对它落在哪儿。

## 四、变异自测计划

| # | 变异 | 预期 |
|---|---|---|
| C1 | `locate()` 的 `rank <= accumulated` 改成 `<` | n06 红（秩压在边界上会挪到下一桶） |
| C2 | `locate()` 的 `rank <= below_` 改成 `<` | n04 红（溢出样本不再走 `min_`） |
| C3 | `percentile_bucket` 的 `exact` 恒 `false` | n04 红（溢出被报成"量化过"） |
| C4 | `percentile_bucket` 的 `samples` 给 `accumulated` 而不是桶计数 | n02 / n06 红 |
| C5 | `percentile_range` 的 `low` 用 `std::min`、`high` 用 `std::max` | n03 红（范围变空或超宽） |
| C6 | `percentile_range` 去掉与 `min_` 求交（直接用桶界） | n03 红（下界变 0） |
| C7 | `median_of_window_medians_ns` 的秩改 `recorded / 2` | n07 红（3 ms → 4 ms） |
| C8 | `median_of_window_medians_ns` 不排序直接取 `medians[recorded/2]` | n07 红（窗口值不是递增输入时） |
| C9 | `bucket_high_ns` 少加一个桶宽（等于 `bucket_low_ns`） | n02 / n03 红 |
| C10 | 报告层 `p50_range_low_ns` 写成 `p50_range_high_ns`（两格对调） | 校验器 N2 红 |

C10 是唯一一条打在校验器层的 —— 桌面单测看不到报告层（它只在 Android 编）。

## 五、不做的事

1. **不改桶宽。** 250 µs 是为"1 帧时长（16.7 ms @60fps）"这个 G6 判据选的，
   对 `over_budget_frames` 完全够用。为了让 p50 好看而把桶改到 1 µs，
   桶数要涨 250 倍（1024 → 256000），8 KB 变 2 MB —— 那是为了一格诊断数字
   把热路径结构改掉。
2. **不存全样本。** 见 §1.5。
3. **不引入分位数草图。** t-digest / KLL 各有各的误差界，而这里要解决的问题
   是"读者会不会读错"，不是"能不能再准 100 µs"。
4. **不改 `p95` / `p99`。** 它们与 G6 的 45 ms 预算比，250 µs 是 0.55%，
   无关紧要。只有 `p50` 被拿去和窗口中位数并排比，才需要这一组标注。
5. **不重写 `/11` 及以前的证据。** 那些证据里没有这四格，N 判据只在 `/12` 上成立。

## 六、诚实清单（设计期）

1. **`p50_range` 不是置信区间。** 它只是"桶界 ∩ 样本范围"—— 一个几何上的
   可能范围，不含任何概率含义。真值在这个范围内的分布是未知的（从 98.8%
   挤在一个桶里这个事实看，它极可能贴近桶的下沿，而不是均匀分布）。
   **不要把它当成 95% CI 去引用。** 真正的 CI 只在斜率上有（`slope_ci_*`）。
2. **`median_of_window_medians_ns` 不是全体中位数。** 中位数不可合并。
   8 窗等样本时才近似等于整批中位数；seek 之后点可能挤在一窗里，
   那时它会有偏。它存在的意义是"给一个可复算的对照值"，不是"给出真值"。
3. **98.8% 挤在一个桶里这件事，说明直方图在这个量级上几乎没分辨力。**
   本轮只是把这件事写进证据，没有修好它。要真正提高整场分位数的分辨力，
   需要 §5.2 / §5.3 里被否掉的那两条路之一。
4. **`bucket_width_ns` 在三个块里重复出现，是刻意的冗余。** 它可以让每个块
   单独自解释，不必跨块找。代价是每份证据多几十字节。
5. **N7 依赖 `window_median_ns` 数组出版。** 那个数组是 P13-I 加的；
   若哪天有人为了瘦身把它删掉，N7 会静默降级成"无参照可验"（返回 True），
   而不是红。这是这一组里唯一一处"缺数据 ⇒ 不算失败"的地方。
6. **`p50_range` 的钳制在真机上几乎总是生效。** `min` 是 10 782，
   远小于桶下界 0 —— 所以下界永远是 `min`。看起来像"没起作用"，
   实际是"样本范围比桶窄"的正常结果。r4 那份证据的 `min = −406 147`
   （负数，冻结造成的），那时下界才真的是桶下界 −128 ms 以上的一段。
