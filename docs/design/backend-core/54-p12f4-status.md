# P12-F4 · 证据总收口（P12 结题）

- 版本：V1.0
- 日期：2026-10-30
- 设计：`53-p12f4-design.md`
- **结论：P12 可交付。230 份证据、四层校验全通过、7 个子校验器 exit 0，另含 46 项已声明的豁免。**
- 交付物不是这份文档，是 **`tools/verify_p12_all.py`** —— 它会自己变红。

---

## 一、收口跑的是什么

```bash
python tools/verify_p12_all.py            # 全量
python tools/verify_p12_all.py --self-test  # 证明它能打红
python tools/verify_p12_all.py --json artifacts/p12f4/report.json
```

实测输出（2026-10-30）：

```
=== P12 证据总收口 ===
证据文件      230 份（不含 superseded/）
层1 结构层    通过
层2 卡片层    通过
层3 红线层    通过
层4 复用层    通过

--- 豁免明细（不是失败，但要知道范围）---
  ~ 16 份早期音频探针证据无时间戳（P12-C 早期格式，补时间等于伪造，故豁免）
  ~ 30 份长稳中途快照的 completed=false 不计为静默失败（它们本来就没跑完）

结论：P12 可交付（7 个子校验器全部 exit 0，含 46 项已声明的豁免）
```

四层各自的含义：

| 层 | 管什么 | 数量 |
| --- | --- | --- |
| 1 结构 | 可解析、schema 在白名单（24 种）、有实测时间戳、无占位符 | 230 份逐份 |
| 2 卡片 | 12 组不变量（判据抄自各卡验收文档） | 12 组 |
| 3 红线 | 零静默失败 / 零无解释 / 零含糊 / 恒真字段告警 | 全组 |
| 4 复用 | 调 6 个既有校验器（7 次调用），**不重写判据** | 7 个 exit 0 |

## 二、自检：证明它不是"永远通过"

```
=== 校验器自检（8 个变异必须全部被抓到）===
  ok   删掉 schema（期望层1）
  ok   schema 换成未知（期望层1）
  ok   塞一个 TODO（期望层1）
  ok   静默失败（期望层3）
  ok   不可测却无理由（期望层3）
  ok   HDR 没设 dataspace（期望层2）
  ok   seek 超预算（期望层2）
  ok   声称实现了 tonemap（期望层2）

8/8 个变异被抓到
```

变异全部作用在**内存深拷贝**上，不碰磁盘。抓到 <8 个就以退出码 2 失败
—— 这是"校验器的单测"。

## 三、收口过程中修正的 5 处（3 处是我判据写错）

第一次跑全量，结果是 **29 + 5 + 30 + 1 条失败**。逐条看下来，其中三处不是证据有问题，
是**判据与真实语义不匹配**：

| 现象 | 我的判据 | 真实语义 | 处理 |
| --- | --- | --- | --- |
| 30 份 `-t####.json` 报"静默失败" | `completed=false` 且 `error` 空 = 失败 | 长稳每 60s 拍的中途快照**本来就还没跑完** | 排除中途快照，计数并明示 |
| `p12c3-no-audio-track` 报"没解到 EOS" | `reached_eos` 必须 true | 这条是**负向用例**（无音轨），不该解到 EOS | 跳过负向样本 |
| `verify_p12d_multi paced` 报"没开节拍" | 传了 `multi-r1-0.json` | 该传 `p12d2-paced-*.json`（我传错文件） | 改用正确的证据集 |

另两处是**真实的历史欠账**，不是判据错：

| 欠账 | 数量 | 处理 |
| --- | --- | --- |
| 早期音频探针证据无时间戳 | 16 份 | **豁免但明示**；不补（补一个当前时间 = 伪造） |
| F2 未达成时的 5 轮 seek 证据会红 | 5 份 | 移入 `docs/evidence/p12f2/superseded/`，与 F2A 的归档方式一致 |

**关键决定**：豁免必须在输出里显式列出。一个靠隐藏换来的"全绿"，比红更危险。

## 四、一次操作事故（如实记录）

给探针加时间戳后重跑 E1 证据时，我把 `p12e1-probe-8bit.json` **用 10bit 片源覆盖了**
（应该是 8bit AVC，我推的是 `sdr10.mp4`）。

发现方式：比对同组播放证据的 `source.mime`，发现"8bit 探针"报的是 `video/hevc profile=2`，
而 `p12e1-8bit-r1.json` 是 `video/avc`。

修复：用 `probe_seek_1080p30.mp4`（H.264 8bit）重跑，现在 `mime=video/avc profile=8`。
两份的结论仍然一致（`format_after_start=21`，NV12），**E1 的否定结论不变**。

**教训写进家族树硬规矩**：重跑证据前必须核对源文件与同组播放证据的 `source` 段一致。
证据目录没有版本历史，覆盖一次就找不回来 —— 这次能发现，是因为同组还有一份可对照的
`p12e1-8bit-r1.json`。如果没有，这个错误会永远留在证据里。

## 五、诚实清单（七条）

1. **它证明"证据自洽"，不证明"画面好看"。** 花屏、色彩正确性、听感仍是人眼/人耳判据
   （E4 §五 第 1 条、F2A §五 第 6 条）。
2. **46 项豁免不是零。** 16 份无时间戳（真实欠账）+ 30 份中途快照（设计如此）。
   想把它清零，前者要重跑 16 次真机音频探针，后者不可能清零 —— 除非不再做长稳测试。
3. **白名单硬编码 24 种 schema。** 新增卡片必须显式登记，这是刻意的摩擦。
4. **层 2 的阈值来自各卡验收文档。** 改判据要同步改这里，否则收口会与卡片脱节。
5. **`superseded/` 不计入收口。** 那里是留档的反例（F2 的 5 轮、F3 的 2 份、F3B 的旧行为），
   它们是"为什么改"的证据，不是"现在对不对"的证据。
6. **只有一台设备（K40 / Android 13）。** 所有结论的适用范围就是这一台。
7. **收口不等于发布。** 它回答"我们说过的话有没有证据支持"，不回答"能不能上线"。

## 六、P12 整体能力边界（截至本卡，能说的与不能说的）

### 已用证据证明的

| 能力 | 数据 | 证据 |
| --- | --- | --- |
| 硬解零拷贝直出 Surface | 无 CPU 像素拷贝 | P12-B |
| AAudio 主时钟 + 音画同步 | `av_drift` p99 **0.125–0.375 ms** | P12-C |
| 稳态零丢帧 | 多轮 300 送 / 301 收 / 300 上屏 | C/D/E/F 各组 |
| Surface 重建恢复 | 2–29 ms | P12-D1 |
| 3 路并发 | 81%+ 吞吐，轮内极差受控 | P12-D2 |
| 30 min 长稳 | 内存增长 **−0.62 MB**（判据 < 5 MB） | P12-D3 |
| 上屏时刻可测 | Δ p99 ≤ 16.45 ms | P12-D5 |
| HDR 元数据链路 | 合成器侧 `BT2020_ITU_PQ` + `dynamic_range=HDR` | P12-E3 |
| seek 首帧 | **28–60 ms**（G8 预算 150 ms），含后向 seek | P12-F1/F2A |
| 音画双侧重同步 | `gap` 0 或 −8 ms，14/14 轮零追赶 | P12-F2A |
| 错误路径 | 坏文件/无视频轨/无音轨/加密轨 全部有明确 reason | P12-F3/F3B |

### 明确没有证明的

| 项 | 状态 |
| --- | --- |
| 4K / HEVC / 高码率 | **未测** |
| 连续拖动 / 快速多次 seek | **未测** |
| tone mapping | **未实现**（三条路径都试过，见 E4） |
| 位深可判定 | **不可观测**（E1 否定结论） |
| 静态元数据下发 | **未达成**（`hdr-static-info` 键不存在） |
| Dolby Vision / HDR10+ | **未测**，不许宣称支持 |
| 多机型 | **只有 K40**（Redmi / Android 13 / MIUI） |
| DRM | **不支持**（只做到"识别并明确拒绝"） |
| 花屏 / 听感 | **只能人眼人耳**，无自动检测 |
| 字幕 / 倍速 / 音轨切换 / 网络流 | **未做** |

> 「打败市面播放器」这个目标，卡在**上表下半部分**，不在上半部分。
> 上半部分是内核质量，已经用数字站住了；下半部分是产品覆盖面，一张卡都没开。

## 七、P12 之后（交接）

1. **先补覆盖面，不急着优化内核。** 现在的内核指标已经优于大多数播放器的公开数据，
   但只有 1080p30 H.264/HEVC + 一台设备。4K/HEVC/60fps/高码率是第一个该开的卡。
2. **机型矩阵是最大的未知。** MIUI 上踩到的两个坑（`set-user-disabled-hdr-types` 设了被清回、
   `ENCRYPTED` 位不设）都可能是厂商定制行为。换一台设备，`crypto-mode` 是否还在？
   这需要至少 3 台不同 SoC 的设备各跑一遍 `verify_p12_all.py`。
3. **`decode/12` 是当前最终 schema。** 继续加字段就继续升号。
4. **收口脚本要进 CI。** 现在它是手动跑的 —— 手动的东西迟早会不跑。
   建议：每次提交后跑 `--self-test` + 全量，红了不许合。
