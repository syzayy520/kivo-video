# P14-S 状态卡 · 「播放速率」的分子不是媒体时间

> schema：`kivo.p12c.sync/29` → `/30`
> 一张卡只答一个问题：**`timeline.playback_rate` 这个数，分子到底是什么？**
> 答案：**帧数乘出来的名义时长。而同一份报告里另有一个实测跨度，从 `/16` 起就在。**
> 顺带：**216 份节拍侧证据第一次全部进了判据**，109 份判得动，4 份真越界，107 份判不动。

### 1.1 核心一个字没改

`media_pts_span_ns` 取自 `pace.pts_span_ns`，那是 P13-R 为四跨度恒等式
（`due_span == arrive_mono_span + pts_span − elapsed_span`）加的，算法就是
`last_pts − first_pts`，`/16` 起在场。本卡只是把它从"另一条恒等式的中间量"
提到"速率的分子"。与 P14-O 同一个做法：能在报告层解决的不动核心。

### 1.2 为什么必须改名，而不是"再加一个字段"

只加不改的话，同一份 JSON 里会有两个都自称"pts 跨度"的键，而读者看得见的那个是乘法。
`nominal_span_ns` 这个名字说的是"名义时长"，与其算法一致；旧名字说的是
"video pts span"，与算法无关。判据那边加了一条：**`/30` 上旧名还在 → 红**。
半更新的报告不许混进来。

## 二、真机（Redmi K40 / b6e950ee，1080p30 / 60 s / 1800 帧）

| | ① `cpu_paced` | ② `surface_at_time` |
|---|---|---|
| `nominal_span_ns` | 59 966 067 000 | 59 966 067 000 |
| `media_pts_span_ns` | **59 966 666 000** | **0** |
| 差（名义 − 实测） | **−599 000 ns**（0.6 ms） | 59.97 s（根本不可比） |
| `media_span_frames` | **1800** | **0** |
| `presented` | 1800 | 1800 |
| `corrected_wall_span_ns` | 59 966 713 363 | 59 940 034 456 |
| `nominal_rate` | 0.999989 | 1.000434 |
| `media_rate` | **0.999999** | — |
| `media_rate_measured` | `true` | **`false`** |
| `media_rate_reason` | `""` | "没有任何一帧带钟读数（surface_at_time 路径不提供）…" |
| 旧名残留 | 无 | 无 |

### 2.1 三条预言当场兑现

- **两个跨度差 0.6 ms（0.0018 帧）**，一条 60 s 的片子。这说明 `derived_fps`
  （名义帧时长 33 333 000 ns）与真实 pts 步长（33 333 331 ns）几乎一致 ——
  也说明**名义跨度不是"量出来不准"，而是"根本不是量出来的"**：它准，是因为
  帧数准；它一旦错，只会错在帧数上。
- **`media_span_frames == presented == 1800`。** 实测跨度覆盖的帧数与上过屏的帧数
  逐位相等 —— 分子与分母终于数的是同一批帧。
- **② 档把"判不动"落到真机上。** `clock_supplied_frames = 0`，`media_rate`
  没有值、只有理由。`/29` 及之前这一态是隐形的：那里只有一堆 0，
  而 0 会被读成"跑得慢"或"没跑"。

### 2.2 ② 档顺带证明旧判据在"通过"什么

`nominal_rate = 1.000434`，在 `[0.98, 1.02]` 内。**旧判据会判它通过** ——
而这一轮里，那个比值和媒体时间没有任何关系（分子还是帧数乘出来的）。
反过来说：过去 216 份里那些"速率通过"，通过的是同一个命题。

## 三、216 份节拍侧证据，第一次全部进判据

层 4 原来只把 `docs/evidence/p12c/*sync*.json`（27 份）喂给
`verify_p12c_sync.py`。也就是说 `/2` 之后的 189 份，那条四项闭合式
**从没进过总收口**（`150-p14r-status.md` §七.5 记的就是这条）。

| 结局 | 份数 | 说明 |
|---|---|---|
| 账目（四项闭合 / 分布复算 / 钟分档 / 名义跨度恒等式） | **218 / 218 绿** | 一次全绿，没有一份历史证据的账不平 |
| 媒体速率 **判得动且在带内** | **106** | |
| 媒体速率 **判得动且越界（已登记）** | **4** | 见 §3.1 |
| 媒体速率 **不可判** | **108** | 见 §3.2 |

`dns` 缺格：5 份（`p12c8-av-*` 的早期 `/1`），闭合差本来就是 0，所以按 0 判是对的 ——
但判据现在**会说出来**，而不是默默替它补一个 0。

### 3.1 那 4 份是真越界，换分子救不回来

| 证据 | 名义 → 实测 | `media_rate` | 丢帧 | 墙钟比名义短 |
|---|---|---|---|---|
| `p13r/p13r-4k60-r3-sync.json` | 7 983 493 000 → 7 983 333 000 | 1.0565 | 37 | 427 ms |
| `p13ad/p13ad-rate50-off-r1-sync.json` | 同上 | 1.0434 | 0 | 332 ms |
| `p13s/p13s-4k60-r1-sync.json` | 同上 | 1.0320 | 18 | 248 ms |
| `p13v/p13v-8x-r2-sync.json` | 同上 | 1.0212 | 7 | 166 ms |

四份都同时满足两件事：**8 秒的 4K60 轮次**、**两种分子的差只有 160 µs**
（一帧的千分之一）。所以"分子错了"解释不了它们 —— 媒体真的走了 7.983 s，
墙钟只走了 7.5–7.8 s。这是"帧提前交付"的节拍照。

本卡**不解释成因**（要另一张卡），也不改证据、不放宽区间。它们进
`KNOWN_OUT_OF_BAND`，每次跑都被打印一次，并且有一条反向判据：
**登记过的某一份不再越界 → 红**。豁免不能悄悄留着。

### 3.2 那 108 份为什么判不动

拆开是三类，理由各不相同，判据逐份写出来：

| 类别 | 份数 | 理由 |
|---|---|---|
| `/1`–`/15` | 101 | 那一版还没有 `pace.pts_span_ns`（P13-R 之前），实测跨度**补不出来** —— 报告里根本没有 pts |
| `/16`–`/30` 的 `surface_at_time` 档 | 6 + 1 | `clock_supplied_frames = 0`，四跨度全 0，跨度不存在 |
| 其余 | 1 | 只有 1 帧带钟读数（一帧没有跨度） |

**这 108 份不是"通过"。** 上一张卡立的规矩在这儿第一次大规模生效：
三种结局各自成行、各自计数，`不适用：108 份` 会写进总收口的覆盖行。
把所有版本的"速率通过"加起来是 106，不是 216 —— 这个数字比上一版**小**，
因为上一版的 216 里有一大批根本没测到媒体时间。

### 3.3 顺带：P14-R 那条豁免删掉了

`150-p14r-status.md` §三.3 与 `verify_p12c_sync.py` 里原来写着：
"上界对非 `completed` 的报告不成立"，据此删掉了上界、只留下界。理由是
`(received−1)/(presented−1) = 196/190 = 1.0316`。

用实测跨度重算 `p14r-interrupt`：**1.000026**。分子多算的那 6 帧就是 `dns` 那 6 帧
（从未上屏，却按名义时长进了分子）。所以：

- 打断轮跑得一点都不快；
- 那条豁免是**被错分子逼出来的结论**，不是判据的性质；
- 现在没有任何一版享受"只判下界"的待遇。

这是本系列第二次"上一张卡的诚实条款其实是一个度量缺陷"（第一次是 P14-Q
推翻 P14-P 的"1716 帧凭空消失"）。

## 五、两处判据自己的错，都是这一轮撞出来的

### 5.1 按文件名做键，216 份只记了 215 条

第一版用 `path.name` 做"见过哪些"的键。`p14g/p14g-long1800-r1-sync.json` 与
`p14g/pre/p14g-long1800-r1-sync.json` 同名 —— 于是 216 份跑出来只有 215 条记录，
而汇总行照样打印"合计 215 份"。**判据在数自己的样本时丢了一份，却报得很自信。**

改成以 `docs/evidence/` 为根的相对路径做键。登记表也用同一个键，
`KNOWN_OUT_OF_BAND` 里那 4 条写的是 `p13r/p13r-4k60-r3-sync.json` 而不是裸文件名。

### 5.2 版本范围放开了，文件清单没跟上

`verify_p12c_sync.py` 放开到 `/1`–`/30` 之后，层 4 仍然只喂 27 份。
"判据能判多少版本"和"实际喂了多少份"是两张表，只改一张，输出上完全看不出来 ——
因为通过的行长得一模一样。这是 P13-F 的老病（两张表只更新一张）在**另一个维度**上
的第五次发作：那次是同一个文件里的两张表，这次是两个文件之间的两张表。

修法：清单也改成递归的，并让子校验器用 `覆盖：N 份` 自报份数（总收口只认这个前缀）。

## 八、诚实清单

1. **本卡没有新增单测目标。** 这是 P14 系列第一次。理由：改的是报告渲染器的字符串输出，
   而 `av_sync_report.cxx` **只在 Android 侧编译**（桌面 CMake 不编它），
   要给它加桌面测试得先造一堆桩件 —— 那样的测试测的是桩件，不是代码。
   本卡的判断力在 Python 判据侧，由 **11 条变异 + 218 份复判**覆盖。
   写在这里是为了让"没有新测试"是一个**决定**，不是一次遗漏。
2. **4 份 4K60 越界没有解释。** 只知道换分子救不回来、差 160 µs。成因可能是提前交付，
   也可能是我还没想到的东西。它们进了登记表，每次跑都会出现。
3. **106 份"在带内"里，有 6 份是 `p13*` 的 8 秒 60fps 轮次。** 8 秒的窗口对
   ±2% 只有 160 ms 的余量，`media_rate` 在这么短的窗口上能否代表"实时性"，
   本卡没有论证 —— 它只是比名义跨度更接近那个问题。
4. **`surface_at_time` 档的 `media_rate` 永远是"不可判"。** 那是设计（它不提供钟读数），
   不是缺陷。要让它可测，得让 attime 也走 `note_presented` 的钟读数路径 —— 另一张卡。
5. **真机每档只有一轮**（n=1）。60 s 上 0.999999 与 0.999989 的差别不足以断言
   "两个分子在所有情形下都这么接近"。
6. **改名是破坏性的。** 任何外部读者若硬编码了 `video_pts_span_ns` / `playback_rate`
   就会读到 `KeyError`。仓库内三处已改成两名兼容；仓库外不知道，也没有办法知道。
7. **`/1`–`/15` 的 101 份永远补不出实测跨度。** 它们从"通过"退成"不可判"，覆盖率数字
   变小了。这是**退让**，不是进步 —— 但退的是"看起来通过"，留下的是"确实没测到"。
8. **登记表不是赦免。** 4 条越界每次跑都会被打印；任何一条不再越界会立刻变红。
   它的作用是"记住有人看过"，不是"以后不用看"。

## 九、下一步（按价值排序）

1. **4 份 4K60 为什么快** —— 现在全仓只有这 4 个已知越界，成因可查（要看 `due_at`
   与 `present_at` 的逐帧分布，`p13r` 的证据里有直方图）。查清之前 G6 在这类轮次上
   没有结论。
2. **让 `surface_at_time` 也提供钟读数** —— 它一个人贡献了 7 份"不可判"，
   而它是默认档（Direct Play 的首选路径）。不可判的默认档比不可判的取证档严重得多。
3. **切后台的"回来从哪继续"** —— P14-R 起就一直挂着，需要 native 暴露 `position_us`。
4. **`I1` 在样本极少时的分支** —— `superseded/p14q-locked` 仍是可复现样本。
5. **32 位 Android** —— CM311-1A 是现成验证机，但要 32 位 FFmpeg。
