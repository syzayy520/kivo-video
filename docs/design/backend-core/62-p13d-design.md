# P13-D · `av_drift` 采样归一化：把「抖动」「偏移」「漂移」拆成三件事

- 版本：V1.0
- 日期：2026-10-30
- 上游：`61-p13c-status.md` §六 第 3 条（`av_drift` 的采样语义要单独立卡）
- 一句话：**跨帧率的 p99 之所以不可比，是因为我们拿"每帧一个样本"去算分位数，
  而帧率本身就在改样本密度。这条不修，60fps 的播放器永远"更差"。**

---

## 一、问题：同一台机器，同一段 8 秒，p99 差 4 倍

P13-C 的实测（`docs/evidence/p13c/`，全部 `cpu_paced`，全部零丢帧）：

| 组 | 帧数 | `av_drift` 样本 | p50 | p99 |
| --- | --- | --- | --- | --- |
| 1080p **30**（P12-C 基线） | 180 | 180 | 0.125 ms | **0.125–0.375 ms** |
| 1080p **60** | 480 | 480 | 0.125 ms | **0.625–1.875 ms** |
| 4K **60** | 480 | 480 | 0.125 ms | **1.125–1.375 ms** |

p50 一动不动（0.125 ms = 6 个 48 kHz 采样，量化步长），p99 涨了 4–5 倍。
分辨率完全不影响它 —— 变的只有**每秒往里塞多少个样本**。

这就是 P13-C 的结论「帧率才是变量」的**另一半**：帧率改变的不是播放器的同步能力，
而是**我们看它的分辨率**。p99 是"第 99 百分位"，样本越密，越容易摸到调度抖动的尾巴。

> 换句话说：**我们现在测的不是"60fps 更差"，是"60fps 被看得更清楚"。**
> 把这句话写进证据，比改代码重要 —— 否则下一张卡会去优化一个不存在的问题。

## 二、三个被混在一起的量

`lateness = present_at − due_at` 这一个数，同时装了三件事：

| 量 | 定义 | 该用什么统计 | 现在的问题 |
| --- | --- | --- | --- |
| **抖动** jitter | 每帧的瞬时偏差，均值应 ≈ 0 | 分位数（p50/p99） | 样本密度随帧率变 → 不可比 |
| **偏移** offset | 一段窗口内的中位数 | 中位数（抗尾部） | 没单独报，被分位数盖住 |
| **漂移** drift | 偏移随时间的**斜率** | 回归（ppm） | **完全没有** |

前两个靠抽稀就能救。第三个根本救不了：**分位数对"慢速线性增长"是瞎的**。
音频时钟比视频 pts 快 0.1%（1000 ppm）时，每秒多偏 1 ms；8 秒片源里只累积 8 ms，
而抖动本身就有 ±1 ms —— 分位数看不出任何异常，可放到 10 分钟的长片里就是 600 ms 的音画不同步。

**这就是为什么这条卡不能只做"抽稀"。** 抽稀把抖动变成可比，漂移得另立一把尺。

## 三、抽稀：按媒体时间，不按帧序号

门的规则只有一条：

```
接受一个样本  ⟺  pts − 上一个被接受的 pts ≥ 50 ms
```

**为什么不是"每 8 帧采一次"**：8 帧在 30fps 是 267 ms、在 60fps 是 133 ms ——
换了单位，没换问题。密度依旧随帧率变，p99 依旧不可比。
**只有"按时间"这个单位本身与帧率无关。**

50 ms 的取法：8 秒片源 → 160 个样本（p99 = 第 2 差的样本，粗但**可比**）；
60 秒 → 1200 个；20 Hz 对"每秒 30/60/120 帧"三种片源一视同仁。
再密没有意义 —— 我们要的是"跨帧率可比"，不是"更多样本"。

**逐帧的直方图不删。** G6 的 `over_budget_frames`（"有多少帧的抖动超过一帧"）
必须逐帧数，抽稀会漏掉恰好落空的那几帧。所以证据里两个口径**并存且分名**：

| 块 | 口径 | 谁在用 |
| --- | --- | --- |
| `av_drift`（分位数） | 抽稀 20 Hz | 跨帧率比较、G7 |
| `av_drift.per_frame` | 逐帧 | G6 的 `over_budget_frames`、历史对照 |

## 四、漂移：两道斜率必须同号

序列里的点是 `(media_pts, lateness)`。漂移 = 这条线的斜率。

单位用 **ppm**（百万分之一）：1 ppm = 每秒偏 1 µs；1000 ppm = 每秒偏 1 ms。

两道独立算法，都写进证据：

| 算法 | 输入 | 输出 | 用途 |
| --- | --- | --- | --- |
| 逐点最小二乘 | 全部序列点 | `slope_ppm` | 主判据 |
| 窗口中位数回归 | 8 个等长时间窗的中位数 | `slope_from_windows_ppm` | **可复算的旁证** |

为什么要有第二道：逐点斜率依赖原始点，而原始点不进证据（2048 个点没法看）。
窗口中位数只要 8 个数就能重算，第三方可以拿 `window_start_ns` + `window_median_ns`
自己拟合一遍，看是不是同一个量级。
**两道不一致 = 序列不是线性的**，这时候 `slope_ppm` 不能当漂移用。

所以还要报 `r2`：线性度。`r2` 低（< 0.3）说明"斜率"只是在描述噪声，
不是漂移 —— **光有斜率没有 r2，噪声会被读成漂移。**

窗口数取 8：60 秒片源 → 每窗 7.5 s、150 个点，中位数足够稳；8 个点画出来人眼就能看出趋势。

### 判据（本卡验收）

| 编号 | 判据 | 门槛 |
| --- | --- | --- |
| D1 | 同片长 30fps 与 60fps 的抽稀样本数相对差 | ≤ 5% |
| D2 | 抽稀后 60fps 的 p99 与 30fps 的 p99 之比 | ≤ 2×（P13-C 是 4–5×） |
| D3 | 长片 `trend.usable` | `true`，且 `span_ns ≥ 30 s` |
| D4 | 两道斜率的符号 | 一致；且 `|slope_ppm|` 差 ≤ 20% 或 ≤ 5 ppm（取大者） |
| D5 | 逐点斜率 + 窗口斜率的**逐位复算** | `tools/verify_p13d_drift.py` 从 JSON 重算窗口斜率，整数相等 |

D2 是**可以失败**的判据：如果抽稀后 60fps 的 p99 仍然是 30fps 的 4 倍，
那说明 P13-C 那句"采样密度"解释是错的，真实原因在别处（比如调度周期变了），
**那就得在状态卡里承认解释错了，而不是去改判据。**

## 五、家族树落位

```
video_plane/core/pace/
├── pace_drift_series.hpp/.cxx   # 抽稀门 + 定长环形序列（只存点，不解释）
├── pace_drift_trend.hpp/.cxx    # 序列 → 窗口中位数 + 两道斜率 + r2（纯函数）
├── pace_stats.hpp/.cxx          # 改动：多一个抽稀直方图、一个序列、一个 trend
├── pace_action.hpp              # 改动：PaceDecision 增 media_ns
└── frame_pacer.cxx              # 改动：note_presented 把媒体时刻递下去
```

| 文件 | 单一职责 | 不做什么 |
| --- | --- | --- |
| `pace_drift_series.cxx` | 判定"这一帧要不要采"，并把它存进定长环 | 不算趋势、不下结论 |
| `pace_drift_trend.cxx` | 从序列算出窗口与斜率 | 不碰时钟、不认识帧率 |
| `pace_stats.cxx` | 聚合（多一个抽稀直方图） | 不解释斜率 |

**为什么拆两个文件而不是一个**：抽稀是**采样语义**，斜率是**统计语义**，
两者的测试用例完全不重叠（前者断言"60fps 采到的点数和 30fps 一样"，
后者断言"喂一条 1000 ppm 的直线能算回 1000"）。放一个文件里，
两个职责会共用同一份 `namespace {}` 里的辅助函数，然后慢慢长成一个小框架。

### 序列容量与分段

- 容量 **2048 点**（20 Hz × 102.4 s），`std::array`，零堆分配。
- 溢出后**覆盖最旧的**，`truncated = true`，`total_samples` 继续增长。
  为什么不在溢出后停采：长片要的是"**最近** 100 秒的趋势"，不是"开头 100 秒"。
- **seek 会让 pts 倒退**：倒退即视为新时间轴，清空环、`segments++`。
  趋势只算最后一段（`trend.segment_samples` 报出来）。
  跨 seek 把两段拼起来回归，得到的是"两个锚点之间的跳变"，不是漂移。

## 六、报告 schema：`kivo.p12c.sync/1` → `/2`

只加块，不改既有字段的语义：

```
"av_drift": {
  "measurable": true,
  "measured_at": "present",
  "definition": "…",
  "sampling": { "mode": "media_time_decimated", "interval_ns": 50000000,
                "target_hz": 20, "frames_observed": 480,
                "accepted": 160, "skipped": 320, "observed_hz": 20.0 },
  "samples": 160, "p50": …, "p95": …, "p99": …, "max": …,
  "histogram": { … },                       ← 抽稀口径，跨帧率可比
  "per_frame": { "samples": 480, "p50": …, "p99": …, "max": …, "histogram": { … } },
  "trend": { "usable": true, "windows": 8, "span_ns": …, "segment_samples": 160,
             "first_window_median_ns": …, "last_window_median_ns": …,
             "delta_median_ns": …, "slope_ppm": …, "slope_from_windows_ppm": …,
             "r2": …, "window_start_ns": […], "window_median_ns": […],
             "window_samples": […] }
}
```

`per_frame` 保留是因为 **G6 的判据不能改口径**：`over_budget_frames` 数的是逐帧。
两份都叫 `av_drift` 的两个口径会被读者混起来，所以块名分开写、`sampling.mode` 明说。

`/1` 的证据不重写（280 份里 19 份是 sync，重写等于伪造），校验器同时接受 `/1` 与 `/2`。

## 七、诚实清单（写在这张卡开工之前）

1. **抽稀会漏掉瞬时尖峰。** 50 ms 门意味着两次采样之间的帧不进抖动分布。
   这是**有意的取舍**：漏掉尖峰换来跨帧率可比。代价是 `p99` 比逐帧口径更乐观 ——
   所以 `per_frame` 必须一直报，不许删。
2. **窗口切分是人为的。** 8 个等宽窗口对"线性漂移"友好，对"阶梯式跳变"不友好
   （跳变可能刚好落在窗口边界上，中位数把跳变摊平）。
   本卡不处理阶梯 —— 需要时看 `window_median_ns` 数组自己判断。
3. **斜率的置信度只有 `r2` 一个数。** 没有做显著性检验（t 检验 / p 值）。
   样本 < 30 时 `r2` 本身也不可信，所以 `usable` 另设 `samples ≥ 30 && span ≥ 30 s` 的门。
4. **6 个自由度以内的噪声**（8 个窗口意味着 6 个残差自由度）仍可能凑出一个"像漂移"的斜率。
   D4 的两道斜率同号检查挡掉一部分，挡不住全部。
5. **只测 `cpu_paced`。** `surface_at_time` 路径上交出去的时刻由合成器定，
   `av_drift` 在那个路径上本来就 `measurable: false` —— 这张卡没有改变那个结论，
   也没有让它变得可测。
6. **这不是"漂移已修好"，是"漂移第一次被量出来"。** 修不修、怎么修，
   要看 D3/D4 跑出来的数。

## 八、不做的事

| 不做 | 为什么 |
| --- | --- |
| 给 `surface_at_time` 补 drift | 需要 present fence，P12-C6B 已经论证过 NDK 拿不到 |
| 把抽稀做成可配置 | 可配置的采样率等于"每份证据口径都能不同"，那就没人能比较了 |
| 用音频时钟跨度 ÷ 视频 pts 跨度当漂移 | 两个窗口长度不同，差值量的是收尾耗时（P12-C8 已踩过，见报告 `timeline.note`） |
| 现在就改同步实现 | 先把量测对，再谈修。**没有可比的数之前动手，改的是猜测。** |
