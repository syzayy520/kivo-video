# 95 · P13-T 验收：门能证明了，尖峰和时钟也终于分开了

- 版本：V1.0
- 日期：2026-10-30
- 设计：`94-p13t-design.md`
- 判据：T1–T4
- 结论：**T1/T2/T4 达成，T3 达成一半**。
  `drift_rebases` 的接线修好了（此前它被算了却没出版，所以"门没响"与"响了没写"分不开）；
  受控负载下两轮出现 **max 80.14 / 41.82 ms，而 `clock_ahead ≈ 0`、`playback_rate = 1.0000`** ——
  **尖峰可以在时钟完全正常时发生**，这一条把 P13-R 的两个量彻底分开了。

---

## 一、修了什么

`PaceStats::summary()` 漏了 `out.drift_rebases = drift_rebases_;`。于是 P13-S 的三轮
"`drift_rebases` 全 0"有两种读法：门没响，或者门响了但字段没出版。现在只剩前一种。

新增 **S3** 单测：1.5% 假快钟驱动完整 `FramePacer`，断言
`pacer.summary().drift_rebases >= 1`。这条同时钉住 tracker → `PaceStats` → `summary` 三段。

> P13-S §五.7 说"`jump_rebases` 是死字段"——**那句是错的**，已在 `93-p13s-status.md`
> 原文上加了更正块：`FramePacer::summary()` 确实搬了四个计数（257–260 行），
> 442 份证据全 0 是因为 tracker 级跳变一次没发生。真正没接的是本卡修的 `drift_rebases`。

## 二、受控两轮（`docs/evidence/p13t/`，`sync/17`）

负载：设备上 4 个 `yes` 忙循环，**开跑前实测**（`/proc/stat` 两次采样，间隔 1 s）：

```
cpu  27998285 4805835 18925196 116837806 ...
cpu  27998465 4805849 18925449 116838172 ...
idle 增量 366 / 总量增量 ≈ 818  ⇒  空闲率 ≈ 44.7%
```

`ps -A -o ARGS | grep -c '^yes$'` = **4**（本轮先验证了进程真的在，再开跑）。

| 轮 | 空闲率 | max (ms) | 丢帧 | `drift_rebases` | `clock_ahead` | `playback_rate` |
|---|---|---|---|---|---|---|
| on-r1 | 44.7% | **80.14** | 0 | 0 | **+0.03 ms** | **1.000016** |
| on-r2 | 44.7% | **41.82** | 0 | 0 | **+0.02 ms** | **1.000014** |

### 2.1 这两轮说明了什么

**尖峰出现了（80 ms、42 ms），而时钟一点没动（20–30 微秒）。**
所以在 44.7% 空闲率的负载下：

- `lateness` 峰值是**交出动作本身晚**（present 侧），不是时间轴被推快；
- P13-R 那两轮（`clock_ahead +118.79 ms`、`rate 1.0151`）是**另一件事**，
  而且不是每次满载都会发生 —— 本卡两轮就没撞上；
- P13-S 的门在两轮里都没响，**与"这两轮没有时钟位移"一致**，不再有歧义。

## 三、诚实清单

1. **T3 只达成一半**：出现了"尖峰大、时钟不动"的组合，但没出现"时钟动、门响"的组合 ——
   那个组合需要 P13-R r4 那种间歇事件，两轮没撞上。
2. **负载只有 4 个忙循环（空闲 44.7%）**，没做 8 路饱和。P13-R 的异常轮也是 4 路，
   所以"同样的负载有时出、有时不出"这件事本身没被解释。
3. **空闲率只采了一次**（每轮前），没有覆盖整轮。轮中若负载掉了，表里看不出来。
4. **A/B 没有对照组**：没做"门关"的构建。原因是本卡的结论不需要它 ——
   两轮 `drift_rebases = 0` 说明门没参与，有无门结果相同。要做真正的 A/B 得先能**按需触发**
   时钟位移（现在做不到）。
5. **只有一台设备、一种片源、两轮**。
