# 83 · P13-N 状态：分位数必须自己说出精度

> **结论：那份 66% 的差不是"两份测量打架"，是同一批点的两种精度。**
> 四轮真机里 `quantiles.*.p50` 恒为 **125 000**，而八个窗口中位数全在
> **72 761 ~ 82 814**；现在每个 `p50` 旁边都站着它的可能范围
> （实测 `[13 490, 250 000)`）与桶内样本数（**2 553 / 2 600 = 98.2%**），
> 整批点另给一个可复算的精确参照 `median_of_window_medians_ns`（**73 999**）。
>
> 一句话：**读者拿到的不再是一个孤零零的 125 000，而是"它可能是
> 13.5~250 µs 之间的任何值，那里面有 98.2% 的样本，刻度是 250 µs"。**
>
> 这一轮没有把 125 000 改准 —— 改准需要存全样本或引入分位数草图，
> 为了一格差 ±125 µs 的数，代价与收益完全不成比例（见 §六.3）。

## 二、那 66% 到底是什么

P13-M 四轮证据，每轮 `quantiles.*.p50` 都是 125 000：

| 轮次 | 桶 512 里样本 | 占比 | `p50` | 窗口中位数的中位数 | 偏高 |
|---|---|---|---|---|---|
| r1 平跑 | 2568 / 2600 | 98.77% | 125 000 | 73 646 | **+69.7%** |
| r2 向前 seek | 2349 / 2400 | 97.88% | 125 000 | 73 844 | +69.3% |
| r3 向后 seek | 3147 / 3199 | 98.37% | 125 000 | 73 438 | +70.2% |
| r4 冻结 2 s | 2518 / 2555 | 98.55% | 125 000 | 73 321 | +70.5% |

P13-N 三轮（新口径）：

| 轮次 | `dec` 样本 | `p50` | `p50_range` | 桶内样本 | 占比 | 精确参照 | 落在范围内 |
|---|---|---|---|---|---|---|---|
| r1 平跑 130 s | 2600 | 125 000 | **[13 490, 250 000)** | 2553 | **98.19%** | 73 999 | ✓ |
| r2 向前 seek | 2400 | 125 000 | [17 188, 250 000) | 2296 | 95.67% | 77 334 | ✓ |
| r3 35 s 短片 | 700 | 125 000 | [27 969, 250 000) | 683 | 97.57% | 77 395 | ✓ |

三份证据里被拿去做对照的精确参照，**全部落在自己声明的可能范围内**。
这就是"它们不打架"的形式化说法。

### 二之一、一个更刺眼的旁证

r1 那份证据里：

```
p50 = 125000
p95 = 125000
```

两个**不同的分位数**给出**同一个数**。这本身就在说"这把尺子在这个范围内
只有一个刻度"。而 `p99 = 375 000` 同样是桶中心。

整份分布真正的形状（`min = 13 490`，`max = 4 601 719`）只体现在两格极值上，
中间三个分位数全是 250 µs 网格上的点。

## 三、三轮真机（Redmi K40 / Android 13 / arm64-v8a）

| 轮次 | 场景 | 帧数 | 丢帧 | xrun | `segments` | `truncated` | `observed_hz` |
|---|---|---|---|---|---|---|---|
| r1 | 平跑 130 s | 3900 | 0 | 0 | 1 | true | 20.0051 |
| r2 | 30 s 处向前跳到 40 s | 2700 | 0 | 0 | **2** | false | 20.0111 |
| r3 | 35 s 短片 | 1050 | 0 | 0 | 1 | false | 20.0191 |

三轮零丢帧零 xrun。r2 的 `segments = 2` 与 `observed_hz = 20.0111`
与 P13-M 的同一场景逐位一致 —— 说明这一轮改动没有碰到切片逻辑。

各块的精度四格：

| 轮次 | 块 | `samples` | `p50` | `range` | 桶内样本 |
|---|---|---|---|---|---|
| r1 | `media_time_decimated` | 2600 | 125 000 | [13 490, 250 000) | 2553 |
| r1 | `per_frame` | 3900 | 125 000 | [13 490, 250 000) | 3821 |
| r1 | `window_quantiles` | 2048 | 125 000 | [24 832, 250 000) | 2016 |
| r2 | `media_time_decimated` | 2400 | 125 000 | [17 188, 250 000) | 2296 |
| r2 | `per_frame` | 3600 | 125 000 | [17 188, 250 000) | 3448 |
| r2 | `window_quantiles` | 1800 | 125 000 | [18 386, 250 000) | 1721 |
| r3 | `media_time_decimated` | 700 | 125 000 | [27 969, 250 000) | 683 |
| r3 | `per_frame` | 1050 | 125 000 | [27 969, 250 000) | 1016 |
| r3 | `window_quantiles` | 700 | 125 000 | [27 969, 250 000) | 683 |

r3 的 `dec` 与 `window_quantiles` 完全一致（700 样本、同范围、同桶计数）——
那是 P13-I 判据 I4 说的"未覆盖且单段时两份分布逐桶相同"，
在 N 判据下再次自洽。

`quantiles.*.p50` 在九个块里**全是 125 000**。这不是巧合，
是桶宽 250 µs 对 73 µs 这个量级没有分辨力的直接后果。

## 四、判据 N0–N7

| # | 判据 | 结果 |
|---|---|---|
| N0 | 每个分位块都有四格 | ✓ 3 个分位块各带四格 |
| N1 | `bucket_width_ns == 250000` | ✓ 全部等于 250 000 |
| N2 | `p50 ∈ [range_low, range_high]` | ✓ |
| N3 | `0 ≤ p50_bucket_samples ≤ samples` | ✓ |
| N4 | `range_high − range_low ≤ 桶宽` | ✓ |
| N5 | `p50_bucket_samples` = 从 `histogram` 复算的桶计数 | ✓ 全部一致 |
| N6 | `range` = 从 `histogram` 复算的范围 | ✓ 逐位相等 |
| N7 | `median_of_window_medians_ns` = 排序后第 `(n−1)//2` 个 | ✓ 73 999 / 77 334 / 77 395 |

N5 / N6 是这一组里唯一"不信任何手填数字"的部分：桶号、桶计数、范围
全部从 `histogram.buckets` 重算。`/11` 及以前做不到 —— 那时证据里只有
`p50` 一个数，没有桶号，复算方无从核对它落在哪儿。

## 五、变异自测

### 5.1 单元层（改实现，`build/mutate_p13n.py`）

| # | 变异 | 结果 |
|---|---|---|
| C1 | 桶内命中 `rank <= accumulated` → `<` | ✓ 杀死（5 条红） |
| C2 | 下溢 `rank <= below_` → `<` | ✓ 杀死（5 条红） |
| C3 | `exact` 恒 false（溢出被报成量化过） | ✓ 杀死（5 条红） |
| C4 | 桶内样本数填成累计数 | ✓ 杀死（n07 的 `at.samples == 1`） |
| C5 | 范围上下界取反 | ✓ 杀死（2 条红） |
| C6 | 范围不与 `[min, max]` 求交 | ✓ 杀死（2 条红） |
| C7 | 秩改 `n/2` | ✓ 杀死（3 条红） |
| C8 | 不排序直接取中间 | ✓ 杀死（3 条红） |
| C9 | `bucket_high_ns` 少加一个桶宽 | ✓ 杀死（7 条红） |
| C10 | 两条端点分支合并（等价重构） | ✓ **仍绿** |

**C7 与 C8 逼出了两个测试设计问题**，都记在这里：

- C7（秩 `n/2`）：原用例的 8 个窗口中位数是**递增**的（0,1,…,7 ms），
  排序与不排序给同一个数 —— 但 C7 只改秩，仍能红。真正逼出改动的
  是 C8。
- C8（删掉 `sort`）：递增输入下 `medians[3]` 与排序后第 3 个是同一个值，
  变异**会活过去**。所以把 n07 改成**递减**输入（7,6,…,0），
  排序后中位是 3 ms，不排序取 `medians[3] = 4 ms` —— 立刻分开。
  这是 P13-M 的 C6（max vs 累加）那次的同一个教训：
  **凡"排序/取极值"的量，输入必须造得让两种算法给不同结果。**

## 六、诚实清单

1. **`p50_range` 不是置信区间。** 它只是"桶界 ∩ 样本范围"—— 一个几何上的
   可能范围，不含任何概率含义。真值在这个范围内的分布是未知的，而从
   "98.2% 挤在一个桶里"这个事实看，它极可能贴近桶的下沿而不是均匀分布。
   **不要把它当 95% CI 引用。** 真正的 CI 只在斜率上有（`slope_ci_*`）。

2. **`bucket_center_bias_ns` 这个字段我没做。** 设计稿 §2.4 原本想过直接出版
   "桶中心比真值高了多少"，最后没做：那个差不等于
   `p50 − median_of_window_medians`，因为后者不是全体中位数（见第 3 条）。
   把它写成一个带 `bias` 字样的字段，等于给一个近似值盖上精确的章。
   读者要算，两个数都在证据里。

3. **`median_of_window_medians_ns` 不是全体中位数。** 中位数不可合并。
   8 窗等样本时才近似等于整批中位数；seek 之后点可能挤在一窗里，那时它有偏。
   字段名里带 `of_window_medians` 就是为了不让人把它当成 `p50` 的精确版。
   它存在的意义是"给一个**可复算**的对照值"（N7 从 `window_median_ns` 数组
   重算），不是"给出真值"。

4. **98.2% 挤在一个桶里，说明直方图在这个量级上几乎没分辨力。**
   这一轮只是把这件事写进证据，**没有修好它**。要真正提高整场分位数的
   分辨力，需要存全样本（内存随时长线性增长）或引入分位数草图
   （t-digest / KLL，一个新算法加一套新误差分析）——两条都被 §五 否掉了。

5. **`bucket_width_ns` 在三个块里重复出现，是刻意的冗余。** 它让每个块
   单独自解释，不必跨块找。代价是每份证据多几十字节。

6. **N7 依赖 `window_median_ns` 数组出版。** 那个数组是 P13-I 加的；
   若哪天有人为了瘦身把它删掉，N7 会静默降级成"无参照可验"（返回 True），
   而不是红。这是这一组里唯一一处"缺数据 ⇒ 不算失败"的地方。

7. **`p50_range` 的钳制在真机上几乎总是生效。** 三轮的 `min` 是
   13 490 / 17 188 / 27 969，都远大于桶下界 0 —— 所以下界永远是 `min`，
   看起来像"钳制没起作用"。实际是"样本范围比桶窄"的正常结果。
   要看到下界真的是桶下界，得有一份 `min > 0` 且贴近桶下界的证据 ——
   目前没有。

8. **`p95` / `p99` 没加精度标注。** 它们与 G6 的 45 ms 预算比，250 µs 是 0.55%，
   无关紧要。只有 `p50` 被拿去和窗口中位数并排比，才需要这一组标注。
   这个不对称是有意的，但也意味着**不能用 `p95` 去做亚毫秒级的比较**。

9. **P13-M 记的两条账这轮没动**：`media_span` 多段时可以大于片长；
   `unobserved_cells` 把"帧率低"与"播放卡住"混在一起。它们与分位数无关。

10. **单轮 `SE_hac` 仍不是设备常数。** 这一轮 r1 是 0.180276、r3 是 0.924730
    （同机不同片源），P13-M 平跑轮是 0.0857。跨轮汇总判据仍然缺。

## 七、下一步（按优先级）

1. **跨轮汇总判据。** 单轮 `drift_verdict` 不是设备常数：`SE_hac` 在 0.086 ~ 0.925
   之间跳了 10 倍。要谈"这台机器的漂移上界"，必须跨轮取最宽那轮 ——
   现在没有这份汇总，每份证据都在自己跟自己比。（`81-p13m-status.md` §六.9、
   本文 §六.10）

2. **`slope_halves_agree` 只看符号太弱。** r2 的向前 seek 轮两半程
   `−0.002` / `+0.004`（量级 0.001 ppm，纯噪声）会被判成"不一致"，
   而 P13-M 的平跑轮 `−0.239` / `−0.149` 判成"一致" —— 判据分不出
   "换向"和"两段都太短"。应该改成"两个半程的 CI 是否重叠"。

3. **`media_span` 多段时可以大于片长**（P13-M r2 报 159.867 s vs 片长 130 s），
   它是各段之和，重看那段被算两次。没有字段说明这一点。

4. **`unobserved_cells` 把"帧率低"与"播放卡住"混在一起。**
   30 fps 掉 3 帧才算 1 格，10 fps 每个格都会空。

5. **`p50_range` 在"样本范围比桶窄"时钳制不起作用**（§六.7）。
   要验那半条分支，需要一份 `min` 紧贴桶下界的证据 —— 可以人为构造
   （单测已覆盖），真机上暂时没有。
