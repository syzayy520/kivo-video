## 一、构思

`199` 的 B 方案要在**音频输出侧**吃掉频差：钟快 2000 ppm 时按 0.998 的比率消费，
而不是周期性复位位置。0.2% 量级不需要高质量重采样，零阶保持（重复/丢帧）就够。

但"写 100 行"只够写出**算法内核**。真正的工作在接线：
- `rate_ppm` 在视频线程的 `FramePacer` 里，音频回调线程要读 → 需要 atomic 跨线程传递；
- `render()` 是实时路径，`ratio == 1.0` 必须逐位透传，不能有任何额外分支代价；
- 还要保证相位跨 AAudio 回调累积（每次只有 192 帧，0.2% 会被四舍五入掉）。

所以本卡**只交内核**，接线另开卡。

---

## 二、规划设计

1. **零阶保持**：每输入帧按 `ratio` 累积，`>= 1.0` 就输出一帧。
   `ratio < 1` 偶尔丢一帧，`ratio > 1` 偶尔重复一帧。
2. **快路径**：`ratio == 1.0` 时逐帧拷贝，输出帧数恒等于输入帧数 —— 保证默认行为逐位不变。
3. **相位跨调用保留**：`accumulator_` 是成员，不随单次 `process()` 归零；
   `reset()` 显式清（seek / 换片源后调）。
4. **只接受微调**：`ratio` 落在 (0.95, 1.05)，超出就忽略 —— 这不是通用重采样器。
5. **header-only**：与 `ClockRateEstimator` 同理由（`.cxx` 要改两份 CMake 清单，
   而 `backend/CMakeLists.txt` 被他人主线占用）。
6. **不接线**：`RingBufferSampleSource::render()` 一行未改。

### 实现期更正：两处接口问题（只有往实时回调上靠才会暴露）

1. **`process()` 不适合实时回调**。它输出 `输入 × ratio`，而 AAudio 回调必须**填满**
   `num_frames`。`ratio < 1` 时它少几帧，会话只能补静音 —— 那不是"音频变慢"，
   是"每 500 帧断一下"。补了 `fill()`：输出**恰好** `out_frames` 帧，
   调用方先按 `ceil(out_frames / ratio) + 1` 读够输入。
2. **相位要取小数**。初版写 `phase_ = pos - in_frames`，输入读多时会变负、
   被 clamp 成 0，跨调用相位就丢了。改成 `phase_ = pos - floor(pos)` ——
   输入每次都是新缓冲，整数偏移没有意义，只有小数相位需要跨调用。

**为什么 T12–T14 没抓到**：它们只验"累积比率正确"，验不出"输出帧数不固定"
和"相位被清零"。T15 补上这条。

### 结论与边界

- **内核正确**：`ratio=1.0` 逐位透传（所以将来接线时默认行为不会变）；
  小数比率跨 520 次调用累积误差 ≤ 2 帧（0.002%），证明相位没被每次调用四舍五入掉。
- **未接线**：`render()` 一行未改，所以"真机上音质/xrun 如何"**完全没测**。
  零阶保持的失真、以及 0.2% 丢帧会不会有咔哒声，必须接线后听测 —— 本卡不宣称音质。
- 接线是独立卡：跨线程 atomic 传 `rate_ppm` + `render()` 快路径 + `reset()` 时机。

## 六、接线验证：**证伪**（2026-11-06）

后续卡（P1B22）把 `set_rate_ppm` 接到了 `AudioPlayback`，并加了 `kivo.rate_trim_ppm` 参数。
实验：注入 2000 ppm 制造频差，再设 trim 0 / 2000 两组。

| trim ppm | `rate_ppm` | `phase_error` | `drift_rebases` | 帧数 / 丢帧 |
| --- | --- | --- | --- | --- |
| 0 | 2016.3 | **65.8 ms** | 5 | 1050 / 0 |
| 2000 | 2002.8 | **65.8 ms** | 5 | 1050 / 0 |

**trim 2000 完全没有效果。**

### 原因

`phase_error` 来自 `ClockPositionTracker`，而它读的是 **AAudio timestamp**（设备播放位置）。
微调输出样本数改变的是"送给设备的样本内容"，**不改变设备 timestamp** ——
设备仍按自己的晶振走，时钟读数一点没变。

所以：**微调输出不能修正音频时钟**。这个内核作为"重采样器"是对的（T12–T15 都过），
但**用错了地方**：它改变内容，不改变时钟。

### 结论

`199` 的 B 方案（重采样修时钟）**方向错误**；`199` 的初版判断（"没有落点"）才是对的，
我后来的"更正"（"可行、~100 行"）是错的，本轮实验证伪。

要真正改音频时钟，只能"让设备按不同速率播放"——即改采样率并**重建流**；
而 AAudio 采样率只能 builder 阶段设定，重建流必然有间隙（P12-F2A 明确不重建）。
**A1 的速率伺服在架构上确实不可行。**

### 这个内核还有用吗

有，但不是用来修时钟：
- 它可以做"变速播放"（用户要 1.1× 速）的底层，那是功能需求，不是时钟修正；
- 也可以做"音频欠载时的平滑补偿"，但那需要另一套判据。
本卡不宣称它能解决 A1。

### 后续：接线已回退（P1B23）

证伪之后，`rate_trim_ppm` 这套接线**已全部回退**：

- `RingBufferSampleSource`：移除 `rate_ppm_` / `last_ppm_` / `resampler_` / `temp_` / `set_rate_ppm`，
  `render()` 回到两行透传；
- `AudioPlayback::set_rate_ppm` 移除；
- JNI 参数、`NativePlayer.kt` / `PlaybackSession.kt` / `PlayerActivity.kt` 三处声明移除。

验证：`grep -rn "rate_trim|rateTrim|set_rate_ppm"` **零残留**；编译 0 错；
Gradle BUILD SUCCESSFUL；T1–T15 全 PASS；六个门禁全 PASS。

**为什么回退而不是留着**：它没有任何正确用途 —— 改内容不改时钟。
留着就是一个"看起来能修频差、实际不能"的 API，比没有更危险。

**内核保留**（`micro_resampler.hpp` + T12–T15）：它是正确的重采样器，
将来做"变速播放"可以直接用；但那时要重新设计接线 ——
音频变速同样需要改采样率，不是改输出帧数。
