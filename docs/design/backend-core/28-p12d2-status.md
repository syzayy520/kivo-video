## 一句话结论

**3 路 1080p 同时解码，各自 130.8–132.9 fps，是单路的 81.3–82.6%（门槛 60%）。**
真实节拍下 3 路各 30 fps、720/720 帧、**0 丢帧**。

顺带量出一个比判据本身更有用的事实：
**单路 160 fps 不是硬件上限** —— 3 路合计 396 fps，4 路合计还是 395 fps。
也就是说这颗 1080p AVC 解码器的总吞吐天花板约 **396 fps**，
而**单路只吃到 41%**。瓶颈不在算力，在每实例的固定往返开销。

## 一、判据（照卡片，未放宽）

卡片：**同时 3 路 1080p 不互相拖垮，各自 fps ≥ 单路 60%。**

拆成两条独立检查 —— 只做第一条会得到"3 路都很快"而漏掉"是不是每帧都上屏了"：

| 检查 | 内容 | 判据 | 本次 |
| --- | --- | --- | --- |
| ① 吞吐比 | 3 路各自 `decode_fps` / 单路基线中位数 | ≥ 60% | **81.3–82.6%** ✅ |
| ② 真实节拍 | 3 路同时按 30 fps 跑 | 零丢帧、跟得上目标 | **0 丢帧，720/720，30.06–30.11 fps** ✅ |

①是卡片字面判据，②才是用户能感知的那件事。

## 二、主证据（K40 `b6e950ee`，`long_1080p8.mp4` 24 s / 720 帧 / 1080p30，不挂音轨）

### 2.1 吞吐（满速解码，`kivo.fps 0`）

| 并发数 | 各路上屏帧 | 各路 fps | 合计 fps | 相对单路 | 轮内极差 |
| --- | --- | --- | --- | --- | --- |
| **1（基线）** | 720 | **160.84**　（147.27 / 179.58 / 160.84 三轮） | 160.84 | 100% | — |
| **3** | 720 | **132.87 / 132.61 / 130.81** | 396.29 | **246%** | 1.6% |
| **3** | 720 | 132.89 / 131.82 / 131.44 | 396.15 | 246% | 1.1% |
| **3** | 720 | 132.55 / 131.50 / 131.05 | 395.10 | 246% | 1.1% |

三轮 3 路的最差比例是 **81.3%**，门槛 60% —— 余量 21 个百分点。

## 三、为什么"单路 160 fps 不是上限"

这组数字自己就把答案说清楚了：

```
单路        161 fps     ← 只占天花板的 41%
3 路合计    396 fps
4 路合计    395 fps     ← 加一路不涨 ⇒ 天花板在这里
```

- **合计不随路数增长** ⇒ 396 fps 是硬件/驱动给的总预算，不是我们的代码瓶颈；
- **单路只吃到 41%** ⇒ 单实例吃不满预算，卡在"每实例的固定开销"上，
  而不是像素算力（4K 单路 133 fps，像素是 1080p 的 4 倍，帧率只掉 17% —— 同一个结论）。

这条对后续优化有直接指向：想提高**单路**吞吐，该动的是每帧的送收往返
（C6 已经量过四段耗时，见 `20-p12c6-status.md`），不是换解码器、也不是拆线程
（C6 已证拆线程无增益）。

> ⚠️ 别把这句话读成"所以单路还能优化 2 倍"。41% 只是**当前实现**距硬件预算的距离，
> 能不能补上取决于往返里有多少是平台强制的。C6B 已经证明其中一部分
> （`dequeue` 的 2000 µs 空等）在真实节拍下根本不存在。**没有实测就不许宣称能提升。**

## 四、这条卡的实现

### 4.1 native 侧：**一行没改**

3 路并发用的是三个独立 `SessionHandle`，每个有自己的 `DecodeSession`、
自己的线程、自己的 codec。C6 之后每个会话本来就不共享状态，所以并发是天然的。

> 这是架构上值得记一笔的地方：D2 没有在 C++ 里加任何东西。
> 如果当初把会话状态做成全局/单例（很常见的省事写法），这张卡就得先做一次重构。

### 4.2 Kotlin 侧：两个新文件

| 文件 | 职责 |
| --- | --- |
| `bridge/PlaybackSession.kt` | 一条会话的生命周期包装：一个 handle + 一个 fd + open/start/写证据/释放 |
| `ui/MultiPlayerActivity.kt` | N 个 SurfaceView 横排 + N 条会话；**先全部 open，再全部 start** |

"先全开再全启"不是洁癖：一条一条 `open+start` 会让第一路先跑几十毫秒，
测出来的是接力不是并发 —— 而这张卡问的正是"同时跑会怎样"。

### 4.3 为什么不复用 `PlayerActivity`

`PlayerActivity` 里 `onSurfaceAvailable` / `onSurfaceLost` 是**一对一**假设
（D1 刚把换面做对），塞进 N 路会立刻失效。所以单开一个 Activity。

代价是 `PlaybackSession.kt` 与 `PlayerActivity` 的内联逻辑有重复 ——
这是**已知且刻意**的：`PlayerActivity` 那条路径承载 C5–C8 与 D1 的全部取证口径，
在 D2 里顺手重构它会让那些已收口的复跑命令全部失效。收敛留给 **D4（生命周期收敛）**，
那张卡本来就要求"`SessionHandle` 释放顺序唯一性"。

## 五、独立校验（`tools/verify_p12d_multi.py`）

只读证据，不 import 项目代码，不接受手填 fps。基线取三轮中位数，
比例在脚本里算。两种检查分开跑：

```bash
python tools/verify_p12d_multi.py ratio \
  --baseline "docs/evidence/p12d/p12d2-baseline-r*.json" \
  --multi    "docs/evidence/p12d/p12d2-multi-r*.json"

python tools/verify_p12d_multi.py paced \
  --files "docs/evidence/p12d/p12d2-paced-*.json" --target-fps 30
```

脚本除了 60% 门槛，还守三条：

1. **每路必须 `completed=true` 且 `error` 为空** —— 没跑完的数字不许拿来比；
2. **帧数闭合**（`rendered + dropped + discarded + 1 == received`）—— 漏交缓冲会先在这里露头；
3. **轮内极差 ≤ 10%** —— 超过就说明有某一路被饿着了，即使每一路都过了 60%。

第三条是特意加的：3 路都跑 70% 但相差 30%（比如 90/70/50）时，
只看"最差 ≥ 60%"会漏掉"其中一路被欺负"。

## 六、这次没做到的（诚实清单）

1. **只测 AVC 1080p，一台 K40。** HEVC、4K、别的芯片都没测。
   4K 单路 133 fps（`20-p12c6-status.md`），3 路很可能掉到 60% 以下 —— **没测就不许猜**。
2. **多路路径不带音轨。** 真实"三个视频同时播"还有三路 AAudio。
   C8 只验过一路音频 + 一路视频；三路音频会不会互相拖，没测。
3. **画面尺寸不一样，这个混杂因素偏向"多路更好看"。**
   单路占满全屏（1920 宽），3 路各占 1/3（640 宽）。
   缩放是每帧的 GPU 工作，所以 3 路的总缩放像素 ≈ 1 屏 < 3 屏。
   也就是说：如果三路都占满全屏，比例会比 81% 低。**这条必须跟着数字一起引用。**
4. **基线本身有 ±10% 的轮间抖动**（147.27 / 160.84 / 179.58）。
   用中位数当分母是折中；若拿最高基线（179.58）当分母，3 路是 **72.8%**，仍过门槛。
5. **只测了 3 路和 4 路。** 2 路没测；5、6 路（`sessionCount` 上限）没测 ——
   按 4 路已贴天花板推断大概率不达标，但**推断不算证据**。
6. **没有并发下的长稳**（30 min）。那是 D3 的活。
7. **没测后台/分屏/多窗口**下多路的表现。D1 只验了单路的切后台。

M=/sdcard/Android/data/com.kivo.cinema/files/media
