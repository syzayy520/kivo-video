# 89 · P13-Q 验收：整段的账，和丢帧时它为什么会不平

- 版本：V1.0
- 日期：2026-10-30
- 设计：`88-p13q-design.md`
- 判据：Q1–Q5
- 结论：**达成，并且抓到了单帧尺子看不见的东西**。跨帧恒等式在零丢帧轮上逐位闭合；
  满载轮里 80.488 ms 的峰值中只有 10.2 ms 来自"交出晚"，**70.2 ms 来自目标时间轴累积前移** ——
  而这 70 ms 在单帧口径里 `due_step_frames = 0`。

---

## 一、改了什么（一句话版）

P13-P 出版的是**一步**（`due_step`），本卡出版的是**整段**（两侧的累积）：

```
lateness[k] − lateness[0] = Σ present_step − Σ due_step
```

`pace` 五格 + `worst` 三格，schema `sync/15`。残差 `closure_gap_ns` 照样出版，
不假装它一定是 0。

### 1.1 一条被修正的小结论

设计稿 §1.2 写"首帧 `lateness` 恒为 0"。真机 6/6 轮都报 18–29 µs ——
因为锚点在**到达**那一刻建，而 `lateness` 记的是**交出**那一刻，中间隔着"醒来 → 交出"。
不是 0，是微秒级；判据 Q3 因此从"等于 0"改成"≤ 1 ms"。
（"首帧不可能迟到 88 ms"这个结论不受影响：微秒级离 88 ms 差三个数量级。）

## 二、真机六轮（`docs/evidence/p13q/`，`sync/15`）

片源 `p13c_4k60_av.mp4`（8 s / 480 帧），`cpu_paced`。前 3 轮空载，
后 3 轮在设备上跑 4 个 `yes` 忙循环（实测 `ps` 4 个进程，`dumpsys cpuinfo` 里
`system_server` 132%）。

| 轮 | 负载 | max (ms) | 丢帧 | Σpresent (ms) | Σdue (ms) | 残差 (ms) | 最差帧累积账 |
|---|---|---|---|---|---|---|---|
| r1 | 空 | 98.726 | **2** | −140.51 | −0.04 | **+140.52** | 账不平（见 §三） |
| r2 | 空 | 12.088 | 0 | +0.04 | −0.02 | 0 | cumP +12.08 / cumD +0.01 |
| r3 | 空 | 3.999 | 0 | +0.03 | −0.02 | 0 | cumP +3.96 / cumD −0.02 |
| **r4** | **满载** | **80.488** | 0 | −70.19 | −70.26 | **0** | **cumP +10.23 / cumD −70.23** |
| r5 | 满载 | 97.879 | **2** | −157.99 | −18.17 | **+140.39** | 账不平 |
| r6 | 满载 | 40.531 | 0 | −28.40 | −28.48 | 0 | cumP +12.08 / cumD −28.43 |

### 2.1 满载把峰值抬了一个数量级

空载两轮（r2 / r3）**3.999 / 12.088 ms**；满载三轮（r4 / r5 / r6）**40.5 / 80.5 / 97.9 ms**。
同一片源、同一构建、零丢帧（r4 / r6）。`derived_fps` 六轮全是 59.999 ——
**这不是"4K 解码算力不够"，是系统被占满时播放线程排不上队。**

r1 是空载轮却报了 98.726 ms 并丢了 2 帧：它就是 P13-P 里那种"十轮撞一次"的偶发，
也是为什么本卡要连跑多轮而不是挑一轮讲故事。

### 2.2 峰值到底是谁的：单帧口径说 present，整段口径说 due

r4 是最清楚的一份：

| 口径 | 读数 | 结论 |
|---|---|---|
| 单帧（P13-P） | `due_step = −36 µs`，`present_step ≈ +80.5 ms` | `present_side` |
| 整段（本卡） | `cumP = +10.23 ms`，`cumD = −70.23 ms` | **`due_side`**（70.2 / 80.5 = 87%） |

两者不矛盾：**那一步确实是手慢了**（80 ms 几乎一次性出现在某一帧上），
但**把时间轴整体往前推了 70 ms 的是"表"**，而那 70 ms 是分几步挪的，
每步都没到一帧的门限，所以 `due_step_frames` 记 0。

r6 同理但更平均：`cumP +12.08` / `cumD −28.43`，两边都占，判 `mixed`（0.70 差一点到 0.75）。

> 这条就是 P13-Q 的全部意义：**"哪一步错了"和"整段是谁在错"是两个问题**，
> 一个尺子答不了。上一张卡（P13-P）的结论"due 侧一次都没发生"只在单帧口径下成立，
> 已被本卡在整段口径下推翻。

## 三、丢帧时账为什么不平（本卡唯一的已知缺陷）

`note_presented()` 只对被**呈现**的帧调用：

- `present_step` 跨过丢帧时用 `frames_since_present_ × 帧长` 补上中间那几帧；
- `due_step` 只记了最后那一帧，中间被丢的几帧的 `due` 推进没人记。

两个分母不同，账必然差 `丢帧数 × 帧长` 量级。实测 r1 / r5（各丢 2 帧）
残差 **+140.5 / +140.4 ms**，**不是小数**。

处理方式：**如实出版残差**，校验器在丢帧轮只要求"残差非 0"（证明没被抹平），
不给累积归类（`cum=invalid(丢帧)`）。要真修得让丢帧也进账 —— 那会改动
`due_step_frames` 的口径，留作下一张卡的候选。

## 五、诚实清单

1. **满载是"4 个 `yes`"，不是受控的 CPU 配额。** 没记每轮的实际空闲率，
   也没做"1/2/4/8 路"的梯度 —— 只能说"满载下峰值抬到 40–98 ms"，说不出拐点在哪。
2. **r1 空载却 98.7 ms + 2 丢帧，没有解释。** 它是本卡最刺眼的一条：说明空载也有偶发，
   而我们的样本只有 3 轮。
3. **`cumD = −70 ms` 的物理成因没查。** 本卡只证明"目标时刻整体前移"这件事发生了，
   没证明是音频时钟的 `elapsed` 估计、还是 `pts` 差分、还是 `anchor` 重算。
   下一步应该把 `elapsed` 与 `mono` 也记进最差帧。
4. **丢帧轮的两个口径都不可用**（§三），但「`due_step_frames = 0` 不代表没位移」这条仍然成立。
5. **`closure_gap` 的容差 1 µs 是拍的。** 它只是在"零丢帧时必须为 0"这个事实下取的一个小量；
   真要卡精度得从 `present_step` 的整数运算推。
6. **只有一台设备、一种片源、一种帧率。** 30/60/120 fps 的差异没测。
7. **`present_step` 与 `note_interval()` 共用一个计算**（P13-Q 改的）：好处是不会两处算错，
   代价是如果那一次算错了，`present_jitter` 与恒等式会**一起**错，彼此不再互为对照。
