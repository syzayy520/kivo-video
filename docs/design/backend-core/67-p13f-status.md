# P13-F 状态卡：最差那一下在哪儿 —— 88 ms 未复现，位置全长分散

> 设计：`66-p13f-design.md`。前序：`65-p13e-status.md` §六.1。
> 证据：`docs/evidence/p13f/` 20 份（10 轮 × decode+sync），**全部出自同一 APK**。
> 结论：判据 F1–F3 全通过；总收口 316 份 / 四层通过 / 8 子校验器 exit 0。

---

## 一、改了什么

`quantiles.<口径>` 里多一格 `worst`。`max` 只说最差**多大**，这一格说最差**在哪儿**：

```jsonc
// /4（P13-F）
"quantiles": {
  "media_time_decimated": {
    "samples": 160, "p50": ..., "p99": ..., "max": 665416,
    "worst": {
      "index": 79,          // 全场第几个被接受的样本（0 基）
      "of": 160,            // 全场累计样本数（= samples）
      "media_ns": 3950000000,   // 那一点的媒体时刻 —— 直接对 source.duration_us
      "lateness_ns": 665416     // 与 max 逐位相等（判据 F1）
    },
    "histogram": { ... }
  }
}
```

`schema` 升 `kivo.p12c.sync/4`。`present_jitter` 那个块**不写** `worst` ——
`note_interval()` 只收到两个时刻相减，调用方不给媒体时刻，结构上就没有位置可言。

## 二、判据

| 判据 | 内容 | 结果 |
| --- | --- | --- |
| F1 | `worst.lateness_ns == 同口径 max`，逐位相等 | ✅ 20/20 |
| F2 | `0 ≤ index < of == samples`，`media_ns` 落在片长内 | ✅ 20/20 |
| F2′ | 抽稀口径 `media_ns` 与 `index × 50ms` 对齐 | ✅ 10/10，**偏移全部 0.000 ms** |
| F3 | 有样本 ⇔ 有 `worst` | ✅ 20/20 |

**F2′ 是意外收获。** 判据原本是拿来抓"把直方图桶下标当成样本下标"那类错位的
（250000 ns 落在一个 8 秒片源里完全"合法"，只有和 `index` 摆在一起才看得出不对）。
实测十轮偏移**全部恰好 0.000 ms** —— 顺带证明了抽稀的绝对格点推进没有累积误差，
这条在 P13-D 是靠"20.08 vs 20.13 Hz"间接说的。

**负向自测**：

| 层 | 变异 | 打红 |
| --- | --- | --- |
| C++ 单测 | 极值改按**绝对值**比较 | t04 三条（`worst` 选了 −90 ms 而不是 −1 ms） |
| C++ 单测 | `index` 取 `count() + 1`（差一位） | t10 / t11 两条 |
| C++ 单测 | `max_point()` 改回**扫序列** | t07 / t08 六条（覆盖与 `clear()` 后极值丢失） |
| Python | `worst.lateness = max + 1` | F1 |
| Python | `worst.index = of` | F2 + F2′ |
| Python | `media_ns` 写成桶宽 250000 | F2′（偏移 −3949.75 ms） |
| Python | 删掉 `worst` 整格 | F3 |
| 端到端 | 把坏证据放进 `docs/evidence/p13f/` 跑总收口 | 层 4 红，结论「不可交付（1 条失败）」 |

**mtd/max 中位 2.315 ms、最大 12.494 ms；pf/max 中位 4.016 ms、最大 12.494 ms。**
十轮零丢帧、零 xrun。

### 三个读数

**① 88 ms 没复现。** 十轮最大 12.494 ms，是 P13-E 那轮 88.231 ms 的 **1/7**。
P13-E 的 `63-p13d-status.md` 表里那三个数（57.070 / 24.875 / 88.231）在本轮一次都没出现。

**② 位置全长分散。** 位置比（`media_ns / 8s`）：

```
0.49  0.07  0.67  0.41  0.58  0.40  0.64  0.79  0.53  0.98
```

既没有堆在片头（只有 r2 的 0.07 靠前），也没有堆在片尾（只有 r10 的 0.98 靠后）。
设计里那张归因表要回答的三选一，答案是**第三种**：位置分散 ⇒ 系统抢占，与 4K 分辨率无关。

**③ 两个口径指向同一时刻时，那是一次真事件。** r3 / r5 / r8 的
`mtd.worst.media_ns` 与 `pf.worst.media_ns` **完全相同**（5.35s / 4.65s / 6.35s）——
说明抖动跨过了 50 ms 抽稀格点，两条采样路径都抓到了同一个点。
反过来 r9 是两条口径各抓一个（mtd @4.20s、pf @0.03s），说明那一轮有**两次**独立抖动。

这一条顺带自证了两套计数没串味：如果 `worst` 记的是别的点的媒体时刻，
两条口径不可能在同一轮独立地给出一模一样的秒数。

## 四、过程里修掉的两个缺陷

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | 总收口层 4 只 `glob("docs/evidence/p13d/*-sync.json")` | **p13f 的 10 份证据一份都没被 F 判据看过**；端到端植入 `worst = max + 1`，总收口照样报"四层通过 / 可交付" |
| 2 | 我自己的端到端测试文件名叫 `p13f-mutation-bad.json` | 不匹配 `*-sync.json`，**第一次测试假通过** —— 我差点据此宣布"接线已证明是活的" |

第 1 条是 P13-E 抓到的"加 schema 忘了加分发"的**第二次发作**，换了个位置：
上次是白名单有、`card_checks` 没写；这次是 `card_checks` 有、**层 4 的证据目录没写**。
两次都是"两张表，只更新了一张"。改成按 `docs/evidence/p13*/*-sync.json` 扫，
新增证据目录只要符合这个模式就自动纳入。

第 2 条更值得记：**测试自己也会假通过**。判据红不红，取决于它有没有看到那份文件；
"我跑了一遍，全绿"这句话，在"文件根本没被扫到"和"文件被扫到且通过"之间不作区分。
所以端到端测试的第一个断言，永远是**这份坏证据确实进了被检查的集合**
（本轮的做法：改名前 317 份全绿、改名后立刻红，两份输出都在）。

## 五、诚实清单（六条）

1. **十轮没复现，不等于 P13-E 那轮不是 4K 的问题。**
   只能说：同一台机、同一份 APK 配置、连续十轮 8 秒播放，最大 12.494 ms。
   那轮的 88 ms 至今**没有被解释**，只是现在有了"下次发生时能定位"的工具。
   拿本轮的十轮去覆盖那三轮，是把一条未归因的观测偷偷删掉。

2. **`worst` 只记一个点。** P13-E 那轮的直方图显示 6 个阶梯状离群点
   （18.25 / 24.75 / 40.75 / 57.0 / 73.25 / 88.0 ms），`worst` 只留下最大的那个。
   要还原完整形态，需要 top-K 或全序列 dump，本卡**没做** ——
   见 §七 的边界：那属于另一条诊断通道。

3. **`index` 不能拿去 `at()` 取点。** 它是全场累计序号，`at()` 收窗口内下标。
   极值由 `note()` 累计维护，所以环形覆盖后仍然指得到那个点 ——
   代价就是这两个下标不再通用。头文件里写死了这一条。

4. **F3 的"无样本 ⇒ 无 worst"分支在真实路径上不可达。** 不可测时 `quantiles` 是空对象，
   根本不存在 `samples = 0` 的口径块。这条判据是**防御性**的，不是观测性的；
   它的 C++ 侧对应（`DriftExtreme::valid == false`）由单测 `t01` 覆盖。

5. **层 2 不查 F 判据。** `card_checks` 只管"字段在不在、版本对不对"，
   数值自洽（F1）在层 4。所以"层 2 通过"**不代表** `worst` 是对的 ——
   这与 P13-E 那条"`/2` 从未被层 2 校验过"是同一类边界，只是方向相反。

6. **漂移量准仍卡在 7 ppm 的尺子上。** 本卡一个字都没动那条线：
   0.25 ms 桶宽 / 8 s 片源，分辨率上限 ≈ 7 ppm。要谈 1 ppm 的改动，
   先解决"桶更细 / 片更长"。这条从 P13-D 到 P13-F 没变。

## 六、下一步

1. **`per_frame` 降级分支仍缺真机证据。** 从 P13-E 欠到现在：
   `note_presented()` 拿不到媒体时刻的那条路只有单测覆盖。
   要造它得让呈现路径不传 pts，本轮没做。

2. **要真归因 88 ms，需要逐帧时间线。** `worst` 给的是"最差那一下在哪"，
   不是"为什么"。要区分"CPU 被抢占"与"视频 pts 停滞"，得把
   `present_at` / `pts` / `audio_position` 三列逐帧落盘 ——
   这是另一条诊断通道（`--dump-drift`），不是证据 JSON 该承载的东西。

3. **抽稀格点精确性的副产品值得单独记一笔。** 十轮 F2′ 偏移全部 0.000 ms，
   这是"绝对格点推进"设计的一次强验证（P13-D 只有 20.08 vs 20.13 Hz 的间接证据）。
   如果以后有人把格点改回"距上一接受点 +50 ms"，这条判据会立刻红。
